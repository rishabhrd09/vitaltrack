One backend design, separate data targets

In short: the same code runs in three environments. What separates them is configuration — which API URL the app was built with, and which database and secrets each backend service uses.

EnvironmentClient and APIDatabase intent
DevelopmentExpo Go, or a development build once expo-dev-client is installed → local API, normally port 8000A local PostgreSQL 16 with development data. Tests use a separate database whose name contains test — never a live URL.
StagingPreview APK → staging-api.carekosh.comDocumented database vitaltrack_staging, with synthetic QA data.
ProductionProduction-profile build → api.carekosh.com, including Play internal testingDocumented database neondb. Preserve personal and tester data as well as future user data.

The names above are documented database names, not proof of distinct Neon branches or projects. Check each service's target privately. Isolation depends on configuration: the same source tree does not prove the services run the same commit or image.

Configuration boundaries

  • Runtime (backend): DATABASE_URL, ENVIRONMENT, SECRET_KEY, FRONTEND_URL and the mail/telemetry settings come from each backend service.
  • Build time (mobile): in EAS builds, EXPO_PUBLIC_API_URL is embedded into the mobile JavaScript bundle, so use the matching EAS profile and rebuild to change it. During local expo start development, Metro injects the running value into each bundle instead; a .env change needs only a full app reload.
  • Authentication: use different secrets in each environment. A different database does not by itself isolate the token-signing keys.
  • Transport: the backend enables database TLS outside development/testing. Production and preview builds disable cleartext HTTP through app.config.js.
  • CORS controls browser access, not native-app authorization. The branch is chosen by CORS_ORIGINS: vitaltrack-backend/render.yaml sets ["*"] for production, and the wildcard configuration sets allow_credentials=False. Per-user authorization still runs in the API.

Email verification is enforced for accounts that have an email only when both REQUIRE_EMAIL_VERIFICATION and the Brevo credential (MAIL_PASSWORD) are configured. Local configuration can differ from staging; inspect the effective settings without printing secrets.

Assistant (AI) settings are per service too. Every AI_* flag defaults to off and render.yaml sets none, so the /api/v1/ai/* routes refuse work on any service where the dashboard has not set them. Optional Groq understanding needs AI_ENABLED, AI_DATA_CONTROLS_REVIEWED and a server-side GROQ_API_KEY; the phone never holds a provider key. Speech recognition itself runs on the phone, so voice does not depend on these settings. AI usage counters live in each service's database. Rate limiting is best effort: five auth routes, counters in memory per worker process, reset on restart.

Current migration and runtime

Every start of the production Docker image runs Alembic migrations before Gunicorn starts two Uvicorn workers; a failed migration stops the container. The migration head is 0010_order_local_id_unique; 0007–0010 exist only on the feature branch, and main ends at 0006_order_item_qty_positive. Use alembic heads to see the source revisions and alembic current for an explicitly selected database. File ordering is not the revision graph.

Migrations 0007–0010 add order_number_counters and users.session_version with three token-digest indexes (0007), the ai_consents and ai_usage metadata tables (0008), consent scopes and a usage provider column (0009), and a per-user unique index on order local_id (0010): 11 application tables in total. The counter is deliberately independent of user deletion. See the hardening notes for rollout details.

Local networking and cache

On a physical Android device, localhost means the phone itself. For USB testing against the local API, reverse both Metro's actual port (usually 8081) and API port 8000. Staging and production API traffic uses the phone's own network, not the Metro tunnel.

TanStack Query persists a display cache to AsyncStorage. It is not an offline write queue. staleTime=30 seconds marks data as stale; it does not poll or guarantee freshness within 30 seconds. Returning to the foreground (AppState), mounting, pull-to-refresh and invalidation trigger refetches of stale queries. Earlier (September 2026): refetchOnReconnect was configured but TanStack's onlineManager was not connected to NetInfo, so regaining connectivity alone did not refetch. Current (7 Oct 2026): QueryProvider.tsx wires onlineManager to NetInfo (online = connected and internet not known to be unreachable), so reconnecting refetches stale queries. Screens' own offline checks still use NetInfo isConnected only. Mutations never queue offline. Auth tokens use SecureStore. The cache flag is in the source code, so installed release apps need a new build to change it; the cache buster changes only when the visible app version changes.

Safe operations

Keep data unless you intend to reset a confirmed disposable environment. docker compose down -v deletes volumes; it is not a normal shutdown command. Do not assume staging is safe to wipe just because of its name.

Merging to main can deploy production. vitaltrack-backend/render.yaml declares only the production service, tracking main (whether Render reads that file is not verified), and the container runs alembic upgrade head before Gunicorn starts. CI also calls the production deploy hook after a push to main when the hook secret is set. Whether Render auto-deploy is on is a dashboard setting (NOT VERIFIED). The staging service exists only in the dashboard: older guides recorded it as watching main; on 7 Oct 2026 the owner reported switching it to the feature branch to deploy b1c8dd7 (owner-reported, not re-checked). Check each service's branch and deployed commit in the dashboard before relying on either. For migrations 0007–0010, follow the release gate: preserve the existing staging database (do not run the one-way 0007–0010 on it); stage the candidate on an isolated fresh database and verify the 0006 → 0010 upgrade on a populated synthetic legacy database, because fresh-schema tests alone do not prove a legacy upgrade is safe; then run the E2E checks with a preview APK; and control both deploy triggers (the CI hook secret and Render auto-deploy, not verified) before merging; the updated gate diagram covers all four migrations:

A rollback must keep the additive schema. An image older than the schema fails alembic upgrade head ("Can't locate revision"), exits, and Render keeps the current version. Old code meets the new schema only while old instances still run during a deploy, and it ignores session generations.
