The recommendation in one page

Build a “truth-preserving voice inventory assistant,” not a free-form medical chatbot.

For a normal stock question, CareKosh identifies the requested item in the active mobile inventory snapshot, generates a typed answer card, and generates the spoken sentence—without another database request. The app refreshes its existing inventory query only when the snapshot is stale or the user explicitly requires the newest server-confirmed result. A language model may classify unclear wording; it never supplies a quantity, supplier, expiry date, medical recommendation, UI markup, or a database query.

First product slice

Text question → fixed overlay

“How many hand gloves are left?” and “Where do we order them?” are answered from the inventory data already loaded for the active session. Missing supplier data is stated precisely; it is never guessed.

Then

Alba speaks a deterministic script

Use the approved Piper en_GB-alba-medium voice through an isolated TTS provider. The visual card remains the primary record.

After validation

Press-to-talk, never always-listening

Speech is transcribed, shown for edit/confirmation, then treated exactly like typed text. “Close this overlay” is a local UI command, not an LLM request.

Do not expose your own provider key to app users.

A ChatGPT Free/Plus/Pro chat subscription must not be treated as a shared API allowance, and a permanent OpenAI or other provider key must never appear in a mobile build, client-side JavaScript, logs, screenshots, or a Settings field. The provider documentation explicitly says API keys are secrets and must be loaded on a server. Use a server-owned key with per-user budgets, or defer bring-your-own-key (BYOK) entirely.

The architecture: a model understands; CareKosh answers

The safest architecture makes an LLM optional and non-authoritative. It is also cache-first: the assistant reuses the same active inventory snapshot that powers the mobile screens, rather than creating a second database read for every spoken question. This makes normal answers fast, cheap, private, and easy to test.

1 · Mobile promptTyped question or press-to-talk transcript. Local UI commands run here.
→
2 · Intent layerDeterministic matcher first; optional LLM returns one small, validated intent only.
→
3 · Cache adapterAllow-listed local functions read the active items snapshot and its timestamp.
→
4 · Freshness + rendererRefresh the existing query only when policy requires it; create a typed card and speech text from the snapshot.
→
5 · ReplyMobile shows the fixed card with freshness state; optional Alba audio renders the same verified text.

One concrete question, end to end

User: “What is the quantity of hand gloves left, and from where do we normally order them?”

  1. The app accepts typed text, or first shows the recognized transcript for correction.
  2. A local parser identifies a composite request: item_status + supplier_info. If common rules cannot parse it, the optional LLM receives only the user’s question and returns that same small intent envelope—not inventory data or a tool call.
  3. The mobile cache adapter matches only active items from the existing queryKeys.items snapshot. If two exact/approved aliases match, it asks the user to choose; it never silently guesses.
  4. The freshness policy decides whether the snapshot can answer immediately or whether the app should run its normal, deduplicated inventory-query refresh. There is no assistant-specific database route or new “sync” endpoint.
  5. A deterministic mobile renderer creates the overlay. If supplier_name is empty, it states Supplier information is not recorded, never an invented store.
  6. The identical verified facts become a short speech script and are sent to the Alba TTS provider only if the user presses Speak or has explicitly enabled reply audio.

The fixed answer contract

The mobile screen renders a known card type. The LLM never returns React Native layout, HTML, a stock number, a freshness claim, or a proposed medical action. The client owns the answer envelope; a remote intent service validates only its own tiny input/output contract.

Other initial answer types: low_stock_summary, inventory_summary, expiring_soon, ambiguous_item, item_not_found, missing_data, and overlay_closed. Use a versioned TypeScript discriminated union for the mobile answer cards; use Pydantic only where the FastAPI intent/feedback boundary needs runtime validation.

No RAG for live stock.

Retrieval-augmented generation is useful later for user-authored notes, manuals, or policy documents. It is the wrong source for “how many gloves are left?” The active inventory snapshot is structured, user-scoped, and already present on the device. Start with cache tools; add RAG only after a real document-use case and permission boundary exist.

Cache-first answers: fast without pretending stale data is live

Your proposed boundary is correct.

The assistant should not hit the database whenever someone asks a question. CareKosh is not “serverless”—it has a FastAPI backend and database that remain authoritative—but the assistant can be client-cache-first because the app already loads the user’s inventory into TanStack Query. The cache is a read-only server snapshot, never a second source of truth and never a write queue.

Snapshot stateAssistant behaviorWhat the overlay / voice may say
Fresh
At or below the existing 30-second freshness window.		Read the local items snapshot. No inventory network request is made for the question.“18 pairs are in stock.” Footer: “Server snapshot confirmed at 10:42.”
Stale, online
Older than the window, while connectivity is available.		Render the cached answer immediately with a visible refreshing state, and start one normal, deduplicated refresh of the existing items query. Re-render the card if newer data arrives.“Last confirmed at 10:41. Refreshing inventory…” Never label the old value “live.”
“Current / now / latest” asked while staleRequest the normal items-query refresh before claiming a latest result. If it fails or times out, retain the cached answer only with its timestamp and failure state.“I could not refresh. Last server-confirmed quantity at 10:41 was 18 pairs.”
Offline or refresh failedUse a retained snapshot only if one exists. Do not invent a refresh, make a database claim, or hide the age.“Offline — last confirmed at 10:41: 18 pairs.”
No relevant snapshotAsk the app to load the normal inventory query once. If unavailable, show a fixed unavailable card.“Inventory is not available on this device yet. Please refresh and try again.”

Terminology matters: call this a refresh, not an assistant “sync request.” CareKosh already has a user-facing Refresh from Server recovery path, but normal assistant refreshes must not clear the whole query cache. They should use the same narrow queryKeys.items query function that screens use, preserving active UI and allowing TanStack Query to deduplicate in-flight work.

The only normal network events are: the app’s existing initial/foreground/reconnect fetches; invalidation after a successful server mutation; an explicit user refresh; a stale question needing a newer result; and, only when rules cannot understand wording, a small remote intent call that does not query the inventory database. Fresh stock questions make none of these extra inventory calls.

Privacy and reliability benefit

The optional remote LLM need see only the question the user chose to ask. It does not receive the cached inventory list, supplier contacts, notes, identifiers, tokens, or a database connection. If it is unavailable, local intent rules still cover the named first-release questions; the cache adapter and fixed renderer continue to work.

Using the existing Iris “Alba” voice responsibly

Read-only inspection of the supplied Iris DeskBuddy project confirms that the voice is not a cloud voice model. It is Piper’s British-English en_GB-alba-medium ONNX voice. Iris verifies the model before speaking and the installer pins its exact MD5:

Voice:      en_GB-alba-medium
Language:   en_GB (British English)
Quality:    medium · 22,050 Hz
Model file: 63,201,294 bytes
MD5:        c07f313752bb3aba8061041666251654

The hash exactly matches the published Piper voice manifest. The voice model card lists an MIT model repository license and a CC BY 4.0 source dataset, so a redistribution/attribution record is required. The maintained Piper runtime used by Iris, however, is GPL-3.0. This is a separate runtime-license question; do not package the current runtime into the Play app or copy a binary between products until the distribution approach has had a focused OSS-license review.

Speaking and listening are different systems.

Alba is TTS: it speaks validated text. It does not hear, transcribe, understand, search stock, or control an overlay. The Iris project’s Vosk vosk-model-small-en-in-0.4 is a separate, closed-grammar listener intended for a few safety-limited commands. Its published result for Indian English is not appropriate as the only recognizer for open inventory questions with arbitrary product and supplier names.

Understanding, transcription, and LLM choices

The primary recommendation: tool-first, hosted text model optional

For the first production assistant, implement a deterministic parser for the common intents, then use one server-held text LLM only to return an allow-listed intent object when wording is ambiguous. The remote request contains the user’s question and a constrained intent schema—not a tool schema that can reach inventory. It does not receive the cached item list, notes, supplier contacts, user identifiers, tokens, or database rows. The small POST /ai/interpret endpoint is an intent proxy only; it does not open an inventory database session.

Local model architecture: feasible, but not on the current API host

CareKosh’s Render service is a small server-first API connected to Neon. It should continue to serve requests and database transactions, not hold a local LLM, Whisper, or Piper synthesizer. One slow model turn must never hold the inventory database session or make standard stock updates slow.

Good local use

Developer/demo or an opted-in household gateway

Run llama.cpp/Ollama with a benchmarked Qwen model, plus optional Whisper/Piper, on a Mac, Linux mini-PC, or dedicated household node. CareKosh calls it only through a protected adapter with a strict allowlist, private-network/TLS authentication, health checks, short timeouts, and a deterministic fallback.

Do not do this

Expose Ollama or llama.cpp to the public internet

An unauthenticated local inference port is not a production integration. Do not put a home IP, tunnel token, or local-model URL in the mobile client. A public API must authenticate CareKosh users and the server must own the provider connection.

Use the Iris architecture as an engineering pattern, not as a literal dependency: it already shows an OpenAI-compatible local adapter, bounded output JSON, a semaphore, health check, timeout, and cancellation. Those concepts can become a small CareKosh AiProvider interface with three implementations: deterministic, hosted_text, and local_gateway.

Local acceptance gate

A model is admitted only after a repeatable benchmark reports tool-selection accuracy on the golden set, p50/p95 latency, timeout behavior, memory/cost, transcript quality for target language, and clean fallback behavior. “It responded once on my laptop” is not an admission criterion.

Phase 1 backlog, in the correct order

  1. Define the mobile answer-card discriminated union, cache-freshness contract, and renderer catalogue before selecting any LLM. Define Pydantic contracts only for the later intent/feedback API boundaries.
  2. Write the golden and adversarial test sets first: vague questions, exact names, duplicate names, Hinglish, missing suppliers, injection attempts in item names, five freshness states, logout/login cache clearing, and “close overlay.”
  3. Implement cache tools as pure TypeScript functions over the existing item snapshot and query metadata. Test that a fresh question makes zero inventory network calls and that no snapshot can cross an account boundary.
  4. Add one narrow refresh coordinator for the existing queryKeys.items query. Test stale-online, stale-offline, failed-refresh, deduplication, and re-render-on-refresh; never call the destructive recovery qc.clear() path for a normal question.
  5. Build deterministic response and speech renderers. Test that every displayed/spoken quantity is a field from the cache adapter result and every freshness claim uses query metadata.
  6. Add capability/kill-switch data and /api/v1/ai/feedback; update the repository’s exact API-route-count gate in the same pull request if that server endpoint ships.
  7. Only then add /api/v1/ai/interpret behind timeout, per-user budget, global ceiling, structured validation, one retry at most, and deterministic fallback. It must not query inventory data.

Overlay UX: fixed, readable, and honest

The interface should feel calm rather than like a chat transcript. The answer panel opens over the active screen, respects the existing light/dark theme, remains accessible, and always displays the exact item/data source and generation time.

Item status overlay

Header: Hand Gloves · In stock
Primary number: 18 pairs
Threshold: Minimum 10 pairs
Supplier: No supplier information recorded
Footer: Server snapshot confirmed at 10:42 · Speak · Close · Report AI response

Typography rules

Primary quantity: 32–40 sp. Item title: 20–24 sp. Labels/body: at least 16 sp. Do not encode criticality with color alone; include text and an icon/shape.

Low-stock summary

Count first, then rows sorted by out-of-stock, criticality, and item name. Critical supplies get a textual “Critical” label. The voice gives a short summary and invites the user to open the list.

Ambiguity

“I found two items: Nitrile Hand Gloves and Sterile Hand Gloves. Which one do you mean?” Show selection buttons. Never pick based solely on fuzzy similarity.

Do not let speech be the only response.

Audio may be inaudible, interrupted, inappropriate in a shared room, or misunderstood. The readable, fixed-format visual overlay is the authoritative response; audio is an optional rendering of it.

Why “gigantic AI application” is not the first milestone

The strongest portfolio architecture is narrow and reliable: a data-bound assistant with typed tools, model isolation, audio consent, evaluable behavior, cost controls, and evidence of safe failure. RAG, autonomous writes, WhatsApp, image extraction, forecasting, multi-agent choreography, and local-model hosting are independent projects. Adding them before the core is measured turns a good agent story into an untestable collection of integrations.

What evidence makes this a serious job portfolio feature

Publish an architecture decision record for cache freshness, provider choice, and Piper licensing; a threat model; anonymized intent/cache-tool golden-set results; shared-device isolation tests; latency/fallback/cost dashboards; an honest limitations section; and a short demo that shows a question, local cache tool, typed response, Alba playback, and a stale/offline fallback. That demonstrates FastAPI, typed agent/tool design, evaluation, LLMOps, mobile privacy, and incident-minded engineering without overstating what the model does.

This feature is a strong portfolio project precisely because it combines mobile state, bounded AI, typed server boundaries, evaluation, and privacy. Study only what directly improves those decisions; do not begin with a generic “agent framework” tutorial.

A model is not “working” until it passes this suite on a versioned golden set.

The decisions to make before implementation

  1. Alba distribution: Is CareKosh allowed to use the existing model file, and has the team accepted the required attribution plus the Piper runtime distribution obligations? If uncertain, do a short OSS/legal review before shipping audio.
  2. Voice hosting: Choose a dedicated, authenticated Alba TTS service versus a later on-device native integration. Do not place it inside the current API process by default.
  3. Initial LLM provider: Select one server-owned provider only after reading the current data-use terms and setting a small project budget. Its only first-release role is text-to-intent; it receives no inventory snapshot. The product works deterministically when that provider is disabled.
  4. Voice input privacy: Decide whether the first STT trial can use a platform service or must wait for self-hosted Whisper. Either path has a transcript-confirmation gate.
  5. Launch timing: Ship this after the current Play launch cycle, in a separate build/review cycle. Do not mix a novel microphone/AI surface into the production-access submission.
Recommended decision set

Start with Phase 1 deterministic text overlays from the existing mobile inventory snapshot, with an explicit freshness badge and targeted normal-query refresh only when necessary. Add a single server-owned text LLM only as structured text-to-intent fallback, with no inventory data. Deploy Alba as a separately validated TTS provider after license review. Add press-to-talk only after the text assistant, audio output, feedback control, Data Safety update, and transcript UX have passed testing. Keep BYOK, local LLMs, RAG, and AI stock updates outside the first public release.
