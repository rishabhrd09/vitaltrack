Chapter 01 · The central decision

Should you self-host a local LLM?

Short answer: no. But the instinct was sound, and the reasoning is worth keeping.

🛡️ First, the strongest honest case for your idea

This deserves to be argued properly before it is dismissed, because three of these points are genuinely good engineering instincts.

1 · Privacy is a real asset, not sentiment. CareKosh holds household medical-supply data. Keeping inference on your own machine is a defensible privacy posture for a health-adjacent product.

2 · API keys are a real operational surface. Keys leak. Providers deprecate models without warning. And because updates.enabled is false in your app.json REPO, you have no over-the-air update channel — you cannot hotfix the mobile app. That makes external dependencies genuinely scarier for you than for most teams.

3 · Fixed cost, no runaway bill. A self-hosted model cannot generate a surprise invoice from a buggy retry loop.

4 · There is a real free option. Oracle Cloud's Always-Free ARM tier is genuinely free and genuinely private — a far better comparison than Render.

5 · In some markets, self-hosting is the differentiator. Regulated, on-premise and healthcare AI infrastructure is a real hiring segment, and CareKosh sits adjacent to it.

⚖️ The four tests it has to pass

Test 1 — Does it physically fit? Fails

Your render.yaml pins plan: starter REPO, which is 512 MB RAM and 0.5 vCPU VERIFIED. Render offers no GPU instances of any kind DIRECTIONAL. That memory has to hold FastAPI, SQLAlchemy, asyncpg and two Gunicorn workers before a model is loaded. A 4-bit quantised model costs roughly 0.6 GB per billion parameters, so even a 3B model needs several times the entire box. Only sub-1B models would fit, and those are not reliable enough to decide which database function to call.

Test 2 — What would it cost to make it fit? Fails badly

Scaling Render to a machine that could serve a small model means a plan roughly two orders of magnitude more expensive per month than the hosted API alternative — and on CPU only, so it would still be slow. Meanwhile the hosted path costs a few dollars a month. You would be paying dramatically more for a materially worse agent.

Intellectual honesty: this test is unfair to your idea, because Render is the weak version of self-hosting. The strong version — Oracle's free ARM tier — was never properly costed by the research, and one verifier called this out. It would fit a 3–4B model. The reason self-hosting still loses is Test 3, which is independent of hardware.

Test 3 — Would a small model actually be reliable enough? Unproven, and the risk is asymmetric

The task is not chatting; it is choosing the right database function and passing the right arguments, sometimes across two steps (find the item, then read its status). Small models degrade sharply on exactly this multi-step tool-calling axis.

Retracted: earlier research put precise benchmark percentages here and called them "the real killer". A verifier fetched the cited page and the numbers were not on it — and the model named was not even the model benchmarked. RETRACTED
What stands: the direction is well established — small models are meaningfully worse at multi-step tool selection. But you should measure it, not cite it. See the "$0.50 experiment" below.

On an app tracking medical supplies, a confidently wrong stock number is a safety problem, not a UX annoyance. That asymmetry is what settles this test.

Test 4 — Does it help your career? Fails

Industry practice is overwhelmingly hosted-API-first, and self-hosting signals read as infrastructure work — LLM serving and inference optimisation — rather than applied AI engineering. That is a different, narrower job family than the one you are targeting. DIRECTIONAL

🔑 The premise that has to be corrected

Your reason for wanting to self-host was that creating and managing API keys is difficult. For this repository, that is simply not true — and since it was the load-bearing reason, it deserves a direct answer.

You already manage three secrets by exactly the mechanism a Groq key needs REPO:

# vitaltrack-backend/render.yaml — the pattern you already use

  - key: DATABASE_URL
    sync: false          # ← paste the value in the Render dashboard
  - key: MAIL_PASSWORD
    sync: false
  - key: SENTRY_DSN
    sync: false

  - key: GROQ_API_KEY

Getting the key itself is: open the Groq console → sign up → API Keys → Create. No command line, no service account, no IAM roles, no approval queue, no credit card for the free tier. VERIFIED

Where the confusion probably comes from. Google has two products with similar names. AI Studio is a button that gives you a key in seconds. Vertex AI is the enterprise platform — gcloud, service accounts, IAM bindings, regional endpoints — and it is genuinely a slog. You will never touch Vertex AI.

The comparison that matters: self-hosting means choosing a model, quantising it, provisioning a VM, installing a runtime, managing memory, monitoring, patching and keeping it alive — tens of times more operational work than the four-line paste you were trying to avoid.

⚖️ Is it legal? You asked, so here is the real answer

Yes, self-hosting open-weight models commercially is legal — but the licences differ in ways that matter specifically for a health app. VERIFIED

Using a hosted API, you never download or redistribute weights — that relationship sits between the model owner and the inference provider, not between them and you. 💡 Keep 90% of the value for two hours of work

Here is the move that turns this rejected idea into an asset. Write the decision down. Create docs/adr/0001-hosted-vs-selfhosted-llm.md containing: the constraint (your actual instance specs), the options considered, the break-even arithmetic, and — critically — the explicit threshold at which you would switch (say, sustained spend above a set figure, or a hard data-residency requirement from a customer).

Why this matters more than the code. "I self-hosted a local LLM" is a weak interview line. "I evaluated self-hosting against a hosted API, measured the break-even, documented the switch threshold, and shipped the hosted path" is a senior one. The reasoning is the hiring signal. The act is not.

Optional: the $0.50 experiment that replaces every retracted benchmark

Rather than citing a number you cannot defend, generate your own. Once your 50-case golden set exists (Ch 08), run it against a small model and record the real tool-selection accuracy. That is roughly fifty cents of tokens and it converts the weakest section of this analysis into your own measurement — the single most defensible thing you could put in the ADR.

Two reasons, and the first is the one people miss:

  • Free-tier rate limits apply at the organisation level, not per user VERIFIED — so every one of your users shares one small quota. A handful of simultaneous conversations exhausts it for everybody.
  • The bill is trivially small. Realistically a few dollars a month at your scale. Set a spend alert and stop thinking about it.
Retracted: an earlier estimate of "$0.38/month" was quoted repeatedly. A verifier showed it omitted reasoning tokens and the fact that a multi-round tool-calling turn re-sends the whole growing context on every round — understating cost by roughly an order of magnitude. RETRACTED
What stands: the conclusion is unchanged — the cost is negligible. Budget single-digit dollars per month, and never quote a to-the-cent figure you have not measured.

🔀 One LLM lane, and one deterministic lane

The instinct is to build a failover chain: Groq, then Gemini, then something else. Resist it. Every extra provider is another terms-of-service document to comply with, another key to rotate, another data processor to declare, and another code path that is never exercised until the day it matters.

Groq  ──▶ (fails: timeout / quota / outage / model retired)
            │
            └──▶ deterministic renderer   ← always correct, always available

The fallback that keeps you alive is not a second model. It is your own code, which is the subject of the next chapter.

Two operational rules. Put the model name in an environment variable (GROQ_MODEL), never a constant in code — providers retire models on short notice and you have no over-the-air update path. And make model-not-found an explicit trigger for the deterministic fallback, alongside timeout and quota errors.
Chapter 03 · Architecture

The architecture — deterministic first

The counterintuitive inversion that makes this safe, cheap and testable.

🔄 The idea in one sentence

The obvious design is: user asks → LLM decides what to do → LLM writes the answer. Do the opposite. Build a plain, deterministic engine that answers correctly with no API key at all, and let the LLM do nothing but rephrase an answer that is already right.

The model's job is not "answer this". It is "say this more naturally."

Shrinking the model's responsibility is what makes a small, cheap model sufficient; makes every answer testable without a network call; makes your outage fallback the primary code path instead of untested dead code; and means you can demo the whole feature — and pass a Play review — with the AI provider switched off entirely.

🗺️ Request flow

The green path is always available. The gold path is an enhancement that can fail safely at any point.

📁 Where the code goes

Your app/services/ currently contains only __init__.py and audit.py REPO — so the new AI service package follows the pattern audit.py already establishes: plain async functions taking a database session, not classes.

No new database table, no migration. The conversation lives in memory on the device and is gone when the screen closes. That removes a migration, a new category of personal data at rest, a Data Safety line item, and a deletion obligation. It also matters operationally: your container runs alembic upgrade head on boot and aborts startup if it fails REPO — zero migrations means zero deploy-abort risk during a launch window.

🧰 Why no agent framework

LangGraph, PydanticAI and the rest solve problems this feature does not have: multi-agent handoffs, durable long-running state, human-in-the-loop gates spanning requests. You have six tools and one loop.

Decisively: httpx==0.28.1 and pydantic==2.10.3 are already pinned in your requirements REPO. A hand-rolled loop adds zero new runtime dependencies — which on a 512 MB instance is a first-order engineering constraint, not a matter of taste.

The career-flavoured counter-argument, answered. LangChain and LangGraph appear in job descriptions and a hand-rolled loop does not. The right response is not to adopt a framework you do not need — it is to write the comparison down in docs/adr/0002-agent-framework-choice.md. "I built it two ways, shipped the simpler one, and here is the memory and latency difference" outperforms framework loyalty in any real interview.

🔌 The kill switch — your only hotfix mechanism

Because updates.enabled is false REPO, you cannot push a fix to an installed app without a new store build. So the feature must be remotely disableable from the server.

# app/api/v1/auth.py — GET /auth/me gains one field.
# No new route, so the CI route-count gate is unaffected.
{
  "id": ..., "email": ..., "name": ...,
  "aiEnabled": True        # ← mobile hides the Ask button entirely when false
}

One environment-variable flip in the Render dashboard removes the feature from every installed copy of the app within seconds — no rebuild, no review, no store involvement. These are the highest-value twenty lines in the whole plan.

The same reasoning applies to every user-visible string. The refusal message, the error copy, the system prompt and the model name must all live on the server; the app renders whatever it is given and hardcodes nothing.

Do not forget the CI gate. Your pipeline asserts an exact API route count — scripts/check_api_routes.py --expected 39 appears in both the script default and .github/workflows/ci.yml REPO. Adding the AI routes means bumping both numbers in the same pull request, or CI hard-fails.
Chapter 04 · Tools & safety

Tools and the guardrail ladder

Six read-only tools. Six layers ensuring the model can never invent a number.

🧰 The six tools

All read-only, all filtered by the authenticated user, all returning typed objects with numbers already formatted as strings so the model has nothing to compute.

ToolAnswers
find_item“do I have paracetamol?” — fuzzy name match
get_item_status“how much oxygen is left?” — stock vs minimum, criticality
list_needs_attention“what am I running low on?”
get_inventory_summary“how are we doing overall?”
list_expiring“anything expiring soon?”
list_by_category“what's in wound care?”
The single most important test file you will write. There is no repository layer and no row-level security in this codebase — ownership is enforced manually in every query REPO. Every tool must re-apply its user_id filter, and tests/ai/test_tools.py must contain a cross-user isolation test per tool proving user A can never see user B's items. This is also the first thing a technical interviewer will probe.
# app/services/ai/tools.py — the shape every tool follows

async def get_item_status(db: AsyncSession, user_id: str, item_id: str) -> ItemStatus:
    stmt = select(Item).where(
        Item.id == item_id,
        Item.user_id == user_id,      # ← NEVER omit. No RLS backstop exists.
        Item.is_active.is_(True),
    )
    item = (await db.execute(stmt)).scalar_one_or_none()
    if item is None:
        raise ItemNotFound(item_id)

    # Every number is computed HERE and shipped as a formatted string.
    # The model receives words, never operands — it cannot do arithmetic wrong
    # if it is never given arithmetic to do.
    return ItemStatus(
        ref=item.id,
        name=item.name,
        quantity_text=f"{item.quantity} {item.unit}",
        minimum_text=f"{item.minimum_stock} {item.unit}",
        status=_derive_status(item),        # Literal["ok","low","out"] — server-side
        is_critical=item.is_critical,
    )

🪜 The guardrail ladder

Six layers, each independently sufficient to prevent a fabricated number from reaching the user.

LayerRuleWhy
L0The model never performs arithmeticEvery figure is pre-computed and pre-formatted in the tool result
L1Numbers travel as references, not valuesThe app renders each digit from Postgres; status is derived server-side
L2Validator rejects any number absent from tool outputOne retry, then fall back to the deterministic answer
L3Refuse if the model called no toolAn answer with no data behind it is a hallucination by definition
L4Strict allowlist of what leaves your serverMessage text and item name/quantity/unit only. Never email, user id, supplier name or contact, purchase link, or notes
L5Tool results injected as typed data, never concatenated into the promptItem names are user-authored free text — an untrusted prompt-injection surface
⚠️ The hole a verifier caught — fix this or the whole ladder leaks.
The spoken answer needs numbers as words — “four packs”, not “4 pcs”. But the L2 validator looks for numerals. It will never catch four, a dozen, or about half. If the model authors the speech string, the spoken channel becomes the one unguarded path in a system built specifically to prevent unguarded numbers — on a medical-supply app, read aloud with the authority of a voice assistant.

The fix: render the speech string deterministically from the same data as the visual card. Never let the model author it.

🚑 The medical-advice gate

Your Play Store submission commits to CareKosh not offering medical advice. That promise must be enforced in code, before the model is ever called — a keyword gate that short-circuits to a fixed, hardcoded response.

Be honest about this gate's limits. A verifier pointed out, correctly, that an English keyword list does not fire on natural Hinglish phrasing — “kitna lena chahiye”, “ye kis liye hai”, “papa ke liye theek hai kya”. And a golden set you write yourself cannot prove its own coverage; scoring 100% against your own examples is circular.

Therefore: (1) cover Hinglish phrasings explicitly, (2) add a conservative refusal instruction in the system prompt as a second line of defence, and (3) write a small adversarial set separate from the golden set — jailbreak attempts, indirect phrasings, and injection through item names.
Rehearse the reviewer's session. Play reviewers get a login for your app. Handed a care-supply app with an “Ask” button, a reviewer will type medical questions at it — that is the review. Sit down before submitting and try to break your own gate for twenty minutes.

Shipping speech output alone gets you the demo-defining moment — the app talks back — while adding no permission, no disclosure flow and no Data Safety change. That is an unusually good trade.

You still need a new store build. expo-speech is not currently in your dependencies REPO, and it is a native module — so a new AAB is required regardless. The point is that this build carries a zero-permission delta, which is what keeps the review boring.

⚠️ Three implementation traps

  • Android throws above a maximum utterance length. Read the limit at runtime and chunk on sentence boundaries. LLM-length answers will exceed it — this is the most likely crash in a naive implementation.
  • Android has no pause or resume. Stop speech explicitly when the screen unmounts and when the app is backgrounded, or it keeps talking.
  • iOS silent mode mutes it entirely. The written transcript must always be visible — never make speech the only channel for an answer.
Auto-speak defaults to OFF. Speech is triggered by an explicit tap. Automatically reading medical-supply levels aloud in a shared household is a privacy problem, not a feature.

🎙️ When you do add voice input (V2)

Including one mandatory requirement that every previous plan — including my own — missed.

🚨 REQUIRED, NOT OPTIONAL. Google Play's AI-Generated Content policy requires that apps generating content with AI provide in-app reporting or flagging, so users can report offensive output without leaving the app. A chat assistant where AI interaction is a central feature is squarely in scope. VERIFIED

What this changes: the plan to add exactly one endpoint is wrong. You need POST /api/v1/ai/feedback and a visible Report control on every AI message. Deferring it is not a scoping choice — it is a policy violation. (Reference: Play Console Help, “AI-Generated Content” policy, article 13985936.)

🗂️ Data Safety — the correction

Earlier claim: sending item names to Groq is “third-party sharing” and must be declared as such; and self-hosting would delete that declaration entirely. RETRACTED
Correct position: Play's own guidance excludes service providers from the definition of sharing — parties that process data on your instructions. A provider under a contractual no-training and deletion commitment fits that description. So there is likely no third-party-sharing line to declare — which also means self-hosting would have changed your Data Safety form by roughly zero fields, collapsing the strongest privacy argument for it.

The real change is different, and simpler: your users' typed chat messages are a new category of data leaving the device. Because nothing is persisted, this is likely ephemeral processing — which is declared in the form but not displayed publicly.

Audit the existing form first — this predates AI. Your app already sends data to Neon (database), Sentry (error tracking) and an SMTP provider (email) REPO. If your current Data Safety declaration omits those, that is a live compliance gap on the launch build, independent of anything AI-related. Check it this week.

✅ Compliance checklist before the AI build ships

  1. In-app AI reporting. Endpoint plus a visible Report control on every AI message. Mandatory.
  2. AI disclosure in the UI. Label AI-generated responses clearly. Cheap to add, awkward to retrofit.
  3. Data Safety update. Declare chat messages; verify the pre-existing processors are declared too.
  4. Privacy policy. Name the AI processor, the data categories sent, the purpose, and the no-training commitment.
  5. Health apps declaration. Re-review it. Note that Play requires this of all published apps — do not wait to be prompted, and do not assume your existing answers still hold once an AI assistant exists. VERIFIED
  6. Content rating questionnaire. Re-check it. Your current answers state there is no user-to-user communication; Play's AI policy explicitly draws an analogy to user-generated-content reporting rules, so confirm whether an AI chat surface changes any answer.
  7. Store listing language. If Groq is down, users get deterministic template answers. Keep bold AI claims out of the listing, or gate them behind the same aiEnabled flag, so an outage cannot become a misrepresentation.
Beyond Play: India's DPDP Act. Your allowlist permits item names to leave the country, and in a care-supply app item names are medicine names. That is health-adjacent personal data crossing a border to a foreign processor. Notice-and-consent obligations under India's data protection law are not addressed in any planning document so far. This is a legal question rather than a Play question — worth a professional opinion before scale, not before your first tester.

⚔️ The tension you should confront, not hide

A hiring manager could reasonably push back. If the deterministic renderer produces the answer and the model only rephrases it, then “I built an agent” and “the agent's output is never load-bearing” cannot both be true. Strip away everything deferred — writes, retrieval, streaming, multi-agent — and what remains is six read-only queries with a paraphraser attached. Here's the eval harness that proves the numbers are grounded, and here's the decision record with the threshold at which I'd hand more control to the model.”

That is a senior answer. “I let the LLM decide everything and it usually works” is not.

Chapter 08 · Execution

Build plan, effort and sequencing

The order matters more than the estimate.

Rule one: do not ship AI in the same submission as your production launch build. Launch first with AI_ENABLED=false. Ship AI in the next build cycle. Your closed-testing clock and production-access application are already in motion; adding a novel AI surface to that submission introduces review risk for no benefit.

🧭 The build order

This ordering is the most important decision in the chapter, and it is deliberately backwards from the obvious one.

  1. Days 1–2 · Write the tests before the feature. The 50-case golden set and guard tests, running against a scripted fake model. No API key needed. Doing this first means the code structurally cannot be built without them — which is the only defence against the eval layer being cut later.
  2. Days 3–4 · Build the deterministic engine and the six tools. Ship a version of the endpoint that answers correctly with AI_ENABLED=false and no API key configured at all, passing the entire golden set.
  3. Day 5+ · Add the LLM as a rewriting layer on top of an answer that is already correct.
  4. Then the guardrails, the mobile screen, voice output, and compliance — in that order.
Why this ordering wins. It narrows the model's job to phrasing; it makes every answer testable without a network call; it means your fallback is the primary path rather than a rarely-exercised branch; and it lets you demo the entire feature with the AI provider switched off.

🧪 The measurement you must not skip

The golden set run against a fake model tests your loop, not the model. Before committing, spend roughly fifty cents running the same set against the live model and record real tool-selection accuracy. If it falls short, change the model name in an environment variable — no code change, no rebuild. That is exactly why the model name is configuration and not a constant.
