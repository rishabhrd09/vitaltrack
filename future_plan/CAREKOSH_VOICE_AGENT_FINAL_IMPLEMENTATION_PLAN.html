What stays on the phone

Item matching, recent resolved-item context, freshness checks, stock calculations, read-only UI actions, fixed answer formatting and immediate playback cancellation.

03 / The question journey

From your words to recorded facts.

  1. Capture

    Press Talk after account consent and microphone permission. Or type a question. No background listening.

  2. Review

    Whisper returns a transcript. Show Send, Edit and Cancel. Reject silence or unusable recordings instead of guessing.

  3. Understand

    The parser must cover the whole request. Otherwise one model request returns a constrained intent, not an answer.

  4. Validate

    Check the action and fields. Resolve item references locally. Clarify duplicates or uncertain wording. Reject writes.

  5. Read

    Use a complete, account-owned, suitable snapshot. If required, refresh it and re-resolve against the selected snapshot.

  6. Respond

    Build one answer object. Show the card immediately; speak its matching text if enabled. Never ask an LLM to rewrite the facts.

Close and Stop bypass stock fetching once their intent is recognised. In V1, a spoken “close” is heard only during an explicit recording turn; a visible Close/Stop control is always immediately available. “Show low stock” calls an approved view handler, not screen-coordinate automation.

04 / Data and capability boundaries

The server stays authoritative.

Reusing a server snapshot is an optimisation inside the existing server-first app—not an offline-first rewrite, a second database or a promise of instantaneous updates from other devices.

Data conditionRequired behaviour
Fresh, complete, correct accountReuse the existing inventory query data. No inventory API call for this question. Relevant pending mutations must already be settled.
Stale, invalidated, missing or incompletePerform a targeted, deduplicated refresh through the current query/API. Do not call queryClient.clear() as an ordinary assistant refresh.
“Refresh / check the latest”Request a new normal server read before claiming a newly checked result. A query timestamp is not a guarantee that no remote change happened afterward.
Stock update still pendingWait for the relevant operation to settle and refetch. If it cannot settle within the turn timeout, state that the update is pending; do not speak a quantity as final.
Offline or refresh failureUse suitable last-known data with an explicit timestamp, or say that the answer is unavailable. Do not generate a global summary from a partial inventory.
Account changes / logout / cancellationCancel work, clear local conversational context and reject late results from the old session or turn.

A 30-second stale threshold is not polling. Stable pagination ordering, duplicate-ID checks and totals help detect issues, but do not by themselves prove a coherent multi-page snapshot during concurrent changes. Define and test the completeness contract before promising aggregate accuracy.

Allowed in V1Explicitly excluded
Quantity, unit, recorded stock status and recorded supplier detailsChanging quantities, adding/deleting items or modifying suppliers
Low-stock, out-of-stock and inventory summaries using shared UI rulesCreating orders, purchases, payments or sending WhatsApp messages
Open a read-only stock view; close an overlay; stop speechArbitrary navigation, executing code, generated SQL or model-chosen URLs
Clarification, missing-data responses and last-resolved-item follow-upsHistorical ordering answers without an explicitly supported tool; medical advice
Read-only refers to the assistant's business capabilities.

There is no assistant inventory-write tool, even with verbal confirmation. Backend-managed authentication, consent and usage accounting may use operational records; they do not authorise the model to change stock or orders. Existing manual application workflows remain separate.

06 / Sequential delivery

Build the reliable parts first.

These eight steps are milestones within the first complete voice release. A working typed assistant is an internal milestone, not completion of the voice requirement. Begin the rights review and native feasibility checks in Step 1; add product behaviour in the sequence below.

  1. Freeze the contract and unblock feasibility

    Write the architecture decision record: supported intents, answer schemas, freshness rules, model choices, data flows and prohibited actions. Start the Alba provenance/runtime review. Run a small Expo Audio development-build check without real-user uploads.

    • Inspect the actual merged Android manifest, recording permissions and background services. Configure microphone use text for supported iOS builds.
    • Use synthetic fixtures publicly; keep consented recordings and real inventory privately. Check existing tracked files before adding ignore rules.
    • Pin supported dependency versions and keep all new capabilities off in production.

    Exit: contracts and test categories defined; native recording feasibility understood; explicit Alba release go/no-go checkpoint recorded.

  2. Make reuse of inventory data safe

    Review and reconcile the existing cache-fix work with the current branch; do not blindly merge an older, diverged branch into a dirty working tree.

    • Add account ownership/session-epoch checks, cancellation and rejection of old-session responses.
    • Use targeted query refresh; preserve mutation tracking and wait for relevant pending stock writes.
    • Verify connectivity/foreground refresh, pagination tie-breaking, duplicate handling and completeness under concurrent changes.

    Exit: fresh suitable answers make zero inventory requests; stale data is identified; account changes and incomplete snapshots cannot produce misleading results.

  3. Build the deterministic assistant

    Create pure TypeScript readers, a conservative parser, local item resolution and fixed answer/speech renderers. Reuse the same low-stock rules as the dashboard.

    • Ship typed input and quick chips first, with dedicated read-only result components.
    • Handle quantity + supplier compound questions, missing values, aliases, duplicate names, summaries and view/close/stop commands.
    • Store only minimal last-resolved-item context locally; clear it at logout and account change.

    Exit: the test suite proves correct data-bound answers without any LLM. The assistant cannot reach mutation handlers.

  4. Add the protected AI boundary

    Extend the existing FastAPI app with the proposed transcription, interpretation and speech routes. Add mobile-client support for cancellation, deadlines, multipart upload and audio responses.

    • Use existing authentication with short-lived transactions; pass an immutable principal to long-running provider work.
    • Keep provider keys server-side. Add per-account usage reservations/settlement, global spend caps and bounded concurrency using existing infrastructure.
    • Enforce actual received-body limits before multipart parsing, as well as type, duration and text limits. Clean up temporary processing files.
    • Record account-scoped consent and settle disclosure/retention terms before real recordings are uploaded.

    Exit: disabled routes fail clearly; unauthorised, oversized and over-budget calls are rejected; provider waits do not occupy inventory DB transactions.

  5. Add language understanding

    Use openai/gpt-oss-20b through one backend adapter with strict JSON-schema output. The prompt contains the selected question and allowed intent schema—not an inventory dump.

    • Use non-streaming intent extraction, bounded completion tokens and supported low-reasoning settings. Treat errors or truncation as failures.
    • Validate the returned structure and meaning. The model never supplies a quantity, supplier fact, executable function, URL or SQL statement.
    • A local parser match must cover the whole request. Do not answer a historical or negated question using only a recognised stock keyword.

    Exit: unfamiliar supported wording works; ambiguity, unsupported clauses and malicious requests fail safely. Schema validity alone is not accepted as semantic accuracy.

  6. Add press-to-talk listening

    Integrate Expo Audio with whisper-large-v3. Start with short English recording turns and explicit Send/Edit/Cancel after transcription.

    • Test the actual encoded file on Android/iOS; sample-rate requests are not guarantees. Validate duration, container and decoded audio.
    • Handle permission denial, silence, noise, interruptions, upload failure, quota exhaustion and logout while recording.
    • Stop playback before recording to reduce self-transcription. Do not infer correctness from Whisper confidence heuristics alone.

    Exit: real target phones and held-out speakers meet the evaluation criteria; private audio is not logged or committed; text fallback is usable.

  7. Add approved Alba speech

    After rights approval, provision the exact model and matching configuration with a recorded checksum. Run pronunciation preparation and synthesis together in a separate bounded Piper worker.

    • The authenticated speech adapter accepts capped deterministic text and returns audio. The worker is not a publicly exposed unlimited TTS endpoint.
    • Do not load Piper or a local LLM into the small inventory API process. Measure service memory, concurrency and latency.
    • Tie audio to the answer/session/turn ID. Close, Stop, logout or a newer answer cancels or discards obsolete work.

    Exit: card and speech agree on names, quantities, units and freshness; cancelled answers never play; rights and required notices are recorded.

  8. Evaluate, stage and release

    Test the complete journey and existing touch workflows. Run a small consented internal pilot before enabling accounts gradually in production.

    • Evaluate accuracy, clarification, stock-rule agreement, silence/noise, cold starts, stale/offline states and shared-device isolation.
    • Measure end-of-recording → card and → first audio separately, including p50/p95, failures and actual per-turn costs.
    • Update privacy disclosures and Play Data Safety before release. Inspect the final release manifest and verify the kill switch.

    Exit: all required safety checks pass; quality and cost evidence is recorded; manual usage remains intact when AI is disabled. Then publish through the normal release workflow.

07 / Implementation contracts

Small interfaces, replaceable providers.

Keep listening, interpretation and speech separate from inventory logic. Future provider changes should replace an adapter, not the assistant's data or presentation layer.

Intent and answer contracts

Suggested intent families: read_item, list_stock, inventory_summary, show_stock_view, close_overlay, stop_speaking, clarify, unsupported_action. Enumerate allowed fields and views. No arbitrary tool name.

{
  "intent": "read_item",
  "reference": "named_item",
  "itemQuery": "hand gloves",
  "fields": ["quantity", "supplier"]
}

This is a shape illustration, not a complete schema. The production schema must constrain each intent, reject extra fields and handle every response variant. For “those gloves,” return a last-item reference; resolve it on the phone rather than sending previous stock facts to the model.

The mobile answer object should include an answer ID, turn/session association, answer type, resolved item facts, missing-field flags, snapshot timestamp, freshness state, completeness status and deterministic speechText. A new refresh creates a new answer version; do not let old audio describe a silently changed card.

Backend routes and operational controls

Paths are relative to the existing API prefix. Existing authentication may read account records. “No inventory lookup during interpretation” is the correct boundary—not “no database access anywhere.”

  • Register the intended routes consistently; disabled capabilities return a clear unavailable response. Update route-count tests from the actual route set, not a hardcoded planning assumption.
  • Make model IDs and provider selection server configuration. Keep a versioned schema and adapters such as transcribe(audio), interpret(question) and synthesize(text).
  • Set account/global budgets with atomic reservations and settlement; include provider minimum billing units. Operational accounting is not an inventory mutation tool.
  • Use provider data controls appropriate to the account. Do not equate a paid plan with guaranteed privacy, or claim “no storage” without examining temporary files, proxies and retention obligations.
  • Log request IDs, model version, duration, status and usage without raw questions, recordings, secrets or answer content by default. Final retention requirements require a separate policy review.

No automatic cross-provider failover in V1. A future replacement must pass the same regression set before configuration changes. Two models on Groq do not protect against a Groq-wide outage.

Cost and sustainability boundaries
  • Mobile tools and local parsing have no AI inference fee. Inventory refresh still uses the existing backend.
  • Groq free allowances are useful for development, not a permanent production funding plan. Budget for transcription and interpretation and handle quota exhaustion.
  • A self-operated Piper service has hosting/compute costs, even without a per-utterance third-party API bill.
  • On-device models can remove those network/inference charges but add development, download size, memory, battery and maintenance costs.
  • Re-evaluate adapters after provider deprecation notices and dependency updates. Long-term stability comes from contracts and tests, not a promise that a model ID never changes.
08 / Release evidence

Proof before a public voice release.

These are required checks, not completed results. Use approximately 150–200 supported-question recordings from 8–10 speakers as an initial evaluation, with held-out speakers/wording and realistic noise and devices. Keep real recordings private.

  • Truth: quantities, units, stock categories and missing fields agree with the selected server snapshot and dashboard rules.
  • Read-only enforcement: unsupported requests cannot reach stock/order mutation functions, even through compound questions or prompt injection.
  • Isolation: account switching, delayed responses, cache restoration and logout cannot leak another account's data or speech.
  • Freshness: reusable fresh data generates zero inventory requests; incomplete, pending or stale states are never described as fully current.
  • Understanding: predefine supported questions before testing. Report per-speaker, device and noise results, clarification quality and end-to-end answer correctness.
  • Audio: real item names and quantities are understood and pronounced acceptably; silence, interruption, Close and Stop behave predictably.
  • Privacy and rights: account-scoped consent, approved processor terms, retention policy, updated disclosures and Alba notices/permission are documented.
  • Operations: measured latency/cost is acceptable; budgets, limits, error handling, cleanup and feature kill switches work in staging.
  • Regression: existing touch-based stock and order workflows still work independently of the assistant.

Suggested statistical gate: a two-sided 95% Wilson interval's lower bound of at least 90% for the predefined supported-question metric, plus separate mandatory safety gates. Repeated clips from the same speaker are correlated, so also report held-out and per-speaker results; this interval is not proof of accuracy across all users. Do not auto-send transcripts solely from recognition confidence scores.

A clear release boundary

Ship the complete voice feature only after the listener, read-only tools, overlay, approved speaker and failure handling pass together. Internal text-only milestones are useful. A public release must not claim Alba or fully offline operation before they actually exist.

09 / What follows V1

Keep the offline path open.

Phase 1 · selected

Reliable voice inventory

Hosted listening and intent extraction; local validated tools and answer cards; approved Alba service; consent, budgets and measured quality.

Phase 2 · benchmark first

Move stages onto the phone

Prototype Whisper through whisper.rn. Evaluate the complete native Alba pronunciation/synthesis path after rights review. Promote only if target-phone quality, latency and battery tests pass.

Phase 3 · separate approval

New workflows, if wanted

PDF generation, external sharing or order creation need distinct capability and confirmation designs. They are not part of the read-only assistant. Stock mutations remain excluded under the current requirement.

Gemini, ElevenLabs, OpenAI conversational audio, Kokoro and Pocket TTS remain alternatives—not additional layers to implement. Any replacement of the exact Piper Alba voice requires an explicit product choice. A provider or preset containing the name “Alba” does not prove it is the same model or voice.

A backend-hosted local LLM still requires a phone-to-backend connection. A downloaded speech model alone does not make the whole assistant offline. Even fully local voice processing cannot learn another device's latest stock update without refreshing from the server.
