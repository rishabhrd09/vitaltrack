Section 00 · Read first

Stop — five things that can bite you this week

Scannable on purpose. Everything else can wait until you have looked at these.

1 · Your production email may be going to a sandbox

MAIL_SERVER is never set in render.yaml, so it falls back to the Mailtrap sandbox default in app/core/config.py. REPO If the Render dashboard does not override it to your real provider, email verification never arrives — and the account-deletion confirmation link your public page promises Google is never sent. Account deletion is a Play requirement, so this is a rejection risk, not a nuisance.

Do now: in the Render dashboard confirm MAIL_SERVER, MAIL_PASSWORD and SENTRY_DSN are really set. DASH Then register a throwaway account and confirm the verification email actually arrives.

2 · You cannot recruit testers yet — a link sent today is wasted

Your app status is Draft. While an app is in Draft, the closed-testing opt-in link does not exist. CLAIM So "0 testers opted in" is not a recruitment failure — nobody can opt in. Build the roster during the review wait (§07), distribute nothing until the app is published.

3 · Your internal testers may be disqualified from closed testing

Anyone who opted into internal testing is ineligible for closed testing, and removing them from the internal list does not undo it — the person must explicitly opt out. CLAIM If your friends and family are already enrolled internally, audit that list before counting on them. Remediation in §07.

4 · eas submit cannot run today

vitaltrack-mobile/credentials/google-service-account.json does not exist — the directory holds only a README — yet eas.json points at it. REPO This does not block the manual upload path you have been using, but it blocks every automated submit from here on. Fix in §05.

5 · Render legacy workspaces auto-migrate 1 August 2026

Included bandwidth reportedly drops from 100 GB to 25 GB with overage billing, and your service is on a legacy plan. CLAIM This lands mid-launch-window. Nothing to do with Play — but check your egress in the Render dashboard, because it could cost more than everything else here combined.

Section 04 · Action 2

Create the service-account key

The one prerequisite that was never started. Not blocking today, but it blocks every automated release.

eas.json points at credentials/google-service-account.json, and that file does not exist — the directory contains only a README. REPO Until you create it, eas submit fails.

  1. Google Cloud Console → create (or pick) a project → IAM & Admin → Service Accounts → Create service account. Name it something like carekosh-play-publisher.
  2. On that service account → Keys → Add key → Create new key → JSON. The file downloads once. Save it as vitaltrack-mobile/credentials/google-service-account.json.
  3. Play Console → Setup → API access. Link the Google Cloud project if it is not already linked. (The previous edition's navigation for this step was outdated.)
  4. Play Console → Users and permissions → Invite new users. Paste the service account's email address. This invitation is what actually grants upload rights — not any Google Cloud IAM role. (The previous edition told you to grant roles/iam.serviceAccountUser; that does not grant Play upload permission and is busywork.)
  5. Least privilege. Grant only "Release apps to testing tracks" at app level. Do not grant account-level Admin to a CI key. Add "Release to production, exclude devices, and use Play App Signing" later, only if you automate production releases.
  6. Confirm it is gitignored. Run the check in Appendix A before you commit anything.
This key is a publishing credential. If it leaks, someone can push releases to your app. Never commit it, never paste it into a chat or an issue, and rotate it if you suspect exposure.
Section 05 · Action 3

The first Closed (Alpha) release

Submitting this is what triggers your first-ever Google review — and what finally kills "Draft".

First, identify which kind of track "Alpha" is

Closed testing → Manage track on the Alpha row. Does a "Countries/regions" tab exist?

  • Yes → it is the default closed track. Everything below applies unchanged.
  • No → it is an additional closed track: no country targeting, no device-compatibility data, and the standard opt-in URL form is undocumented for these. In that case copy the opt-in link from the Testers tab only — never hand-construct it. CLAIM

Clear the five pending tasks

  1. Countries/regions. Closed tracks sync to Production by default — and on a brand-new app Production has no countries, which can resolve to nothing. Click Unsync countries/regions → Edit countries and select generously: India plus every country your testers' Play account is registered in. Targeting keys off the account's registered country, not physical location. CLAIM
  2. Testers — pick ONE mode. Email list or Google Group; they are mutually exclusive radio options and cannot be mixed. Use the email list. A Google Group adds a silent failure mode: a pending, unaccepted invitation is not membership, so that person was never a tester and you are never told.
  3. Feedback channel. Put a real email in the feedback field. It shows on the tester opt-in page, and you will be asked in the production application how you collected feedback — this is your answer.
  4. Create the release. Releases tab → Create new release → Add from library and pick the AAB already uploaded to internal. Do not rebuild — version codes auto-increment remotely and a needless rebuild only adds a moving part. Write release notes inside the <en-US> tags.
  5. Preview and confirm. Expand "Errors summary" via Show more and clear every error. Warnings — including "No deobfuscation file" — do not block. Then Start rollout to Closed testing.
Then go to Publishing overview and click "Send for review". Google does not auto-submit. A large share of "my release is stuck for days" reports are simply an unsubmitted change sitting in that queue. You should see "Changes in review" before you walk away. CLAIM
Then freeze the console. Google counts the review SLA from the last submitted change. One screenshot tweak on day 3 of review sends you back to the end of the queue. Change nothing until it clears.

If it comes back rejected

  • The app drops back to Draft — which kills the opt-in link again. Warn any testers you have already lined up.
  • Your internal track also loses its instant-publish exemption until the next approval.
  • Nothing resubmits itself. Fix the cause, then Publishing overview → Send for review.
  • Do not treat this as a cheap first attempt — repeated rejections can escalate.

Four documented rejection causes worth pre-empting: demo credentials that do not work; a privacy policy that is unreachable or does not match the app; a Data safety declaration that contradicts observable behaviour; and functionality the reviewer cannot reach.

Section 06 · Action 4

Who actually counts as a tester

New section. The previous edition never covered this, and one of these rules is pointed straight at you.

The trap you are standing in. Internal testing is currently Active on your app, and you smoke-tested on your own device. Google's rule: a user who opts into your app's internal test is no longer eligible to receive an open or closed test. CLAIM

Anyone still on that internal list — including you — will silently receive nothing from Alpha and will never count toward the 12. There is no error and no notification. You would discover it when testers say "I don't see the app."

Remediation, before you distribute anything:

  1. List everyone currently on the internal tester list.
  2. Have each person open the internal opt-in URL and explicitly opt out. Removing them from the list does not do this for them.
  3. Ask for a screenshot confirming opt-out.
  4. Treat your own developer account as permanently burned for counting purposes — recruit 12 other people.

Section 07 · Action 5

Recruit 12 without risking your account

Do this during the review wait. Target 18–20 commitments, not 12.

State the asymmetry once, plainly. A rejected release costs you a week. A terminated developer account costs you the $25, the permanent package name com.carekosh.mobile, and the ability to publish under that identity at all — and Google's enforcement policy states related accounts are also permanently suspended, with any replacement account terminated too, without refund. CLAIM

That asymmetry is why the next four rules are absolute, not advisory.

The four absolutes

  1. Never fabricate Google accounts to pad the count — not yours, not family burners. This is the single highest-probability suspension vector for a solo developer under deadline pressure.
  2. Never pay, gift or UPI your recruits to stay opted in. Incentivised installs are a named prohibited pattern.
  3. Never buy testers. A cheap gig buys addresses that opt in once; engagement is what gets graded, and the refund covers the fee, never your account.
  4. Never share Play Console access with someone helping you set things up.
Reassurance, because the internet is loud about this: I went looking for a Play policy that prohibits reciprocal tester exchange between developers, and there isn't one. The ratings/reviews/installs policy is scoped to placement manipulation; the misrepresentation policy is scoped to concealing identity. The realistic downside of exchange-community testers is a production-access rejection for non-engagement — not suspension. The account-level risk lives on the paid and fabricated paths only.

  • testers-community@googlegroups.com — the funnel for a commercial vendor running a paid tier plus a credit economy where you earn installs by installing. Posting is also owner/manager-only, so you could not post there anyway.
  • TestHive Discord — a coin-based tester marketplace. Same product class as the paid tier this guide tells you to decline.

Say "DM me" — never "drop your email below". Public collection publishes your testers' personal addresses for scraping, and it is the fastest way to attract throwaway accounts onto your list. Tester authenticity is precisely what the production review grades.

Distribute in one coordinated wave, not a trickle. Staggered opt-ins mean staggered streaks, and your application date is set by your 12th-slowest tester. Wait a few hours after publish before sending — the test link takes time to propagate — and test it yourself in an incognito window first.
Section 08 · Action 6

The 14-day lookback

Reframed. The previous edition called this a "clock that resets" — that is the wrong mental model.

The rule: a minimum of 12 testers who have been opted in for at least the last 14 days continuously, evaluated at the moment you click Apply.

It is a lookback, not a countdown. There is no banked "completed" state you reach and hold. When you apply, Google looks backwards 14 days and checks that at least 12 people have an unbroken streak covering that whole window. If you are at 11 the day before you apply, you are not eligible that day — regardless of how long the test has been running.

Continuity is per-tester. Google's wording: even if they opt back in so that they are opted in for a total of 14 days, these 14 days must be consecutive. A dropout loses their own accumulated days permanently and needs a fresh 14.

An honest note on a scary claim. Nearly every vendor blog says dropping below 12 resets the whole campaign for everyone. I found no Google source for that — the published wording is per-tester. Your behaviour is identical either way (over-recruit), but you should know the frightening version is unsourced. CLAIM

What Google never tells you

  • When the clock starts. No documented start event — not on publish, not on the 12th opt-in, not on first install. Only the end condition is defined. Every blog claiming otherwise invented it.
  • Whether testers must open the app. The numeric gate says only "opted in." But "your testers not being engaged with your app during your closed test" is verbatim Google policy as a reason to be sent back. No source states any frequency, session count or duration — every specific number circulating is invented.
  • Whether uninstalling breaks continuity. Google addresses opting out but never uninstall. Support told one developer it resets the period. Asymmetric downside — tell testers not to uninstall.

Run the window deliberately

  1. Do not start counting day 1 until you have 15+ confirmed installs. Write the date down. This buffer is the whole strategy — it lets you absorb three dropouts without drama.
  2. Message every 2–3 days with one specific micro-task. "This week: add a medicine with an expiry date and tell me if the reminder text reads right." Never daily spam.
  3. Keep a dated feedback log from day 1. Tester, date, channel, what they said, what you did. This is the raw material for five of the eight application answers and cannot be reconstructed afterwards.
  4. Read Ratings and reviews → Testing feedback in the console, not just your inbox. Testers leave private feedback there that reaches you nowhere else.
  5. Ship 1–3 small updates driven by real feedback. Research split on this — one strand advised freezing the build. I lean toward shipping because the rejection email explicitly cites failure to act on feedback through updates. If you are risk-averse, ship exactly one meaningful mid-window update.
  6. Around day 10, audit the roster. Confirm everyone is still installed and opted in. A replacement recruited on day 10 starts their own 14 days — which is why you over-recruited.
  7. Apply on day 15 or 16, never 13 or 14. The console shows no per-tester day counter, so you cannot audit the boundary. Give yourself the margin.

Section 09 · Action 7

The production-access application

Pre-drafted. The previous edition said "answer Google's short questionnaire", which gives you nothing.

Draft all eight answers in a separate document before opening the form. Google warns — once per section — that clicking Discard or quitting without pressing Next/Apply loses everything you typed. CLAIM

Three sections, eight inputs. Section 1 is the one that is actually assessed; Google states Section 2's answers do not affect your access or eligibility.

Section 1 — About your closed test scored

Q1 · How easy was recruiting testers? Multiple choice, telemetry only. Answer honestly, do not overthink it.

Q2 · Tester engagement. Google's own examples of what it wants: whether testers used all your features, and whether their usage matched how a production user would behave.

All [N] testers installed from the Play Store and remained opted in for the full 14 days. Coverage across the core flows: all [N] created an account and added inventory items; [N] set expiry dates and saw the expiry warnings; [N] used the low-stock threshold and reorder flow; [N] generated an order and exported the PDF; [N] exercised account deletion on a throwaway account. Where tester usage differed from real usage: testers seeded their inventory in one sitting, whereas a real household accumulates items over weeks. That means the expiry and low-stock paths were exercised with artificially clustered dates, so I additionally seeded staggered dates on two devices to test them realistically.

Q3 · Feedback received, and how you collected it.

Feedback came through three channels: the feedback email address published on the tester opt-in page, a WhatsApp group for testers from my personal network, and the Play Console "Testing feedback" panel for private tester feedback. Themes: [e.g. the low-stock threshold wasn't discoverable during onboarding; the item form asked for too many fields before letting you save; the expiry reminder wording was ambiguous about whether it meant "expired" or "expiring soon"].

Section 2 — About your app not scored

Intended audience — Google asks you to be as specific as possible.

Indian households managing recurring medicines and medical consumables — typically one adult keeping track of supplies for elderly parents or for someone with a chronic condition. Most currently track this on paper or not at all, which leads to buying duplicates of one item while running out of another.

Value provided — one paragraph on the problem and how CareKosh solves it. Install estimate — a wide range picker; a rough figure is fine.

Section 10 · Action 8

The first production release

Corrected. The previous edition promised a safety net you will not have.

There is no staged rollout on a first production release. It is all-or-nothing: 100% of users in every selected country, at once. The percentage dial appears from your second release onward. CLAIM

The previous edition instructed "10–20% → 50% → 100%" in four separate places, and made "pause the staged rollout" step one of mobile incident response. That control will not exist on launch day. Combined with updates.enabled=false — no over-the-air fix — you would have gone to 100% believing you had two safety nets you do not have.
  1. Set countries BEFORE creating the release. Production → Countries/regions. Consider India-only first, expanding after a week of clean vitals — that is the closest thing to a staged rollout available to you.
  2. Promote the exact build your testers validated rather than uploading a fresh AAB. It is the one with 14 days of real evidence behind it.
  3. Confirm pricing is Free and the store listing is final.
  4. Create the release, write release notes, send for review. Expect up to another 7 days, and note it can still come back rejected on policy grounds — production access and app approval are two separate gates.
Section 11 · Action 9

The first 48 hours

Stand the monitors up before launch day, not after. They are currently template-only.

Watch these

  • Android vitals — crash rate and ANR rate. This is what Google uses against you.
  • Health endpoints — the curl pair in Appendix A.
  • Render, Neon and your email provider dashboards — and confirm a Sentry event actually arrives (send a test error; if nothing shows, SENTRY_DSN is unset and error tracking is silently off). DASH
  • Connection budget — 2 workers × (pool 5 + overflow 10) = up to 30 Postgres connections. REPO Check that against your Neon plan cap before traffic arrives.
  • Play Console reviews — respond to the first ones. Early reviews weigh heavily.
Point uptime monitors at /live, not /health. /live never touches the database and always returns 200. /health runs a real query under a 2-second timeout and returns 503 by design when Neon has idled and needs to wake. REPO A single /health 503 that recovers is not an outage — alert only after two consecutive failures. Render's own health check is deliberately set to /live for exactly this reason.
Evidence hygiene: record outcomes, never tokens, passwords, database URLs or user emails.
Section 12

If something goes wrong

Rewritten, because the old incident-response plan depended on controls you do not have.

Start from the constraint. updates.enabled = false REPO — there is no over-the-air update channel. Nothing in the mobile app can be hotfixed: not a string, not a URL, not a crash. Every mobile fix is a full build → upload → review cycle. And on release 1 there is no rollout dial to pause.

Therefore: the backend is your only fast lever. Design fixes to land server-side wherever possible.

Mobile — a bad release is live

  1. There is no true rollback on Play. You cannot un-ship a version.
  2. Halt or unpublish to stop the bleeding for new installs. Existing installs keep the bad build.
  3. Forward-fix only. Build a fix with a higher version code, submit, wait for review.
  4. Keep the backend backward-compatible with the installed bad client for as long as it is out there. This is the single most useful habit — it turns most mobile bugs into server-side fixes.

Backend — roll back

  • Render → Events → Rollback to the last good deploy. Note this disables auto-deploy — remember to re-enable it.
  • A Render rollback does not roll back Neon data. Schema and data changes are separate; plan migrations to be backward-compatible.
  • A failed Alembic migration exits non-zero and Render keeps the previous instance live REPO — a bad migration is a failed deploy, not a broken service. That is a good failure mode; do not "fix" it.

Do NOT roll back for

  • A single /health 503 that recovers (Neon waking up).
  • One user reporting a problem you cannot reproduce.
  • Cosmetic issues, or anything fixable by an environment-variable change.
Section 13

Release 2 and beyond

The loop this guide never had. Everything gets easier from here.

  1. eas build --profile production --platform android
  2. eas submit --profile production --platform android → lands on the internal track. Always. REPO The profile is named production but its track is internal; it can never reach production directly.
  3. Smoke-test on internal, then promote internal → closed → production in the Console.
  4. Now the staged rollout dial exists. Start at 10–20%, watch vitals for a day or two, then 50%, then 100%. Halt and resume are available.
  5. Version codes auto-increment remotely — never hand-edit app.json.
Two things to keep safe forever: Play App Signing is enabled, so Google holds the app signing key — but you hold the upload key via EAS. Back up your EAS credentials. And set your Expo token to no expiry or schedule a yearly rotation, or CI will fail months from now for no obvious reason.

Section 15

This release ships no AI

Stated here to prevent scope creep during a launch window.

The decision is recorded in first_agentic_integration.html: launch first with AI disabled; the AI build ships in the next cycle. Do not bundle a novel AI surface into the submission that is already carrying your production-access application.

Consequences for this launch, all of them simplifying: no AI claims in the store listing · no content-rating change · no new Data Safety category · no AI-content reporting requirement · nothing in the AI plan blocks this launch.

One retraction worth knowing. The AI implementation plan gated work on adding an updated_at bump, believing the current update path did not refresh it. That was tested against the real update shape and it does bump correctly — the prerequisite is withdrawn. Do not spend launch-window days on it.
When the AI build does come, it carries a delta this guide does not cover: a mandatory in-app reporting control for AI-generated content, a Data Safety update for chat messages, and a new AAB. All of it is in the decision record. Not now.

Appendix G — Known gaps and open code tasks

None of these block launch. Recorded so they are not rediscovered under pressure.

  • No in-app link to the privacy policy or deletion page. The About dialog has only a support email. The in-app Delete Account flow itself exists. Low effort, and the kind of thing a reviewer looks for.
  • carekosh.com/terms and /support return 404 LIVE — do not reference them in the listing's support-website field.
  • Mobile has no test infrastructure — npm test is dead.

  • Slug and URL scheme still say vitaltrack. Cosmetic, invisible to users.
