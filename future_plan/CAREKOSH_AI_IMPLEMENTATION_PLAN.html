Chapter 00 · Preface

The vision, the constraints, and the system you already have

Read this first — every later chapter assumes it.

🎯 What we are building, in one paragraph

CareKosh today is a hardened, launched inventory tracker: a caregiver types, taps and reads. The AI layer turns it into something you can talk to: “oxygen kitne bache hain?” → the app answers in plain language, speaks the vital numbers aloud, and renders a beautiful item card — photo, current stock vs minimum, brand, supplier, expiry — right on screen. The same brain lives on WhatsApp, where it answers the family for free and (with consent) sends the morning stock report, low-stock warnings, and “this item hasn’t been synced in a while — is the count still right?” nudges. Everything is grounded in the live Postgres data through the REST endpoints you already shipped; the model never invents a number.

The three inherited rules (from the parent feasibility doc — unchanged):
1 · Foundation first. None of this ships in the first Play Store release. The AI layer is gated on launch + roughly the first 50 active users.
2 · WhatsApp-only, and inbound-first. No Telegram, ever. Replies to user-initiated WhatsApp messages are free; business-initiated (proactive) templates cost a few paise — so proactive alerts default to free in-app push, with WhatsApp templates as an explicit opt-in.
3 · Free LLMs only. Groq (Llama 3.1 8B, native tool-calling, 14,400 req/day) as primary; Google Gemini Flash free tier as failover; Cloudflare Workers AI / OpenRouter :free as emergency lanes; deterministic non-LLM answers straight from the DB when everything throttles. Recurring cost target: ~₹0/month.

🗺️ The system you already have (the AI layer is ~70% pre-built)

Chapter 01 · The flagship

Ask CareKosh — the conversational inventory agent

Type or say an item’s name → get its live quantity, stock status and a spoken summary, plus a rich on-screen item card. This chapter is the brain every other chapter reuses.

₹0 · Groq + Gemini freeEffort MV2.0 — build firstJob signal: agentic tool-calling (must-have, +300% YoY)

📖 1.1 Overview — what & why

What. A chat surface inside the app (and later on WhatsApp and voice) where the caregiver asks in plain English or Hinglish — “oxygen kitne bache hain?”, “what’s running low?”, “show me the critical items” — and CareKosh answers from the live database: the quantity, whether it’s below minimum, whether it’s a critical item, and everything needed to act (brand, supplier, reorder link). The reply arrives three ways at once: text, a spoken summary of the vital numbers (expo-speech), and an item card — an aesthetic inline panel with the item photo, a stock-vs-minimum meter, brand and expiry.

Why. A home-ICU caregiver is often mid-task, gloved, or holding equipment. Scrolling a list is friction; asking is instant. And because the family thinks in mixed Hindi-English item names, natural language beats exact-match search. Crucially, this is not a chatbot bolted on: every answer is a read of your own Postgres rows through the endpoints you already hardened — the model routes, the database speaks.

Design law №1 (repeated all book long): the model never emits a number. It selects tools; quantities come from tool JSON. For writes it proposes a signed delta (“+5”), the app computes new_qty = max(0, current + delta) and writes through the existing version-CAS endpoint with a confirm card on critical items. A hallucination cannot corrupt stock.

🏛 1.2 Architecture

One tool-calling agent; tools are thin wrappers over the services you already trust. Reply = {text, speech, cards[]}.

The free-only LLM client with failover

# app/services/ai/llm.py  (prototype — httpx is already a backend dependency)
class LLMClient:
    async def chat(self, messages, tools) -> LLMResult:
        try:
            return await self._groq(messages, tools, model="llama-3.1-8b-instant")
        except (RateLimited, ProviderDown):
            try:
                return await self._gemini(messages, tools, model="gemini-flash")
            except (RateLimited, ProviderDown):
                raise AllProvidersDown       # caller renders deterministic DB answer

# app/services/ai/tools.py  (prototype)
# Read tools return exactly the JSON the answer may use. No tool ⇒ “I don’t know.”
async def search_item(db, user_id: str, query: str) -> list[ItemCard]: ...

async def get_stats(db, user_id: str) -> StatsOut: ...

# The ONLY write-adjacent tool. It does not write — it returns a proposal.
async def propose_stock_delta(db, user_id, item_id: str, delta: int, reason: str) -> StockProposal:
    item = await get_item(db, user_id, item_id)          # fresh read: quantity + version
    return StockProposal(item_id=item.id, current=item.quantity,
                         new_qty=max(0, item.quantity + delta),
                         version=item.version, reason=reason,
                         needs_confirm=item.is_critical)  # confirm card on critical items

The agent loop (LangGraph — same effort as hand-rolled, instant JD keyword)

# app/services/ai/agent.py  (prototype)
# StateGraph: plan → call_tools → (maybe more tools) → compose
graph = StateGraph(TurnState)
graph.add_node("llm",     run_llm_with_tools)     # Groq function-calling
graph.add_node("tools",   execute_tool_calls)     # dispatch to tools.py, collect JSON
graph.add_node("compose", compose_reply)          # text + speech + cards from tool JSON only
graph.add_conditional_edges("llm", wants_tools, {True: "tools", False: "compose"})
graph.add_edge("tools", "llm")                    # let the model read results, then answer
agent = graph.compile()

Mobile — the hook that types, listens and speaks

// hooks/useAssistant.ts  (prototype)
export function useAssistant() {
  const [turns, setTurns] = useState<Turn[]>([]);
  const send = async (message: string) => {
    setTurns(t => [...t, { role: "user", text: message }]);
    const reply = await postChat(message);            // services/ai.ts → /api/v1/ai/chat
    setTurns(t => [...t, { role: "assistant", ...reply }]);
    if (reply.speech) Speech.speak(reply.speech, { language: "en-IN" }); // expo-speech
  };
  return { turns, send };
}

Chapter 02 · Ears & mouth

Voice mode — hands-free stock audit

Tap-to-talk on top of the Chapter 1 brain: speak the question, hear the answer, verify the physical shelf without touching the screen.

₹0 · on-device STT + TTSEffort L (permission + store build)V3 — after the text agent proves outJob signal: voice AI pipelines

📖 2.1 Overview — what & why

What. A microphone button on the assistant screen. Speech is transcribed on the device (nothing leaves the phone), shown as text for confirmation, sent through the same /ai/chat brain, and the reply is spoken back. On top of single questions sits Audit Mode: the app walks you item-by-item through the stale/critical list — “Oxygen shows 2 — is that right?” — you answer “yes” or “no, it’s 4”, and each correction goes through the delta-proposal + CAS write. This is your “verify against the physical list” requirement, made hands-free.

Why. The core caregiver moment is standing at the supply shelf, hands full. Voice turns a 90-second phone session into a 15-second exchange — and Audit Mode attacks the #1 real-world failure of every inventory app: digital counts drifting from physical reality.

🏛 2.2 Architecture

Voice is a peripheral: ears (on-device STT) and mouth (TTS) around the unchanged Chapter 1 brain. Optional server lane: Groq Whisper large-v3 (free, 2,000 req/day) or the Apache-2.0 Whisper-Hindi2Hinglish model for heavy code-switching.

// components/ai/VoiceButton.tsx  (prototype)
import { ExpoSpeechRecognitionModule, useSpeechRecognitionEvent } from "expo-speech-recognition";

export function VoiceButton({ onFinal }: { onFinal: (text: string) => void }) {
  const [partial, setPartial] = useState("");
  useSpeechRecognitionEvent("result", (e) => {
    setPartial(e.results[0]?.transcript ?? "");
    if (e.isFinal) onFinal(e.results[0].transcript);   // → transcript gate, NOT straight to send
  });
  const start = () => ExpoSpeechRecognitionModule.start({
    lang: "en-IN",              // hi-IN also works; native engine handles code-mixing tolerably
    interimResults: true,
    requiresOnDeviceRecognition: true,   // privacy: no network audio
  });
  return <MicButton onPressIn={start} partial={partial}/>;
}

Audit Mode sketch: app/audit.tsx pulls the stale + critical queue (Ch.4 endpoint), loops: speak “Item shows N — correct?” → listen for “yes / no, it’s M” → yes logs a verification touch (bumps updated_at via a no-op-delta endpoint), no routes through propose_stock_delta with the confirm card. Ten items ≈ one minute, hands-free.

📱 2.4 What the user sees

Mic button pulses while listening and prints the live partial transcript. On finish, the gate: “You said: add five oxygen” with [Send] [Edit] [Retry] — a deliberate friction, because STT mishears medicine names and Hinglish, and a mis-write on a medical item is the one unforgivable bug. Then the normal Chapter 1 reply, spoken aloud. In Audit Mode the screen shows a big per-item card with ✓/✗ voice or tap — designed to be glanceable from arm’s length.

⚖️ 2.5 Feasibility

  • FREE STT on-device (native engines) and TTS via expo-speech — ₹0, private, offline-capable. Server Whisper lanes stay free (Groq 2,000 req/day) if Hinglish accuracy demands them.
  • Verified specifics (2026-07): pin expo-speech-recognition@sdk-54 (v3.1.3) — do not install latest into this SDK 54 app; it needs a dev build (never Expo Go); true on-device recognition requires Android 13+ / iOS 17+ (network-based is the default below that — check getSupportedLocales() for Hindi per device). TTS quirks: no pause/resume on Android, ~4,000-char input cap, silent-mode mutes it on iOS.
  • The real cost is procedural, not monetary: RECORD_AUDIO is currently blocked in app.json — unblocking it changes the permission manifest ⇒ a new store build + Play review, and permission changes cannot ship via OTA. It also reopens the Data-safety form (“Audio: not collected — processed on device, never transmitted” if on-device only).
  • Hence the sequencing verdict: ship Chapter 1 as text first (zero new permissions), add voice when the brain has proven itself. Effort L overall; the code itself is small.

📖 3.1 Overview — what & why

What. A WhatsApp number for CareKosh. Anyone in the family messages it — “kya kya low hai?”, “oxygen?” — and the agent replies with the grounded answer, formatted for WhatsApp (list + bold numbers). The Cloud API itself costs nothing. So: replies = ₹0 forever; a scheduled 8 AM report to a user who hasn’t messaged since yesterday = ~11.5 paise; the same report to someone who chatted with the bot today = ₹0.

# app/api/v1/webhooks.py  (prototype)
@router.get("/integrations/whatsapp/webhook")        # Meta's one-time subscribe handshake
async def verify(mode: str = Query(alias="hub.mode"),
                 token: str = Query(alias="hub.verify_token"),
                 challenge: str = Query(alias="hub.challenge")):
    if mode == "subscribe" and token == settings.WA_VERIFY_TOKEN:
        return PlainTextResponse(challenge)
    raise HTTPException(403)

@router.post("/integrations/whatsapp/webhook")
async def receive(request: Request, db: DB):
    verify_hmac(await request.body(), request.headers["X-Hub-Signature-256"],
                settings.WA_APP_SECRET)                       # reject forgeries
    msg = parse_inbound(await request.json())                 # text or button reply
    link = await get_wa_link(db, wa_id=msg.wa_id)
    if link is None:
        return await wa.send_text(msg.wa_id, LINK_INSTRUCTIONS)   # “open CareKosh → Connect WhatsApp”
    reply = await agent.run(db=db, user_id=link.user_id, message=msg.text)
    if reply.proposal and reply.proposal.needs_confirm:           # critical write → buttons
        return await wa.send_buttons(msg.wa_id, reply.text,
                                     yes=f"confirm:{reply.proposal.token}", no="cancel")
    await wa.send_text(msg.wa_id, format_for_wa(reply))          # free service reply

async def scan_stale(db, user_id, days=7) -> list[Item]:
    cutoff = now_utc() - timedelta(days=days)

Chapter 05 · The memory

Semantic search & RAG over your inventory

“O2 cylinder”, “oxygen”, “ऑक्सीजन” and “that breathing tank thing” should all find the same row. pgvector on the Neon you already run — no new infrastructure.

₹0 · pgvector + local embeddingsEffort MV2.1Job signal: RAG (~65% of applied-LLM JDs)

📖 5.1 Overview — what & why

What. An embedding column on items, filled from name + brand + notes + category with a multilingual sentence-embedding model, plus a /items/semantic-search endpoint the agent uses as a smarter search_item tool. Retrieval is hybrid: exact ilike first (fast, precise), vector similarity as the fallback for fuzzy/Hinglish/synonym queries.

Why. The Chapter 1 agent is only as good as its retrieval: ilike '%oxygen%' misses “O2 concentrator”. Families name items inconsistently across languages; embeddings bridge that. This is also, verbatim, the RAG pattern the job market screens for — grounded retrieval feeding generation.

Chapter 07 · The oracle

Consumption forecasting & smart reorder

“At this pace, Oxygen runs out next Tuesday — reorder by Saturday.” Plain arithmetic over your own activity log, verbalised by the agent. No ML infrastructure, honest about its limits.

₹0 · pure SQL + arithmeticEffort SV3 (needs weeks of history)

📖 7.1 Overview — what & why

What. The activity log already records every stock change (“Stock: 6 → 4”). From the negative deltas over a trailing window we compute a daily consumption rate per item, then days_to_stockout = quantity / rate and a suggested reorder date (stockout minus lead-time buffer). Surfaced three places: a line on the item card (“≈ 9 days left at current pace”), a digest section (“reorder this week: …”), and the agent (“when will saline run out?”).

Why. Minimum-stock thresholds are static; consumption is not. A family using 2 oxygen cylinders/week and one using 2/day need different warnings — this feature personalises urgency from data the app already collects, for free.

🧩 7.2 Code & placement

vitaltrack-backend/ ├── app/services/forecast.py ← NEW: rate + days-to-stockout (window: 30d, min 3 events) ├── app/api/v1/items.py ← MOD: forecast fields on GET /items/{id} (+ /stats) └── app/services/ai/tools.py ← MOD: forecast_item tool for the agent
# app/services/forecast.py  (prototype — deliberately boring math)
async def consumption_rate(db, user_id, item_id, window_days=30) -> float | None:
    # sum of negative stock deltas from activity_log over the window
    used = await sum_negative_deltas(db, user_id, item_id, since=days_ago(window_days))
    events = await count_stock_events(db, user_id, item_id, since=days_ago(window_days))
    if events < 3 or used <= 0:
        return None                       # honesty rule: too little history ⇒ say nothing
    return used / window_days

def days_to_stockout(qty: int, rate: float | None) -> int | None:
    return None if not rate else max(0, floor(qty / rate))
Honesty rule (product + prompt): below 3 consumption events in the window, the app shows nothing and the agent says “not enough history yet” — a wrong forecast on a medical item is worse than no forecast. The LLM verbalises the number; it never computes it.

📱 7.3 UI · ⚖️ feasibility · 💼 job relevance

UI: one quiet line on the item card + a “Reorder this week” digest block + agent answers. Feasibility: FREE, Effort S — two SQL aggregates and division; ships in a day once history exists (hence V3 timing). Job relevance: classic-ML forecasting is a declining JD differentiator (generic ML postings −18% since 2024) — so don’t oversell it; its real interview value is judgment: “I chose transparent arithmetic over an ML model because n≈30 rows/item, explainability beats accuracy at this scale, and the failure mode of silence is safer than a confident wrong prediction.” That answer outperforms a TensorFlow name-drop in 2026 rooms.
