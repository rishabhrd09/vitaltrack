Part 1 · Welcome

Welcome to CareKosh

In short: CareKosh is one Android app, one FastAPI service and one PostgreSQL database. This page hands you what you need to set it up, change it, test it and ship a change safely.

What CareKosh is

CareKosh helps a family or caregiver keep a home ICU stocked: suction catheters, gloves, dressings, oxygen accessories, medicines and equipment.

People record what they have and see what is running low. They prepare a purchase order, mark it received, and add the received quantities to stock.

An inventory assistant with local drafts answers typed or spoken questions such as "How many nitrile gloves are left?". Voice never changes stock or saved orders. It can prepare an unsaved local draft; only touch confirmation saves an order.

For the big picture and every API flow, read page 1, the system overview. This page is about doing the work.

Four facts to keep in your head

The server is the truth

Core

The app is server-first. The phone caches what it reads for display, and every write goes straight to the API. There is no offline write queue: most buttons block offline saves, and mutations are not queued for later replay. Started requests may still wait on the network.

Two lines of code

Branches

main is 835fad3, with migrations up to 0006 and no assistant routes. The newest code is on feature/backend-hardening-ai-voice-agent-foundation at 03cfebb, pushed but not merged. This page describes the feature branch.

Legacy folder names

Do not rename

The repository is still called vitaltrack, and so are vitaltrack-backend/ and vitaltrack-mobile/. The CI workflow, the rootDir in render.yaml and the Expo slug in app.json use those names.

A public repository

Careful

Anyone can read what you push. Use synthetic data such as asha@example.com and "Nitrile gloves", and keep every secret out of Git (Part 13).

Run the backend locally

In short: Run docker compose -f docker-compose.dev.yml up --build -d in vitaltrack-backend/. PostgreSQL 16 and the API start, migrations run by themselves, and http://localhost:8000/health answers "healthy".

First-time setup

Clone the repository and run the setup script from its root. On Windows, run setup-local-dev.bat instead.

git clone --branch feature/backend-hardening-ai-voice-agent-foundation https://github.com/rishabhrd09/vitaltrack.git
cd vitaltrack
chmod +x setup-local-dev.sh
./setup-local-dev.sh
  1. Checks your tools. It stops if node, npm, git or docker is missing.
  2. Finds your LAN address. It detects the laptop's IP on your Wi-Fi network.
  3. Writes two .env files, only if they do not exist. vitaltrack-backend/.env gets LOCAL_IP and an email-link base on that IP. vitaltrack-mobile/.env gets EXPO_PUBLIC_API_URL=http://<your LAN IP>:8000.
  4. Installs the app's packages. It runs npm install --legacy-peer-deps in vitaltrack-mobile/.
  5. Prints "Setup Complete!". Re-running it never overwrites an existing .env file.
After your IP changes

A new Wi-Fi network usually means a new laptop IP, and the script will not rewrite the files. Edit EXPO_PUBLIC_API_URL in vitaltrack-mobile/.env, and LOCAL_IP and FRONTEND_URL in vitaltrack-backend/.env. Update existing files carefully; deleting them would discard any settings you added. The walkthrough

Keep docker compose -f docker-compose.dev.yml logs -f api open in a second terminal while you go.

  1. Start everything. The backend in Docker (Part 4) and the app in Expo Go (Part 5). /health should say healthy and connected.
  2. Register. Tap Create Account with a synthetic address such as asha@example.com. The password needs 8 to 128 characters with an upper-case letter, a lower-case letter and a digit. The app then shows the verify-email screen: registering never signs you in.
  3. Verify, only if enforced. With MAIL_PASSWORD empty, nothing is sent or enforced, so tap "I've Verified — Go to Login". With email configured, open the emailed link first.
  4. Log in. The app stores a 30-minute access token and a 30-day refresh token in SecureStore, clears any old cache and opens the dashboard. The dashboard computes its counts on the phone.
  5. Build inventory. Dashboard → "Build Inventory" opens the Builder → "+ Add New Category". Then Inventory tab → "+" → add "Nitrile gloves" with quantity 40 and minimum stock 50.
  6. Edit the item. Open it, change the quantity to 38 and Save. The save carries the version captured when the form opened. A stale save returns 409; active views refetch, and you reopen the form to load fresh values.
  7. Create an order. Orders → "+" → pick lines → "Confirm order & export PDF". The order gets a number such as ORD-YYYYMMDD-NNNN, stock does not change, and the phone makes the PDF.
  8. Receive and apply. On the order card, tap "Have you received the order?", then "Update Stock". The quantities rise once; a second apply is refused.
  9. Ask the assistant. Profile menu → Voice setup → turn on Assistant → "Try a typed question here". Type "Show low stock", then "How many nitrile gloves are left?".
What the app offers today

The order screens offer only two moves: pending → received, and received → apply. "Remove" appears for every order, but the server deletes only pending and declined ones. There is no stock +/- control; quantities change through the Edit Item form or by applying an order.

Rules you must not break by accident

The code enforces these rules. Changing one is a product decision, so it should be the stated point of a pull request.

Stock never goes negative

Database

A CHECK (quantity >= 0) constraint, plus API limits of 0 to 999,999.

Stock changes only on purpose

API

Creating an item sets its initial quantity. Existing quantities change through version-checked item edits, the API-only PATCH /items/{id}/stock adjustment, or applying a received order. Creating, receiving, declining or deleting an order never changes stock.

An order is applied once

API

Only from received, adding the full ordered quantity of every line in one transaction.

History stays

API

Only pending and declined orders can be deleted. Order numbers are never reused.

Everything is per user

API

Protected business-resource queries filter on the signed-in user; auth lookups, the daily counter and global AI quota queries have different scopes. Another user's id behaves as "not found" (404).

The assistant reads and prepares local drafts

API

Voice cannot change inventory or saved orders. It can prepare local unsaved drafts; its only server writes are consent and usage records. Touch confirmation on Create Order saves an order.

The full list of twelve rules is in section A3 of the complete developer guide.

Checklist: add a field to items, end to end

The example is a hypothetical optional field, storage_location, sent as storageLocation in JSON.

  1. Model. Add a nullable column to the Item model in app/models/item.py. Optional fields keep existing rows valid and older app builds working.
  2. Migration. From a shell whose DATABASE_URL points at your local database, run alembic revision --autogenerate -m "add item storage location". Read the generated file. Its down_revision must be 0010_order_local_id_unique, and the change should only add.
  3. Schemas. Add the field to ItemCreate, ItemUpdate and ItemResponse in app/schemas/item.py, with alias="storageLocation".
  4. Handlers. create_item and update_item in app/api/v1/items.py copy fields one by one, so add yours to both. In update_item, copy the model_fields_set pattern of the other nullable fields: an explicit null clears the value, and an omitted field stays unchanged.
  5. Backend tests. Extend tests/test_items.py: create with the field, update it, clear it with null, and omit it. Run with --migrated-schema so your migration runs too.
  6. App types. Add storageLocation?: string to the Item interface in types/index.ts, and to CreateItemRequest and UpdateItemRequest in services/items.ts.
  7. The form. Add the input to the item editor app/item/[id].tsx. The same file serves Add Item, when the route id is new, and Edit Item.
  8. Other readers. Search the app for an existing optional field such as supplierName. It also appears in the Builder, order creation, the export modal and the order PDF.

Checklist: add an API endpoint

  1. Pick the router. Add the route to the resource's file in app/api/v1/. A new resource needs its own router, included in app/api/v1/__init__.py under the /api/v1 prefix.
  2. Authenticate and scope. Declare current_user: CurrentUser and db: DB from app/api/deps.py. Scope protected resource queries on user_id == current_user.id, so another user's id returns 404.
  3. Shapes. Add request and response models in app/schemas/, set response_model=, and give multi-word fields camelCase aliases with populate_by_name.
  4. Write safely. Group each business mutation and its history writes in the shared session; commit explicitly once its checks pass. get_db finishes any remaining transaction, and rollback cannot undo an earlier commit. FastAPI 0.118 moved when that later code runs, so explicit commits keep you safe across upgrades.
  5. Status codes the app understands. 401 starts a token refresh, 409 shows a conflict message, 422 shows validation details, and status 0 means "could not connect". Return codes that match what really happened.
  6. Tests. Use the client fixture and the helpers in tests/conftest.py (register_and_auth, create_category, create_item). Include a test where another user's id returns 404.
  7. The route gate. CI counts route objects under /api/v1 with python scripts/check_api_routes.py --expected 44. Raise that number in .github/workflows/ci.yml; the script's own default is also 44. The gate also fails for any /sync route, or for /health or /live mounted under /api/v1.

  9. The mobile caller. Add a function in services/<resource>.ts and a hook: reads in hooks/useServerData.ts, writes in hooks/useServerMutations.ts. A write hook invalidates the affected query keys after success.
  10. Older apps. A deploy cannot update installed apps, and over-the-air updates are off. Keep existing routes working for every app version still installed; prefer adding a field or a route over changing one.

Checklist: change a screen

  1. Find the file. expo-router maps files to routes. The tabs are app/(tabs)/index.tsx (dashboard), inventory.tsx and orders.tsx; sign-in screens live in app/(auth)/. Shared pieces live in components/.
  2. Read through hooks. Use useItems, useCategories, useOrders or useActivities from hooks/useServerData.ts.
  3. Write through mutation hooks. Use or add a hook in hooks/useServerMutations.ts. Never save domain data to AsyncStorage: the app has been server-first since PR #8, and it uses no optimistic updates.

    git switch -c fix/short-name

Contributing from a fork

Without write access, fork the repository on GitHub, clone your fork, and add the original as upstream. Push branches to your fork and open the pull request "across forks". To catch up with a moving main:

git fetch upstream
git rebase upstream/main
git push origin feature/my-contribution --force-with-lease

--force-with-lease refuses to overwrite work that someone else pushed to your branch in the meantime. Never force-push main.

What decides what

The app build picks the API

Build time

Each EAS profile compiles its EXPO_PUBLIC_API_URL into the app. app.config.js refuses a preview or production build whose address is set to anywhere else, so a preview APK cannot reach production by accident. An empty address is not refused; the app then falls back to http://localhost:8000. A production AAB in Play's internal testing does use production data.

The service picks the data and secrets

Run time

DATABASE_URL, SECRET_KEY, ENVIRONMENT, MAIL_*, FRONTEND_URL, SENTRY_DSN and any AI_* flags are set per backend service. Each environment needs its own SECRET_KEY: a separate database alone does not separate tokens.

Database branches copy data

Careful

A Neon branch made from production contains production data, and it inherits production's database roles and passwords. Use a new, empty database for staging experiments.

Deploys and builds are separate

Two pipelines

Backend changes reach every installed app as soon as they deploy. App changes reach people only when they install a new build, because over-the-air updates are off.

Part 13 · Rules that protect data

Rules that protect data and secrets

In short: The repository is public and production holds real caregivers' data. Keep secrets out of Git, run tests only on throwaway databases, and change shared databases only through a reviewed deploy.

The rules

The repository is public

Public

Anyone can read every commit, branch and pull request. Use synthetic data in code, tests, screenshots and docs: asha@example.com, "Nitrile gloves", "Suction catheter 12FR". No real people, emails or inventory.

Never commit secrets

Secrets

.env files and credentials/*.json are git-ignored; keep it that way. Stage explicit paths and read git diff --staged before each commit. If a secret reaches GitHub, treat it as leaked and tell the owner so it can be rotated.

App variables are public

App builds

Every EXPO_PUBLIC_* value is compiled into the app. Never put a key there. Provider keys such as GROQ_API_KEY live only on the backend service.

Tests only on throwaway databases

Tests

The backend fixtures drop every table. Use a separate database whose name contains test, never staging, production or your development database.

down -v deletes data

No undo

docker compose down -v removes the PostgreSQL volume (postgres_data_dev or postgres_data) with every local account, item and order. Plain down keeps it. Use -v only for disposable local data.

No migrations on shared databases

Databases

Migrations reach staging and production only through a reviewed deploy that follows the release gate. Never run alembic upgrade or alembic downgrade against them from your laptop. To check a deploy, use read-only commands such as alembic current.

Keep development away from production

Real data

Avoid npm run start:prod: even signing in writes session and activity rows to production. Never run Start Fresh, Replace All, "Update Stock" or account deletion against production: they change real data at once, and deletion sends real email.

Security findings stay private

Security

Do not describe a vulnerability in an issue, pull request, commit message or document in this repository. Tell the owner privately, and keep security write-ups out of the public repository.

Know the limits of the protections

Rate limiting is best effort: five auth routes, counters in memory per worker process, reset on restart; an open finding about how clients are identified is tracked privately.

CORS is a browser rule. It does not authenticate anyone and does not restrict the Android app. Security comes from authenticated tokens and owner checks on protected business-resource queries.
