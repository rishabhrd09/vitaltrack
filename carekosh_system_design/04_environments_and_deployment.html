Part 1 · The big picture

The three environments at a glance

In short: the same code runs in development, staging and production. The app build decides which API a phone calls. Each backend service decides which database and secrets it uses.

An environment is one complete copy of the system: an app build, an API host and a database. CareKosh keeps its environments apart through configuration alone. The backend code never names staging; it treats any ENVIRONMENT value other than development or testing as a deployed service.

For what each component does, start with the system overview. This page is about where those components run and how changes reach them.

Rules that keep data safe

Staging is not disposable

Staging

Do not wipe staging because of its name; testers may depend on its accounts. Reset only an environment you have confirmed is disposable.

down -v deletes data

Local

docker compose down -v removes the database volume. Use docker compose down for a normal stop.

Tests drop every table

Tests

The test fixtures drop and recreate tables. The suite refuses a database unless its name contains test or pytest and its URL does not look like staging, production or a cloud host. Never aim it at a shared database.

Internal testers use production

Play

A production AAB calls api.carekosh.com in every Play track, internal testing included. Treat those testers' data as real.

A Neon branch copies data

Neon

By default, a Neon branch starts with all of its parent's data. A branch of production therefore contains production data. Use a new empty database for staging experiments.

Secrets stay out of Git

Public repo

The repository is public. .env files and credentials/*.json are git-ignored; keep keys, database URLs and tokens in dashboards and GitHub secrets only.

Part 2 · Configuration

Configuration boundaries

In short: the app's API address is fixed when the app is built. Everything the backend needs comes from environment variables on each service. Secrets live in provider dashboards and GitHub, never in the repository.

Two kinds of configuration

Build time · the app

Mobile

The API address (EXPO_PUBLIC_API_URL) is written into the JavaScript bundle when the app is built. Each EAS profile in eas.json sets it. To change it, build again.

Locally, npx expo start inlines the current value as it bundles; after changing .env, restart Expo with --clear. With no value at all, services/api.ts falls back to http://localhost:8000.

Run time · each backend service

Backend

app/core/config.py (pydantic-settings) reads every setting from environment variables, then from a .env file if one exists. Environment variables win.

The Docker image never contains .env, because .dockerignore excludes it. On Render, each service holds its own values in the dashboard.

Never a secret in EXPO_PUBLIC_

Anything in an EXPO_PUBLIC_ variable can be read by anyone who has the app. Provider keys such as GROQ_API_KEY stay on the server.

Backend variables, per service

These are the settings that differ between environments or matter for a deployment. "render.yaml" below means what that file declares for production. The live dashboard values were not checked.

Secrets and switches that must differ

A different SECRET_KEY per environment

Required

The key signs every access and refresh token. A separate database does not isolate tokens: two services sharing one key can validate each other's signatures. Full acceptance also needs matching user ids and session generations; copied databases make that risk concrete. Rotating the key signs every user of that service out.

Email verification needs two switches

Conditional

Verification is enforced only when REQUIRE_EMAIL_VERIFICATION=true and MAIL_PASSWORD is set. Without MAIL_PASSWORD, no email goes out, and forgot-password and account deletion return 503.

The assistant's AI is off by default

Conditional

Every AI feature-enable flag defaults to off, and render.yaml sets none. Groq understanding needs AI_ENABLED, AI_DATA_CONTROLS_REVIEWED and a server-side GROQ_API_KEY; while AI is off, accepting consent returns 503. Speech recognition runs on the phone and needs none of this.

What CORS does and does not do

CORS tells browsers which web pages may read API responses. It authenticates nobody and does not restrict the Android app. With ["*"], the API allows every origin with credentials disabled. Tokens and the per-user ownership filter provide the security.

Owner report, not verified: GROQ_API_KEY is set on staging. The live AI flags of both services were not checked.

Part 3 · Backend runtime

A URL without a port slows start-up

The host pattern needs an explicit :port. Without one, the script falls back to localhost:5432, the wait fails for about 60 seconds, and start-up continues. Migrations still use the real URL, so the deploy works, only slower.

Neon's default connection strings usually omit the port. Whether the live URLs include one is not verified: look for Extracted HOST: in the deploy log, or set DATABASE_HOST and DATABASE_PORT.

Earlier A-27: a percent-encoded password could fail Alembic configuration before migration. Fixed locally on 8 October 2026: alembic/env.py escapes percent signs for ConfigParser, which returns the original URL. Encode reserved password characters normally; deploy the fix before relying on it.

Inside one running instance

The concepts behind workers, pools and the event loop are explained on the backend page. Here are the numbers that matter for deployment.

Workers
Gunicorn supervises 2 Uvicorn worker processes. Each has its own event loop and its own connection pool.
Connections
Each worker keeps 5 pooled connections plus up to 10 overflow, and waits up to 30 s for a free one. One instance can open up to 2 × (5 + 10) = 30 connections.
Query limit
Every pooled connection sets statement_timeout = 8000 ms, so one hung query cannot hold a connection forever. pool_pre_ping replaces dead connections.
Database TLS
On outside development and testing (ssl=True), for the app and for Alembic.
Logs
The access log goes to stdout and the error log to stderr. SQL parameter values are hidden (hide_parameters=True).
Rate limiting
Rate limiting is best effort: five auth routes, counters in memory per worker process, reset on restart; an open finding about how clients are identified is tracked privately.
Shutdown
The app's lifespan disposes the database engine when the process stops.

Overlapping instances during a deploy, and other services on the same database server, add to the 30. The provider's connection limit is not verified here.

/live versus /health

GET /live

Liveness

Answers from the process alone and never touches the database. It returns 200 with database: "not_checked".

Render's health check and the Docker HEALTHCHECK use it. A short database outage therefore neither restarts nor removes an instance.

GET /health

Readiness

Runs SELECT 1 with a 2-second timeout. It returns 200 with database: "connected", or 503 with status: "unhealthy" and database: "unavailable".

Use it for monitors and people. The local Compose health checks use it too.

Neither names the running commit

Both report the constant version 1.0.0 and the environment value. To know what is deployed, read Render's deploy record and run alembic current (Part 8).

Part 4 · CI/CD

What each Git action runs

In short: a feature push alone does not trigger this CI workflow. A pull request to main runs the checks, and so does every later push to its branch. Render can independently auto-deploy its linked feature branch if enabled. Merging to main can trigger a production backend deploy. App builds are separate EAS builds.

Triggers

One workflow, .github/workflows/ci.yml, listens for three events. They are pull requests to main (opened, synchronize, reopened, labeled), pushes to main, and a manual run (workflow_dispatch). A newer run for the same pull request or branch cancels the older one.

What protects main

Read through the GitHub API on 7 Oct 2026; not re-checked since. There is no classic branch protection. One active ruleset, protect-main, has no bypass actors.

Pull request required

Enforced

Direct pushes to main are rejected. A pull request needs 0 approvals.

No force push, no deletion

Enforced

Non-fast-forward pushes and deleting the branch are blocked.

Status checks

Not required

A failing CI run does not technically block a merge. Reading every job before merging is a team rule.

If required checks are added later, remember two GitHub behaviours. A job skipped by its if: condition reports success. A job or step with continue-on-error never fails the run.

Two ways a backend deploy starts

Render auto-deploy

Not verified

Render watches the branch each service tracks. render.yaml has no autoDeploy key, and a new Blueprint service defaults to deploy-on-commit, while an existing service retains its current setting when autoDeployTrigger is omitted. Render also offers "after checks pass" and "off".

The dashboard decides, so assume it is on until you see otherwise. It can start before CI finishes. An April 2026 record found both services filtered to the vitaltrack-backend folder, so frontend-only commits did not redeploy them.

CI deploy hook

If the secret is set

deploy-backend requests the secret RENDER_DEPLOY_HOOK URL after both test jobs pass on a push to main. A GET or POST to that URL asks Render to start a deploy, or queues it (202); a suspended service refuses it (409). The call sends no commit, so Render deploys the latest commit on the service's branch, which can be newer than the one CI tested.

The hook ignores the folder filter. Earlier docs say it points at production; the repository cannot show which service it targets. Both triggers can fire for one merge.

Render keeps the old instance serving until the new one passes its health check. Render sends SIGTERM to the old instance 60 seconds after traffic switches; graceful shutdown has a separate delay (30 seconds by default), so old in-flight work can continue beyond that point.

How migrations run at start-up

alembic/env.py runs these steps inside the entrypoint's alembic upgrade head.

  1. Open one transaction. Every pending migration runs inside it, so if one fails, the whole run rolls back, earlier migrations included.
  2. Limit lock waits. SET LOCAL lock_timeout = '30s' stops a migration from queuing forever behind busy tables.
  3. Take the runner lock. pg_advisory_xact_lock(1128354383, 1) makes two containers that start together take turns. A runner that waits longer than the 30 s lock timeout fails like any other migration error.
  4. Apply and commit. Pending migrations run in order; the commit releases the lock.
  5. On failure, stop. The entrypoint exits 1 and the new container never serves. Render keeps the previous version running.
What the lock does not do

The advisory lock coordinates migration runners only. It does not stop old application instances from writing. A start-up that fails after migrating keeps the new schema, and redeploying older code does not undo it.

Migrations open their own connection, without the 8-second statement timeout. Neon recommends direct (unpooled) connections for schema migrations. Which endpoint the live DATABASE_URL uses is not verified. The app sends statement_timeout as a connection start-up parameter, which Neon's pooler rejects, so a -pooler URL would make every app connection fail. main has neither the advisory lock nor the lock timeout.

Why a plain merge is unsafe for 0007–0010

main (835fad3) knows migrations up to 0006, and production presumably runs it Not verified. Merging the feature branch would run four migrations in one container start.

No way back

Risk

0007 refuses to downgrade. An older image cannot undo it and will not even start against the migrated database (see Rollback). Old instances still running ignore session_version.

Orders pause briefly

Risk

0010 takes a SHARE lock on orders while it builds its unique index. Order writes wait until it finishes.

Order numbers can collide

Risk

During the zero-downtime overlap, old code numbers orders by counting rows while new code uses the counter. A collision also rolls back the counter, so order creation can keep failing for the rest of that day.

Unverified accounts are blocked

Risk

The new code applies the verification rule to protected bearer-authenticated requests and token refresh. With both switches set, unverified email accounts get 403 EMAIL_NOT_VERIFIED. Count the active unverified accounts first.

The release gate, step by step

  1. Freeze and record. Control both triggers: turn Render auto-deploy off and hold the CI deploy hook for the cutover. Turning auto-deploy off alone does not block the hook. Record each service's deployed commit and alembic current; production should show 0006_order_item_qty_positive.
  2. Stage the candidate. Preserve the existing staging database: do not run the one-way 0007–0010 on it. Stage the candidate on an isolated fresh database, and verify the 0006 → 0010 upgrade on a populated synthetic legacy database. Fresh-schema tests alone do not prove a legacy upgrade is safe; CI's two upgrade tests (tests/test_migration_safety.py) use a handful of synthetic rows. Then run the end-to-end verification guide with a preview APK built from the same commit, including order retries and the assistant. A preview APK calls staging-api.carekosh.com, so point that service at the isolated database for the test. The owner reports staging already runs b1c8dd7; check its alembic current first.
  3. Back up. Take a production backup or restore point. Rehearse the restore on a separate throwaway database with scripts/restore_drill.py.
  4. Cut over with writes paused. In a maintenance window, stop old instances first by suspending the service or using a verified maintenance procedure that blocks new writes and drains in-flight work. Render documents a maintenance mode for paid web services: public requests get 503 while the instance keeps running. A suspended service rejects deploy-hook calls (409). Remember that 0010 briefly locks the orders table.
  5. Deploy and verify. Deploy the reviewed commit. Before reopening, confirm Render's commit, alembic current = 0010_order_local_id_unique, /live and /health.
  6. Only if writes could not be paused. Run the idempotent counter re-seed below, after the backup and once the old instance is gone.
  7. Check logs and privacy. Read the real access and error logs and telemetry, using synthetic tokens.
  8. Monitor. Watch order-create failures (409), 401 and 403 spikes, refresh failures, database connections and lock waits.
  9. Re-enable auto-deploy. Only after every check above passes.
-- Idempotent order-counter re-seed; safe to repeat.
-- Run only on the confirmed production database.
INSERT INTO order_number_counters (day, last_value)
SELECT substring(order_id from 5 for 8), max(substring(order_id from 14)::bigint)
FROM orders
WHERE order_id ~ '^ORD-[0-9]{8}-[0-9]{4,18}$'
GROUP BY 1
ON CONFLICT (day) DO UPDATE
  SET last_value = GREATEST(order_number_counters.last_value, EXCLUDED.last_value);

The full record is in BACKEND_HARDENING.md and the complete developer guide, F5.

Rollback is a data decision

Code rollback keeps the schema

Redeploying an older image runs no downgrades. The database stays at the newer revision.

Downgrades stop at 0007

0008–0010 have untested downgrades. 0007 raises, so the chain cannot go lower automatically.

Old code may refuse to start

After 0007–0010, main's Alembic cannot find revision 0010 ("Can't locate revision"). Its alembic upgrade head fails and the container exits. Going back needs a database restore.

Restores lose writes

Restoring a backup discards every write made after it. Prefer a reviewed forward fix while writes stay paused.

Capacity planning

The planning target

Assumption

Up to 10,000 accounts and perhaps 100–1,000 simultaneously active users. It is a planning assumption; nobody has measured it.

Accounts are not requests

Principle

Capacity depends on how many requests arrive each second and how long each takes. Nothing in the repository measures that, and no load test has been run.

  • One instance opens up to 30 database connections: 2 workers × (5 + 10). Deploy overlaps and other services add more, and the provider's limit is not verified.
  • Rate limiting is best effort: five auth routes, counters in memory per worker process, reset on restart; an open finding about how clients are identified is tracked privately.
  • Measure first: request rate, latency, pool use and lock waits. Then add resources for an observed need, keeping the single service.

When something goes wrong

  1. Confirm the symptom. Check /live, /health and one authenticated read with a test account.
  2. Look at the deploy. Check Render's latest deploy and logs, and alembic current.
  3. Protect data first. If data is at risk, stop writes by suspending the service before anything else.
  4. Prefer a forward fix. Redeploying an older image does not undo migrations, and an image older than the schema will not start.
  5. Restore only deliberately. Confirm the target and accept that later writes are lost.
  6. Write it down. Record what happened, with times and commits.
Rotating SECRET_KEY

A new key signs out every user of that service, because existing tokens stop validating. Rotate only if the key may be compromised, and only on the affected service.

Portability

Another container host

Swappable

Any host that runs a container, provides $PORT, terminates TLS and reaches PostgreSQL can run the image. Recreate the variables, replace render.yaml and the deploy hook, then repoint DNS.

Another PostgreSQL provider

Swappable

Another database engine

Large project

The code relies on PostgreSQL: JSONB, partial unique indexes, INSERT … ON CONFLICT, advisory locks, statement_timeout, row locks and transactional DDL.
