Part 1 · The big picture

One app, one API, one database

An Android app talks to one FastAPI service over HTTPS. The service owns one PostgreSQL database. Everything else either supports those three or runs only when someone switches it on.

What CareKosh is

CareKosh helps families who run a home ICU keep life-critical supplies in stock: suction catheters, gloves, dressings, feeding sets and medicines.

People record what they have and see what is running low. They prepare an order, mark it received, and add the received quantities to stock in one step.

An inventory assistant with local drafts answers questions such as “How many nitrile gloves are left?”. Voice never changes stock or saved orders. It can prepare an unsaved local draft; only touch confirmation saves an order.

The project was originally named VitalTrack. The code folders are still called vitaltrack-backend/ and vitaltrack-mobile/ because hosting paths and build settings depend on those names.

The system at a glance

The colours below mean the same thing in every diagram on these four pages. A dashed outline marks something that runs only when it is configured.

Phone app

Phone

Expo and React Native on Android. Screens read through TanStack Query and write through one API client, services/api.ts.

Backend

Backend

FastAPI on Python 3.12, run by Gunicorn with two Uvicorn workers inside one Docker container on Render.

Database

Data

PostgreSQL: version 16 in CI and local Docker. Production is documented as Neon; its server version is not verified. Alembic migrations 0001–0010 own the schema on the feature branch.

Outside services

Only when configured

Brevo sends email; Groq interprets unfamiliar reviewed text and can transcribe finished recordings with separate audio consent; Sentry collects errors when enabled.

Five facts that explain most behaviour

  1. The server is the only source of truth. The phone keeps a display cache. It never holds a second database and never queues writes for later.
  2. Protected inventory, category, order and activity queries are scoped to the signed-in person. Inventory queries include user_id = current_user.id, so someone else's id returns 404 and reveals nothing.
  3. Business changes commit together. Data and history writes in a mutation are grouped before commit. A request can use several transactions; rollback cannot undo an earlier commit. Applying an order to stock either changes every line or none.
  4. The writes most likely to race carry a guard. Items carry a version, orders carry a localId, and status changes and token refreshes use conditional updates. Category edits have no such guard.
  5. Offline recognition is the default. Live words and offline final transcription run on the phone. Separately selected Groq online listening uploads a finished take after Stop with audio consent. Unmatched reviewed text goes through the server after Send with separate text consent; no inventory list is uploaded.

What is not built

Knowing what is absent prevents wrong guesses when you debug.

No queue, cache server or worker

There is no message queue, no Redis and no background worker service. Email is sent by FastAPI BackgroundTasks after the response.

No offline writes

Most write buttons block when the phone reports no network. Mutations are not queued for later replay. A request that does start can still wait on the network; concurrent edits still need version checks.

No over-the-air updates

updates.enabled is false in app.json. Every app change reaches people only through a new build.

No roles

is_superuser exists on the user model, but no route uses it. Every person sees only their own data.

No server push

The server never pushes changes. Another phone's edits appear after the next refetch.

Optional server speech

voice-service/ contains optional speech services. Backend adapters reference the configured Kokoro and Piper service URLs, but hosted speech output is disabled in the current mobile build. Optional Groq audio transcription has its own consent and capability checks. Their deployment is not verified.

Why no optimistic updates

Changing the screen before the server agrees would show stock that might not exist. CareKosh waits for the commit, so a number on screen is always a number the database accepted.

What happens when a backend container starts

Every deploy and every restart runs the same entrypoint, docker-entrypoint.sh.

1Wait for PostgreSQLpg_isready up to 30 times, 2 s apart, then carries on with a warning. A DATABASE_URL without :port makes it probe localhost:5432, which adds about a minute
2Migratealembic upgrade head in one transaction under an advisory lock; a failure stops the container
3Start GunicornTwo Uvicorn workers bound to $PORT
4ServeRender polls /live (the path in render.yaml; the live setting is not verified) and sends traffic once it passes

During a zero-downtime deploy the old container keeps serving while the new one migrates and starts, and it is stopped only after traffic has switched. That overlap matters for migrations, which is why the next section exists.

Before the feature branch is merged

A plain merge is unsafe

A merge can deploy production if a trigger is configured. The candidate container runs migrations 0007–0010 at its next start. 0007 refuses to downgrade, and an image from before 0010 fails its own start-up migration (“Can't locate revision”), so going back needs a database restore.

Old instances still number orders by counting rows, which can collide with the new daily counter while both run. Follow the release gate on page 4: freeze both deploy triggers; keep the existing staging database; stage the candidate on an isolated fresh database and test the 0006 → 0010 upgrade on a populated synthetic legacy database; check end to end with a preview APK; back up; cut over with writes paused; verify.

One instance at run time

Processes
Gunicorn starts 2 Uvicorn workers per container. Each worker is one Python process with one event loop.
Database pool
5 connections plus up to 10 overflow per worker, so up to 30 per instance. pool_pre_ping checks a connection before use.
Query limit
Statements on the application engine have an 8-second limit (statement_timeout). A timed-out statement aborts its transaction; earlier commits remain. Alembic uses a separate engine without this limit.
Slow work
Argon2 password hashing runs in a worker thread, so one login does not stall the loop.
Body size
At most 2,000,000 bytes; 12,000 for AI JSON routes; 900,000 for /ai/transcribe.
Health
/live answers without touching the database. /health runs SELECT 1 with a 2-second limit. Neither reports the running commit.
Capacity is a planning assumption

The target is up to 10,000 accounts and perhaps 100–1,000 people active at once. No load test has measured it.

Rules every endpoint follows

Validate before the handler

Pydantic checks the path, query and JSON body. Invalid fields get 422 before the handler runs. Authentication dependencies run first and can query PostgreSQL, so a bad token gets 401 even with invalid fields; malformed JSON is rejected before those dependencies.

Check the caller

get_current_user checks the token's signature, expiry, type and session_version, then whether the account is active and, when verification is enforced, verified.

Scope to the owner

Every inventory query filters on the caller's id. Someone else's id returns 404.

One shared business session

get_db supplies the business handler and its auth dependency with one session. Handlers usually commit explicitly; teardown commits or rolls back any remaining transaction. It cannot undo an earlier commit. AI routes use separate short sessions.

Write history with the change

Handlers record activity for many mutations and audit snapshots for selected changes, such as item edits and order application. Those rows commit with the mutation; not every route creates both kinds of history.

camelCase out

Responses use aliases such as minimumStock and isActive. Token fields stay snake_case, such as access_token.

Part 6 · The data

Eleven tables, one owner per row

Almost every row belongs to one user, so deleting a user removes everything they own in one cascade. PostgreSQL enforces the rules that must never break; the API enforces the rest.

Two kinds of history

activity_logs

Shown in the app

A short feed for people: sign-ins and sign-outs, new and deleted categories, item changes and order steps. Action names are reused, such as ITEM_CREATE for a new category. The Dashboard shows the latest 20 through GET /activities.

audit_log

Server only

JSONB snapshots of old and/or new values for every item change, including order apply (one row per line) and category deletion, and for order deletion. Category edits, order creation, status changes and account changes write none. No route reads it.

Enums are stored as names

orders.status and activity_logs.action are VARCHAR columns that hold the upper-case enum names, such as STOCK_UPDATED. The API returns lower-case values, such as stock_updated. Raw SQL must use the upper-case names.

Part 7 · One request, end to end

From the Save button to PostgreSQL and back

Follow one real request, saving a new quantity for Nitrile gloves, through every layer. Every other write in CareKosh takes the same path with a different handler.

The whole trip in one picture

Hop by hop

The example: Nitrile gloves show 40 pairs at version 3. The person opens Edit Item, types 45 and taps Save.

  1. The screen starts a mutation. app/item/[id].tsx calls useUpdateItem().mutate with fields and version captured together when the form opened, then closes. A cache refresh cannot replace the form version (A-1 fixed locally).
  2. The hook calls the service. TanStack Query runs itemService.update(id, data) in services/items.ts, which drops undefined values and blank strings (stripEmpty) but keeps null, which the form sends for cleared optional fields. It calls api.put('/items/{id}', …).
  3. The API client builds the request. services/api.ts joins EXPO_PUBLIC_API_URL with /api/v1, reads the access token from SecureStore and adds Authorization: Bearer …. Ordinary calls have a 90 s overall deadline covering transport, shared-refresh/retry waits and response parsing. AI calls retain their 50 s deadline.
  4. The request crosses the internet. A production build calls https://api.carekosh.com. DNS for carekosh.com is documented as Cloudflare, and Render's edge ends TLS and forwards the request to the container Not verified.
  5. A worker picks it up. One of the two Uvicorn worker processes that Gunicorn supervises accepts the connection. Its event loop runs this request alongside others that are waiting on I/O.
  6. The middleware runs, outermost first. AIBodyLimit reads the whole body (at most 2,000,000 bytes, else 413). The next layers note the X-Request-ID (echoed or created) and add it and the security headers on the way out. CORS lets the request through, since it applies only to browsers.
  7. FastAPI matches the route and parses JSON. PUT /api/v1/items/{item_id} maps to update_item in app/api/v1/items.py. Malformed JSON gets 422. Dependencies run next and field validation after them, so invalid fields can still follow SQL.
  8. Dependencies prepare the call. get_db creates an AsyncSession; it checks out a pooled connection on first SQL. get_current_user loads and checks the user (401 or 403 on failure). Pydantic validates ItemUpdate before calling the handler, but that auth lookup can precede a 422 for invalid fields.
  9. The handler takes the name lock, then checks ownership. Edit Item always sends name, so the handler first takes the account's name lock (pg_advisory_xact_lock, held until the transaction ends); item saves that carry a name run one at a time per account. It then reads the item with WHERE id = :id AND user_id = :me. Someone else's item, or a missing one, returns 404.
  10. One compare-and-swap UPDATE. UPDATE items SET …, version = version + 1 WHERE id = :id AND user_id = :me AND version = 3. One row changed means the save won. No row means another save (or a delete) got there first, and the handler returns 409 with the version and quantity it read in the previous step.
  11. History is written in the same transaction. An ITEM_UPDATE row goes into activity_logs, and audit_log gets the old and new values. Then the handler commits. A failure before that commit rolls back this mutation. A refresh, serialization or network failure afterwards cannot undo the committed change.
  12. The response goes back out. db.refresh re-reads the row in a new transaction, and ItemResponse is serialised in camelCase with quantity: 45 and version: 4. get_db then commits that read and closes the session, before the reply is sent. The middleware adds X-Request-ID and the security headers on the way out.
  13. The phone refreshes its lists. onSuccess invalidates ['items'] and ['activities']. TanStack Query fetches them again, every screen that shows them re-renders, and the new cache is saved to AsyncStorage.
  14. If the token had expired. The first reply is 401. The client runs one shared refresh for every waiting request (30-second limit), stores the new pair and retries once. A refresh that is refused signs the person out.

The 409 body carries the values loaded by the handler's initial SELECT, for example {"error": "Version conflict", "message": "…", "server_version": 4, "server_quantity": 45} after the winning save above. An Edit Item save waits at the name lock, so it reads the winner's values; a request without a name, such as the API-only stock PATCH, can report stale values when requests overlap. Refetch before editing again. “Unchanged” means no change by the losing request; another request may have changed the row.

Rate limits

Rate limiting is best effort: five auth routes, counters in memory per worker process, reset on restart; an open finding about how clients are identified is tracked privately.

Part 9 · The flows that matter

Seven flows, from the tap to the table

Each flow shows what the person does, what the app sends, what the server checks and what the database holds afterwards. The database states come from a scripted walkthrough with synthetic data, replayed on 7 October 2026 and re-run on 8 October 2026 against a disposable local PostgreSQL 16 database (89 steps, all matched).

Sign in and stay signed in

Login

The identifier is lower-cased; one with @ is looked up as an email, anything else as a username. A wrong user or password gets 401 “Incorrect email/username or password”. Argon2 verification runs in a worker thread.

Every request

The access token carries sub, exp, type and session_version. get_current_user rejects a refresh token, a missing user or an older session_version.

Refresh

One conditional UPDATE revokes the presented token only if it is still active and unexpired, then a new pair is issued. Replaying an old token gets 401, but the newer token keeps working.

Logout and password changes

Logout revokes that refresh token; the access token still works until it expires. A password change or reset raises session_version and revokes every refresh row, so every older token fails at once.

Create an order safely

  1. Save creates the key. app/order/create.tsx generates one localId per press of Save. Retry reuses it; a second press of Save makes a new one.
  2. Pydantic checks the body. orderId must be present (its value is ignored); 1 to 1,000 lines, each quantity 1 to 999,999. Otherwise 422.
  3. It looks for the key. An order with the same (user, localId) already exists? Return it with 200 and write nothing, even if the lines have changed.
  4. It checks the items, then numbers the order. Every item id must belong to the caller (else 400). INSERT … ON CONFLICT (day) DO UPDATE SET last_value = last_value + 1 RETURNING gives the next number for today in UTC, such as ORD-20261007-0001.
  5. It writes and commits. The order, its lines and an activity row commit together, and the reply is 201. A rolled-back create does not use up a number.

Read-only by construction

Phone

The allowed intents are reads, summaries, low and out of stock, clarify, close, stop and unsupported_action (a refusal). There are no write intents, and the assistant calls no saving code.

Gated on the server

Backend

Interpret needs AI_ENABLED, AI_DATA_CONTROLS_REVIEWED, a Groq key and consent voice-2026-10-06. Default limits per UTC day: 20 interprets per person and 200 in total, because the cost budgets bind before the 50 and 500 request caps; failed attempts count. At most 4 run at once, 1 per person.

How screens stay current

Fresh for
30 s (staleTime); orders are stale at once (staleTime 0), so every trigger refetches them. Data no screen uses stays in memory for 24 h (gcTime); the saved copy has its own 24 h limit, counted from its last save.
Refetch when
A screen mounts, the app returns to the foreground, the connection comes back, the person pulls to refresh, or a save invalidates the list.
Reads retry
3 times. Saves never retry on their own.
Saved copy
carekosh-query-cache in AsyncStorage. Auth queries and mutations are never saved.
Offline
Lists keep showing cached data; the Dashboard and the Orders tab say “showing last synced data”. The assistant labels such answers “Last known”.
Item lists
Fetched in pages of 100; the client rejects overlapping pages or a total that does not add up. Offset pages are not a snapshot, so some concurrent changes can still slip through.

Part 10 · When things go wrong

A failed request leaves nothing half done

A request that fails before it commits rolls back that transaction; an earlier commit stays. Multi-request jobs, such as the Builder's replace-all, can stop part-way. The status code tells the app what happened, though some 409 messages are generic (A-3).
