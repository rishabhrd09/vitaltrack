Part 1 · Present the project

How to present CareKosh

In short: Lead with the shape: one Android app, one FastAPI service, one PostgreSQL database. Then trace one request, name the safety rules and finish with the honest limits. Quote only numbers you can point to.

The 30-second pitch

Say what it is, what is hard about it, and how you know it works. Practise it until each sentence fits in one breath.

Say this

“CareKosh helps families keep a home ICU stocked: gloves, suction catheters, dressings and medicines. I built the backend as one async FastAPI service on PostgreSQL with 47 HTTP operations.”

“Several phones can share one account, so item edits carry a version and the server rejects a stale version with 409. It adds a received order to stock only once, and order creation is safe to retry.”

“Sessions use rotating refresh tokens and Argon2 password hashes, and protected business data is scoped to the signed-in user. 242 backend tests run against a real, migrated PostgreSQL schema, including deliberate race tests.”

Then add one sentence of status. The hardening and assistant work is on a pushed feature branch (03cfebb) that is not merged into main yet.

The 2-minute architecture walkthrough

Use this order. Each step is one or two sentences out loud, and each points to a later part of this page.

  1. The product. Caregivers record supplies, see what is running low, raise purchase orders and add received stock. Several people may share one account on different phones.
  2. The shape. An Android app (React Native and Expo) calls one FastAPI service over HTTPS. The service owns one PostgreSQL database. There is no queue, no Redis and no separate worker service.
  3. One request. Gunicorn runs two Uvicorn worker processes. A request passes the middleware, reaches a router under /api/v1, receives a database session and the current user from dependencies, and usually commits its business mutation explicitly (Part 4). A session and a transaction are different concepts.
  4. The data rules. Protected business-resource queries filter by owner; auth lookups and global counters use different keys. Item edits carry a version, and a stale one gets 409. Orders follow a state machine, and applying stock claims the order first (Part 8).
  5. Security. Argon2 runs off the event loop. Access tokens last 30 minutes; refresh tokens rotate and work once. A password change bumps session_version and ends every session (Part 7).
  6. Operations. The container migrates the database before it starts the server. /live checks the process and /health checks the database. The application engine sets an 8-second per-statement limit; Alembic does not (Part 9).
  7. The assistant. An optional inventory assistant with local drafts can ask Groq to classify a question, behind consent, quotas and a strict schema (Part 11).
  8. Evidence and limits. 242 backend and 121 mobile tests passed on 7 October 2026 and again on 8 October. Name the known gaps yourself before you are asked (Part 12).

Why these choices

FastAPI on ASGI

Core

Handlers spend most of their time waiting for the database. ASGI lets one worker interleave many waiting requests. One typed signature drives validation, injection and the API docs.

Async SQLAlchemy with asyncpg

Core

The driver gives the event loop back while PostgreSQL works. SQLAlchemy 2.0's typed Mapped[...] models and select() queries keep the code checkable.

PostgreSQL

Core

The correctness patterns depend on it: row locks, advisory locks, INSERT … ON CONFLICT, partial unique indexes, JSONB audit snapshots and transactional DDL. Moving to another engine would be a project of its own.

Gunicorn with Uvicorn workers

Infra

Uvicorn speaks HTTP and runs the event loop. Gunicorn supervises two worker processes, so two Python interpreters serve in parallel. The worker class uvicorn.workers.UvicornWorker is deprecated (finding A-22).

Argon2 and HS256 JWTs

Core

Argon2 is slow and memory-hard by design; OWASP lists Argon2id first. HS256 suits one service that both issues and verifies tokens with one secret.

pydantic-settings

Core

One Settings class reads the environment once at import, converts the types and rejects unsafe values before the server starts.

Part 3 · Python

Python foundations you can see in the code

In short: CareKosh uses modern Python everywhere: coroutines and an event loop, type hints with Annotated, Pydantic models, async context managers, generator dependencies, decorators and enums. Each idea below points at a real file.

async, await and the event loop

Calling an async def function returns a coroutine. The event loop runs it until it reaches an await on something not ready yet, such as a database reply. Then the loop runs another request. This is cooperative multitasking on one thread.

Each Uvicorn worker process has one event loop. Every CareKosh handler is async def, and every query is awaited through asyncpg. While one request waits for PostgreSQL, the same worker serves others.

Concurrency still has limits. A worker can hold at most 15 database connections (5 pooled plus 10 overflow). The 16th request waits up to 30 seconds for a free one.

CPU work goes to a thread

Argon2 is deliberately slow CPU work with no await inside. Called directly in a coroutine, it would freeze every request on that worker. anyio.to_thread.run_sync runs it in a worker thread and awaits the result.

# app/api/v1/auth.py, register (excerpt)
hashed_password=await anyio.to_thread.run_sync(hash_password, data.password),

# app/api/v1/auth.py, login (excerpt)
if not user or not await anyio.to_thread.run_sync(
    verify_password, data.password, user.hashed_password
):
    raise HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Incorrect email/username or password",
        headers={"WWW-Authenticate": "Bearer"},
    )

Register, login, password reset and change-password all hash or verify this way. The database query stays on the loop, because asyncpg yields while PostgreSQL works.

Common misconception

Async does not make CPU work faster. The hash costs the same CPU time and 64 MiB of memory in a thread. AnyIO's default limit is 40 threads per event loop, shared with any sync code.

Python's GIL lets one thread run Python bytecode at a time. Threads can interleave Python execution and overlap I/O waits. CPU work runs in parallel within a process only when native code releases the GIL; separate worker processes can also run in parallel. argon2-cffi calls its C code through CFFI, which releases the GIL during the call, so a hash can overlap the event loop's work. Throughput on the target instance is still unmeasured.

Context managers and generator dependencies

async with guarantees clean-up: the session closes even when a handler raises. A dependency that yields is a setup and teardown pair around the handler.

# app/core/database.py
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:   # async context manager
        try:
            yield session                         # the handler runs here
            await session.commit()                # after the handler returns
        except Exception:
            await session.rollback()              # any exception, HTTPException included
            raise
        finally:
            await session.close()

The same shape appears three more times. The app's lifespan is an @asynccontextmanager in app/main.py. get_db_context serves the /health probe. The AI module uses async with AsyncSessionLocal.begin() for its short transactions.

Part 4 · FastAPI

FastAPI internals, as CareKosh uses them

In short: FastAPI combines Starlette (ASGI routing and middleware), Pydantic (validation) and dependency injection. The handler's signature is the contract: it decides path, query and body parameters, dependencies and the response shape.

ASGI, Starlette and the app factory

ASGI is the async interface between a server and an app: async def app(scope, receive, send). Uvicorn parses HTTP, builds the scope and calls the app on its event loop. WSGI, the older standard, makes one blocking call per request and cannot await.

FastAPI subclasses Starlette, so the CareKosh app object is an ASGI callable. Gunicorn imports it as app.main:app.

# app/main.py (excerpt)
def create_app() -> FastAPI:
    app = FastAPI(
        title=settings.APP_NAME,
        docs_url="/docs" if settings.DEBUG else None,          # docs only with DEBUG
        redoc_url="/redoc" if settings.DEBUG else None,
        openapi_url="/openapi.json" if settings.DEBUG else None,
        lifespan=lifespan,
    )
    # CORS, then add_request_id and add_security_headers ...
    app.include_router(api_v1_router)
    app.add_middleware(AIBodyLimit)        # added last, so it runs first
    app.state.limiter = limiter
    register_exception_handlers(app)
    register_health_endpoints(app)
    return app

app = create_app()

The factory keeps the wiring order in one place. Importing app.main also configures logging, may start Sentry, loads settings and creates the database engine. Tests reuse this module-level app and override get_db.

Response models and camelCase

  • The response model is a filter. response_model=ItemResponse lets only declared fields leave the server, so a new ORM column cannot leak by accident.

  • One route returns two statuses on purpose. POST /orders declares 201 and sets 200 through the injected Response when a localId repeats.

Dependencies with yield, and when the commit happens

  • Cached per request. get_current_user depends on get_db, and the handler also asks for DB. FastAPI calls get_db once, so the user lookup and the handler share one session, sharing a transaction until the handler commits or rolls back. Depends(f, use_cache=False) would opt out.
  • Dependencies run before body errors are reported. A request with a bad token and a body that breaks the schema gets 401, because get_current_user raises first. With a valid token, its user SELECT has already run when the 422 comes back. Malformed JSON is different: it fails with 422 while the body is read, before any dependency runs.
  • Handlers commit explicitly. The routers contain 25 await db.commit() calls. A handler can then refresh() and serialize the saved row; the commit in get_db usually ends only a read transaction.
  • AI routes are the exception. They use a separate Principal dependency that opens its own short session, so no pooled connection is held while the model provider answers.
Commit timing depends on the FastAPI version (A-23)

In the pinned FastAPI 0.115.6, the code after yield runs after the response is built and before it is sent. A failing final commit still becomes an error response.

FastAPI 0.118.0 moved that teardown to after the response is sent. From 0.121.0, Depends(scope="function") can explicitly request earlier teardown; the default request scope still exits after sending. Before upgrading, review dependency scope and explicit write commits so a failed final commit cannot follow a success response.

Rollback cannot undo a commit

If something fails after the handler's commit, for example in refresh() or serialization, the client sees an error but the write is saved. That is why retries need an idempotency key (Part 8).

What the 8-second limit does not cover

Transactions, flush and commit, and READ COMMITTED

A transaction groups statements so they all apply or none do. Item write handlers stage the change, an activity row and an audit row, then call await db.commit() once; some other writes record only an activity row, or neither. log_audit in app/services/audit.py only calls db.add(), so the audit row rides the same transaction.

flush() sends pending SQL inside the open transaction; commit() makes it durable. get_db rolls back on any exception, including an HTTPException raised by the handler.

PostgreSQL's default isolation level is READ COMMITTED: each statement sees data committed before it started. When an UPDATE waits for another transaction's row lock, it re-checks its WHERE clause against the committed row. That makes UPDATE … WHERE version = :v a safe compare-and-swap without SELECT … FOR UPDATE.

Loading relationships: selectin, noload and MissingGreenlet

Lazy loading fetches a relationship on first access. In async SQLAlchemy that implicit I/O raises MissingGreenlet. So the models declare lazy="selectin", which loads children with batched WHERE … IN (…) queries, up to 500 parent keys per batch in SQLAlchemy 2.0. Large result sets or nested relationships can need several queries.

Eager loading is wasteful when you do not need the children. User has five selectin collections: categories, items, orders, activity logs and refresh tokens. So get_current_user and the auth routes add noload("*"), and authenticating a request stays one scalar SELECT.

# app/api/deps.py, get_current_user (excerpt)
# noload("*") stops the User's eager selectin relationships from firing on

result = await db.execute(
    select(User).where(User.id == payload.sub).options(noload("*"))
)

  • A test, test_auth_responses_do_not_load_account_history, checks that register, login, refresh and profile updates load no collections.
  • Order.items is selectin, so an order's lines serialize after commit without a lazy load.
  • The current SQLAlchemy 2.0 documentation marks noload as legacy and suggests raiseload or lazy="raise". The use here is deliberate. A refactor to raiseload needs tests first: account deletion relies on noload's empty collections and the database cascade.

Why merging needs a release gate

  • A merge can trigger production deployment. render.yaml names main, and every container migrates before it serves. Merging the feature branch would run 0007–0010 in one start. A push to main calls the CI deploy hook if its secret is set, and Render may also auto-deploy; both are dashboard settings Not verified.
  • Old and new instances overlap. During a zero-downtime deploy, main's code still numbers orders by counting rows while the new code uses the counter. They can collide, so the cut-over needs old writers stopped.
  • Rollback is a data decision. The entrypoint only runs upgrade head. Redeploying an older image leaves the newer schema in place, and an image from before 0007 cannot even start: its Alembic does not know the database's revision, so the entrypoint exits.

# app/api/v1/auth.py, refresh_token (excerpt)
claim_result = await db.execute(
    update(RefreshToken)
    .where(
        RefreshToken.jti == jti,
        RefreshToken.user_id == user_id,
        RefreshToken.is_revoked.is_(False),
        RefreshToken.expires_at > datetime.now(timezone.utc),
    )
    .values(is_revoked=True)
    .returning(RefreshToken.id)
)
if claim_result.scalar_one_or_none() is None:
    raise HTTPException(status_code=401, detail="Invalid or expired refresh token")
  • Race-safe. Two simultaneous refreshes with one token give one 200 and one 401 (reproduced 7 and 8 Oct 2026).
  • Lock order. Login, refresh and password changes all lock the user row first, so a refresh cannot slip a new token past a password change.
  • No reuse detection. A replayed old token gets 401, but the newer token stays valid. RFC 9700, an OAuth best-practice document that applies here by analogy, describes revoking the active token when a rotated one is replayed.
  • Logout. It needs a valid access token plus the refresh token in the body, and revokes that refresh row only. The access token keeps working until it expires, up to 30 minutes (finding A-14, reproduced).
  • Password change or reset. session_version + 1, every refresh row revoked, pending reset and deletion tokens cleared. Every older token fails on its next use, on every device.

Part 8 · Correctness

Correctness patterns for concurrent writes

In short: Put every “check, then write” into one SQL statement or one lock. Versions stop lost updates, and a client key makes order creation retry-safe. An upsert counter numbers orders, a status claim applies stock once, and a consistent item lock order removes the opposing-order deadlock pattern between order applies; it is not a proof against every deadlock.

Optimistic concurrency with version

# app/api/v1/items.py, update_stock (excerpt)
cas_result = await db.execute(
    update(Item)
    .where(
        Item.id == item_id,
        Item.user_id == current_user.id,
        Item.version == data.version,        # the guard lives in SQL
    )
    .values(quantity=data.quantity, version=Item.version + 1)
    .returning(Item.version)
)
if cas_result.scalar_one_or_none() is None:
    return JSONResponse(status_code=409, content={
        "error": "Version conflict",
        "message": "This item was modified by someone else. Please refresh and try again.",
        "server_version": item.version,      # values read at the start
        "server_quantity": item.quantity,
    })
  • The read is not the guard. The handler reads the item only for the 404, the history rows and the conflict body. PostgreSQL evaluates the version check and writes in one atomic statement.
  • Two lock paths. Edit Item's PUT always sends the name, so it first takes the account's name lock; a second save with the same version waits there, then fails the version check. That lock queues every named item edit of one account. The stock PATCH takes no name lock; it waits on the row lock and re-checks its WHERE.
  • The loser must refetch. The 409 carries the values read at the start of the losing request, which can already be stale. The handler never refreshes a possibly deleted row, which would turn a clean 409 into a 500.
  • Ordinary deletes carry no version. A delete wins over a concurrent edit. Resets opt into ?version=N, checked under a row lock, to preserve records changed after their backup.
A-1 fixed locally — the client/server protocol matters

The audit found that the editor paired old fields with a newer cache version. The fix captures fields and version together; a background refresh cannot change the version sent by an open form. Stale saves receive 409, relevant active queries refetch and the person reopens the editor. A rendered component test covers this. Real-device acceptance is still required.

Order numbers from an atomic daily counter

# app/api/v1/orders.py
async def allocate_order_id(db: DB, now: datetime) -> str:
    day = now.strftime("%Y%m%d")
    result = await db.execute(
        insert(OrderNumberCounter).values(day=day, last_value=1)
        .on_conflict_do_update(
            index_elements=[OrderNumberCounter.day],
            set_={"last_value": OrderNumberCounter.last_value + 1},
        ).returning(OrderNumberCounter.last_value)
    )
    return f"ORD-{day}-{result.scalar_one():04d}"
  • Atomic. PostgreSQL guarantees an atomic insert-or-update, even under concurrency. The day is the UTC date.
  • Transactional. The upsert runs inside the order's own transaction, so a rolled-back create does not use up a number.
  • Never reused. The counter has no user link and survives order and account deletion. main still numbers orders by counting rows, which is why the 0007 cut-over needs old writers stopped.
  • The cost. The day's counter row stays locked from allocation until that order's transaction ends, so creates on the same UTC day queue there, across all users.

Applying an order: claim first, then increment

  1. Load the order. It must be yours, in received, with at least one line (else 404 or 400).
  2. Check every item still exists. If one is missing, return 409 and change nothing.
  3. Claim. UPDATE orders SET status = 'STOCK_UPDATED', applied_at = now WHERE status = 'RECEIVED'. A second apply matches no row and gets 400.
  4. Increment in item-id order. quantity = quantity + n and version = version + 1 per line, with one audit row each.
  5. Commit once. Write the ORDER_APPLIED activity and commit. Any failure before the commit rolls back steps 3 to 5.
  • The status is the dedupe key. Claiming first means the loser writes nothing and takes no item locks.
  • The database does the arithmetic. quantity + n is never a read-modify-write in Python. Bumping version makes any phone holding the old version get 409 on its next edit.
  • Consistent item lock order reduces deadlocks between applies. Two applies that share items lock rows in the same order and queue. An ungated test fires two such applies together.
  • Precise wording. Stock is credited at most once per order. A retry after a lost 200 gets 400, so the client must re-read the order.
  • Status rules. A same-status request is a 200 no-op, an illegal transition gets 400, and a concurrent change gets 409. The app offers only pending → received and received → apply.

Part 11 · Design case study

The AI feature as a backend design case study

In short: POST /api/v1/ai/interpret turns one unfamiliar question into a validated inventory-query or local-draft specification (legacy v1 reads remain supported). The model receives the question text and a previous-item flag, but no inventory dataset, database access or mutation tools. The question itself may contain an item name or other user-entered information. Consent has scopes, quotas are counted in PostgreSQL, no database connection is held during the call, and the answer must pass a strict schema and server-side checks.

The problem

Feature branch only Off by default Real Groq calls not verified

The phone understands familiar questions on its own, such as “How many nitrile gloves are left?”. For wording the local matcher cannot handle, the server can ask Groq to classify the question, but only after Send, with groq_text consent, the phone's cloud switch on and the server's AI settings enabled.

The model must never answer with stock facts or cause a write. The phone builds every answer from inventory it reads itself.

The app sends {question,has_previous_item,contract_version:2} to CareKosh when v2 is supported; older clients use v1. The backend sends question/context flag plus its system instructions and strict schema to Groq, without inventory or recordings in the interpretation call. The latest local build also offers Groq Whisper listening through /ai/transcribe, requiring separate groq_audio consent and fresh local audio opt-in. It does not interpret before transcript review and Send. Hosted speech /ai/speak remains unreachable from this build.

Python

What does await actually do, and how does one worker serve many requests?

await suspends the coroutine when the awaited operation is not ready, for example a database reply. Control returns to the event loop, which runs other ready requests.

Each Uvicorn worker has one loop, every CareKosh handler is async def, and asyncpg queries are awaited. It is concurrency on one thread; database-bound work per worker is still capped by the 15-connection pool.

Why hash passwords in a thread but query the database on the event loop?

The query is I/O-bound: asyncpg sends it and yields while PostgreSQL works. Argon2 is CPU-bound with no await inside, so it would freeze the loop.

CareKosh wraps every hash and verify in anyio.to_thread.run_sync (app/api/v1/auth.py). The thread does not make hashing faster; it keeps other requests moving. The rule: await I/O, offload CPU work.

Process, thread or coroutine: which does CareKosh use, and for what?

All three. Gunicorn runs two worker processes, which can execute Python in parallel. Inside each, coroutines handle requests on one event loop, and AnyIO worker threads run Argon2 (default limit 40 per loop).

The GIL lets one thread run Python bytecode at a time. That is why CPU-heavy Python work needs processes.

What is Annotated doing in deps.py?

It attaches metadata to a type without changing it. DB = Annotated[AsyncSession, Depends(get_db)] tells FastAPI to call get_db and tells the editor the value is an AsyncSession.

Handlers then read db: DB, current_user: CurrentUser. Only those two aliases are used by routes; ActiveUser, VerifiedUser, SuperUser, OptionalUser and Pagination exist but are unused.

How does a generator dependency like get_db work?

The code before yield is setup, and the yielded session is injected into the handler. The code after yield is teardown: commit, roll back on any exception, then close (app/core/database.py).

It is the request-scoped form of an async context manager. The same shape appears in the app's lifespan and in get_db_context.

Why does the API say stock_updated while the database stores STOCK_UPDATED?

OrderStatus is a str, Enum, so JSON uses the value. SQLAlchemy's Enum(..., native_enum=False) stores the member name in a VARCHAR column.

There is no CHECK constraint, so only Python enforces the set, and raw SQL must use the upper-case names (seen in the 7 and 8 Oct 2026 walkthroughs). The upside: adding a status needs no ALTER TYPE.

How do you tell “omitted” from “sent as null” in a Pydantic v2 update?

model_fields_set holds only the fields the client sent, even as null. PUT /items/{id} writes an optional field when its name is in that set.

So {"brand": null, "version": 1} clears the brand while {"version": 1} keeps it. Required fields ignore null. Categories and the profile treat null as “not sent” (A-15).

FastAPI

What is ASGI, and why does FastAPI need it?

ASGI is the async server interface: async def app(scope, receive, send). WSGI makes one blocking call per request. ASGI lets a handler await I/O and supports lifespan events and WebSockets.

FastAPI subclasses Starlette, an ASGI framework, and Uvicorn calls app.main:app. Without ASGI, CareKosh's awaited queries would not free the worker.

In what order do CareKosh's middlewares run?

Starlette's add_middleware inserts at the front, so the last one added runs first. Inbound: ServerErrorMiddleware, AIBodyLimit, security headers, request id, CORS, ExceptionMiddleware, then the route.

AIBodyLimit is added last, after the routers, so it is the outermost user middleware. Responses travel back out in reverse.

Why is AIBodyLimit pure ASGI instead of @app.middleware("http")?

It must read and cap the raw body stream and give the app a replacement receive before anything parses the request. It also answers 401, 408 and 413 itself without calling the app.

Function middleware wraps finished Request and Response objects. The trade-off: its own responses skip the security-header and request-id middleware.

How does dependency injection work, and when is a dependency cached?

FastAPI builds a dependency graph from the signatures and calls each dependency once per request by default. get_current_user depends on get_db, and the handler also asks for DB; both get the same AsyncSession.

So the auth lookup and the handler share one transaction until the handler commits. Depends(f, use_cache=False) opts out, and tests replace get_db through app.dependency_overrides.

When does get_db commit relative to the response?

In the pinned FastAPI 0.115.6, the code after yield runs after the response is built and before it is sent. A failed final commit still becomes an error. FastAPI 0.118.0 moved it after sending.

CareKosh's write handlers commit explicitly anyway, so the get_db commit usually ends only a read transaction. Before upgrading, confirm every write handler commits itself (A-23).

What does a validation error look like, and why customize it?

FastAPI raises RequestValidationError before the handler runs. CareKosh's handler in app/main.py returns 422 {error, message, details: [{field, message, code}], timestamp}.

A client can map each message to its field; the app currently joins them into one message. Other errors use {detail} and the item conflict has its own body, so the shapes are not uniform yet.

Why separate request and response models, and what is from_attributes?

The request model is a gate: it validates, sanitizes and requires fields like version. The response model is a filter: only declared fields leave the server, with camelCase aliases, because response_model_by_alias is on by default.

from_attributes=True lets ItemResponse.model_validate(item) read an ORM object attribute by attribute.

How are unexpected errors handled, and what is the catch?

Three handlers in app/main.py: validation becomes 422, IntegrityError becomes 409 “A conflict occurred”, and any other exception becomes 500 “An unexpected error occurred”. Logs keep only the exception type and code locations.

The catch: the 500 handler runs in Starlette's outermost ServerErrorMiddleware, so those responses lack X-Request-ID and the security headers (A-13, reproduced).

When are BackgroundTasks the right tool, and when not?

CareKosh queues verification, reset and deletion emails with background_tasks.add_task(...). They run after the response, in the same process. That suits best-effort email: a failed send is logged and the person can resend.

There is no retry, and a crash loses the task. For guaranteed delivery, use a durable queue or an outbox table.

Data layer

Engine, sessionmaker and session: what is the difference?

The engine is built once per worker process and owns the connection pool. AsyncSessionLocal is a factory that makes sessions. An AsyncSession is one request's unit of work, opened by get_db and closed at the end.

One AsyncSession must never be shared across concurrent tasks such as asyncio.gather.

How many database connections can one instance open?

Each worker's pool allows 5 connections plus 10 overflow, so 15. Two workers make 30 per instance; Alembic at start-up and an overlapping deploy add more.

The 16th waiter in a worker waits up to 30 seconds (pool_timeout) and then fails with a 500. pool_pre_ping replaces connections that died while idle.

What does statement_timeout protect against, and what does it miss?

Application-engine connections set statement_timeout=8000, so PostgreSQL aborts any statement that runs over 8 seconds, lock waits included. One hung query cannot pin connections until the pool is exhausted.

It does not bound idle time inside a transaction, the wait for a pool connection, connection set-up or a dead network path.

What is MissingGreenlet, and how does CareKosh avoid it?

Async SQLAlchemy raises it when code triggers implicit I/O, such as a lazy relationship load or reloading an expired attribute.

expire_on_commit=False keeps loaded values readable after commits, and relationships use lazy="selectin" so they load up front. Touching an unloaded relationship would still raise; the fix is explicit eager loading.

What is the N+1 problem, and why does the auth path use noload("*")?

N+1 is one query for the parents plus one per parent for its children. selectin batches child reads into IN (...) queries, rather than one query per parent. It can emit several batches or queries for nested relationships.

User has five selectin collections, so a plain select(User) would load the account's whole history on every request. get_current_user adds noload("*"), and a test checks that auth responses load no collections. The current SQLAlchemy 2.0 documentation marks noload as legacy. raiseload is an alternative to evaluate in a tested change, since accidental relationship access would then raise.

Why does order_items.item_id have no foreign key?

An order line is a snapshot: name, brand, unit and stock as the app sent them. With a cascading foreign key, deleting an item would erase order history.

The trade-off is no referential integrity on that column. Apply therefore checks that every line's item still exists, and returns 409 if one is missing.

Which rules live in the database and which only in the API?

Database: quantity >= 0 on items, quantity > 0 on order lines and email or username on users. Also unique email, username, order number and refresh jti, the partial localId index and cascading foreign keys.

API only: case-insensitive unique names (under an advisory lock, because old data has duplicates), status transitions and password rules. Constraints protect against every writer; API rules give friendlier errors.

What are the limits of the pagination here?

GET /items and GET /orders use offset pagination (page, pageSize up to 100) with a stable order and a total computed with the same filters.

Offset pages can shift under concurrent writes, and deep offsets get slower. The phone fetches every page of 100 and rejects duplicates or a changed total, but a delete plus a create between pages can still hide an item. Keyset pagination would fix both if lists grew large.

Authentication and security

Walk me through what happens on every authenticated request.

get_current_user reads the bearer token, decodes the JWT with a pinned HS256 list and requires type=access. It loads the user with noload("*") and compares session_version with the token.

Missing or stale means 401, a disabled account 403, and an unverified email while enforced 403 EMAIL_NOT_VERIFIED (app/api/deps.py). One small SELECT per request buys immediate revocation.

JWTs are stateless. How do you revoke them here?

A password change or reset increments users.session_version and revokes every refresh row, so every older token fails on its next use.

Plain logout revokes only the presented refresh token; the access token works until it expires, up to 30 minutes (A-14). There is no access-token deny-list.

Explain refresh-token rotation and why it is race-safe.

Refresh locks the user row and checks session_version. Then one conditional UPDATE claims the token: it sets is_revoked = true only if the row is not revoked and not expired, with RETURNING id.

Only one request can flip the flag, so two simultaneous refreshes give one 200 and one 401 (reproduced). The limit: a replayed old token gets 401 but does not revoke the newer token.

Why Argon2, and what does deprecated="auto" do here?

Argon2id is slow and memory-hard, which makes offline guessing expensive; OWASP lists it first. CareKosh uses argon2-cffi's defaults: 64 MiB, 3 passes, 4 lanes.

deprecated="auto" marks bcrypt as deprecated. Login calls verify(), not verify_and_update(), so old bcrypt hashes are never upgraded.

Why are email-link tokens stored as SHA-256 digests rather than Argon2 hashes?

The raw token is secrets.token_urlsafe(32), 256 random bits, so guessing is infeasible even with a fast hash. A deterministic digest can also be looked up by index.

Only the digest is stored. Links expire (reset after 1 hour, verification and deletion after 24 hours) and each works once. Passwords are low-entropy, so they need the slow hash.

How is authorization done, and why 404 instead of 403?

Protected item, category and order queries include owner checks, including their UPDATE statements. Auth lookups, global counters and global quota checks are exceptions to that wording. Another user's id finds no row, so the API returns 404 and never confirms that the row exists.

There are no roles in use. The risk is one forgotten filter; cross-account tests cover items, categories and orders.

Does CORS protect this API?

No. CORS is a browser rule about which web pages may read responses. Native apps and curl ignore it, and it authenticates nobody.

CareKosh allows all origins with credentials disabled (render.yaml sets ["*"]). The protection comes from bearer tokens plus owner filters.

How do you keep secrets and personal data out of logs?

SECRET_KEY, MAIL_PASSWORD and the provider keys are SecretStr, so they print as asterisks. SECRET_KEY must be at least 32 characters, and the placeholder is rejected outside development and testing.

The log factory redacts link tokens and token or password query values and logs exceptions without values. SQL parameters are hidden and Sentry is scrubbed. DATABASE_URL is a plain string, so never log the settings object.

Concurrency

Two phones save the same item at the same moment. What happens?

Both send version: 3. Edit Item's PUT includes the name, so each save first takes the account's name lock. The second waits there until the first commits version 4; its UPDATE … WHERE version = 3 then matches no row and it gets 409 with server_version and server_quantity.

A request without a name, such as the API-only stock PATCH, instead waits on the row lock and re-checks its WHERE clause under READ COMMITTED. That path was reproduced: one 200, one 409. The app now refetches relevant active queries after 409 and retains the form's original version. Reopen the form for fresh values (A-1 fixed locally).

Optimistic or pessimistic locking: where does CareKosh use each?

Optimistic: item edits and stock changes (version), and order transitions (WHERE status = :old). Pessimistic: SELECT … FOR UPDATE on the user row in login, refresh and password flows, plus advisory locks for name checks, migrations and AI quotas.

Optimistic suits rare conflicts on rows people edit. Locks suit short critical sections.

How do you make order creation safe to retry?

The app sends one localId per Save press. The server first looks for that user's order with the key and returns it with 200. If two requests race past the lookup, the partial unique index rejects the second INSERT, and the handler rolls back and returns the winner.

Limits: no request fingerprint, and requests without a key are never deduplicated.

How do you guarantee a received order adds stock only once?

Claim first: UPDATE orders SET status = 'STOCK_UPDATED' WHERE status = 'RECEIVED' RETURNING id. Only one request matches, and the second gets 400. Then each line runs quantity = quantity + n in item-id order, all in one transaction.

Strictly, it is at-most-once credit. A retry after a lost 200 gets 400, so the client must re-read the order.

How do you number orders without races?

INSERT INTO order_number_counters … ON CONFLICT (day) DO UPDATE SET last_value = last_value + 1 RETURNING last_value, inside the order's transaction. PostgreSQL guarantees an atomic insert-or-update, a rollback releases the number, and the counter survives deletions.

The cost: one hot row per day serializes order creation for all users.

Can you run queries in parallel with asyncio.gather on one session?

No. An AsyncSession is a stateful unit of work that can span successive transactions and is not safe for concurrent tasks. Give each task its own session from the factory.

CareKosh avoids the problem: one session per request, with queries awaited one after another.

Testing

How do the tests use a real database without risking real data?

The suite runs against a disposable PostgreSQL 16. tests/conftest.py refuses to start unless the database name contains test or pytest and the URL does not look like staging, production or a hosted provider.

The fixtures drop every table before and after each test, so only point the suite at a database you can lose.

Why run tests with --migrated-schema?

It builds each test schema with alembic upgrade head, so tests see the same constraints, indexes and defaults as production. create_all from the models can drift from the migrations.

For example, the legacy verification_token column exists only in migrated databases. CI on this branch always uses the flag.

How do you test race conditions, and how much do the tests prove?

Requests run together with asyncio.gather; each has its own connection, so locks and unique indexes are real. Gated tests force the overlap, and one checks pg_stat_activity for a real lock wait.

About ten tests are ungated, so a pass there does not prove the race actually happened.

What do your tests not cover?
  • rate limiting, which is disabled in tests;
  • security headers and X-Request-ID;
  • the forgot-password and resend-verification routes;
  • migration downgrades and lifespan events;
  • real Groq or Brevo calls, several workers and the production session settings.

The full account-deletion cascade was shown only by the API walkthrough (7 and 8 Oct 2026).

Is 88 % coverage good, and what does CI enforce?

Coverage is a regression signal. A CI run fails on Ruff, the test suite or the 44-route gate. It also needs 70 % coverage for items.py and orders.py, which had 96 % and 91 % on 7 and 8 Oct. mypy (23 errors on 7 Oct) and Trivy are advisory.

Deployment and operations

Liveness or readiness: which endpoint does Render poll, and why?

/live never touches the database. /health runs SELECT 1 with a 2-second timeout and returns 503 when it fails.

render.yaml and the Docker HEALTHCHECK point at /live, so a database blip does not restart instances. The price: Render does not take an instance out of rotation while the database is down.

What happens when the container starts?

docker-entrypoint.sh waits for PostgreSQL with pg_isready (up to 30 tries, 2 seconds apart). It runs alembic upgrade head and exits with 1 if that fails, then execs Gunicorn with two Uvicorn workers on $PORT.

Migrations run in one transaction with a 30-second lock timeout and an advisory lock, so two starting containers take turns; a wait longer than 30 seconds fails that start.

Does rolling back the code roll back the database?

No. The entrypoint only upgrades, and 0007's downgrade raises on purpose. An image from before 0007 cannot even start against the newer database: its Alembic does not know the revision, so the entrypoint exits.

A schema problem is fixed forward or by restoring a backup, which loses later writes. That is why 0007–0010 need a release gate.

How do you know which commit is deployed?

Not from /health: both probes report the APP_VERSION setting (default 1.0.0), not the commit. Read the commit in Render's deploy record and run alembic current against the confirmed database.

As of 7 Oct 2026, the owner reported staging running b1c8dd7, and production's commit is not verified.

What does merging to main do?

It can trigger production backend deployment when the hook or Render auto-deploy is configured. render.yaml names main, CI calls the deploy hook if one is configured, and Render auto-deploy may also fire (a dashboard setting, not verified). The new container migrates before it serves.

It does not update phones. Over-the-air updates are off, so app changes need a new build that people install.

System design and scaling

What capacity does CareKosh support?

Unknown, and you should say so. The planning target is up to 10,000 accounts and perhaps 100–1,000 active users, and nothing in the repository load-tests it.

Accounts are not concurrent users, and users are not concurrent requests. Measure request rates, latency and pool waits before claiming a number.

Where does shared state live, and what is still per process?

Sessions (refresh rows and session_version), order counters, advisory locks and AI quotas live in PostgreSQL, so any worker can serve any request.

Rate-limit counters and BackgroundTasks are per process. Adding instances is safe for data, but each adds 30 connections and its own limiter counts.

How would you scale it if traffic grew a lot?

Measure first, then pick the smallest fix for the bottleneck you found:

  • slow queries: indexes and better query shape;
  • CPU: a bigger host or more instances, watching the connection budget;
  • global abuse limits: shared limiter storage;
  • email that must not be lost: a durable job queue;
  • proven read pressure: read replicas or caching.

Known hot spots: the daily counter row, user-row locks, and /items/stats, which loads every active item into memory.

How would you add shared households with roles?

Add a household id to owned tables, plus membership and roles, and a require_permission(...) dependency on the existing chain. Apply the tenant filter centrally rather than in each handler, with PostgreSQL row-level security as a backstop.

Record grants in audit_log. Today, sharing means sharing one account.
