Releasing the current branch (migrations 0007–0010)

  1. Make sure every intended source, test and migration file is committed on the feature branch (it is, as of 03cfebb); open a PR to main. A push cannot include uncommitted changes.
  2. Run CI and read every job, including the advisory ones. Stage the candidate separately before merging, on an isolated fresh database (preserve existing staging data), and verify the 0006 → 0010 upgrade on a populated synthetic legacy database. vitaltrack-backend/render.yaml declares production on main, and staging is configured in the dashboard. Control both deploy triggers (the CI hook secret; Render auto-deploy, not verified) before merging. A preview APK does not deploy its backend.
  3. Build and install a preview APK from the same candidate. Test login/verification/recovery, profile, stock edits and version conflicts, order create (including a retry) / status / apply / delete, older history, PDFs, shared-device logout, and the assistant (typed questions; microphone on a real phone).
  4. Confirm the production database, its current revision (alembic current, expected 0006_order_item_qty_positive) and a restorable backup/recovery point. Rehearse the restore on a separate target.
  5. Arrange a brief write pause and drain old workers during the cutover. Old COUNT-based order numbering and the new counter must not write concurrently, and 0010 briefly holds a SHARE lock on the orders table. The migration-runner lock does not stop old application writers.
  6. Merge and deploy the reviewed revision. Check Render's actual commit, alembic current = 0010_order_local_id_unique, /live and /health before resuming writes. A successful hook response is not deployment confirmation.
  7. Expect these behaviour changes for existing users: unverified email accounts get 403 EMAIL_NOT_VERIFIED on login, refresh and protected bearer-authenticated requests when verification and email sending are both configured; order creation from new app builds becomes retry-safe, while older installed builds keep creating a new order per request. AI routes stay disabled unless the production service sets the AI_* variables.
  8. Build a fresh production AAB for mobile changes, upload it to internal testing (internal testers use production data), then install and test that exact version before promoting it.

The full gate with the re-seed SQL is in BACKEND_HARDENING.md; the same steps updated for 0007–0010 are in the Complete developer guide (F5).

Rollback is a data decision

Rolling back an application image does not roll back its database. Revision 0007 refuses automatic downgrade because removing session generations and counter history could re-enable old credentials or reuse order numbers; 0008–0010 have downgrades, but the chain cannot go below 0007 automatically, and downgrades are untested. An image older than the schema cannot start: its alembic upgrade head cannot find revision 0010, the container exits, and Render keeps the current version. Old code meets the new schema only while old instances still run during a deploy, and it ignores those protections. Prefer a reviewed forward fix; keep affected writes paused while diagnosing. A backup restore discards writes made after the recovery point.

A bad mobile release needs a higher-version corrected build. Halting a rollout does not uninstall versions already installed, and over-the-air updates are disabled.

Proportional capacity planning

The target is up to 10,000 accounts with perhaps 100–1,000 simultaneously active users. This is a planning assumption, not a measured concurrent-request capacity. Measure representative traffic, latency, database pool usage and lock waits before adding infrastructure. Two workers with default pool 5 + overflow 10 allow up to 30 application connections per instance; deployments, overlapping old/new instances during a deploy and multiple services increase aggregate usage. The provider's connection limit is not verified here. Rate limiting is best effort: five auth routes, counters in memory per worker process, reset on restart; an open finding about how clients are identified is tracked privately.
