How to read this page. Each section starts with a one-line summary, then a diagram, then the details that matter. The colours mean the same thing in every diagram:

  • Green — core. FastAPI, PostgreSQL and the Android app. The product cannot work without them.
  • Blue — current provider (swappable). Render, Neon, Brevo and Expo EAS host or deliver the core, and could be replaced.
  • Grey — supporting infrastructure. DNS, TLS and similar plumbing.
  • Dashed amber — conditional. Sentry, email and the assistant's optional Groq interpretation are active only when they are configured.

Request topology

In short: the app sends HTTPS requests to one API host; the FastAPI backend on Render reads and writes PostgreSQL on Neon.

  • The app sends a Bearer access token with every signed-in request. The API address is fixed when the app is built.
  • Cloudflare serves the DNS for the public hostname. Whether Cloudflare also proxies the traffic must be checked in its dashboard.
  • The backend runs two Gunicorn/Uvicorn workers and serves 44 API route objects under /api/v1 on this branch (39 on main, which has no assistant routes), plus /, /health and /live. Queries for protected business data are limited to the signed-in owner; sign-in lookups and the global order counter use other keys.
  • Database access uses SQLAlchemy async with asyncpg. Each worker has a pool of 5 connections plus up to 10 overflow — up to 15 per worker, 30 for two workers. Every application SQL statement has an 8-second limit; the migration engine sets none.
  • Brevo sends email through its HTTP API (not the legacy SMTP settings), and only when MAIL_PASSWORD is set.
  • Sentry is optional. It receives scrubbed diagnostic events only when SENTRY_DSN is set.
  • EAS Build and Google Play deliver the app. They are not hops in an API request.
  • vitaltrack-backend/render.yaml asks for the Starter plan. Whether Render reads that file, and the live configuration, are not verified.
  • Assistant providers (not drawn here): speech recognition runs on the phone with a Moonshine speech pack downloaded once from Moonshine's servers. Optional text interpretation goes phone → CareKosh API → Groq, only when the phone's local matcher cannot handle the question and the server's AI_* settings, the person's consent and the phone's cloud switch allow it; render.yaml sets none of those settings. Separately selected Groq online listening sends the finished recording through /ai/transcribe after audio consent and Stop. The generated system context diagram shows the local and conditional cloud components.

A write request

In short: a request passes inward through the middlewares and the dependencies, the handler commits its writes, and the response passes back out through the same layers.

  • Middleware order on the way in: security headers → request ID → CORS. Starlette's error middleware wraps all three.
  • Added on this branch, not drawn in Figure 2: an outer AIBodyLimit layer sits just inside the error middleware. It reads the whole request body first and rejects oversized bodies (2 MB for ordinary routes, 12 KB for assistant JSON, 900 KB for the switched-off audio upload), answers assistant requests without a Bearer token with 401 before reading the body, and gives uploads a 10-second deadline. Its own error responses skip the security-header and request-ID layers. The generated request lifecycle diagram includes it.
  • Dependencies: FastAPI parses the JSON body first (malformed JSON gets 422 here), then opens a database session and loads the signed-in user, and only then validates the fields. A 422 for a bad field can therefore follow the user SELECT.
  • Rate limits wrap the handler call on the five limited routes. The limiter is not a guaranteed first line of defence that runs before the dependencies.
  • The handler checks ownership and workflow rules, runs conditional writes, adds activity and audit rows where implemented, and commits.
  • The response is serialised and returned. A failure after the commit cannot undo the committed write.
  • X-Request-ID is only a response header. It is not added to log lines or external traces.
  • Security headers: nosniff, DENY (frame blocking), Referrer-Policy, Cache-Control, X-XSS-Protection and, in production, HSTS. Permissions-Policy is not configured. X-XSS-Protection is set to the legacy 1; mode=block; current OWASP guidance is to send 0 or omit it.
  • Crashes: an unhandled exception becomes a 500 from outside these middlewares, so it carries none of these headers and no X-Request-ID.
  • CORS is a browser rule. It is not access control for a native app.

Session and recovery state

In short: every signed-in request re-checks the user row; a refresh token can be claimed once; a password change or reset bumps session_version, so every older token stops working.

  • Tokens issued before the generation claim existed count as generation zero, so deploying this change does not log everyone out.
  • After a password change or reset, old tokens fail the next time they are checked.
  • Ordinary logout revokes only the refresh token it is given. A copied access token stays valid until it expires.
  • Email verification applies to login, protected bearer requests and refresh for accounts with an email — only when the flag and the mail configuration enable it. Registration still returns tokens.
  • Rate limits cover five auth routes only. The counters live in memory in each worker process and reset when it restarts, and an open finding about how clients are identified is tracked privately. Treat them as best effort; do not describe them as globally enforced limits.
  • Password hashing uses Argon2. Legacy bcrypt hashes still verify but are not upgraded. Hashing runs in an AnyIO worker thread; benchmark the real runtime instead of assuming a fixed latency.

Account deletion

In short: deletion takes two steps. The app asks, an email link is sent, and only the button on the confirmation page deletes anything.

  • The request stores only a digest of the challenge token and queues a confirmation email.
  • Opening the link shows a page. Mail scanners that open the link therefore delete nothing.
  • The confirmation checks the challenge with the account row locked, then deletes the user-owned rows. Cancellation clears the challenge under the same lock.
  • All these paths use the /api/v1 prefix.
  • Deletion is permanent in the active database. Exported files, local caches, logs and provider backups are handled separately.
  • The daily order-number counter is not owned by a user, so it survives deletion.

Eleven application tables at migration 0010

In short: users owns the other tables, directly or (for order lines) through orders; items belong to categories; order lines copy item details; the assistant keeps only consent and usage metadata; the daily order counter stands alone.

Earlier diagram: nine tables at migration 0007 (drawn 23 September 2026)
  • All ten foreign keys use ON DELETE CASCADE. Migration 0008 added the two on ai_consents.user_id and ai_usage.user_id; at 0007 there were eight.
  • ai_consents holds one row per user (consent version, accepted flag, scopes such as groq_text, time). ai_usage holds one row per online assistant request that passes the consent and quota checks (kind, provider, status, reserved cost in micro-US-dollars, token and audio counts) for quotas and cost limits. Neither stores question text, audio or inventory.
  • orders has a partial unique index on (user_id, local_id) where local_id is set (0010), which makes order creation retry-safe (Figure 8).
  • order_items.item_id is a snapshot reference without an item foreign key. Line quantities must be positive, and each line keeps snapshot metadata.
  • categories also store a description. refresh_tokens keep optional device and request metadata. activity_logs is a human-readable history with a copied item name.
  • audit_log is a singular table name. Alembic's own version table is separate from these eleven.

Stock concurrency

In short: a save succeeds only if the item's version has not changed since the phone read it; otherwise the phone gets 409 and must refetch.

  • This is optimistic concurrency (compare-and-swap). Nothing is locked while the user edits. Each phone sends an absolute quantity with the version it expects.
  • The conditional UPDATE checks owner, item and version, and increments the version in the same statement.
  • The conflict snapshot sent with a 409 may itself lag behind a later write, so refetch before retrying. The updated item mutation shows the server message and invalidates affected active queries so they refetch. Reopen the editor with current values; generic Retry retains the original version.
  • Edit Item's PUT always sends the name, so the server first takes the account's name lock; a second save waits there and then fails the version check. The API-only stock PATCH instead waits on the row lock. The two-save race was reproduced through the stock PATCH (7 and 8 Oct 2026).
  • Applying an order claims the received order once and adds line quantities with database arithmetic, all in one transaction. A repeated apply is rejected; it does not replay the earlier successful result.
  • Version checks do not protect order creation. Earlier (September 2026): a retried order create after a lost response made a second order. Current: creation is retry-safe through localId (Figure 8).
  • A-1 fixed locally (8 October 2026): Edit Item captures the version with its form values; a background refetch cannot bypass server CAS. Conflicts refresh active queries; reopen the editor for current values. See API traceability and remaining issues.
  • Order numbers come from a daily counter that increments atomically.
  • Names: category and item creates, and updates that send a name, serialise their duplicate-name checks with per-owner, per-type transaction advisory locks. Direct SQL still needs a reviewed uniqueness policy.

Order state machine

In short: orders move forward only; stock_updated can be reached only through POST …/apply.

  • A request for the status the order already has is accepted without changing anything.
  • The generic status endpoint cannot set stock_updated.
  • Delete is limited to pending and declined, and the final SQL re-checks this.
  • The server code is the authority: LEGAL_STATUS_TRANSITIONS and the apply/delete handlers.

Order-create retries

In short: the app sends a fresh localId with each Save; repeating the same request returns the order already created instead of making a second one.

  • The app generates one localId per Save press and reuses it when the person taps Retry after a failure. Pressing Save again later is a new order by design.
  • The server first looks up (user_id, localId). If an order exists it returns it with 200 and writes nothing.
  • Two identical requests at the same moment collide on the partial unique index uq_orders_user_id_local_id. The loser's transaction rolls back, which also releases its order number, and it returns the winner's order with 200.
  • Requests without localId, such as those from app builds older than this branch, always create a new order.
  • The order number ORD-YYYYMMDD-NNNN comes from the daily counter row in the same transaction; numbers are never reused, even after an order or account is deleted.

Mobile data flow

In short: the app is server-first. It shows cached data quickly, fetches fresh data from the API, and has no offline write queue.

Earlier diagram (23 September 2026): reconnecting did not refetch then, and the API had 39 routes
  • Read: API → TanStack Query → screen. The last-known display cache persists in AsyncStorage.
  • Write: user action → API → invalidate and refetch. There is no offline sync queue: a save attempted offline fails.
  • Local state: Zustand holds UI and auth state; SecureStore holds the persisted auth data.
  • staleTime=30 s is a staleness threshold, not polling. Data refetches when a stale query remounts, when the app returns to the foreground, on pull-to-refresh and after invalidation.
  • Earlier (September 2026, and still on main): regaining connectivity alone did not refetch, because TanStack's online manager was not connected to NetInfo. Current branch: QueryProvider.tsx connects it (online = connected and the internet not known to be unreachable), so reconnecting refetches stale queries. Screens' own offline checks still look only at NetInfo's isConnected.
  • gcTime=24 h controls how long unused data stays in memory; the saved copy has its own 24-hour maxAge, counted from its last save. Neither limits how old a shown value can be.
  • The cache buster follows the visible app version. Over-the-air updates are disabled, so changing a source flag needs a rebuild.
  • The API client shares one refresh promise between concurrent requests, and follows bounded order-history pages.
  • npm test runs 121 Node test-runner tests in nine files (passed 7 Oct 2026 and again 8 Oct 2026): refresh, logout, order creation, the query provider, sanitising, the voice policy and assistant parsing. Native device testing is still required. Earlier (September 2026): eight API tests ran via npm run test:api, which now runs only the refresh tests.
  • Ordinary API requests now have one 90 s overall deadline including refresh/retry waits and response parsing. Token refresh retains 30 s and assistant calls retain 50 s; a timed-out write may still have committed.

Voice assistant: inventory answers and local drafts

In short: the phone turns speech into text and answers from inventory it reads; the server supplies inventory and optional separately consented text interpretation/audio transcription; voice never changes inventory or saved orders; it can prepare an unsaved draft, with a separate touch-confirmed save.

  • Recognition on the phone: The latest Kotlin module uses one Android AudioRecord to capture mono PCM16/16 kHz WAV (maximum 28 seconds) and feed genuine provisional Moonshine English live captions. Offline final transcription follows Stop; separately consented Groq Whisper can instead produce the final transcript. Older modules retain Expo AAC/M4A at 44.1 kHz/128 kb/s with words after Stop. It needs a native Android build that includes the module, such as the EAS preview APK (not Expo Go), and the English speech pack, downloaded once from Moonshine's servers and checked before use.
  • Review before sending: the transcript is editable and nothing leaves the phone until the person presses Send.
  • Understanding: local parsers recognize familiar inventory queries and unsaved draft commands. Inventory mutation, saved-order commitment, apply and supplier-send actions remain blocked. Only when it cannot match, the person has opted in (consent plus the phone's cloud switch) and the server's AI settings are on, the question text (no audio, no inventory) goes to POST /api/v1/ai/interpret, which asks Groq (openai/gpt-oss-20b, strict JSON schema, temperature 0, no tools) for one allowed intent. The server rejects any answer that names an item not present in the question, and the phone validates the intent again.
  • Answer: the phone reads inventory (its own cache if loaded in this login session less than 30 seconds ago, otherwise GET /api/v1/items), builds the answer itself and can read it aloud with an installed offline Android voice. Offline answers are labelled as last-known data.
  • No server mutation tool by construction: the dispatcher has no order-save or stock-update operation; local drafts are reviewed separately and saving requires touch confirmation. Its only server writes are ai_consents (consent) and ai_usage (one row per online interpretation, for quotas and cost limits). So "no inventory writes" is not "zero database writes".
  • Switched off in this build: hosted speech output (/ai/speak) remains blocked by CLOUD_VOICE_ENABLED=false. Optional online transcription is separately enabled in code by CLOUD_TRANSCRIPTION_ENABLED=true, and requires explicit audio opt-in, groq_audio consent and server flags before a finished recording is uploaded.
