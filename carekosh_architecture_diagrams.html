Chapter 01

System topology

Four hops, two of which appear in no other document — and one of them decides whether rate limiting works at all.

CareKosh is three tiers and three side dependencies. The tiers are obvious; the side dependencies are where the interesting failure modes live. Note especially Cloudflare: the backend reads CF-Connecting-IP first when identifying a client, so the correctness of every per-IP rate limit depends on a hop that the previous edition never drew.

The CORS honesty note

Production really does ship CORS_ORIGINS='["*"]'. The previous edition claimed a validator rejects the wildcard in production — no such validator exists. What does exist is a safety interlock in app/main.py: the wildcard branch forces allow_credentials=False, and the API is bearer-token only with no cookies, so there is no ambient-credential CSRF surface. That is the honest answer to “isn't a wildcard a red flag?”, and it is stronger than pretending a guardrail exists.

Chapter 02

The request lifecycle

Middleware is registered inside-out, so the order you read in the file is the reverse of the order a request meets.

Four middleware layers wrap every request, then a route-level rate limiter, then dependency injection, then the handler. Registration order in app/main.py is CORS first, then add_request_id, then add_security_headers — and because Starlette wraps each new middleware around the previous stack, the last one registered is the first one a request touches.

Chapter 03

Authentication

The single most defensible piece of engineering in this codebase is one UPDATE statement — and the previous edition deleted it.

Two token types, one atomic rotation guarantee, and one enforcement gate that lives at login rather than in a dependency. Everything below is read from app/api/v1/auth.py and app/core/security.py.

TokenAlgorithmLifetimeClaimsStored?
AccessHS25630 minutessub · exp · iat · typeNo — stateless, no jti, no denylist
RefreshHS25630 dayssub · exp · iat · type · jtiYes — one refresh_tokens row per jti

Password hashing — the real parameters

CryptContext(schemes=["argon2","bcrypt"], deprecated="auto"). The code sets no Argon2 options, so library defaults apply: Argon2id, m = 64 MiB, t = 3, p = 4, roughly 38 ms per hash. Because p=4, each login can occupy four threads and 64 MiB — a real capacity consideration on a two-worker instance. Note also that deprecated="auto" makes bcrypt hashes verifiable and flags them via needs_update(), but no rehash is implemented: verify_and_update appears nowhere in the codebase.

Chapter 04

Account deletion

It takes two HTTP verbs for one reason: email clients follow links before humans do.

Deletion is irreversible and cascades across every user-owned table, so it is gated behind an emailed token and split across two verbs. The GET renders a confirmation page and deletes nothing; only the POST destroys data.

Chapter 05

The data model

Eight tables, every column read from the model files — because the previous edition invented seven of them.

Every table except order_items hangs directly off users with ON DELETE CASCADE. Three columns carry the architecture: items.version (optimistic locking), refresh_tokens.is_revoked (rotation), and local_id (a client-supplied correlation id — forward-looking scaffolding, not a live sync feature).

Reading the diagram

? marks a nullable column. Unless noted, every table also carries id (uuid4 string), created_at and updated_at from the shared mixins. Arrows point from parent to child and every one is ON DELETE CASCADE.

Chapter 06

Concurrency

Two caregivers, one cupboard, one shared count — resolved in the database rather than in the client.

The original app was offline-first and merged conflicts on the device. That was deleted. Now the server is the only arbiter, and the mechanism is a single-statement compare-and-swap on items.version. A stale write does not silently win and does not silently lose — it returns 409 carrying the server's current truth so the client can show the user what actually happened.

Two related guards, same philosophy

PATCH /items/{id}/stock takes an absolute quantity plus a version, never a delta — so a replayed request cannot double-apply. And the order apply-to-stock path is a single atomic statement per item, with a database CHECK (quantity > 0) constraint on order_items added in migration 0006 as a defence-in-depth backstop.

Chapter 07

The order state machine

Six states with an explicit transition table, because “received twice” must not mean “stock added twice”.

An order moves through a restricted graph enforced server-side by LEGAL_STATUS_TRANSITIONS. The terminal states are stock_updated and declined; neither has an outgoing edge, which is what makes applying stock a one-way door.

Chapter 08

The mobile client

Server-first, not offline-first — and that distinction was a deliberate deletion, not an omission.

The app does not maintain an offline queue, does not persist domain data as its own source of truth, and does not reconcile conflicts on reconnect. services/sync.ts was removed and useAppStore shrank from about 1,100 lines to 61. TanStack Query owns all server state; Zustand holds only UI state.

One honest gap

There is no mobile test infrastructure. package.json declares "test": "jest" but jest is not a dependency and no test files exist, so npm test fails immediately. The backend has 132 tests behind CI gates; the client has none. Worth volunteering before anyone asks.

  • Seven invented column names across five tables — see the table in Chapter 05. Each returns zero grep hits.
  • “Seven tables” in prose while the diagram drew eight. Eight is correct.
  • Gunicorn described as -w 4; the Dockerfile uses --workers 2.
  • Health check shown as GET /health; render.yaml sets healthCheckPath: /live, deliberately.
  • Alembic head given as 0005; the real head is 0006_order_item_qty_positive.

  • The product called “offline-first” in seven places, after offline-first was deliberately removed.
  • No @media print rules at all — the dark background printed behind light text, and wide diagrams were clipped rather than scaled.

What the previous edition got right

Its prose was largely maintained and its account of the server-first philosophy, the audit-versus-activity distinction, and the cascade-on-deletion design were all sound. Diagram 5 even stated the GET/POST deletion split correctly, contradicting its own Diagram 2. The failure was concentrated in the hand-drawn SVGs, which had drifted away from the code while the text around them was kept current.
