Chapter 01

The trigger matrix

A feature-branch push runs nothing anywhere — the most common misconception about this pipeline.

CI fires on exactly three events: a pull request targeting main, a push to main, and a manual workflow_dispatch. Pushing to feature/* triggers nothing — no CI, no Render deploy, no EAS build. Until you merge, your code runs on your laptop and nowhere else.

TriggerCIBackend deployMobile buildWho sees it
Push to feature/*———Only you
Open or update a PR → mainYes——Reviewers
PR + label build-apkYes—Preview APKReviewers can sideload
Merge to mainYesProduction—Live backend
eas build --profile production——AABPlay Console upload
workflow_dispatchYes——Same as a PR

Two things the matrix does not show

The PR trigger includes the labeled event type, which is why adding build-apk to an existing PR starts a build rather than requiring a new push. And merging does not build anything for mobile — mobile releases are a separate manual step (Chapter 07).

Chapter 02

The CI job graph

Only two jobs can actually stop a merge; two more report problems they are not allowed to block on.

Nine jobs, but the dependency structure is simple: test-backend and test-frontend are the only blocking gates, and everything downstream waits on both. Two advisory jobs run in parallel and cannot fail the build.

One addition to the previous edition

build-preview is advisory (continue-on-error: true) — the previous edition never said so. That matters in practice: if your labelled APK build fails, the pull request still shows green. Open the job to confirm the artifact actually exists before telling a reviewer to sideload it.

Chapter 05

One image, two environments

The same Docker image runs in both places; every difference between them is an environment variable.

This is the orthodox twelve-factor split — one immutable artifact, per-environment configuration. Data never crosses: wiping the staging database touches zero production rows.

Chapter 06

Which backend does this build talk to?

Whichever URL was compiled in — and no server-side change can redirect an installed app.

EXPO_PUBLIC_API_URL is a build-time constant baked into the binary. Once an artifact exists, its backend is fixed forever.

Chapter 07

Shipping a mobile release

Still manual, deliberately — the job that would automate it exists and is switched off.

# from the mobile package root
cd vitaltrack-mobile
npx expo-doctor                                      # sanity check

# build — the production profile bakes in api.carekosh.com
eas build --profile production --platform android

# read the version code EAS assigned (never hand-edit app.json)
eas build:version:get --platform android

# upload — lands on the INTERNAL track, always
eas submit --profile production --platform android

Two constraints to internalise

eas submit can never reach production. The profile is named production but its submit track is internal. Promotion internal → closed → production is manual in the Play Console.

The version code lives on EAS servers, not in the repo. appVersionSource: remote with autoIncrement means app.json's versionCode is inert — editing it does nothing.

The disabled automation

build-production sits in the workflow with if: false, and the file records the condition it was disabled from: github.ref == 'refs/heads/main' && github.event_name == 'push'. To enable it you would flip that back and wire an EAS robot token as a secret. Note it also needs: deploy-backend, so a backend deploy failure would correctly block a mobile release.

Chapter 08

The HTML endpoints

Four routes return HTML instead of JSON, because a human arrives at them from an email client.

EndpointWho reaches itWhat it returns
GET /api/v1/auth/verify-emailBrowser, from the verification emailHTML — “email verified”
GET /api/v1/auth/reset-passwordBrowser, from the reset emailHTML form, submitting to POST /reset-password
GET /api/v1/auth/confirm-delete/{token}Browser, from the deletion emailHTML confirmation page — deletes nothing
POST /api/v1/auth/confirm-delete/{token}The user submitting that formPerforms the deletion; cascade runs server-side

Why the GET/POST split exists

Mail clients and link scanners issue GET requests automatically to preview links. A GET that deleted an account would fire on prefetch with no human involved. Splitting the flow closes that exactly — and it is worth stating precisely, because an earlier architecture document drew the GET as the destructive step and thereby described a vulnerability this design prevents.

JSON variants exist for in-app flows: GET /verify-email/{token}, POST /reset-password, POST /cancel-delete.

Chapter 09

The slow first request

Neon waking, not Render sleeping — and the difference decides where you point your monitors.

This chapter was wrong in the previous edition

It described “Render free-tier cold start — free web services sleep after 15 min” and listed moving to paid Render as work still to do. Production runs plan: starter — paid and always-on, with a comment in render.yaml saying it exists precisely to remove free-tier spin-down. That task is done; there is no 15-minute container sleep for a reviewer to hit.

What remains is Neon scale-to-zero. The serverless database idles, and the first query afterwards must wake it. That surfaces in exactly one place: /health, which runs SELECT 1 under a two-second timeout and returns 503 by design when the wake takes longer.

EndpointTouches the database?Behaviour when Neon is asleepUse it for
/liveNoStays 200Render's health check · your uptime monitors
/healthYes — SELECT 1, 2 s timeoutMay return 503, then recoverReadiness debugging, by hand

The practical rule

A single /health 503 that recovers on retry is not an outage. /live failing is. Point monitors at /live — a monitor on /health will page you for a non-incident, which is the fastest way to start ignoring your own alerts.

Mitigation status

ItemState
Paid always-on backendDone plan: starter
Client-side cold-start UX — status pill, per-row indicators, retry dialog, cache persistenceDone
Uptime monitors on /liveOutstanding — the one real gap
Staging planUnknown from the repo — dashboard-managed

Launch-day verdict, updated

The hosting half is closed. What is still open is observability: stand up the /live monitors before launch, not after, because a first-week backend outage on a login-gated app converts directly into one-star reviews. And if staging is still free-tier, the original 15-minute sleep applies there — check the dashboard before blaming a staging timeout on your code.

Chapter 10

Practical answers

Four questions that come up every week, answered once.

“My PR says 2 commits behind main. Should I rebase?”

Usually no. GitHub counts every other merged PR against your branch, so after each merge on main every open PR gains one. Rebase for conflicts, not for the counter. Genuine reasons: you need a fix from main that your work depends on; your branch is weeks old and ancestry matters for review; or CI fails because of a change on main your branch lacks.

“How do I verify a deploy actually worked?”

# 1. health — check BOTH; they fail differently
curl -s https://api.carekosh.com/live      # always 200, no DB probe
curl -s https://api.carekosh.com/health    # SELECT 1 under a 2s timeout
#   {"status":"healthy","version":"…","environment":"production",
#    "database":"connected","timestamp":"…"}
#   a lone /health 503 that recovers = Neon waking, NOT an outage

# 2. Render dashboard → Events → top entry reads "Deploy live"

# 3. migration head, in the Render shell
alembic current                            # expect 0006_order_item_qty_positive
#   confirm against the tree rather than trusting this page forever:
#   ls -1 vitaltrack-backend/alembic/versions/ | tail -1

# 4. smoke: register → login → create item → delete item

Full step-by-step with every expected response: CAREKOSH_E2E_VERIFICATION_GUIDE.html.

“Can we move off Render later?”

Yes. The backend is portable by construction — Dockerfile, docker-entrypoint.sh, Alembic and app/core/config.py already define a Docker-plus-environment-variables runtime, so Fly.io, Railway, DigitalOcean, Hetzner or any Docker-capable host works. A laptop or home server is fine for a demo, not for a published app.

The catch is the public hostname, not the platform. Because the mobile app bakes EXPO_PUBLIC_API_URL at build time and app.config.js guards the current URLs, a hostname change means updating eas.json, app.config.js and the start:* scripts, then rebuilding every artifact. Since api.carekosh.com already fronts the backend, a platform move can usually be DNS-only for apps already installed — which is the main reason that custom domain was worth setting up.

“Which device is the reference for manual QA?”

A real physical Android device, installed with adb install -r app.apk. Expo Go is fine for dev iteration but does not exercise the EAS-built binary path — native module behaviour, the baked API URL and the release signing config only appear in a real build.

Expect exactly three permissions

INTERNET, ACCESS_NETWORK_STATE and ACCESS_WIFI_STATE — all “normal” protection level, so no runtime prompt should ever appear. If the app asks for camera, microphone or storage, something regressed: those sit in blockedPermissions. Confirm in Play Console → App bundle explorer → Permissions.
