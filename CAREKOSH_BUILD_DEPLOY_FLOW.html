  • Mobile checks (Node 20): install with --legacy-peer-deps, confirm the carekosh-voice native module is autolinked for Android, then TypeScript (tsc --noEmit), npm test (121 Node test-runner tests in tests/*.test.cjs on 7 Oct 2026, and again on 8 Oct), ESLint (errors fail; warnings do not) and Expo Doctor. Expo Doctor's result is discarded (|| echo), so it can never fail the job; on 7 Oct it reported patch-version mismatches. Earlier (September 2026 notes): the job ran eight API tests via npm run test:api; main's job runs TypeScript, ESLint and Expo Doctor only.
  • Advisory jobs: mypy and the PR-only Trivy scan. Green required checks do not mean there are no typing or dependency findings.
  • Other jobs: the PR summary job (pr-check, not required by GitHub), the deploy hook, the label-gated preview build and the disabled production build.

The preview build job is not marked continue-on-error; only its notification step is. On main it runs on Node 18, below React Native 0.81's minimum of Node 20.19.4; the feature branch moves it to Node 22 (matching .nvmrc). A red CI run therefore does not technically stop a merge; reading every job before merging is a discipline, not an enforced gate.

Container startup and migration

The production image uses Python 3.12 and runs two Uvicorn workers managed by Gunicorn. The shell entrypoint:

  1. waits for PostgreSQL — up to 30 attempts, 2 seconds apart; after that it logs a warning and proceeds anyway;
  2. runs alembic upgrade head, and exits if it fails;
  3. appends the PORT bind argument and execs Gunicorn from an exec-form Docker CMD.

A failed start-up does not automatically undo schema changes. The host parser falls back to localhost for a DATABASE_URL without a port. With such a URL, every start waits about 60 seconds before migrating. Look for Extracted HOST: in the deploy log, or set DATABASE_HOST/DATABASE_PORT explicitly. Earlier A-27 made percent-encoded URLs fail during Alembic configuration. The 8 Oct 2026 local fix escapes percent signs for ConfigParser, which returns the original URL. Continue URL-encoding reserved password characters; this needs the updated backend deployment.

The migration head on the feature branch is 0010_order_local_id_unique (main ends at 0006_order_item_qty_positive). 0007_session_order_safety adds session_version, durable daily order counters and token-digest indexes; 0008 creates consent and usage tables; 0009 adds consent scopes and the usage provider field; 0010 adds a partial per-user unique index on non-null order local_id, exempting later legacy duplicates by id, and takes a SHARE lock on orders until migration commit. Its duration depends on the table size and lock contention. They preserve existing application rows. Automatic downgrade below 0007 is deliberately refused (it raises an error); 0008–0010 have downgrades, which are untested. Redeploying an image older than the schema does not roll it back: that image's alembic upgrade head cannot find revision 0010, the container exits, and Render keeps the current version. Follow the release gate, cutover and rollback notes.

An AAB is not installed directly: Google Play (or bundle tooling) turns it into installable, device-specific APKs. Expo artifact guide.

Backend-only fixes reach existing compatible installations as soon as the API is deployed. Mobile changes, such as the refresh and history fixes, retry-safe order creation and the voice assistant, need a new installation, because over-the-air updates are off (updates.enabled=false). The EAS channels in eas.json do not enable OTA updates. Custom-domain DNS can move an existing hostname to another host without changing the embedded URL.

Release sequence for this change

In short: open a PR, stage the candidate deliberately with both auto-deploy and the CI deploy hook controlled, back up, then cut over with old writers drained. This is the same gate as in BACKEND_HARDENING.md.

Details that matter for this release:

  • Branch and PR first. Commit all intended source, test and migration files to a feature branch, push, and open a PR to main. A push cannot include uncommitted changes. Read every CI job; on 7 Oct 2026 GitHub required no status checks.
  • Staging (step 2). Preserve existing staging data. Do not run the one-way 0007–0010 on the existing staging database. Deploy the candidate deliberately to an isolated target, testing a fresh database and a populated synthetic 0006 → 0010 upgrade, because fresh-schema tests alone do not prove a legacy upgrade is safe; control both the CI hook and Render auto-deploy (not verified) before merging. A preview APK does not deploy its backend.
  • Device test (step 2). Build and install a preview APK from the same candidate. Test login, verification and recovery; profile; stock edits (Edit Item, including a version conflict from a second device); order create (including Retry after a failed save, which must return the same order), status, apply and delete; older order history (the Orders tab list and each order card's timeline); PDFs; shared-device logout; and the assistant (typed questions anywhere; the microphone only on a real phone with the speech pack downloaded).
  • Back up (step 3). Confirm the target database, the current migration and a restorable backup or recovery point, and rehearse the restore on a separate target.
  • Cut over (step 4). The old COUNT-based allocation and the new counter must never write at the same time. The migration-runner lock does not stop old application writers, and 0010 blocks writes to orders while it builds its index (duration depends on data and contention). Unverified accounts that have an email receive 403 EMAIL_NOT_VERIFIED on login, refresh and protected bearer routes when both verification and email sending are configured; public health and token-link routes are outside that policy. A successful deploy-hook response does not confirm the deployment: check the commit Render actually deployed.
  • Mobile release (after the backend). For mobile changes, build a fresh production AAB and submit it to internal testing. With the current eas.json, the submission may become available to testers immediately; set releaseStatus: "draft" first if you need a manual release step. Then install and test that exact version.

The re-seed SQL and the rollback notes are in the release gate.

Verify service health

/live does not query the database. /health runs a database probe with a two-second timeout and returns 503 when it fails. render.yaml sets /live as Render's health check (whether Render reads that file is not verified), so a database outage alone does not fail that liveness probe. Other platform conditions may still restart or remove an instance. Add a separate readiness alert on /health, with retry and grace thresholds, so a sustained database failure is visible. A transient 503 may reflect the database waking up, but that cause must be established from evidence. A healthy /live does not prove that users can load their inventory.

render.yaml requests Starter hosting; it cannot prove the current plan. The actual staging plan, Neon suspension policy, alert destinations and provider retention remain dashboard evidence.
