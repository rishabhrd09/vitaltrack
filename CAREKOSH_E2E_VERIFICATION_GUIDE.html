How to run the two alembic commands safely:

  • Prefer the provider's console or a one-off shell on the staging service.
  • From a local checkout, first securely load the deployed configuration, including a non-default SECRET_KEY of at least 32 characters (the settings loader rejects the public default in staging). Then set the target explicitly: export DATABASE_URL='<confirmed staging URL>' ENVIRONMENT=staging. Outside development/testing Alembic requires a verified TLS connection; with the default development it only tries TLS without checking the certificate, so set ENVIRONMENT=staging. Environment variables override a leftover .env, which could otherwise point at the wrong database. Percent-encoded passwords are now preserved correctly by Alembic (A-27 fixed locally); URL-encode reserved password characters normally.
  • Confirm the host before running. Run only alembic heads and alembic current — never upgrade or downgrade from a laptop.

What to expect:

  • The source head on the feature branch is 0010_order_local_id_unique (main ends at 0006_order_item_qty_positive). Compare it with the deployed commit and the database revision; a staging database that has run this branch is at 0010 and cannot be moved back below 0007 automatically. Sorting migration filenames is not a migration check; the order comes from the revision graph.
  • /live checks only that the process is up. /health also queries the database, with a two-second deadline, and returns 503 when the database is unavailable.
  • Investigate sustained 503s. Do not dismiss failures as cold starts without evidence.

2. Register, verify and rotate

jq -n --arg email "$EMAIL" --arg password "$TEST_PASSWORD" \
  '{name:"Staging review",email:$email,password:$password}' |
  curl -fsS -X POST "$BASE/api/v1/auth/register" \
    -H 'Content-Type: application/json' --data-binary @- |
  jq '{user_id:.user.id}'

Expect 201. UserRegister requires an email; the username is optional and must already be lower case (upper case is rejected with 422).

Email verification is enforced only when both the REQUIRE_EMAIL_VERIFICATION flag and the mail configuration (MAIL_PASSWORD) are set. When it is enforced, login, bearer requests and refresh for the unverified account must fail with EMAIL_NOT_VERIFIED. Open the verification email, then log in. The configured rate limits are counted per worker process; they are not guaranteed global quotas.

LOGIN=$(jq -n --arg identifier "$EMAIL" --arg password "$TEST_PASSWORD" \
  '{identifier:$identifier,password:$password}' |
  curl -fsS -X POST "$BASE/api/v1/auth/login" \
    -H 'Content-Type: application/json' --data-binary @-)
ACCESS=$(printf '%s' "$LOGIN" | jq -er '.access_token')
REFRESH=$(printf '%s' "$LOGIN" | jq -er '.refresh_token')
USER_ID=$(printf '%s' "$LOGIN" | jq -er '.user.id')
OLD_REFRESH=$REFRESH
ROTATED=$(jq -n --arg token "$REFRESH" '{refresh_token:$token}' |
  curl -fsS -X POST "$BASE/api/v1/auth/refresh" \
    -H 'Content-Type: application/json' --data-binary @-)
ACCESS=$(printf '%s' "$ROTATED" | jq -er '.access_token')
REFRESH=$(printf '%s' "$ROTATED" | jq -er '.refresh_token')
AUTH="Authorization: Bearer $ACCESS"
# Replaying OLD_REFRESH should return 401. Do not print or share tokens.
jq -n --arg token "$OLD_REFRESH" '{refresh_token:$token}' |
  curl -sS -w '\nHTTP %{http_code}\n' -X POST "$BASE/api/v1/auth/refresh" \
    -H 'Content-Type: application/json' --data-binary @-

Refresh-token rotation means each refresh returns a new refresh token and retires the old one. It locks the user row and then claims the refresh row with a conditional update, so a token can be used only once. A manual, sequential replay checks only one scenario; the local concurrency tests cover simultaneous refresh and password-change races.

3. Inventory and optimistic concurrency

CAT=$(curl -fsS -X POST "$BASE/api/v1/categories" -H "$AUTH" \
  -H 'Content-Type: application/json' -d '{"name":"Review supplies"}' | jq -er '.id')
ITEM=$(jq -n --arg cat "$CAT" \
  '{categoryId:$cat,name:"Review item",quantity:10,minimumStock:5,unit:"pieces",isCritical:true}' |
  curl -fsS -X POST "$BASE/api/v1/items" -H "$AUTH" \
    -H 'Content-Type: application/json' --data-binary @- | jq -er '.id')
curl -fsS "$BASE/api/v1/items/$ITEM" -H "$AUTH" | jq '{name,quantity,version}'
curl -fsS -X PATCH "$BASE/api/v1/items/$ITEM/stock" -H "$AUTH" \
  -H 'Content-Type: application/json' -d '{"quantity":8,"version":1}' |
  jq '{quantity,version}'
# The app writes through PUT. Test a stale version explicitly here;
# the form now retains its opening version (A-1 fixed locally).
# Version 1 is now stale, so this must return 409 and change nothing.
curl -sS -w '\nHTTP %{http_code}\n' -X PUT "$BASE/api/v1/items/$ITEM" -H "$AUTH" \
  -H 'Content-Type: application/json' -d '{"quantity":9,"version":1}'

Expect quantity 10 / version 1 at first, then 8 / version 2. Repeating the same stock request with version 1 must return 409 (conflict), and so must the stale PUT. This is optimistic concurrency: each write names the version it read, and the server rejects it if the item has changed since.

  • After a failure, refetch before deciding how to retry. A failed response does not prove the write did not commit.
  • Check the duplicate-name responses for categories and items without merging or deleting existing stock.
  • The Android app changes quantities through Edit Item (PUT /api/v1/items/{id} with version); PATCH …/stock is API-only in the current app. Repeat the conflict check with PUT, as above, or on two devices.

4. Order lifecycle and history

ORDER=$(jq -n --arg item "$ITEM" \
  '{orderId:"CLIENT-REVIEW",totalItems:1,totalUnits:20,items:[{itemId:$item,name:"Review item",unit:"pieces",quantity:20,currentStock:8,minimumStock:5}]}' |
  curl -fsS -X POST "$BASE/api/v1/orders" -H "$AUTH" \
    -H 'Content-Type: application/json' --data-binary @- | jq -er '.id')
curl -fsS -X PATCH "$BASE/api/v1/orders/$ORDER/status" -H "$AUTH" \
  -H 'Content-Type: application/json' -d '{"status":"ordered"}' | jq '.status'
curl -fsS -X PATCH "$BASE/api/v1/orders/$ORDER/status" -H "$AUTH" \
  -H 'Content-Type: application/json' -d '{"status":"received"}' | jq '.status'
curl -fsS -X POST "$BASE/api/v1/orders/$ORDER/apply" -H "$AUTH" | jq '.status'
curl -fsS "$BASE/api/v1/items/$ITEM" -H "$AUTH" | jq '{quantity,version}'
curl -fsS "$BASE/api/v1/activities?limit=20" -H "$AUTH" \
  | jq '{total,recent:[.activities[]|{action,itemName,timestamp}]}'

What to expect:

  • The schema still requires orderId, but the server allocates the public ORD-YYYYMMDD-NNNN value itself.
  • After apply: status stock_updated, and the item at quantity 28 / version 3.
  • A second apply is rejected and leaves the quantity at 28.
  • Deleting this applied order is rejected. Create a separate pending order to test an allowed deletion; capture that exact response id, never select an arbitrary order from the list.
  • Earlier (September 2026): separate create requests were never deduplicated, so a retry after a lost response made a second order. Current (migration 0010): a request that carries a localId is retry-safe — repeating that key returns the existing order with 200 and creates nothing, even when the repeated schema-valid payload differs. Legacy duplicate rows are preserved and exempted from the index. Requests without localId (the example above, and app builds older than this branch) are still never deduplicated, so check the order history before retrying those.
# Retry safety: send the same body (same localId) twice. Expect HTTP 201, then 200,
# and only one new order. Then delete that pending order (allowed for pending/declined).
RETRY_BODY=$(jq -n --arg item "$ITEM" --arg lid "$(uuidgen)" \
  '{orderId:"CLIENT-RETRY",localId:$lid,items:[{itemId:$item,name:"Review item",unit:"pieces",quantity:1}]}')
FIRST=$(printf '%s' "$RETRY_BODY" | curl -fsS -X POST "$BASE/api/v1/orders" \
  -H "$AUTH" -H 'Content-Type: application/json' --data-binary @-)
PENDING=$(printf '%s' "$FIRST" | jq -er '.id')
REPLAY=$(printf '%s' "$RETRY_BODY" | curl -fsS -X POST "$BASE/api/v1/orders" \
  -H "$AUTH" -H 'Content-Type: application/json' --data-binary @-)
REPLAY_ID=$(printf '%s' "$REPLAY" | jq -er '.id')
if [ -n "$PENDING" ] && [ "$PENDING" = "$REPLAY_ID" ]; then
  printf 'Same order returned: %s\n' "$PENDING"
  curl -fsS -X DELETE "$BASE/api/v1/orders/$PENDING" -H "$AUTH"
else
  printf 'Replay mismatch: stop and investigate; nothing deleted.\n'
fi

Activity JSON uses itemName and timestamp, not the database field names item_name and created_at. Pagination uses page/pageSize; the mobile service follows pages of 100 rows and rejects an incomplete fetch. With a suitable synthetic fixture, verify older actionable orders and older order history (the Orders tab list and each order card's Ordered/Received/Applied timeline). A changing dataset is not a snapshot.

5. Credential and profile checks

  • Name and username edits work in the app (Profile sends only those two fields; the app has no phone field). Through the API, PATCH /api/v1/auth/me also accepts phone, but an explicit null is ignored, so a phone number cannot be cleared that way (an empty string "" does clear it). A different profile email must be rejected (400); the existing UI keeps the email read-only.
  • Reset the test password through the app's Forgot Password flow and the emailed link. The app has no change-password screen, so exercise POST /api/v1/auth/change-password with curl (JSON fields current_password and new_password). After either, old access/refresh pairs must fail on their next use, and a fresh login must preserve inventory and orders.
  • Use a reset or verification link once; reusing it must fail. Concurrent use is covered by the local tests.
  • Check the real application, hosting-edge and telemetry output using synthetic capability tokens. Redacted local unit-test output alone does not prove platform redaction.

Getting the candidate onto staging. Staging was documented as deploying from main, which means after the merge; on 7 Oct 2026 the owner reported pointing it at the feature branch instead (not re-checked — confirm the branch in the dashboard). To test a candidate before merging, control both Render auto-deploy and the CI deploy hook, then deploy that commit to an isolated staging target manually. Use a manual deploy of the commit, or temporarily point the staging service at the candidate branch. For migrations 0007–0010, follow every step of the release gate, preserving the existing staging database and verifying both a fresh candidate database and a populated synthetic legacy database upgraded from the old revision. A fresh database alone does not prove upgrade safety for stored data. The current expanded release gate covers both deployment triggers and old-writer draining.

Install the APK using its compatible signing identity; an AAB itself cannot be installed directly. Test the old installed client as well as the new candidate. Production builds distributed through Play internal testing use production data.

  • Register/verify/login, password recovery, profile save and every existing navigation button.
  • Builder, inventory edits, critical/low-stock indicators, quantity conflicts and network failures.
  • Order create/status/apply/delete, older order history (Orders tab list and order-card timelines), and the order and inventory PDFs.
  • Cache display after a restart. After reconnecting, confirm data refreshes on its own: in this branch TanStack Query's onlineManager follows NetInfo, so regaining the network refetches stale queries, as do returning to the foreground and pull-to-refresh (earlier, September 2026: reconnecting alone did not refetch). Saves never queue offline: a save attempted offline is rejected by a screen guard or attempted immediately without automatic replay; its network failure may be delayed. Inspect server state after an uncertain response before deciding to retry. Log out and in as another account without exposing the previous user's cache.
  • Generated manifest permissions and release behaviour; do not infer the exact permission set from app.json alone. This build asks for the microphone (RECORD_AUDIO) only when the user turns the assistant's microphone on in Voice setup, and checks the permission again before each recording.

Assistant checks (inventory reads and local drafts; saving requires touch)

The assistant answers questions about stock but never changes it. Speech recognition runs on the phone; only a typed or reviewed question can be sent to the server, and only when optional online understanding is on. Use a preview APK on a real Android phone; Expo Go and emulators without a microphone cannot test recording.

  • Typed questions: open Profile menu → Voice setup, turn the assistant on, then choose "Try a typed question here" (shown as "Practice a command here" once voice is ready). In the tab dock a "Type a question here" button appears only after a recording problem. Ask "how many hand gloves do we have", "show low stock" and "delete hand gloves" (use an item name from your synthetic data). Expect a stock answer, a low-stock list using the same rules as the Dashboard, and a refusal for the delete request — and no change to any item or order.
  • Voice setup: Profile menu → Voice setup. Download the speech pack (English only; downloaded from Moonshine's servers and checked before use), allow the microphone, record a question, edit the transcript, then tap Send. The question text is not sent for interpretation before Send; capabilities, consent and model-download requests are separate. Recognised local questions can be answered without a Groq call. Remove the pack and confirm that recording is unavailable until the pack is downloaded again (typed questions keep working).
  • Offline: in airplane mode, ask a question answered from data loaded since the app was last started (in this login). The answer must be labelled as last-known data; with no such data (for example after a restart, when only the cache on disk is left) it must refuse rather than guess.
  • Online understanding (only if staging sets the AI_* variables): accept the consent screen, ask an unusually phrased question, and confirm the answer. Without the variables, Voice setup must show "Online understanding is unavailable. Basic commands still work." and unfamiliar wording must get a "could not safely match" reply rather than a guess.
  • Spoken replies: turn on "Read answers aloud"; it works only with an installed offline English Android voice.
  • Database effect: the only server rows the assistant itself writes are in ai_consents and ai_usage (one usage row per accepted processing reservation; failed reserved attempts also count, while requests refused by the flag, consent or quota checks create no usage row; every withdrawal writes a consent row). As with any signed-in use, a token refresh can also rotate a refresh_tokens row. Inventory, order and activity rows must not change.

staleTime is not a polling interval. A cache flag in the source requires rebuilding the installed release. The cache buster follows the visible app version, not every auto-incremented Android versionCode.

7. Delete only the disposable account

Capture any stock or audit evidence you need before deletion. Then:

  1. From Profile, request deletion.
  2. Cancel it with curl -fsS -X POST "$BASE/api/v1/auth/cancel-delete" -H "$AUTH". The app has no cancel button. Obtain fresh access credentials first, because access tokens last 30 minutes, and rebuild AUTH="Authorization: Bearer $ACCESS" after updating ACCESS.
  3. Confirm the emailed link now shows "Invalid or Expired Link".
  4. Request deletion again. Opening the link (GET) must show a confirmation page without deleting anything.
  5. Submit the form to delete. Any later login must fail, and the owned rows must be gone.

Inspect the database with SELECT-only queries against the explicitly verified staging database. Note that the audit table is singular: audit_log. For the captured user, check categories, items, orders, order_items (through their orders), activity_logs, refresh_tokens, audit_log, ai_consents and ai_usage. The independent order_number_counters table must remain. Do not run bulk user cleanup or database resets as part of this guide.
