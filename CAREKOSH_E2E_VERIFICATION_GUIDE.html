End-to-End Verification Guide

Every curl, every expected response, every gate. Run this after a deploy; if a step fails, stop and fix — do not proceed.

CareKosh · com.carekosh.mobile v1.0.0 · Staging + Production · re-verified against source, July 2026

Corrections applied in this edition — read once, then forget

The previous edition was stamped “As of PR #13” while main had moved ~44 pull requests ahead. Eight defects were found by re-checking every command against the source. Two were curl bodies that would have failed outright, so a tester following the old guide would have concluded the API was broken.

  • Step 13 order create would 422. It sent title (not a field) and omitted orderId, which is required. Order items also require name. Fixed.
  • Step 14 jq path was wrong. /activities returns {activities:[…], total:N}, not a bare array, so jq '.[]' failed. Now jq '.activities[]'.
  • Step 7 expected the wrong 401 body. It expected "Token has been revoked" — a string that exists nowhere in the codebase. The real detail is "Invalid or expired refresh token".
  • Step 3 pinned a stale Alembic head (0005). Real head is 0006_order_item_qty_positive, so the check failed if followed literally.
  • Step 22 used com.vitaltrack.mobile. The package is com.carekosh.mobile, so that adb command silently did nothing.
  • Step 1 understated the /health body and described production as free-tier with 15-minute sleep. Production is plan: starter — always-on.
  • “Neon branch” was wrong in three places; staging and production are two databases inside one branch.
  • No print styles existed. In OS dark mode the page printed a dark background behind light text.
Ground rules

1. Run the full flow on staging first. 2. Only hit production with read-only and idempotent requests, unless you are deliberately cleaning up your own test account. 3. Never create real-looking data on production. 4. Phase 5 is irreversible — only run it against a throwaway staging account.

Staging

Neon database: vitaltrack_staging · test data only · safe to wipe

Production

Two clarifications worth internalising

Databases, not branches. Both are databases inside the same Neon branch, sharing one connection host — created with CREATE DATABASE vitaltrack_staging. Looking for a Neon “branch” named vitaltrack_staging will waste your time.

Only production is in render.yaml. The service defined as infrastructure-as-code is vitaltrack-api on plan: starter. Staging is managed entirely from the Render dashboard, so its plan is not knowable from the repo — check it there before trusting any cold-start expectation below.

Phase 1 Pre-flight

Step 1

Both services healthy

Two endpoints, two different jobs. Check both — they fail differently and that difference is the diagnosis.

# liveness — never touches the database, should ALWAYS be 200
curl -s https://staging-api.carekosh.com/live
curl -s https://api.carekosh.com/live

# readiness — runs SELECT 1 under a 2 s timeout
curl -s https://staging-api.carekosh.com/health
curl -s https://api.carekosh.com/health
Expected — /health (200) {"status":"healthy","version":"…","environment":"production","database":"connected","timestamp":"…"}
Expected — /live (200) {"status":"…","database":"not_checked",…} — no database probe, so this stays up even when Neon is asleep.
What a failure actually means

Production is plan: starter — always-on. There is no 15-minute container sleep to wait out. If you see a slow first response it is Neon waking from scale-to-zero, not Render.

A single /health 503 that recovers on retry is by design: the readiness probe times out at 2 s while Neon wakes. It is not an outage. That is also exactly why render.yaml sets healthCheckPath: /live — so Render never restarts the instance over a transient database blip — and why any uptime monitor you create should point at /live, not /health.

Both endpoints failing, or /live failing at all, is a genuine incident.

Step 2

Latest deploy is live

  1. Open dashboard.render.com
  2. Staging service → Events tab → the top entry should read “Deploy live”
  3. Repeat for vitaltrack-api (production — this is the name in render.yaml)
  4. Confirm the commit hash matches the last merge on main
Expect a slow-looking boot

docker-entrypoint.sh cannot parse a port-less Neon URL, so DATABASE_HOST falls back to localhost and every boot burns the full 60-second pg_isready loop before migrations run. Harmless, but it makes deploys look hung. Setting DATABASE_HOST in Render removes the delay.

Step 3

Alembic head matches code

In the Render shell for each service:

alembic current
Expected 0006_order_item_qty_positive — from alembic/versions/20260623_order_item_quantity_positive.py. That migration adds the CHECK (quantity > 0) constraint on order_items.

Rather than trusting this printed value forever, confirm it against the tree — the newest file wins:

ls -1 vitaltrack-backend/alembic/versions/ | tail -1
A failed migration is a failed deploy, not a broken service

The entrypoint wraps alembic upgrade head in a guard and exits non-zero on failure, so Render keeps the previous instance serving. That is the desired behaviour — do not “fix” it by bypassing the guard.

Phase 2 Auth flow — register through refresh

Step 4

Register a test user

BASE=https://staging-api.carekosh.com
EMAIL="e2e+$(date +%s)@example.com"

curl -s -X POST $BASE/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d "{
    \"name\": \"E2E Test\",
    \"email\": \"$EMAIL\",
    \"password\": \"TestPass123!\"
  }" | jq '{access_token: .access_token[0:20], expires_in, user: .user.email}'
Expected (201) {"access_token":"…","refresh_token":"…","token_type":"bearer","expires_in":1800,"user":{…}}
Schema notes

email is required; omitting it returns 422. username is optional — if you send one it must match ^[a-z0-9_]+$, 3–50 characters, so "e2etest" is valid but any capital letter is not. Password policy: at least 8 characters with one uppercase, one lowercase and one digit.

Rate limit: 3 registrations per hour per IP. Loop this step four times and the fourth returns 429.

Register hands you tokens even when unverified

This is worth noticing rather than glossing over: registration returns a full access + refresh pair regardless of verification state. The verification gate lives at login (Step 5), so a client that never logs out is never re-checked.

Step 5

Verify-email gate

Applies only when REQUIRE_EMAIL_VERIFICATION=true and a mail password is configured. Without clicking the link first, login should fail:

curl -s -w "\nHTTP %{http_code}\n" -X POST $BASE/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d "{\"identifier\":\"$EMAIL\",\"password\":\"TestPass123!\"}"
Expected (403) {"detail":"EMAIL_NOT_VERIFIED"}

Click the verification link from the email, then retry — login should now succeed.

If you get 200 instead of 403

The gate is deliberately fail-open: it requires both the flag and a configured mail password, so a deploy that forgets the mail credential cannot lock out every user. A 200 here therefore means the mail password is missing in that environment — check it before assuming the gate is broken.

Step 6

Login + extract tokens

LOGIN=$(curl -s -X POST $BASE/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d "{\"identifier\":\"$EMAIL\",\"password\":\"TestPass123!\"}")
ACCESS=$(echo $LOGIN | jq -r '.access_token')
REFRESH=$(echo $LOGIN | jq -r '.refresh_token')
echo "ACCESS:  ${ACCESS:0:20}…"
echo "REFRESH: ${REFRESH:0:20}…"
Note

identifier accepts an email or a username. Rate limit is 5 per minute, so a fumbled password a few times over will lock you out briefly — this is the same limit a Play reviewer can hit.

Step 7

Refresh with rotation

OLD=$REFRESH

curl -s -X POST $BASE/api/v1/auth/refresh \
  -H "Content-Type: application/json" \
  -d "{\"refresh_token\":\"$OLD\"}" | jq '{access: .access_token[0:20], refresh: .refresh_token[0:20]}'
Expected (200) A new access + refresh pair. The old token's row now has is_revoked = true.

Now prove the rotation is single-use by replaying the same old token:

curl -s -w "\nHTTP %{http_code}\n" -X POST $BASE/api/v1/auth/refresh \
  -H "Content-Type: application/json" \
  -d "{\"refresh_token\":\"$OLD\"}"
Expected (401) {"detail":"Invalid or expired refresh token"}
What you just verified — and how to describe it

Rotation is a single-statement compare-and-swap, not a delete: UPDATE refresh_tokens SET is_revoked=true WHERE jti=? AND user_id=? AND is_revoked=false RETURNING id. Only one concurrent request can flip false → true, so a token submitted twice simultaneously rotates at most once — the loser gets the 401 above. The row is never deleted.

The deliberately generic message is anti-enumeration: “already used”, “expired” and “never existed” are indistinguishable to a caller.

Phase 3 CRUD + optimistic concurrency

Step 8

Create category → create item

Request bodies use camelCase aliases (categoryId, minimumStock, isCritical); snake_case also works because the schemas set populate_by_name.

AUTH="Authorization: Bearer $ACCESS"

CAT=$(curl -s -X POST $BASE/api/v1/categories \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"name":"Oxygen"}' | jq -r '.id')

ITEM=$(curl -s -X POST $BASE/api/v1/items \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d "{
    \"categoryId\":\"$CAT\",
    \"name\":\"Oxygen Mask (Adult)\",
    \"quantity\":10,
    \"minimumStock\":5,
    \"unit\":\"pieces\",
    \"isCritical\":true
  }" | jq -r '.id')

echo "CAT=$CAT  ITEM=$ITEM"
Expected Two non-empty UUIDs. An empty ITEM almost always means the categoryId did not belong to you — ownership is re-checked on every write.
Step 9

Read back, confirm version = 1

curl -s $BASE/api/v1/items/$ITEM -H "$AUTH" | jq '{name,quantity,version}'
Expected {"name":"Oxygen Mask (Adult)","quantity":10,"version":1}
Step 10

Update with the correct version — it increments

curl -s -X PUT $BASE/api/v1/items/$ITEM \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"name":"Oxygen Mask (Adult)","quantity":12,"minimumStock":5,"version":1}' \
  | jq '{name,quantity,version}'
Expected {"name":"Oxygen Mask (Adult)","quantity":12,"version":2}
Step 11

Update with a stale version — 409 Conflict

curl -s -w "\nHTTP %{http_code}\n" -X PUT $BASE/api/v1/items/$ITEM \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"name":"X","quantity":99,"minimumStock":5,"version":1}'
Expected (409) {"error":"Version conflict","message":"This item was modified by someone else. Please refresh and try again.","server_version":2,"server_quantity":12}
Why this matters

This is the single reason the server-first migration was worth doing. Two caregivers editing the same item in the same second no longer silently overwrite each other — and the 409 body carries the server's current truth, so the app can say “someone changed this to 12” instead of only “that failed”.

Step 12

Quick stock update via PATCH

curl -s -X PATCH $BASE/api/v1/items/$ITEM/stock \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"quantity":8,"version":2}' | jq '{quantity,version}'
Expected {"quantity":8,"version":3}
Absolute, never a delta

quantity is the resulting absolute value, not an adjustment — so a replayed or double-tapped request cannot double-apply. Keep the value you send in mind for Step 13's arithmetic.

Phase 4 Orders + apply endpoint

Step 13

Create order, mark received, apply to stock

This command was broken in the previous edition

It sent {"title": …} — orders has no title column — and omitted orderId, which is required. Each order item also requires name, not just itemId and quantity. The old body returned 422, so this phase could never pass.

# --- create -------------------------------------------------------------
ORDER=$(curl -s -X POST $BASE/api/v1/orders \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d "{
    \"orderId\": \"ORD-E2E-$(date +%s)\",
    \"totalItems\": 1,
    \"totalUnits\": 20,
    \"items\": [{
      \"itemId\": \"$ITEM\",
      \"name\": \"Oxygen Mask (Adult)\",
      \"unit\": \"pieces\",
      \"quantity\": 20,
      \"currentStock\": 8,
      \"minimumStock\": 5
    }]
  }" | jq -r '.id')

echo "ORDER=$ORDER"

# --- transition: pending -> ordered -> received --------------------------
curl -s -X PATCH $BASE/api/v1/orders/$ORDER/status \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"status":"ordered"}'  | jq -r '.status'
curl -s -X PATCH $BASE/api/v1/orders/$ORDER/status \
  -H "$AUTH" -H "Content-Type: application/json" \
  -d '{"status":"received"}' | jq -r '.status'

# --- apply to stock -----------------------------------------------------
curl -s -X POST $BASE/api/v1/orders/$ORDER/apply -H "$AUTH" | jq -r '.status'

# --- verify the item went 8 -> 28 ---------------------------------------
curl -s $BASE/api/v1/items/$ITEM -H "$AUTH" | jq '{quantity,version}'
Expected Status prints ordered, then received, then stock_updated. Item quantity moves from 8 to 28 and the version increments.
The state machine is the safety property

Legal transitions are enforced server-side: pending → ordered | received | declined, ordered → partially_received | received, partially_received → received. stock_updated is reachable only through POST /apply and has no outgoing edge, so a retried apply cannot add the same stock twice. Try the apply a second time — it should be rejected.

Step 14

Activity log records every write

curl -s "$BASE/api/v1/activities?limit=10" -H "$AUTH" \
  | jq '{total, recent: [.activities[] | {action, item_name, created_at}]}'
Expected Entries for category create, item create, item updates, order create, two status changes and the apply — each with a created_at.
Response is an object, not an array

/activities returns {"activities":[…],"total":N}. The previous edition used jq '.[]', which fails on an object — hence .activities[] above. limit accepts 1–200 and defaults to 50.

item_name is stored denormalised on purpose, so the feed still reads correctly after the underlying item is deleted.

Phase 5 Account deletion — irreversible

Staging only

Step 17 permanently destroys the account and every row it owns. Run it only against the throwaway account created in Step 4, and never against production.

Step 15

Request deletion — email sent, nothing deleted

curl -s -X DELETE $BASE/api/v1/auth/me -H "$AUTH" | jq -r '.message'
Expected A confirmation email has been sent. Please check your inbox and open the link to review and confirm account deletion. The link expires in 24 hours.

The email contains a link to GET /api/v1/auth/confirm-delete/{token}. The token in the link is raw; the database stores only its SHA-256 hash with a 24-hour expiry. The GET route renders a page and deletes nothing.

Step 16

Cancel a pending deletion

curl -s -X POST $BASE/api/v1/auth/cancel-delete -H "$AUTH" | jq -r '.message'
Expected Account deletion request has been cancelled. — and the emailed link now fails, because the stored hash was cleared.
Step 17

Confirm deletion — irreversible

Re-run Step 15, open the email, then load the confirmation page:

curl -s $BASE/api/v1/auth/confirm-delete/RAW_TOKEN | head -20
Expected An HTML confirmation page. No data deleted. This is the whole point of the two-verb design — mail clients and link scanners follow GET links automatically, so a destructive GET would fire on prefetch with no human involved.

Submit the form in the page, or reproduce it directly:

curl -s -X POST $BASE/api/v1/auth/confirm-delete/RAW_TOKEN | head -20
Expected An HTML completion page. The user row is deleted and the cascade unwinds categories, items, orders, order_items, activity_logs, refresh_tokens and audit_log.

Prove it — any authenticated call with the old access token:

curl -s -w "HTTP %{http_code}\n" -o /dev/null $BASE/api/v1/items -H "$AUTH"
Expected HTTP 401. The token still decodes and its signature is still valid — the user simply no longer exists, which is what get_current_user checks.

Phase 6 Database-side checks

Step 18

Row counts + optimistic-locking evidence

Connect via the Neon Console SQL editor, or psql with the connection string, against the vitaltrack_staging database:

SELECT count(*) FROM users;
SELECT count(*) FROM items;
SELECT count(*) FROM activity_logs;

-- optimistic-locking evidence
SELECT id, name, quantity, version
FROM items
ORDER BY updated_at DESC
LIMIT 5;

-- audit ledger  (note: the table is SINGULAR)
SELECT action, entity_type, old_values, new_values, created_at
FROM audit_log
ORDER BY created_at DESC
LIMIT 10;
Expected Item rows have version >= 1, and the item you edited shows version = 3 or higher. audit_log carries JSONB old_values / new_values for recent writes.
Two names people get wrong

The audit table is audit_log, singular — audit_logs does not exist. Its JSON columns are old_values and new_values. And the item threshold column is minimum_stock, not minimum_quantity.

Step 19

Cascade check (after Step 17)

-- substitute the deleted user's id; all of these must return 0
SELECT count(*) FROM categories     WHERE user_id = 'DELETED_USER_ID';
SELECT count(*) FROM items          WHERE user_id = 'DELETED_USER_ID';
SELECT count(*) FROM orders         WHERE user_id = 'DELETED_USER_ID';
SELECT count(*) FROM activity_logs  WHERE user_id = 'DELETED_USER_ID';
SELECT count(*) FROM refresh_tokens WHERE user_id = 'DELETED_USER_ID';
SELECT count(*) FROM audit_log      WHERE user_id = 'DELETED_USER_ID';

-- order_items has no user_id — it cascades via its parent order
SELECT count(*) FROM order_items oi
LEFT JOIN orders o ON o.id = oi.order_id
WHERE o.id IS NULL;   -- orphans; must be 0

Phase 7 Mobile APK

Step 20

Build a preview APK

cd vitaltrack-mobile
eas build --profile preview --platform android

Or add the build-apk label to a pull request and let CI do it. The preview profile builds an APK with EXPO_PUBLIC_API_URL = https://staging-api.carekosh.com baked in; the production profile builds an app bundle pointing at https://api.carekosh.com. The URL is compiled in at build time — it cannot be changed afterwards.

Version codes live on EAS

eas.json sets appVersionSource: remote with autoIncrement on production, so the versionCode in app.json is inert. Read the real value with eas build:version:get --platform android; never hand-edit it.

Step 21

Device checklist

  • Install with adb install -r app.apk
  • Register a new account → receive the verification email → verify
  • Login → dashboard loads
  • Builder → seed inventory → items appear in the Inventory tab
  • Create an item → PATCH stock → the activity feed updates
  • Create an order → mark received → apply → item quantity updates
  • Export an order PDF → opens with no “unknown order ID” error
  • Export an inventory PDF → status badges reflect stock state (OUT OF STOCK / LOW / OK), critical items marked ★
  • Tap the profile button → bottom sheet opens → Edit Profile → profile screen opens
  • “About CareKosh” → modal shows the app version from Expo constants and a tappable support email
  • Shared-device privacy: log out, log in as a second account → the first user's inventory must not appear
  • Profile → Delete Account → receive email → confirm → forced logout
  • Try logging in with the deleted account → 401
Permissions to expect in the build

Exactly three, all “normal” protection level, so no runtime prompts should ever appear: INTERNET, ACCESS_NETWORK_STATE, ACCESS_WIFI_STATE. If the app asks for camera, microphone or storage, something regressed — those are all in blockedPermissions. Verify in Play Console → App bundle explorer → Permissions.

Phase 8 Loading UX — skeletons, cache persistence, cold-start retry

Step 22

Skeleton loading

  • Clear app data — adb shell pm clear com.carekosh.mobile — or use a fresh install, then log in
  • Dashboard → animated skeleton placeholders during the initial fetch
  • Inventory → list-shaped skeletons
  • Orders → card-shaped skeletons
  • Skeletons give way to real content with no layout jump (header and safe area stay put)
Package name

It is com.carekosh.mobile. The previous edition said com.vitaltrack.mobile, which adb accepts silently while clearing nothing — so the test appeared to pass while doing nothing at all.

Step 23

Cache persistence

  • Browse dashboard, inventory and orders while logged in, to populate the cache
  • Kill the app from recents, wait a minute, reopen → cached data appears instantly, then refreshes (30 s staleTime)
  • Enable airplane mode and reopen → cached data still renders as a read-only snapshot
  • Log out, log in as a different user → the previous user's inventory must not appear
  • Optional: set ENABLE_CACHE_PERSISTENCE = false in providers/QueryProvider.tsx and restart Metro → no instant load
What persists where

The query cache lives in AsyncStorage under the key carekosh-query-cache, with a 24-hour retention and a buster tied to the app version — so a version bump discards a stale cache automatically. Tokens never go there; they live in expo-secure-store. And allowBackup=false means Android Auto Backup copies neither.

Step 24

Cold-start auto-retry

Reproducing this is harder than it used to be

The old instruction — “wait 15 minutes for Render to sleep” — no longer works against production, which is plan: starter and always-on. Check your staging service's plan in the Render dashboard: if staging is also paid, the only remaining warm-up is Neon scale-to-zero, which is shorter and less predictable. To exercise the retry path deliberately, point the app at an unreachable host or stop the staging service instead of waiting.

  • With the backend unreachable, open the app, enter valid credentials, tap Sign In
  • A “server is waking up” card appears with a spinner, an attempt counter and a Cancel button
  • Copy escalates after several attempts to indicate a longer wait
  • Retry stops after the configured maximum (12 attempts at 5-second intervals)
  • When the backend returns, login completes automatically — no manual re-tap
  • Wrong password → immediate error, no retry loop. 401 and 403 must never be retried
  • Tap Cancel mid-retry → the interval stops, the form re-enables, state resets cleanly
