Part 1 · Overview

The project at a glance

In short: CareKosh has an Android app and a browser app backed by a shared FastAPI service and PostgreSQL. It keeps a family's home-ICU supplies counted, ordered and restocked, and it is built so that two phones, a flaky network or a bad deploy cannot quietly corrupt that count.

1.1 What CareKosh is, and why it is not a toy

Family caregivers who run a home ICU for a chronically ill relative juggle dozens of consumables: tracheostomy tubes, suction catheters, feeding-tube extensions and medicines. Running out of one of them is a medical emergency. CareKosh is the app they use to know what is left, what is low, what has been ordered and what has arrived.

The product was first released as VitalTrack. That is why the code lives in vitaltrack-backend/README.md and vitaltrack-mobile/README.md: the folder names are kept on purpose, because the Render service, the EAS project and the Git history depend on them. Everything a person sees says CareKosh.

What a caregiver can do:

  • Keep an inventory. Categories and items, each with a quantity, a unit, a minimum stock level and a "critical" flag. An optional expiry date is stored and shown, but it does not raise alerts.
  • See what needs attention. An item is out of stock when its quantity is 0 or less, and low when it is above 0 but below its minimum (is_low_stock). The dashboard counts these on the phone.
  • Order and restock. Build an order, export it as a PDF, mark it received, then apply it to stock in one step.
  • Follow the history. An activity feed for people, and a server-side audit table with before-and-after snapshots for selected changes.
  • Ask the assistant. "Ask Care Coach" answers inventory questions and prepares unsaved order drafts. It is read-only: only a touch on the Create Order screen saves an order.

Why it is a good interview project: the hard parts are the ones real systems have. Two family members can edit the same item at the same time. A phone can lose the reply to a request that the server already committed. A migration can make a deploy impossible to roll back. Accounts need verification, password recovery and revocable sessions. And an AI feature must not send private data anywhere without consent.

Say it in the interview

"CareKosh is a medical-supply inventory app for families running a home ICU. It's an Expo React Native app talking to a FastAPI service on Render with PostgreSQL on Neon. The interesting work was correctness: optimistic locking for concurrent edits, idempotent order creation for retries, rotating refresh tokens, and a release process for one-way migrations."

1.2 Three pitches: 30 seconds, 2 minutes, 5 minutes

30 seconds

"CareKosh is a web and Android application that helps families track life-critical medical supplies. The app is Expo and React Native; the backend is FastAPI with async SQLAlchemy and PostgreSQL, deployed as a Docker container on Render. I focused on data correctness: version checks for concurrent edits, safe retries for orders, and secure sessions with rotating refresh tokens."

2 minutes

Add the shape: two clients, one API and one database. The phone keeps a read-only cache with TanStack Query and stores tokens in SecureStore. Every protected request carries a JWT; the server re-checks the user row, so a password change ends every session. Writes are owner-scoped and either compare a version number or use an idempotency key. Migrations run when the container starts, and CI tests both a fresh and a migrated schema.

5 minutes

  1. Problem: running out of a supply is an emergency, and several family members update the same data.
  2. Architecture: draw the big picture: Android or browser → Cloudflare proxy → Render → FastAPI → PostgreSQL, plus email and optional AI providers.
  3. One request: trace "Save an edited item" through middleware, dependencies, the version-checked UPDATE and the commit (Part 3).
  4. Correctness: optimistic concurrency, idempotent orders, atomic stock application, row locks for auth.
  5. Security: Argon2id password hashes, signed short-lived access tokens, single-use refresh tokens, hashed one-time email tokens, encrypted personal provider keys.
  6. Operations: Docker, migrations at start-up, liveness versus readiness checks, CI gates, a release gate for one-way migrations.
  7. Honest limits: no load test, shared hosted rate limits, a logout window, no MFA. Say what you would do next.

1.5 The system on one page

A caregiver loads the browser app from its Cloudflare Worker or opens the installed Android app. Both clients send authenticated requests to the environment’s API hostname. At the edge, Cloudflare adds an origin-verification header to proxied API traffic. The Render container runs FastAPI, checks the request and sends account-scoped SQL to PostgreSQL. Hosted workers share rate limits through Redis.

The public landing site and the signed-in browser app have separate builds. A visit to the landing page makes no inventory change. A successful inventory edit has to reach the API and commit in PostgreSQL.

2.4 Data architecture: eighteen application tables and their ownership boundaries

At a14b623 SQLAlchemy defines 18 application tables. Alembic tracks its own revision separately. Start with users, items, categories, orders and order_items. User-owned reads and writes filter by the authenticated account. Order lines retain item snapshots, which lets history survive an item deletion. Activity records describe business events and audit records capture mutation details.

The later migrations matter when tracing a request. Revision 0012 adds encrypted OpenAI credentials. Revision 0013 adds supply revisions, review runs, proposals, confirmations and closed order submissions. A supply revision gives cooperating writers a per-owner lock and lets the API detect when an earlier recommendation has become stale.

2.6 Build-time versus run-time configuration

This distinction answers many "how do you configure environments?" questions.

Fixed when the app is built

EXPO_PUBLIC_API_URL comes from the EAS profile and is inlined into the JavaScript bundle. Anyone can read it from the APK, so it must never hold a secret. app.config.js refuses a preview build aimed anywhere but staging and a production build aimed anywhere but https://api.carekosh.com. An empty URL is not refused: the client then falls back to http://localhost:8000.

Set on each backend service

DATABASE_URL, SECRET_KEY, FRONTEND_URL, mail, Sentry and AI settings are environment variables read by pydantic-settings at start-up. The validators refuse the public default SECRET_KEY outside development and testing, any key shorter than 32 characters, and an empty FRONTEND_URL in production.

Part 3 · Request journeys and system design

How a request flows

In short: if you can trace one save from the button to PostgreSQL and back, naming every layer and every way it can fail, you can answer most system-design follow-ups about this project.

3.1 The life of one request: saving an edited item

Open a saved item and change quantity from 10 to 8. The browser or Android editor sends the item fields and its opened version in an authenticated PUT. The backend checks ingress, request limits, the bearer token and account ownership. A scoped database session carries the mutation. Updating a deleted or unowned item returns 404. A stale version returns 409.

On success the API returns the updated item. Reopen it after a reload to verify the saved quantity. A successful CORS preflight only proves that the browser may send the actual request.

3.2 Signing in and staying signed in

Android signs in through /api/v1/auth/login, keeps the access and refresh tokens in secure device storage and sends a bearer access token for data requests. Browser login uses /api/v1/web-auth/login. The browser holds the access token in memory, and the API sets a scoped HttpOnly refresh cookie. On reload the browser can renew its session through the refresh endpoint.

Both clients call the same owner-scoped inventory handlers. A valid token identifies an account. The query must still constrain every item to that account. Password changes and resets advance the user’s session_version and revoke refresh tokens. Browser logout revokes its browser session family and clears the cookie.

3.5 The phone's cache is a copy, never a database

  • Reads: stale after 30 s, kept for 24 h, retried 3 times; queries use networkMode: 'offlineFirst'.
  • Writes: networkMode: 'always' and retry: 0. A save is attempted at once and never queued for later replay, so the app cannot replay an old edit over newer data.
  • Privacy on shared phones: the persisted copy excludes auth queries, uses the app version as a "buster", and is cleared at login and at logout.

3.9 Capacity, honestly

This review established no system-wide throughput figure, so never quote a requests-per-second figure. Reason from the design instead:

  • Database connections are the first hard limit: 2 workers × (5 + 10) = up to 30 per instance, and a deploy briefly runs old and new instances side by side.
  • Argon2 deliberately costs 64 MiB of memory per hash with these parameters; an earlier laptop measurement took about 24 ms. Login bursts are CPU- and memory-bound; that is the price of password safety.
  • Eager loading. The User model loads its collections with selectin. Auth paths disable that with noload("*") because loading every item and order on each request would grow with the account.
  • Lists. GET /items is paginated (up to 100 per page) and the app fetches all pages; activities are capped at 200. Large accounts would need cursor pagination.
Say it in the interview

"I haven't load-tested it, so I won't quote throughput. The first limits I'd watch are database connections per instance and Argon2's CPU and memory during login bursts. The app tier is stateless, so I'd add instances behind a connection pooler before changing the design."

34How do you handle two people editing the same item?intermediate

Short answer. Optimistic concurrency: each save sends the version it read; UPDATE … WHERE version = :v SET version = version + 1. Zero rows updated means someone else won, and the API returns 409 with the current values without writing anything.

Deeper. Item renames also take a per-account advisory lock so duplicate names cannot race. Stock changes from applying an order bump the version too, so a form opened before a delivery cannot overwrite the delivered stock.

Likely follow-ups. Why not SELECT FOR UPDATE? (A lock cannot be held across a person's think-time.)

concurrencyocc

35What if the phone sends the same order twice?intermediate

Short answer. A matching replay of an existing order submission returns the saved order with 200. Reusing its localId with a different payload returns 409.

Deeper. The service takes the owner lock and compares the stored order snapshot. A closed submission is handled separately. Apply-to-stock has its own guard: a second apply to an already applied order returns the existing result without incrementing inventory again.

idempotency

36Is "one request = one transaction" true here?advanced

Short answer. Not as a blanket rule. get_db gives one session per request; handlers commit explicitly, and a later refresh starts a second transaction, which get_db commits at teardown. The AI routes use their own short sessions.

Deeper. A session is a unit of work that can span several transactions. What matters: everything that must be atomic (the change and its history rows) commits together, and nothing after the commit can undo it.

transactionssqlalchemy

37What does the client do on a timeout?intermediate

Short answer. Each request has a 90-second overall deadline. A timeout tells the person "the server may still be processing it" and asks them to check the latest data before retrying.

Deeper. The client never assumes a timeout means nothing was saved. Mutation hooks invalidate the affected queries after uncertain failures so the screen shows the server's truth.

reliabilitymobile

38How do you know which request caused an error?intermediate

Short answer. Every response carries an X-Request-ID, either the client's (if short and printable) or a new random one; logs and errors can be matched by it.

Deeper. Logging redacts tokens in URLs and messages and replaces exception messages with type and code location. Sentry, when configured, sends no request bodies, no personal data and no trace headers to AI providers.

observability

39What happens during a cold start?basic

Short answer. The first requests wait for an instance. The app's start-up waits 8 seconds for the profile; if that times out it keeps the cached session, shows a "server warming up" status and retries in the background.

Deeper. render.yaml's comment says the paid starter plan was chosen to avoid free-tier spin-down; the cold-start handling remains for database wake-ups and restarts.

reliabilitymobile

40What is the consistency model of the system?advanced

Short answer. Strong for writes within PostgreSQL transactions; the phone's reads are eventually consistent because they come from a cache refreshed on focus, reconnect, mount after 30 seconds, or after a write.

Deeper. There are no replicas, so the server itself reads its own writes. The window of staleness is on the client and is bounded by refetch triggers rather than by time alone.

consistency

41Where could data still go wrong?advanced

Short answer. A lost reply after commit (the person may retry a non-idempotent action), a person acting on a stale screen before a refetch, and race windows in flows that are not version-checked.

Deeper. Creates other than orders have no idempotency key; category and item names use a lock and a duplicate check rather than a unique index for legacy reasons. Say these plainly and mention the next step for each.

Security overview

42How do authentication and sessions work, briefly?basic

Short answer. Login verifies an Argon2id password hash and returns a 30-minute access JWT and a 30-day refresh JWT. Each request sends the access token; refresh rotates both tokens; password changes end every session.

Deeper. Both tokens are signed with HS256. The refresh token's jti has a database row so it can be revoked; the user's session_version is in every token and compared on each request.

securityauthjwt

43Are JWTs encrypted?basic

Short answer. No. They are signed (HMAC-SHA256), not encrypted; anyone holding one can base64url-decode its header and claims. That is why they carry only ids, times, a type and a counter.

Deeper. Integrity comes from the signature: changing one character breaks verification. Confidentiality comes from TLS on the wire and SecureStore on the phone.

securityjwt

44How are passwords stored?basic

Short answer. As Argon2id hashes from passlib: memory 64 MiB, 3 iterations, 4 lanes, a random 16-byte salt and a 32-byte hash, all inside one encoded string. Never encrypted, never logged.

Deeper. Hashing runs in a worker thread so the event loop stays free. bcrypt is accepted only to verify old hashes.

securityhashing

45What is encrypted in CareKosh?intermediate

Short answer. Traffic (TLS), tokens on the phone (SecureStore), and personal Sarvam and OpenAI API keys in the database (Fernet). Other columns are stored in plain form inside the provider's storage.

Deeper. Fernet is used only where the server must recover the original value later. Passwords and one-time tokens are hashed instead, because the server never needs them back.

securityencryption

46What is rate limited?intermediate

Short answer. Hosted API workers share Redis counters. Sensitive authentication routes use a client key. Authenticated AI requests use an account key. Provider budgets use PostgreSQL.

Deeper. The exhausted quota produces 429 and Retry-After. Protected routes return 503 when the store is unavailable. Selected reads allow an explicit fail-open policy. The in-memory limiter is available for development and tests.

securityrate-limiting

47What would you add to security next?intermediate

Short answer. Refresh-token reuse detection, a way to end access tokens at logout, monitored shared limiter capacity, MFA, and a password policy aligned with NIST SP 800-63B-4 (length and a breached-password check instead of composition rules).

Deeper. Book 3 has the details and the evidence for each gap.

System design and scaling

48How would you scale CareKosh to 10,000 active families?advanced

Short answer. Measure first. Then add API instances (the app tier is stateless), put a connection pooler in front of PostgreSQL, add indexes and cursor pagination where queries grow, and move email to a durable queue.

Deeper. The likely first limit is database connections: each instance can open up to 30. Next are login bursts, because Argon2 is deliberately expensive. Rate limiting needs a design review before scaling out. Push notifications would replace polling-style refetches.

Avoid saying. Quoting throughput numbers that were never measured.

scalingsystem-design

49Why not cache on the server?intermediate

Short answer. Every read is per-user and changes on every write, so a shared cache would mostly hold small, private, quickly invalidated data. The client cache already avoids repeated reads.

Deeper. A server cache becomes worth it for shared or expensive reads, which CareKosh does not have yet. It would also add an invalidation problem across instances.

cachingsystem-design

50Why no message queue?intermediate

Short answer. The only background work is sending a few emails. FastAPI's BackgroundTasks runs them in the same process after the reply, which is enough at this size.

Deeper. The trade-off is durability: if the process dies after replying, that email is lost, and there is no retry. A queue with a worker would fix that and is the first thing to add if email becomes critical.

system-designbackground

51How would you add offline editing?advanced

Short answer. Carefully: a local outbox of mutations, each with an idempotency key and the version it was based on, replayed in order when online, with explicit conflict screens when the server returns 409.

Deeper. The server already supports two pieces (version checks and idempotent orders). The app deliberately does not queue offline writes today, because silent replay of stale edits caused the original data-loss incidents.

offlinesystem-design

52How would you support several caregivers with separate accounts on one inventory?advanced

Short answer. Introduce a household (tenant) table, move ownership from user_id to household_id with memberships and roles, and change every query's scope from user to household.

Deeper. It touches every table, the migrations, the audit model and authorization (roles such as viewer or editor). The optimistic-concurrency design already handles concurrent editors.

system-designauthorization

53Where are the single points of failure?intermediate

Short answer. The single PostgreSQL database, the single region, and the outside providers for email and AI. The API tier can run more instances.

Deeper. Neon offers point-in-time restore within a plan-dependent window, and the repository has a restore-drill script (scripts/restore_drill.py) for rehearsing it on a separate database. Multi-region would be overkill at this scale.

reliabilitysystem-design

54What would you monitor in production?intermediate

Short answer. Error rates by status code (especially 5xx, 401 and 403 spikes, 409 rates), latency, database connection use and lock waits, order-creation errors, email send failures and AI budget refusals.

Deeper. Today there is Sentry when configured, request ids and redacted logs; a monitor template exists for uptime checks of /live and /health. Metrics and alerts are the next step.

55Why PostgreSQL rather than a NoSQL database?basic

Short answer. The data is relational and the correctness rules are transactional: owner foreign keys, cascades, check constraints, unique indexes, row locks and multi-row atomic updates.

Deeper. A document store would push those guarantees into application code. PostgreSQL also gives JSONB for the audit snapshots where flexibility helps.

The assistant

56How does the AI assistant work without writing data?intermediate

Short answer. Speech is recognised on the phone, the person reviews the words, a local parser handles familiar commands, and only unfamiliar text from a consenting user may go to Groq, which returns a strict JSON plan that the server and phone validate and run against cached inventory.

Deeper. The AI routes have no tools and no write access to inventory or orders. Orders can be drafted but only saved by a touch on Create Order.

57How are AI costs controlled?advanced

Short answer. Before any provider call, reserve() takes a short PostgreSQL transaction under a global advisory lock and checks consent, daily budgets per user and globally, daily request counts and concurrency, then inserts a reserved usage row.

Deeper. settle() records a successful call at an estimated cost, never above the reservation, and keeps the whole reservation for failures and cancellations, because the provider may still bill them. Limits reset at 00:00 UTC.

58What data goes to AI providers?intermediate

Short answer. Only what the person consented to for that provider: reviewed question input to the selected Groq or OpenAI interpreter, optional audio to Groq or Sarvam for transcription, and answer text to Sarvam for narration. Never the inventory dataset.

Deeper. Consent has a version and scopes such as groq_text and sarvam_speech; the server re-checks it under the budget lock. Each scope is off unless server flags, a data-controls review flag and keys are set.

Deeper. Classifying it this way stops it from looking like a mandatory layer of the system when you draw the architecture.

5.1 Glossary

ASGI
The asynchronous interface between a Python web server (Uvicorn) and an application (FastAPI).
Access token
A short-lived signed JWT sent on every request as Authorization: Bearer ….
Refresh token
A longer-lived signed JWT used once to obtain a new token pair; its jti has a database row so it can be revoked.
Optimistic concurrency
Writers do not lock while reading; each write states the version it read and fails if the row changed.
Idempotency key
A client-generated id (localId) that makes repeating the same request safe.
Partial unique index
A unique index that only covers rows matching a condition.
Advisory lock
A PostgreSQL lock on an application-chosen number; here held until the transaction ends.
Liveness vs readiness
Liveness: the process answers (/live). Readiness: it can do useful work, including reaching the database (/health).
Migration
A versioned schema change applied by Alembic in order.
EAS profile
A named build configuration in eas.json that fixes the API address and package type.
TanStack Query
A client library that caches server data, refetches it and invalidates it after writes.
SecureStore
Expo's encrypted key-value storage (Android Keystore; iOS Keychain).
Argon2id
A memory-hard password-hashing function (RFC 9106).
HS256
HMAC with SHA-256: a shared-secret signature for JWTs.
Fernet
Authenticated symmetric encryption (AES-128-CBC with an HMAC-SHA256 tag) from the cryptography library.
BOLA
Broken object-level authorization: reading or changing another user's object by its id.
