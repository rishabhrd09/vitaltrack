Part 1 · Concepts

Security foundations, mapped to the code

In short: most security interview mistakes are vocabulary mistakes. Learn the five tools (encoding, fast hash, password hash, encryption, signature), the three meanings of "session key", and exactly which one CareKosh uses where.

1.1 Authentication versus authorization

  • Authentication answers "who are you?": the password at login, then a signed token on every request (get_current_user).
  • Authorization answers "what may you do?": in CareKosh, "only your own rows", enforced by filtering every query on user_id; plus consent scopes for the optional AI providers.
  • Identity: a users row with an email (required at registration) and an optional username; either can be used to log in.

The status codes follow that split: 401 means "not authenticated" (missing, invalid or expired token, or a revoked session); 403 means "authenticated, but not allowed" (disabled account, unverified email when required, missing AI consent); 404 hides another user's row.

1.3 Password hashing, salt and pepper

A password hash must make guessing expensive, because people choose guessable passwords and stolen hash databases are attacked offline. Three properties do that:

  • Salted: a random value mixed into each hash, so equal passwords give different hashes and precomputed tables are useless. The salt is not secret.
  • Slow: many iterations, so each guess costs time.
  • Memory-hard: each guess also needs a lot of memory, which makes GPU and ASIC attacks expensive. Argon2id (RFC 9106) is designed for this.

  • No separate salt column: the salt and the parameters travel inside the string, so verify can recompute the hash with the same settings.

  • Hashing the same password twice gives two different strings, and verify_password accepts both. Reproduced on 21 November 2026.
Trade-offs and limits

Legacy bcrypt hashes are never upgraded: the code does not call needs_update or verify_and_update, so an old bcrypt hash changes only when its owner changes or resets the password. With bcrypt 4.2.1, passlib 1.7.4 logs a harmless "(trapped) error reading bcrypt version" warning, a sign that passlib (last released in October 2020) is no longer maintained. bcrypt also only uses the first 72 bytes of a password.

One-time tokens: 32 random bytes from the operating system, sent raw in the email; only the SHA-256 digest is stored.

  • Entropy: 32 bytes is 256 bits. Even at a trillion guesses per second, guessing one would take longer than the age of the universe, so a fast hash (SHA-256) is enough. Passwords, by contrast, have low entropy and need Argon2.
  • Why store a digest: a copy of the database would not contain usable links.
  • Single use: consuming a token clears or conditionally updates its column, and each has an expiry checked in SQL: 24 hours for verification, 1 hour for password reset, 24 hours for account deletion.

1.5 Symmetric, asymmetric and HMAC: why HS256

  • Symmetric cryptography uses one shared key for both operations; asymmetric uses a private key to sign and a public key to verify.
  • HMAC-SHA256 (HS256) combines a secret key with SHA-256 to produce a tag that only a key holder can make.
  • HS256 fits CareKosh because the same service issues and verifies tokens. RS256 or ES256 fit when other services must verify tokens without being able to mint them.
  • Algorithm allow-list: decoding passes algorithms=[settings.JWT_ALGORITHM], so a token claiming another algorithm (for example none) is rejected, as RFC 8725 recommends.

1.6 Sessions versus tokens, and the anatomy of a JWT

Classic web apps keep a server-side session and give the browser a random session id in a cookie. CareKosh uses a separate HttpOnly browser refresh cookie. Its native app and authenticated inventory endpoints use bearer tokens in the Authorization header instead: whoever holds the token can use it, which is why it lives in SecureStore and travels only over TLS.

Don't say

"JWTs are encrypted." A signed JWT (JWS) is readable; RFC 7519 points to encryption (JWE) or keeping sensitive data out of the token. CareKosh keeps only ids, times, a type and a counter in it.

1.7 Three things people call a "session key"

  1. TLS session keys are symmetric keys negotiated in each TLS handshake (TLS 1.3 uses an ephemeral Diffie–Hellman exchange and an HKDF key schedule), so every connection gets fresh keys and past traffic stays safe even if a server key leaks later (forward secrecy). They exist between the public client and Cloudflare for the proxied API; application code never sees them.
  2. SECRET_KEY is the server's long-lived HMAC key. It signs every token for every user, so it is a master secret, not a session key. Rotating it would sign everyone out.
  3. The application session is what the product calls "being logged in": a refresh_tokens row (identified by the token's jti, with an expiry and a revoked flag) plus the user's session_version. The database records refresh-token state. The browser transports its refresh token in a host-only HttpOnly cookie.
Say it in the interview

"If you mean the TLS session key, that's negotiated per connection and terminated at Cloudflare for a proxied public request. Our application session is a refresh-token row plus a session_version counter on the user; the signing key is a single long-lived secret that we never put in the app."

1.8 Transport security: HTTPS and HSTS

  • Where TLS ends: The supplied DNS inventory shows proxied API CNAMEs. The public client negotiates TLS with Cloudflare. Cloudflare connects to the Render origin, which forwards the request to the container. Verify the active origin TLS policy in the dashboard.
  • Database leg: the API connects to Neon with TLS (ssl=True) outside development and testing.
  • Phone: production and preview builds must use HTTPS URLs; cleartext HTTP is allowed only in development builds (app.config.js).
  • HSTS (max-age=31536000; includeSubDomains) is sent in production and staging. It matters for browsers that open the email-link pages; a native client ignores it.

1.9 Browser policies: CORS, CSRF, XSS and security headers

Browser refresh uses a host-only HttpOnly cookie. Hosted environments use Secure and SameSite=Strict and limit the cookie path to the web-auth endpoints. A native Android request supplies a bearer token explicitly. A browser also uses bearer access tokens for inventory, but its refresh credential can be attached automatically by the browser.

Enabling browser login requires an explicit WEB_APP_ORIGINS list included in CORS_ORIGINS. The cookie endpoint checks the exact Origin and X-CareKosh-Web marker and rejects cross-site fetch metadata. CORS controls browser access across origins. It cannot establish ownership of an inventory item. Server-side authorization still runs on every protected operation.

3.6 App restart (cold start)

After a browser reload the access token in memory is gone. The client can restore a session through cookie-backed refresh. On Android, the startup flow uses secure device storage.

  1. No access token in SecureStore → signed out; show login.
  2. Token present → fetch /auth/me with an 8-second limit. Success → signed in with the fresh profile; the query cache is invalidated so screens refetch.
  3. Timeout (for example a cold server) → stay signed in from the cached state, show a "server warming up" status and retry in the background after 5 seconds.
  4. 401 → the API client tries one shared refresh first; if that also fails, tokens are cleared and the person signs in again. A network error never clears tokens.

The guard in app/_layout.tsx redirects to (auth)/login whenever the store says signed out, and to (tabs) when signed in.

Say it in the interview

"Authorization is ownership. Every query filters on the current user's id from the token, so there's no code path where a client-supplied id can reach another account's row; it just isn't found."

5.1 Fernet for personal provider keys

app/services/sarvam_credentials.pylines 22–33 · exact copy at a14b623
22  def cipher() -> MultiFernet:
23      primary = settings.AI_CREDENTIAL_ENCRYPTION_KEY.get_secret_value()
24      previous = settings.AI_CREDENTIAL_PREVIOUS_ENCRYPTION_KEYS.get_secret_value()
25      try:
26          keys = [primary, *[key.strip() for key in previous.split(",") if key.strip()]]
27          if not primary or len(keys) > 4:

32              503, "Personal key storage is not configured on this backend."

The cipher: a primary key plus up to three previous keys, so keys can be rotated without breaking stored ciphertexts.

  • Fernet (from the cryptography library) is authenticated encryption: AES-128 in CBC mode with a random IV, and an HMAC-SHA256 tag over the version byte, timestamp, IV and ciphertext. A 32-byte key holds a 16-byte signing key and a 16-byte encryption key. Any tampering fails the tag check.
  • Reproduced: two encryptions of the same value differ (random IV); a token starts with the version byte 0x80; MultiFernet decrypts a token made with an older key and rotate() re-encrypts it under the new primary; a ciphertext built for one owner is refused for another with 503.
  • Operational rule: AI_CREDENTIAL_ENCRYPTION_KEY must stay stable across deploys and workers, and must differ from SECRET_KEY. Losing it makes every stored personal key unreadable; people would have to save their keys again.
  • Public metadata never includes the plaintext, the ciphertext, or a prefix or suffix of the key.

Part 6 · Hardening

Abuse protection and hardening

In short: limits on the routes attackers like, caps on request sizes and waiting times, no internals in errors or logs, and a threat model that names what is left.

6.1 Rate limiting

Hosted configurations require shared Redis storage for SlowAPI counters. Development and tests can use memory storage. The edge establishes trusted request identity before the limiter uses it. Browser and mobile login share the login bucket, and their registration routes share the registration bucket. Authenticated AI limits can also use an account key.

An exhausted limit returns 429 with Retry-After. A store outage on a protected fail-closed route returns 503. Selected side-effect-free reads explicitly allow a fail-open policy. These responses diagnose different conditions. Neither one is a reason to clear a valid client session.

2Hashing versus encryption?basic

Short answer. Hashing is one-way: you can only compare. Encryption is reversible with a key. Use hashing when you never need the original (passwords, email tokens) and encryption when you do (a provider key the server must use).

Deeper. CareKosh hashes passwords with Argon2id, hashes one-time tokens with SHA-256, and encrypts personal Sarvam and OpenAI keys with Fernet.

Avoid saying. "We encrypt passwords."

3Encoding versus encryption?basic

Short answer. Encoding (base64url) changes representation and anyone can reverse it; encryption needs a key. A JWT's header and payload are only encoded.

Deeper. Decoding a sample CareKosh access token with plain base64url shows its user id, times, type and session_version; no key is needed. That is fine because nothing in it is secret, and the signature stops anyone changing it.

4What is a salt and why is it needed?basic

Short answer. A random value mixed into each password hash, so identical passwords produce different hashes and precomputed (rainbow) tables are useless. It is not secret.

Deeper. Argon2 generates 16 random bytes per hash and stores them inside the encoded string, so there is no separate salt column. Hashing "Sample-Passw0rd" twice gave two different strings, both verifying.

5What is a pepper? Does CareKosh use one?intermediate

Short answer. A secret value added to every password before or after hashing, stored outside the database (for example in a secrets manager). CareKosh does not use one.

Deeper. A pepper protects hashes if only the database leaks. OWASP describes it as optional defence in depth; it complicates rotation because changing it invalidates every hash unless handled carefully.

6Why Argon2id rather than SHA-256 for passwords?intermediate

Short answer. SHA-256 is fast, so an attacker can try billions of guesses per second on a GPU. Argon2id is deliberately slow and needs lots of memory per guess, which makes offline guessing expensive.

Deeper. CareKosh's parameters are 64 MiB of memory, 3 passes and 4 lanes (argon2-cffi's defaults, above OWASP's minimums), about 24 ms per hash in an earlier laptop measurement.

Short answer. $argon2id is the variant, $v=19 the version, $m=65536,t=3,p=4 the memory (KiB), passes and lanes, then the base64 salt, then the base64 hash.

Deeper. Because the parameters travel in the string, the server can raise them later and still verify older hashes; passlib's needs_update would say when to rehash.

Short answer. A short access token limits the damage if one leaks; a long refresh token, used rarely and only at one endpoint, keeps people signed in and can be revoked through its database row.

Deeper. The access token goes out on every request, to many endpoints and through many logs, so it should die quickly. The refresh token goes to one endpoint, is single-use and revocable, so it can live longer.

55What is refresh-token rotation?intermediate

Short answer. Every use of a refresh token revokes it and issues a new one, so each token works once.

Deeper. RFC 9700 says refresh tokens for public clients (like mobile apps) must be sender-constrained or rotated. CareKosh rotates.

56What is refresh-token reuse detection, and does CareKosh have it?advanced

Short answer. If an already-used refresh token is presented again, the server assumes theft and revokes the whole chain. CareKosh does not: the replay gets 401 but the newer token stays valid.

Deeper. Implementation: a family id shared by rotated tokens; on reuse of a revoked member, revoke every token in the family (RFC 9700 §4.14.2).

81How would you add MFA?advanced

Short answer. Add TOTP or passkeys: enrol with a verified factor, require a second step after the password at login, issue tokens only after both, and provide recovery codes. Refresh would keep working without repeating MFA until the session ends.

Deeper. Rate limiting and lockouts for the second factor, and a recovery path that does not bypass it, are the parts people forget. Passkeys (WebAuthn) would also remove password guessing for users who adopt them.

9.1 Glossary

Salt
A random, non-secret value mixed into each password hash so equal passwords hash differently.
Pepper
A secret value added to every password hash and kept outside the database; not used in CareKosh.
KDF
Key derivation function; Argon2 is a password-hashing KDF, HKDF is used inside TLS 1.3.
PHC string
The $algorithm$version$params$salt$hash format that stores everything needed to verify.
Nonce / IV
A value used once per encryption so equal plaintexts encrypt differently; Fernet uses a random 128-bit IV.
HMAC
A keyed hash that proves integrity and origin to anyone holding the same key.
JWT, JWS, JWE
A JSON Web Token; signed (JWS, readable) or encrypted (JWE). CareKosh uses signed tokens.
sub, exp, iat, jti
Registered claims: subject (user id), expiry, issued-at and token id (RFC 7519 §4.1).
Bearer token
A token whose holder is trusted; sent as Authorization: Bearer … (RFC 6750).
Rotation
Replacing a refresh token with a new one on every use.
Revocation
Making a token unusable before it expires (a revoked row, or a bumped session_version).
Session fixation
Forcing a victim to use a session id the attacker knows; prevented by issuing new credentials at login, as CareKosh does.
CSRF
A forged cross-site request riding on the victim's cookies; not applicable to header-based tokens.
XSS
Injected script in a page; prevented by escaping output in the backend's HTML pages.
HSTS
A header telling browsers to use only HTTPS for a host for a period.
Forward secrecy
A property of TLS 1.3 key exchange: a later key leak cannot decrypt earlier sessions.
Enumeration
Learning whether an account exists from differing responses.
