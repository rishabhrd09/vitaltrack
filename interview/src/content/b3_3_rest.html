Part 4 · Authorization

Authorization and data isolation

In short: every business query includes the signed-in user's id, so one account can never read or change another's rows, and a foreign id looks exactly like a missing one.

Ownership scoping and the 404 policy

{{x:B/app/api/v1/items.py:219-241|Ownership is part of the WHERE clause, not a check after loading. Someone else's item and a non-existent item give the same 404.}}
  • The threat: broken object-level authorization (OWASP API Security Top 10 2023, API1), where changing an id in a URL reaches someone else's data.
  • The rule: the owner comes from get_current_user, never from the request; child rows are reached through their owned parent (order lines through orders; items' categories are checked to belong to the same user).
  • Cross-object checks: an order may only reference items the user owns (400 otherwise); creating an item checks the category's owner.
  • Why 404, not 403: 403 would confirm that the id exists.

"Authorization is ownership. Every query filters on the current user's id from the token, so there's no code path where a client-supplied id can reach another account's row; it just isn't found."

Consent as authorization for third-party processing

Separate the data a person has agreed to send from the credential that pays for the request. Microphone transcription, text interpretation and narration are distinct operations. Provider and consent checks happen before the relevant call. Mobile can select local interpretation or an explicitly enabled cloud option. Personal OpenAI credentials support interpretation. Sarvam credentials support narration.

The backend stores encrypted personal credentials for the owner and exposes status or masked metadata to clients. Keep plaintext keys out of logs, screenshots and frontend build variables. A supply recommendation is a separate workflow. A user explicitly confirms before it becomes a pending order.

Part 5 · Encryption

Encryption and key management

In short: encrypt only what the server must read back later (a personal provider key); hash everything it only needs to check; keep keys in the environment, not the database.

Fernet for personal provider keys

{{fig:fernet-envelope|How a personal Sarvam key is stored: an envelope with owner and provider, encrypted with MultiFernet; only the token is stored; decryption checks the envelope.}} {{x:B/app/services/sarvam_credentials.py:22-33|The cipher: a primary key plus up to three previous keys, so keys can be rotated without breaking stored ciphertexts.}}
  • Fernet (from the cryptography library) is authenticated encryption: AES-128 in CBC mode with a random IV, and an HMAC-SHA256 tag over the version byte, timestamp, IV and ciphertext. A 32-byte key holds a 16-byte signing key and a 16-byte encryption key. Any tampering fails the tag check.
  • Reproduced: two encryptions of the same value differ (random IV); a token starts with the version byte 0x80; MultiFernet decrypts a token made with an older key and rotate() re-encrypts it under the new primary; a ciphertext built for one owner is refused for another with 503.
  • Operational rule: AI_CREDENTIAL_ENCRYPTION_KEY must stay stable across deploys and workers, and must differ from SECRET_KEY. Losing it makes every stored personal key unreadable; people would have to save their keys again.
  • Public metadata never includes the plaintext, the ciphertext, or a prefix or suffix of the key.

Data at rest on the server, and rotating keys

  • Database storage encryption is a property of the hosting provider; the app does not encrypt ordinary columns. {{ev:nv}}
  • Backups contain password hashes, token digests and ciphertexts, never raw passwords, raw email tokens or plaintext provider keys.
  • Rotating SECRET_KEY invalidates every access and refresh token, signing everyone out. A graceful rotation would need several verification keys and a key id (kid) in the token header.
  • Rotating the Fernet key is built in: put the new key first, keep the old one in AI_CREDENTIAL_PREVIOUS_ENCRYPTION_KEYS, re-encrypt, then remove the old key.

Part 6 · Hardening

Abuse protection and hardening

In short: limits on the routes attackers like, caps on request sizes and waiting times, no internals in errors or logs, and a threat model that names what is left.

Rate limiting

Hosted configurations require shared Redis storage for SlowAPI counters. Development and tests can use memory storage. The edge establishes trusted request identity before the limiter uses it. Browser and mobile login share the login bucket, and their registration routes share the registration bucket. Authenticated AI limits can also use an account key.

An exhausted limit returns 429 with Retry-After. A store outage on a protected fail-closed route returns 503. Selected side-effect-free reads explicitly allow a fail-open policy. These responses diagnose different conditions. Neither one is a reason to clear a valid client session.

Hardening measures

  • Request size: ordinary API requests allow 2 MB, Supply Review allows 64 KB, AI JSON allows 12 KB and audio allows 900 KB. AI and Supply Review check for a bearer header before buffering. GET and HEAD /live skip buffering.
  • Timeouts: 8-second statements, bounded provider and email calls, a 90-second client deadline.
  • Errors without internals: generic 500 and 409 messages; SQL parameters hidden; exception messages withheld from logs.
  • Docs hidden unless DEBUG is true.
  • Security headers on every normal response (and on the body-limit refusals); HSTS in staging and production.
  • Least privilege in the container: a non-root user.
  • Safe configuration: unsafe production settings stop start-up; secrets are SecretStr.
  • Privacy-preserving telemetry: Sentry without personal data, bodies, local variables or outbound trace headers.

Part 7 · Honesty

Honest gaps and improvements

In short: each gap below was checked in the code. Interviewers respect a candidate who names them first.

Gaps and next steps

A shared Redis limiter coordinates protected requests across workers. The database connection budget still grows with the number of processes and instances. Before increasing capacity, measure pool usage, lock waits, provider latency, request throughput and error rates under a representative workload.

The request concurrency guard caps work admitted by a single worker. Hosted ingress authentication and browser origin checks address separate boundaries. Review dashboards, secret rotation procedures, backup restoration and installed-client behavior as operational evidence. A source review alone cannot demonstrate that these controls are configured correctly for a particular deployment.
