Part 3 · Request journeys and system design

How a request flows

In short: if you can trace one save from the button to PostgreSQL and back, naming every layer and every way it can fail, you can answer most system-design follow-ups about this project.

The life of one request: saving an edited item

Open a saved item and change quantity from 10 to 8. The browser or Android editor sends the item fields and its opened version in an authenticated PUT. The backend checks ingress, request limits, the bearer token and account ownership. A scoped database session carries the mutation. Updating a deleted or unowned item returns 404. A stale version returns 409.

On success the API returns the updated item. Reopen it after a reload to verify the saved quantity. A successful CORS preflight only proves that the browser may send the actual request.

Signing in and staying signed in

Android signs in through /api/v1/auth/login, keeps the access and refresh tokens in secure device storage and sends a bearer access token for data requests. Browser login uses /api/v1/web-auth/login. The browser holds the access token in memory, and the API sets a scoped HttpOnly refresh cookie. On reload the browser can renew its session through the refresh endpoint.

Both clients call the same owner-scoped inventory handlers. A valid token identifies an account. The query must still constrain every item to that account. Password changes and resets advance the user’s session_version and revoke refresh tokens. Browser logout revokes its browser session family and clears the cookie.

Orders: safe retries and atomic restocking

A phone that loses the response after placing an order cannot infer whether the database committed. Send the same localId and the same saved fields. On the first submission the API takes the owner’s supply-revision lock, checks ownership, allocates the order number and saves the order. A matching replay returns 200. Different notes or persisted line fields under that key return 409. An explicitly closed interrupted submission also returns 409.

{{x:B/app/services/orders.py:135-147|The owner lock and replay check happen before a new order is allocated.}}

Pending can become ordered, received or declined. Ordered can become partially received, received or declined. Partially received can become received or declined. An unapplied received order can still be declined. Applying a received order checks its items and units and updates stock in one transaction. A missing item or changed unit returns 409 with no partial credit. A replay of a completed apply returns 200 and adds nothing. Only pending and declined orders are deletable.

Two phones edit the same item

Two editors open one item at quantity 10 and version 3. One saves quantity 8 with version 3. The transaction succeeds and increments the version to 4. The other submits version 3 and receives 409. Inventory remains at 8. Read the current values and make a fresh decision before retrying.

Both user-facing editors send PUT /api/v1/items/{item_id}. The request carries the version captured when the editor opened. The separate stock-only PATCH is available to API callers. The owner supply-revision lock coordinates cooperating writers. The conditional UPDATE includes the item, owner and submitted version. Success also writes the related activity and audit records in the transaction.

The phone's cache is a copy, never a database

{{fig:sd:mobile-cache|The phone's copy of the data: TanStack Query in memory, persisted to AsyncStorage for fast start-up, refreshed from the server; writes always go to the server.}}
  • Reads: stale after 30 s, kept for 24 h, retried 3 times; queries use networkMode: 'offlineFirst'.
  • Writes: networkMode: 'always' and retry: 0. A save is attempted at once and never queued for later replay, so the app cannot replay an old edit over newer data.
  • Privacy on shared phones: the persisted copy excludes auth queries, uses the app version as a "buster", and is cleared at login and at logout.

An assistant question (conditional feature)

Ask Care Coach is a constrained assistant, not an agent with tools. The phone records and transcribes speech on the device, shows the words for review, and tries a local parser first. Only an unfamiliar question, from a person who opted in, on a server where AI is enabled and reviewed, goes to POST /api/v1/ai/interpret. The configured interpreter (Groq by default, OpenAI when enabled) returns structured data; the server checks it again; the phone runs it against cached inventory data.

  • Read-only by design. The AI routes never write inventory or orders. They write only consent and usage metadata, and encrypted credentials when a person saves a supported personal provider key.
  • Defaults are offline. Device speech is the default voice; Alba and Kokoro voices are only offered in a diagnostics build.
  • Cost and abuse control live in PostgreSQL: daily budgets, request counts and per-account concurrency, checked under a short advisory lock before any provider call.

Capacity, honestly

This review established no system-wide throughput figure, so never quote a requests-per-second figure. Reason from the design instead:

  • Database connections are the first hard limit: 2 workers × (5 + 10) = up to 30 per instance, and a deploy briefly runs old and new instances side by side.
  • Argon2 deliberately costs 64 MiB of memory per hash with these parameters; an earlier laptop measurement took about 24 ms. Login bursts are CPU- and memory-bound; that is the price of password safety.
  • Eager loading. The User model loads its collections with selectin. Auth paths disable that with noload("*") because loading every item and order on each request would grow with the account.
  • Lists. GET /items is paginated (up to 100 per page) and the app fetches all pages; activities are capped at 200. Large accounts would need cursor pagination.

"I haven't load-tested it, so I won't quote throughput. The first limits I'd watch are database connections per instance and Argon2's CPU and memory during login bursts. The app tier is stateless, so I'd add instances behind a connection pooler before changing the design."
