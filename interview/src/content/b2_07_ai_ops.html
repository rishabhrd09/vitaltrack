Part 7 · Case study

The AI feature as a backend design case

In short: the AI routes give the phone optional cloud help with interpreting, transcribing and speaking. They are off by default, consented per provider, budgeted in PostgreSQL and unable to change inventory. Classify every piece as conditional.

Shape and gating

Each provider path is enabled only when several independent settings agree: AI_ENABLED, the kind (AI_TRANSCRIBE_ENABLED, AI_SPEECH_ENABLED), a "data controls reviewed" flag for that provider, and a key. A missing piece gives 503 "This AI feature is unavailable", and the phone falls back to on-device behaviour.

The per-route limits are keyed by the authenticated account ({{s:B/app/utils/rate_limiter.py#authenticated_ai_rate_key}}), which is set by the AI routes' own authentication dependency. Shared budgets and concurrency are enforced in PostgreSQL, across all workers.

Reservation and settlement

{{fig:ai-guard|One cloud AI request: refuse early, authenticate in a short session, reserve under a global advisory lock, call the provider without holding a database connection, then settle.}} {{x:B/app/services/ai_guard.py:177-192|The start of reserve(): a short transaction, a bounded lock wait, the global budget lock and a consent re-check under that lock.}}
  • Why a lock: budgets and concurrency limits are "count, compare, insert". Without one lock around them, two workers could both see room for one more call.
  • Why short: the transaction ends before the provider call, so a 25-second provider wait never pins a pooled connection.
  • Why "busy" instead of waiting: a lock wait over a few seconds, or a cancelled statement, becomes 503 "AI is busy" with Retry-After: 5.
  • Settlement: success is charged an estimated cost from published prices, never above the reservation; failures and cancellations keep the whole reservation because the provider may still have billed them. Daily limits reset at 00:00 UTC.

Provider calls and grounding

{{x:B/app/services/ai_provider.py:348-386|Interpretation: temperature 0, a strict JSON schema derived from the Pydantic model, a finish-reason check, Pydantic validation, then lexical grounding for version-3 plans.}}
  • No tools, no data: the model receives the question and one flag, never the inventory, and can only return JSON that matches the schema.
  • Portable schema: only features Groq documents for strict mode are sent; const becomes a one-value enum.
  • Grounding: {{s:B/app/services/ai_provider.py#ground_plan}} rejects plans that drop, invent or regroup conditions the question did not contain, for example numbers, exclusions or item names. It is a conservative lexical check that fails closed, not proof that the meaning is right.
  • Bounded calls: a total deadline (AI_TIMEOUT_SECONDS, default 25) plus connect and read timeouts, and a response-size cap.
  • Cancellation: when the phone disconnects, the route cancels the provider task and answers 499, a non-standard code borrowed from nginx for "client closed request".

Personal provider keys

Separate the data a person has agreed to send from the credential that pays for the request. Microphone transcription, text interpretation and narration are distinct operations. Provider and consent checks happen before the relevant call. Mobile can select local interpretation or an explicitly enabled cloud option. Personal OpenAI credentials support interpretation. Sarvam credentials support narration.

The backend stores encrypted personal credentials for the owner and exposes status or masked metadata to clients. Keep plaintext keys out of logs, screenshots and frontend build variables. A supply recommendation is a separate workflow. A user explicitly confirms before it becomes a pending order.

Part 9 · Operations

Reliability and operations

In short: every wait has a limit, every error is logged without its secrets, and the platform's health check cannot be fooled into restarting a healthy process.

Logs, request ids and error reporting

  • Redaction at the source. {{s:B/app/core/logging.py#configure_safe_logging}} installs a log-record factory that runs for every handler: tokens in verification and deletion paths and token, access_token, refresh_token and password query values become [REDACTED]; access-log URLs lose their query strings; exceptions keep their type and code locations but not their messages.
  • Correlation. Normal application responses carry an X-Request-ID; a client-supplied id is echoed only if it is short and printable.
  • Sentry (only with a DSN): 10% trace sampling, send_default_pii=False, no request bodies, no local variables, no trace headers sent to outside services, and a scrubber that keeps only the URL path and method and withholds exception messages.

Part 10 · Testing

Testing: what the suite proves

In short: the migrated-schema run passed 975 backend tests with two skips. CI also exercises a model-created schema, and runs integration requests through the ASGI app. Concurrency tests submit overlapping requests.

Test strategy

Run backend integration and unit tests against a disposable local PostgreSQL database. CI exercises a schema created from models and a schema built with Alembic. The migration path matters because indexes, constraints and seeded state can differ from a model-only schema. The versioned route gate expects 65. The workflow also enforces a 70% coverage floor on six selected inventory, order and supply modules.

For this review the full backend suite on the migrated schema passed 975 tests and skipped two. Android Node tests passed 491 and web unit tests passed 103. Those counts describe local suites and exclude installed-device and hosted acceptance.

Part 11 · Workflow

How development is done

In short: run the API and PostgreSQL locally, test against a disposable database, open a pull request, let CI judge, and release migrations through a gate.

Local setup

  • Docker Compose: {{p:B/docker-compose.dev.yml}} runs the API with hot reload (code mounted into the container) and postgres:16-alpine; {{p:B/docker-compose.yml}} runs the production image locally, plus optional pgAdmin.
  • Or a virtual environment: Python 3.12, pip install -r requirements.txt, a local PostgreSQL 16, uvicorn app.main:app --reload.
  • Configuration: {{p:B/.env.example}} lists every variable; exported environment variables override .env.
  • Tests: ENVIRONMENT=testing, a SECRET_KEY of at least 32 characters and a DATABASE_URL whose database name contains "test"; then python -m pytest tests/ unit_tests/ -q, and again with --migrated-schema.

Quality tools and the Git workflow

Open a pull request to main and record the revision you test. Backend and Android CI runs for pull requests targeting main, pushes to main and manual dispatch. Web checks use a separate path-filtered workflow. A build-apk label on an eligible PR requests an Android preview build.

Before using a merge-first release sequence, verify production Render’s native auto-deploy and the production Worker’s Git deploy command. The optional Render CI hook requires passing test jobs, a push to main, ENABLE_RENDER_AUTO_DEPLOY=true and a configured hook secret. A hook acknowledgment means Render accepted the request. Confirm the live SHA in Render.

Advance staging to the candidate and test the affected user journey. Publish the production web build with Release CareKosh web on main. If main moved, test that revision first. API and Android releases use their own service and Play controls. A working screen, a tested commit and a live deployment each supply different evidence.
