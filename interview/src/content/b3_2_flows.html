Part 2 · Data

The identity data model

In short: one users row per account, one refresh_tokens row per login session, digests instead of raw tokens, and secrets that live only in each service's environment.

Tables and columns

ColumnMeaning
users.email, users.usernameUnique; at least one must be set (CHECK email_or_username). Registration now requires an email; username-only rows are legacy.
users.hashed_passwordArgon2id encoded string (salt and parameters inside), or a legacy bcrypt hash
users.session_versionGeneration number copied into every token; incremented by password change and password reset (migration 0007)
users.is_active, users.is_email_verifiedDisabled accounts get 403; verification may be required for accounts with an email
email_verification_token + _expirySHA-256 digest of the emailed token; 24 hours
password_reset_token + _expirySHA-256 digest; 1 hour
deletion_token + deletion_token_expiresSHA-256 digest; 24 hours

Every account flow, end to end

In short: each flow below has a diagram (phone, API, PostgreSQL), the exact code, the failure branches with their status codes, and what is stored where afterwards.

Registration

Browser registration returns the user and verificationRequired. It issues no browser login cookie here. The native endpoint has its own response contract.

{{fig:flow-register|Registration: validate, check uniqueness, create secrets, insert and commit, reply, then send the email in the background.}} {{x:B/app/api/v1/auth.py:154-175|The verification token and the Argon2 hash are created before the user row; only the digest is stored.}}
FailureStatus
Rate limit (3 per hour per client key)429
Invalid email, weak password, bad username422
Email or username taken400 "Email already registered" / "Username already taken"
Stored where afterwards

Database: the user (Argon2id hash, verification digest and expiry), one refresh-token row, an activity row. Phone: nothing: the app deliberately discards the tokens the API returned and shows "check your email". Inbox: the raw token inside the link.

The 400 messages reveal whether an email is registered (account enumeration), while forgot-password and resend do not. That is a usability trade-off; a privacy-first design would always answer "check your email".

Email verification

{{fig:flow-verify|Email verification: the link opens the API's own page; one conditional UPDATE matches the digest and expiry, marks the email verified and clears the token.}} {{x:B/app/api/v1/auth.py:87-97|Single use in one statement: the UPDATE only matches an unexpired digest, and clears it while setting the flag.}}
  • Two endpoints: GET /auth/verify-email?token=… returns an HTML page (the email link); GET /auth/verify-email/{token} returns JSON for the app.
  • Enforcement happens only when REQUIRE_EMAIL_VERIFICATION is true and mail is configured, and only for accounts with an email. Hosted startup refuses a blank mail credential when verification is required. Login, refresh and authenticated request checks enforce the account policy.
  • Resend answers the same generic message whether or not the account exists, replaces the digest (so older links stop working) and returns 503 if mail is not configured.

Login

The browser posts to /api/v1/web-auth/login. The response exposes an access token to the frontend and sets a refresh cookie scoped to /api/v1/web-auth. The Android diagram below shows the native token-pair transport.

{{fig:flow-login|Login: normalise the identifier, lock the user row, verify Argon2 in a thread, check status, mint two tokens, record the session and commit.}} {{x:B/app/api/v1/auth.py:256-290|Lookup, verification and status checks. A wrong password and an unknown account get the same 401 message.}}
FailureStatus
Rate limit (5 per minute per client key)429
Unknown identifier or wrong password401 "Incorrect email/username or password"
Disabled account403 "Account is disabled"
Email not verified (policy on)403 "EMAIL_NOT_VERIFIED"; the app offers to resend
Stored where afterwards

Database: a new refresh_tokens row (jti, expiry, User-Agent, socket address), last_login, an activity row. Phone: both tokens in SecureStore; the user and isAuthenticated in the Zustand store (persisted through SecureStore); the previous user's query cache cleared.

Why lock the user row at login? Login, refresh, password change and reset all lock the same row first, so issuing new tokens and revoking old ones happen in a single order: a login cannot slip a new token past a concurrent password reset.

What happens during a session

{{fig:flow-request|An authenticated request: bearer header, signature and expiry, token type, user row and session_version, status and policy, then an owner-scoped query.}} {{x:B/app/api/deps.py:37-86|get_current_user: every check in order.}}
  • Cost: one HMAC verification and one indexed primary-key lookup per request.
  • Why the lookup: it makes revocation immediate. If the password changed, session_version no longer matches and the request gets 401 at once, without waiting for the token to expire.
  • Inside handlers: the user comes from this dependency, never from the request body, and every business query filters on that user's id.

Access-token expiry and refresh

For browser refresh, the cookie travels with the request and the frontend supplies its browser marker. A successful response rotates the cookie and replaces the in-memory access token. Android submits its refresh token explicitly.

{{fig:flow-refresh|Refresh: one shared refresh on the phone; on the server, lock the user, claim the refresh token once, issue and store a new pair.}} {{x:B/app/api/v1/auth.py:791-814|The claim: only one request can flip is_revoked from false to true for a given jti.}} {{x:M/services/api.ts:146-205|The phone's side: a credential "epoch" stops a slow refresh from writing tokens back after a logout; one shared promise serves every waiting request; tokens are deleted only on 401 or 403 from the refresh call.}} {{fig:token-timeline|A session over time with the default lifetimes: login, a refresh, a replayed old refresh token, logout, and the alternative of a password change.}}
  • Sliding window: every refresh issues a refresh token with a new 30-day expiry, so a phone used at least once a month stays signed in; there is no absolute session limit.
  • No reuse detection: presenting an already-rotated refresh token gets 401, but its successor stays valid. RFC 9700 recommends revoking the active token in that case, because the server cannot tell the attacker from the real client.
  • Refresh has no rate-limit decorator: each attempt needs a valid, signed, unrevoked token, so guessing is not possible.

App restart (cold start)

After a browser reload the access token in memory is gone. The client can restore a session through cookie-backed refresh. On Android, the startup flow uses secure device storage.

  1. No access token in SecureStore → signed out; show login.
  2. Token present → fetch /auth/me with an 8-second limit. Success → signed in with the fresh profile; the query cache is invalidated so screens refetch.
  3. Timeout (for example a cold server) → stay signed in from the cached state, show a "server warming up" status and retry in the background after 5 seconds.
  4. 401 → the API client tries one shared refresh first; if that also fails, tokens are cleared and the person signs in again. A network error never clears tokens.

The guard in {{p:M/app/_layout.tsx}} redirects to (auth)/login whenever the store says signed out, and to (tabs) when signed in.

Logout

Browser logout expires the refresh cookie and revokes refresh rows for the matched browser family. Android revokes the presented refresh row. Already-issued access tokens still follow their expiry and account session-version checks.

{{fig:flow-logout|Logout: immediate local cleanup, then a best-effort background revocation of one refresh token. The access token keeps working until it expires.}} {{x:M/services/auth.ts:31-38|The phone clears tokens first and never waits for a sleeping or unreachable server.}} {{x:B/app/api/v1/auth.py:852-888|The server side: requires a valid access token, revokes the matching refresh row and logs the activity.}}
The logout window

Logout does not revoke the access token: a copy of it would keep working until its exp (at most 30 minutes by default). Options: a shorter access lifetime, a jti denylist checked in get_current_user, or a "log out everywhere" action that increments session_version. A password change or reset already ends every session immediately.

On the phone, logout also clears the TanStack Query cache in memory and its AsyncStorage copy, so the next person on a shared family phone cannot see the previous inventory.

Changing the password

{{x:B/app/api/v1/auth.py:1202-1239|Change password: lock and re-check the session, verify the current password in a thread, store a new hash, bump session_version, clear pending tokens and revoke every refresh row.}} {{x:B/app/api/v1/auth.py:65-74|_lock_current_user: re-reads the user under a row lock and refuses if the session generation changed while the request waited.}}
  • A wrong current password returns 400 (not 401), so the app does not treat it as an expired session.
  • Every device, including this one, must log in again: the response says so, and the old tokens fail at their next use.

Forgot and reset password

{{fig:flow-reset|Forgot and reset: a generic reply, a one-hour single-use link, then a new hash and the end of every existing session.}} {{x:B/app/api/v1/auth.py:707-740|Reset: the token is matched by digest, expiry and active status under a row lock; the new hash, the cleared token, the generation bump and the revocations commit together.}}
  • Anti-enumeration: forgot-password gives the same message for unknown, disabled and real accounts.
  • Two ways to submit: the API's HTML form at GET /auth/reset-password (hidden from the schema) and the app's reset screen both post to POST /auth/reset-password, rate limited to 5 per hour per IP.
  • Notification: a "password changed" email goes out in the background, so the real owner learns about an unexpected reset.

Account deletion

{{fig:flow-delete|Account deletion: request in the app, confirm from the email; the confirmation deletes the user and the database cascades remove every owned row.}} {{x:B/app/api/v1/auth.py:1146-1173|Confirmation: find the user by digest and expiry under a lock, delete, commit, and show a completion page.}}
  • Why two steps: a stolen access token alone cannot delete the account; the attacker would also need the inbox.
  • Why GET only shows a page: mail scanners and link previews fetch URLs; a GET that deleted the account could fire without a human click. The deletion happens only on the form's POST.
  • Accounts without an email cannot use this flow (400 with a support address).

Profile updates

PATCH /auth/me locks the user row, then allows a new unique username, a name and a phone number. Changing the email is refused with 400 "To change your email, contact support." This rule also applies to the browser client. Read {{p:B/app/api/v1/auth.py}} before adding an email-change form. {{ev:code}}
