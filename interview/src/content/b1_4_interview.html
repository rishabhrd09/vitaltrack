Story bank (situation, task, action, result)

These are historical events from the project's dated notes ({{p:docs/PROJECT_LEARNINGS_AND_JOURNEY.md}}, {{p:docs/TECHNICAL_CHALLENGES.md}} and the 8 October review). Dates are the team's notes, not independently verified. {{ev:hist}}

Silent overwrites → optimistic concurrency

Situation: on 4 April 2026 two caregivers editing the same item overwrote each other's quantity. Task: make concurrent edits safe. Action: moved to a server-first design (PRs #4–#8, merged 7–14 April) with a version column, a compare-and-swap UPDATE and 409 responses carrying the current values. Result: the loser now sees a conflict and nothing is overwritten; concurrency tests run on every CI build.

Data wiped on reopen → server as source of truth

Situation: in March 2026, during preview testing, reopening the app during a slow cold start wiped local data before the server answered. Action: stop treating the phone as a database; the server owns data, the phone caches it read-only. Lesson: never destroy local state before the server confirms it has the data.

Signed out by a network error → 401 versus offline

Situation: session start-up cleared tokens on any error, including timeouts. Action: clear credentials only on a real 401; on network errors keep the cached session and show a "warming up" status. Result: the current initialize() waits 8 seconds for the profile and otherwise keeps the cached state.

SMTP stalls → HTTPS email API

Situation: SMTP to Brevo stalled on the hosting platform. Action: switched to Brevo's HTTPS transactional API with a 10-second timeout. Why: the notes record that Render's free web services block outbound SMTP ports; port 443 is not affected.

Stale form version → client follows the protocol too

Situation: the 8 October 2026 review found the edit form could pick up a newer version from a cache refresh while keeping older field values (finding A-1). Action: capture the version together with the form fields; a rendered component test reproduces the old failure. Lesson: optimistic concurrency needs both the server check and a client that sends the version it actually read.

A migration you cannot undo → a release gate

Situation: migration 0007 deliberately refuses to downgrade, and a deploy runs migrations automatically. Action: a written gate: control auto-deploy and the CI hook, test fresh and upgraded schemas on staging with a fresh database, back up, pause writes during cut-over, verify the revision. Result: releases are planned events, not side effects of a merge.

Wrong claims to avoid

Don't saySay instead
"JWTs are encrypted."They are signed with HS256; anyone holding one can read its claims.
"Passwords are encrypted."They are hashed with Argon2id and a random salt; they cannot be decrypted.
"Logout kills the session immediately."Logout revokes the refresh token; the access token works until it expires (30 minutes by default). A password change ends every session.
"Our API is stateless, so no database lookup."Signatures are checked without the database, but every protected request also loads the user to compare session_version.
"One request is one transaction."One session per request; it can span several transactions.
"The app works offline."It shows cached data offline; writes need the server.
"/health proves the deploy."Neither health endpoint reports the commit or the migration revision.
"CORS protects the API."CORS is a browser rule; it does nothing for the Android app.
"The assistant never writes anything."It never writes inventory or orders; cloud features write consent and usage rows.
"It handles N users per second."A route benchmark alone cannot establish end-to-end capacity.
"Staging and production are verified separate."The documents say so; the dashboard settings are not verified here.

Last-hour cheat sheet

At {{f:baseline}}, the application registers 65 operations under /api/v1 and three root operations. PostgreSQL has 18 application tables plus Alembic’s version table. Thirteen migration revisions lead to 0013_supply_reviews.

For an interview, explain one save before quoting counts: the client submits an item version, the API scopes the query to the owner, a conditional update increments the version, and a later stale edit gets 409. For release questions distinguish the Worker version, Render SHA, database migration and Android build.
