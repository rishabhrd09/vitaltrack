Part 3 · Framework

FastAPI internals, as CareKosh uses them

In short: FastAPI is Starlette (routing, middleware, requests) plus Pydantic (validation) plus a dependency-injection system driven by type hints. Most bugs and most interview questions live in the order these pieces run.

The application factory and lifespan

{{s:B/app/main.py#create_app}} builds the app: middleware, routers, the rate limiter, exception handlers and health endpoints. The module ends with app = create_app(), which is what Gunicorn imports as app.main:app.

  • API docs are hidden by default. docs_url, redoc_url and openapi_url are set only when DEBUG is true, so production does not publish its schema.
  • Lifespan replaces the older start-up and shutdown events: create tables in development only, and dispose of the engine's connections at shutdown.
  • Sentry is initialised at import time only if SENTRY_DSN is set, with personal data, request bodies, local variables and trace propagation to outside services all turned off.

Path operations and responses

Each resource has an APIRouter with a prefix (/auth, /items …), included under a parent router with prefix /api/v1. Patterns worth recognising:

  • response_model filters and serialises the return value; it is why internal columns such as hashed_password never leak.
  • status_code=201 on creates; a handler can still change it through a Response parameter, as order creation does when a localId replay returns 200.
  • Returning a JSONResponse directly bypasses the response model. The item 409 does this to send server_version and server_quantity.
  • response_class=HTMLResponse for the pages behind email links; three of them use include_in_schema=False to stay out of the OpenAPI schema.

Dependency injection

A dependency is a function FastAPI calls before the handler, because the handler's parameter type says so. Dependencies can depend on other dependencies; FastAPI resolves the graph once per request and caches each dependency's result within that request.

{{fig:sd:dependency-graph|What FastAPI builds before update_item runs. get_current_user needs get_db too; because results are cached per request, the handler and the authentication share one session.}} {{x:B/app/api/deps.py:37-86|get_current_user: bearer token → signature, expiry and type → user row → session_version, active flag and verification policy.}}
  • HTTPBearer(auto_error=False) returns None when the header is missing, so the dependency can answer with its own 401 and WWW-Authenticate: Bearer.
  • Aliases in use: routes use DB and CurrentUser. Pagination, OptionalUser, ActiveUser, VerifiedUser and SuperUser exist but no route uses them.
  • AI routes differ: their principal() dependency opens its own short session, authenticates and returns only the user id, so no database connection is held while waiting for a provider.

"Authentication is a dependency, not middleware. That gives each route an explicit, typed requirement, it reuses the request's session through dependency caching, and it fails with a clean 401 before my handler runs."

Dependencies with yield: when does the clean-up run?

CareKosh pins FastAPI {{f:fastapi}}. Its DB alias explicitly uses Depends(get_db, scope="function"). The handler and its session-based authentication dependency share the dependency result. After the handler returns, the dependency completes before the response is sent. This allows a failing final commit to affect the HTTP outcome.

Leaving scope unspecified on a yielding dependency gives it request scope in this version. Reusing DB prevents an accidental second session with a different cleanup time. Explicit commits inside a handler can finish a transaction earlier. A subsequent rollback cannot undo an already committed transaction.

{{x:B/app/api/deps.py:26-31|The application chooses the cleanup boundary explicitly.}} {{x:B/app/core/database.py:121-129|Commit on success, roll back on exception and always close the session.}}

Validation order and error responses

A favourite trick question: "does FastAPI validate the body before or after authentication?" In this app:

  1. Malformed JSON fails with 422 while the body is parsed, before any dependency runs.
  2. Dependencies run next. A bad token gives 401 even if the body is also invalid.
  3. Field validation errors (wrong types, out-of-range values) give 422, but only after get_current_user may already have queried the user.
{{x:B/app/main.py:211-265|The custom handlers: validation errors become a structured 422, IntegrityError a generic 409 without SQL details, anything unexpected a generic 500.}}

Two more handlers are registered: slowapi's handler turns RateLimitExceeded into 429, and FastAPI's default turns HTTPException into {"detail": …}. The phone's client understands all of these shapes.

Handlers for Exception are run by Starlette's outermost ServerErrorMiddleware, outside the app's own middleware, so an unexpected 500 lacks the X-Request-ID and security headers (review finding A-13).

The middleware onion

FastAPI constructs the application once. Its installed middleware wraps each request. For a normal application request, CORS is the outermost application-added layer, followed by IngressGuard, RequestCapacity, AIBodyLimit, then the security-header and request-ID layers in their configured order. Starlette also supplies framework-level error handling. Middleware can answer early, so a denied request may never execute a route.

Trace a browser refresh in two steps. A matching OPTIONS request can finish at CORS. The POST continues through ingress validation and capacity and body checks before the browser session handler checks the origin and refresh cookie. A 200 preflight and a 503 POST are consistent outcomes.

Background tasks

Registration, verification resend, forgot-password, reset-password and the account-deletion request add email sends to FastAPI's BackgroundTasks. They run in the same worker process after the response is sent.

  • Why: the person does not wait up to 10 seconds for Brevo, and a slow email provider cannot slow the API's reply.
  • Limits: a background task is not a queue. If the process stops right after the reply, the email is lost; a failure is logged and not retried.
  • Next step: a durable queue (or a transactional outbox table polled by a worker) with retries and idempotent sends.

"Background tasks are like Celery." They are in-process and non-durable.

ASGI servers: Uvicorn under Gunicorn

ASGI is the interface between an async server and an async app. Uvicorn implements it; Gunicorn manages processes. The container runs gunicorn app.main:app --worker-class app.worker.CareKoshUvicornWorker --workers 2, bound to 0.0.0.0:$PORT by the entrypoint.

  • Why two processes: CPU parallelism and fault isolation; if one worker crashes, Gunicorn replaces it.
  • Graceful shutdown: the entrypoint uses exec, so Gunicorn itself receives the platform's SIGTERM and can finish in-flight requests.
  • Version note: uvicorn.workers has been deprecated since Uvicorn 0.30 in favour of the separate uvicorn-worker package; with 0.34.0 it still works but warns. Running Uvicorn's own --workers is another option.

Part 4 · Validation

Pydantic: schemas and settings

In short: Pydantic models define what the API accepts and returns; pydantic-settings turns environment variables into a validated, typed settings object.

Schemas, aliases and validators

  • camelCase on the wire, snake_case in Python. Request fields use alias="minimumStock" with populate_by_name; responses use serialization_alias, and FastAPI serialises by alias. Token responses keep snake_case (access_token).
  • from_attributes lets UserResponse.model_validate(user) read an ORM object.
  • Field validators enforce rules: passwords 8–128 characters with an uppercase letter, a lowercase letter and a digit; usernames 3–50 lowercase letters, digits and underscores; names stripped of angle brackets and quotes; the login identifier lowercased and trimmed.
  • "Omitted" versus "null". The item update writes an optional column only if the field appears in model_fields_set; an explicit null clears it, an omitted field is untouched.

Settings and secrets

{{s:B/app/core/config.py#Settings}} extends BaseSettings: every field can come from an environment variable (case-insensitive) or a local .env file, and get_settings() caches one instance with lru_cache.

  • SecretStr hides secrets in repr and logs; code must call get_secret_value() deliberately.
  • Validators refuse unsafe production values: the public default SECRET_KEY outside development and testing, any key shorter than 32 characters, and an empty FRONTEND_URL in production.
  • DATABASE_URL is normalised: provider URLs become postgresql+asyncpg://, and query parameters such as Neon's ?sslmode=require are removed because asyncpg does not accept them through SQLAlchemy; TLS is requested through connect_args instead.
  • Feature flags such as AI_ENABLED default to false: features turn on deliberately per environment.
