Part 1 · Concepts

Security foundations, mapped to the code

In short: most security interview mistakes are vocabulary mistakes. Learn the five tools (encoding, fast hash, password hash, encryption, signature), the three meanings of "session key", and exactly which one CareKosh uses where.

Authentication versus authorization

  • Authentication answers "who are you?": the password at login, then a signed token on every request ({{s:B/app/api/deps.py#get_current_user}}).
  • Authorization answers "what may you do?": in CareKosh, "only your own rows", enforced by filtering every query on user_id; plus consent scopes for the optional AI providers.
  • Identity: a users row with an email (required at registration) and an optional username; either can be used to log in.

The status codes follow that split: 401 means "not authenticated" (missing, invalid or expired token, or a revoked session); 403 means "authenticated, but not allowed" (disabled account, unverified email when required, missing AI consent); 404 hides another user's row.

Encoding, hashing, encryption and signing

"Passwords are hashed with Argon2id, never encrypted, because the server never needs them back. Tokens are signed, not encrypted, because they carry no secrets. The one thing we encrypt at rest is a user's own provider key, because the server must use it again."

Password hashing, salt and pepper

A password hash must make guessing expensive, because people choose guessable passwords and stolen hash databases are attacked offline. Three properties do that:

  • Salted: a random value mixed into each hash, so equal passwords give different hashes and precomputed tables are useless. The salt is not secret.
  • Slow: many iterations, so each guess costs time.
  • Memory-hard: each guess also needs a lot of memory, which makes GPU and ASIC attacks expensive. Argon2id (RFC 9106) is designed for this.
{{x:B/app/core/security.py:18-34|passlib's CryptContext: Argon2 for every new hash; bcrypt accepted only to verify older hashes (deprecated="auto").}}

What a stored hash looks like. This one was produced by the app's own hash_password("Sample-Passw0rd") during verification (a sample, not a real user's):

$argon2id$v=19$m=65536,t=3,p=4$UWrNGcN4r3XO+Z+TkrL2fg$mAwRDjR7smEkV8CDBh3Op4jZGEVX5acLRv7o7MTLxqM
argon2id
The variant: Argon2id, the hybrid recommended by RFC 9106 and OWASP.
v=19
Algorithm version 1.3 (0x13).
m, t, p
Memory 65,536 KiB (64 MiB), 3 passes, 4 lanes: argon2-cffi 23.1.0's defaults, which passlib adopts.
salt
16 random bytes (base64, 22 characters), different for every hash.
hash
32 bytes of output (43 characters).
  • No separate salt column: the salt and the parameters travel inside the string, so verify can recompute the hash with the same settings.
  • No pepper: there is no extra server-side secret mixed in. OWASP describes a pepper as optional defence in depth, kept in a secrets store separate from the database.
  • Cost on this hardware: about 24 ms per hash in an earlier laptop measurement. Hashing runs in a worker thread so the event loop stays free.
  • Hashing the same password twice gives two different strings, and verify_password accepts both. Reproduced on {{f:checked}}.

Legacy bcrypt hashes are never upgraded: the code does not call needs_update or verify_and_update, so an old bcrypt hash changes only when its owner changes or resets the password. With bcrypt 4.2.1, passlib 1.7.4 logs a harmless "(trapped) error reading bcrypt version" warning, a sign that passlib (last released in October 2020) is no longer maintained. bcrypt also only uses the first 72 bytes of a password.

Randomness and one-time tokens

{{x:B/app/utils/email.py:51-61|One-time tokens: 32 random bytes from the operating system, sent raw in the email; only the SHA-256 digest is stored.}}
  • Entropy: 32 bytes is 256 bits. Even at a trillion guesses per second, guessing one would take longer than the age of the universe, so a fast hash (SHA-256) is enough. Passwords, by contrast, have low entropy and need Argon2.
  • Why store a digest: a copy of the database would not contain usable links.
  • Single use: consuming a token clears or conditionally updates its column, and each has an expiry checked in SQL: 24 hours for verification, 1 hour for password reset, 24 hours for account deletion.

Symmetric, asymmetric and HMAC: why HS256

  • Symmetric cryptography uses one shared key for both operations; asymmetric uses a private key to sign and a public key to verify.
  • HMAC-SHA256 (HS256) combines a secret key with SHA-256 to produce a tag that only a key holder can make.
  • HS256 fits CareKosh because the same service issues and verifies tokens. RS256 or ES256 fit when other services must verify tokens without being able to mint them.
  • Algorithm allow-list: decoding passes algorithms=[settings.JWT_ALGORITHM], so a token claiming another algorithm (for example none) is rejected, as RFC 8725 recommends.

Sessions versus tokens, and the anatomy of a JWT

Classic web apps keep a server-side session and give the browser a random session id in a cookie. CareKosh uses a separate HttpOnly browser refresh cookie. Its native app and authenticated inventory endpoints use bearer tokens in the Authorization header instead: whoever holds the token can use it, which is why it lives in SecureStore and travels only over TLS.

{{x:B/app/core/security.py:40-48|The payload model: registered claims sub, exp, iat and jti (RFC 7519), plus two custom claims.}} {{x:B/app/core/security.py:165-185|decode_token: signature, expiry and the payload shape; any failure returns None, which the callers turn into 401.}}
  • Access token: 30 minutes by default; sent on every request.
  • Refresh token: 30 days by default; has a jti with a row in refresh_tokens (revocable); used only at /auth/refresh; single use.
  • The type claim stops a refresh token being used as an access token and the reverse, since both are signed with the same key.
  • Not purely stateless: after the signature check, every protected request loads the user and compares session_version. One indexed lookup buys instant revocation on password change.

"JWTs are encrypted." A signed JWT (JWS) is readable; RFC 7519 points to encryption (JWE) or keeping sensitive data out of the token. CareKosh keeps only ids, times, a type and a counter in it.

Three things people call a "session key"

{{fig:session-key-meanings|Three things called a session key. CareKosh has TLS session keys (handled by the platform), one long-lived signing key, and application sessions made of a refresh-token row plus a generation number.}}
  1. TLS session keys are symmetric keys negotiated in each TLS handshake (TLS 1.3 uses an ephemeral Diffie–Hellman exchange and an HKDF key schedule), so every connection gets fresh keys and past traffic stays safe even if a server key leaks later (forward secrecy). They exist between the public client and Cloudflare for the proxied API; application code never sees them.
  2. SECRET_KEY is the server's long-lived HMAC key. It signs every token for every user, so it is a master secret, not a session key. Rotating it would sign everyone out.
  3. The application session is what the product calls "being logged in": a refresh_tokens row (identified by the token's jti, with an expiry and a revoked flag) plus the user's session_version. The database records refresh-token state. The browser transports its refresh token in a host-only HttpOnly cookie.

"If you mean the TLS session key, that's negotiated per connection and terminated at Cloudflare for a proxied public request. Our application session is a refresh-token row plus a session_version counter on the user; the signing key is a single long-lived secret that we never put in the app."

Transport security: HTTPS and HSTS

  • Where TLS ends: The supplied DNS inventory shows proxied API CNAMEs. The public client negotiates TLS with Cloudflare. Cloudflare connects to the Render origin, which forwards the request to the container. Verify the active origin TLS policy in the dashboard.
  • Database leg: the API connects to Neon with TLS (ssl=True) outside development and testing.
  • Phone: production and preview builds must use HTTPS URLs; cleartext HTTP is allowed only in development builds (app.config.js).
  • HSTS (max-age=31536000; includeSubDomains) is sent in production and staging. It matters for browsers that open the email-link pages; a native client ignores it.

Browser policies: CORS, CSRF, XSS and security headers

Browser refresh uses a host-only HttpOnly cookie. Hosted environments use Secure and SameSite=Strict and limit the cookie path to the web-auth endpoints. A native Android request supplies a bearer token explicitly. A browser also uses bearer access tokens for inventory, but its refresh credential can be attached automatically by the browser.

Enabling browser login requires an explicit WEB_APP_ORIGINS list included in CORS_ORIGINS. The cookie endpoint checks the exact Origin and X-CareKosh-Web marker and rejects cross-site fetch metadata. CORS controls browser access across origins. It cannot establish ownership of an inventory item. Server-side authorization still runs on every protected operation.
