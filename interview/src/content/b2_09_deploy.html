Backend deployment and hosting guide

In short: one Docker image, built by Render from the repository; every container start waits for PostgreSQL, applies migrations and then starts Gunicorn; Render moves traffic only after /live answers.

The Dockerfile, line by line

{{fig:container-start|Build once, start many times: the two build stages on the left, the entrypoint's start-up sequence on the right.}} {{x:B/Dockerfile:7-81|Image stages, entrypoint and the Gunicorn command with the project’s Uvicorn worker class.}}
  • Two stages: the builder has compilers and headers (build-essential, libpq-dev) to build wheels into /opt/venv; the production stage copies only that virtual environment, so compilers never ship.
  • Runtime packages: libpq5 (PostgreSQL client library), curl (the health check), postgresql-client (pg_isready in the entrypoint), ffmpeg (audio normalisation for the optional transcription route).
  • Non-root: appuser (uid 1000) owns the code and runs the process, limiting what an attacker could do after a compromise.
  • Environment: PYTHONUNBUFFERED=1 so logs appear immediately; PYTHONDONTWRITEBYTECODE=1; ENVIRONMENT=production as a safe default that the platform can override.
  • HEALTHCHECK uses /live (process only), for the same reason as Render's health check.
  • Two small details an interviewer may spot: dos2unix fixes Windows line endings in the entrypoint, and the final stage runs apt-get twice, adding a layer.

The entrypoint

{{x:B/docker-entrypoint.sh:1-62|docker-entrypoint.sh: derive the database host, wait for it, migrate or stop, then exec the server.}}
  • Waiting is bounded: 30 attempts, 2 seconds apart; then it continues and lets the migration fail loudly if the database is really down.
  • set -- "$@" --bind … appends the bind address to Gunicorn's arguments using the platform's $PORT.
  • exec replaces the shell with Gunicorn, so the platform's SIGTERM reaches Gunicorn and in-flight requests can finish.

Render: the production Blueprint

The production Blueprint names vitaltrack-api, selects main, uses the backend Dockerfile and Starter plan, and probes /live. That probe checks the process. Use /health to check database readiness. Staging has its own Render service configured through the dashboard. A main commit, a deployed SHA and an applied Alembic revision can differ.

Runtime configuration includes a private database URL and signing key, an allowed API hostname, an environment-specific origin credential, shared Redis storage, and explicit web origins for cookie authentication. With verification enabled outside development and testing, a blank mail credential prevents startup. Check live values privately in the service dashboard.

Neon PostgreSQL

  • Connection: the service's DATABASE_URL is rewritten to the asyncpg driver; Neon's query parameters are removed and TLS is requested with ssl=True outside development and testing.
  • Databases versus branches: in Neon a branch is a copy-on-write clone with its own compute; databases live inside a branch. The documents describe staging and production as two databases in one project, which is why the release notes recommend a fresh database rather than a Neon branch for testing a one-way migration: a branch of production would copy production data.
  • Scale to zero: an idle compute suspends and wakes on the next connection; the first query after idle can be slow. That is one reason for pool_pre_ping and for /live as the platform health check.
  • Backups: point-in-time restore is limited to a plan-dependent history window. A restore loses writes made after the restore point; {{p:B/scripts/restore_drill.py}} rehearses restores on a separate database.

Domains, TLS and email

Production serves the browser at homeicuinventory.carekosh.com and routes api.carekosh.com to the production Render service. Staging pairs staging-app.carekosh.com with staging-api.carekosh.com. Each frontend custom domain selects a Worker. Each proxied API hostname has its own origin-header rule and Render configuration. The database connection comes from that service’s private DATABASE_URL.

A DNS record selects the destination. A Worker deployment selects the assets. A Render deployment selects the backend commit. The Android build profile embeds the public API URL. Check these independently when a staging screen loads but the data appears wrong. Brevo email links use the backend’s configured public URL.

The release gate and rollback

{{fig:release-paths|The release paths for the tested revision. For a risky migration, also rehearse upgrade and recovery before the production cutover.}}
  • Image rollback ≠ schema rollback. Redeploying an older image leaves the newer schema in place. That works only if the older code tolerates the newer schema (additive changes do).
  • Expand and contract is the general pattern for zero-downtime changes: add the new column or table, deploy code that uses it, migrate data, and remove the old one in a later release.
  • Old and new instances overlap during a zero-downtime deploy. Code must cope with both schemas briefly, which is why the gate pauses writes for the counter change in 0007.

CI/CD in detail

Open a pull request to main and record the revision you test. Backend and Android CI runs for pull requests targeting main, pushes to main and manual dispatch. Web checks use a separate path-filtered workflow. A build-apk label on an eligible PR requests an Android preview build.

Before using a merge-first release sequence, verify production Render’s native auto-deploy and the production Worker’s Git deploy command. The optional Render CI hook requires passing test jobs, a push to main, ENABLE_RENDER_AUTO_DEPLOY=true and a configured hook secret. A hook acknowledgment means Render accepted the request. Confirm the live SHA in Render.

Advance staging to the candidate and test the affected user journey. Publish the production web build with Release CareKosh web on main. If main moved, test that revision first. API and Android releases use their own service and Play controls. A working screen, a tested commit and a live deployment each supply different evidence.
