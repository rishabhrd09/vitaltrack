End-to-end architecture

In short: the app and the API are built and shipped through two separate pipelines, then meet at run time over HTTPS. This part names every box, the files behind it and the environment it runs in.

The big picture: connecting the dots

A caregiver loads the browser app from its Cloudflare Worker or opens the installed Android app. Both clients send authenticated requests to the environment’s API hostname. At the edge, Cloudflare adds an origin-verification header to proxied API traffic. The Render container runs FastAPI, checks the request and sends account-scoped SQL to PostgreSQL. Hosted workers share rate limits through Redis.

The public landing site and the signed-in browser app have separate builds. A visit to the landing page makes no inventory change. A successful inventory edit has to reach the API and commit in PostgreSQL.

Data architecture: eighteen application tables and their ownership boundaries

At {{f:baseline}} SQLAlchemy defines 18 application tables. Alembic tracks its own revision separately. Start with users, items, categories, orders and order_items. User-owned reads and writes filter by the authenticated account. Order lines retain item snapshots, which lets history survive an item deletion. Activity records describe business events and audit records capture mutation details.

The later migrations matter when tracing a request. Revision 0012 adds encrypted OpenAI credentials. Revision 0013 adds supply revisions, review runs, proposals, confirmations and closed order submissions. A supply revision gives cooperating writers a per-owner lock and lets the API detect when an earlier recommendation has become stale.

Development, staging and production

Production serves the browser at homeicuinventory.carekosh.com and routes api.carekosh.com to the production Render service. Staging pairs staging-app.carekosh.com with staging-api.carekosh.com. Each frontend custom domain selects a Worker. Each proxied API hostname has its own origin-header rule and Render configuration. The database connection comes from that service’s private DATABASE_URL.

A DNS record selects the destination. A Worker deployment selects the assets. A Render deployment selects the backend commit. The Android build profile embeds the public API URL. Check these independently when a staging screen loads but the data appears wrong. Brevo email links use the backend’s configured public URL.

Build-time versus run-time configuration

This distinction answers many "how do you configure environments?" questions.

Fixed when the app is built

EXPO_PUBLIC_API_URL comes from the EAS profile and is inlined into the JavaScript bundle. Anyone can read it from the APK, so it must never hold a secret. {{p:M/app.config.js}} refuses a preview build aimed anywhere but staging and a production build aimed anywhere but https://api.carekosh.com. An empty URL is not refused: the client then falls back to http://localhost:8000.

Set on each backend service

DATABASE_URL, SECRET_KEY, FRONTEND_URL, mail, Sentry and AI settings are environment variables read by pydantic-settings at start-up. The validators refuse the public default SECRET_KEY outside development and testing, any key shorter than 32 characters, and an empty FRONTEND_URL in production.

The deployment pipelines, end to end

Open a pull request to main and record the revision you test. Backend and Android CI runs for pull requests targeting main, pushes to main and manual dispatch. Web checks use a separate path-filtered workflow. A build-apk label on an eligible PR requests an Android preview build.

Before using a merge-first release sequence, verify production Render’s native auto-deploy and the production Worker’s Git deploy command. The optional Render CI hook requires passing test jobs, a push to main, ENABLE_RENDER_AUTO_DEPLOY=true and a configured hook secret. A hook acknowledgment means Render accepted the request. Confirm the live SHA in Render.

Advance staging to the candidate and test the affected user journey. Publish the production web build with Release CareKosh web on main. If main moved, test that revision first. API and Android releases use their own service and Play controls. A working screen, a tested commit and a live deployment each supply different evidence.

Mobile build and release

  • Profiles in {{p:M/eas.json}}: development (APK, localhost:8000), preview (APK, staging, channel preview), preview-voice-diagnostics (preview plus the voice diagnostics flag, refused in production) and production (Android App Bundle, api.carekosh.com, channel production).
  • Distribution. A preview APK is installed directly for testing against staging. A production AAB goes to Google Play's internal testing track first, then closed testing and production. Play's tester requirements depend on the type and age of the developer account; check them before planning a launch date.
  • No over-the-air updates. expo-updates is installed but app.json sets updates.enabled to false, so every JavaScript change needs a new build. The upside: what a reviewer approved is exactly what users run.
  • Backward compatibility matters. Old APKs stay installed. The API therefore keeps older contracts working, for example order creation without a localId and assistant contract versions 1 and 2.
