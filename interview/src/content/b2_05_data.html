Part 5 · Data

The data layer: async SQLAlchemy and PostgreSQL

In short: PostgreSQL owns every rule that must hold even if application code is wrong: foreign keys, cascades, checks and unique indexes. SQLAlchemy 2.0's async session gives explicit transactions, and every concurrency guarantee comes from a specific SQL statement.

PostgreSQL and the schema

At {{f:baseline}} SQLAlchemy defines 18 application tables. Alembic tracks its own revision separately. Start with users, items, categories, orders and order_items. User-owned reads and writes filter by the authenticated account. Order lines retain item snapshots, which lets history survive an item deletion. Activity records describe business events and audit records capture mutation details.

The later migrations matter when tracing a request. Revision 0012 adds encrypted OpenAI credentials. Revision 0013 adds supply revisions, review runs, proposals, confirmations and closed order submissions. A supply revision gives cooperating writers a per-owner lock and lets the API detect when an earlier recommendation has become stale.

The engine, the pool and sessions

{{x:B/app/core/database.py:74-101|The engine and the session factory: an 8-second statement timeout, TLS outside development and testing, pre-ping, hidden SQL parameters, expire_on_commit and autoflush off.}}
  • Pool: 5 connections plus up to 10 overflow per worker; wait up to 30 seconds for a free one. pool_pre_ping tests a connection before handing it out, which matters with a serverless database that may drop idle connections.
  • expire_on_commit=False: after a commit, attributes stay loaded. SQLAlchemy's asyncio guide recommends this because reloading an expired attribute would need implicit I/O, which async code cannot do.
  • autoflush=False: pending changes are sent only on flush() or commit(), so a query does not unexpectedly write half-built objects.
  • hide_parameters=True: SQL errors do not print bound values (which can include emails or token digests).
{{fig:session-transaction|One request, one session, two transactions. The handler commits its write; the refresh after it is a new transaction that get_db commits at teardown.}}

"A session is a unit of work, not a transaction. In CareKosh the handler commits the change and its history together; a refresh after that is a second, read-only transaction. That's why I never say 'rollback undoes the request': it only undoes what hasn't committed."

Models, relationships and loading strategy

The User model declares its collections (categories, items, orders, activity logs, refresh tokens) with lazy="selectin": when a user is loaded, SQLAlchemy loads each collection with one extra SELECT … WHERE user_id IN (…). That avoids N+1 queries when you need the collections, and costs a lot when you do not.

  • Authentication only needs scalars, so every user lookup on the auth path uses .options(noload("*")), and handlers avoid db.refresh(user), which would reload every collection.
  • Version note: SQLAlchemy 2.0 documents noload as a legacy feature. lazyload("*") or raiseload("*") are the modern ways to express "do not load", and raiseload turns an accidental access into an error. Changing it needs tests, because noload silently gives empty collections.
  • Cascades: relationships use cascade="all, delete-orphan" and foreign keys use ON DELETE CASCADE, so deleting a user or a category removes its children in the database.

"selectin is always better." It is better than lazy loading inside loops, but the best query is the one you do not run.

Transactions, isolation and locks

PostgreSQL's default isolation level is Read Committed: each statement sees data committed before it started. The rule that makes CareKosh's conditional updates safe:

Read Committed and UPDATE

When an UPDATE finds a row that a concurrent transaction is changing, it waits. If that transaction commits, PostgreSQL re-evaluates the WHERE clause against the new row version, and skips the row if it no longer matches. So two UPDATE … WHERE version = 3 statements cannot both succeed.

  • Deadlock avoidance: applying an order updates items sorted by item id. Two applies that share items take their row locks in the same order and queue instead of deadlocking.
  • Lock waits are bounded: migrations set lock_timeout = 30s; the AI budget sets a few seconds and answers "busy" (503) instead of piling up requests.
  • Lost updates are prevented by the version check, not by a stricter isolation level. Serializable isolation would also work, at the cost of retrying failed transactions.

Migrations with Alembic

  • When they run: alembic upgrade head in the container entrypoint, before Gunicorn starts. A failure stops start-up, so a new instance never serves a schema it does not understand.
  • How they run: {{p:B/alembic/env.py}} uses an async engine from the same settings and sets lock_timeout = '30s' inside each migration transaction, so a migration that cannot get its lock fails instead of blocking traffic for ever.

Part 6 · Domain

Correctness patterns for concurrent writes

In short: each write path has a named guarantee: a version check, an idempotency key, a status claim or a lock, and each one is visible in a single SQL statement.

Optimistic concurrency on items

Two editors open one item at quantity 10 and version 3. One saves quantity 8 with version 3. The transaction succeeds and increments the version to 4. The other submits version 3 and receives 409. Inventory remains at 8. Read the current values and make a fresh decision before retrying.

Both user-facing editors send PUT /api/v1/items/{item_id}. The request carries the version captured when the editor opened. The separate stock-only PATCH is available to API callers. The owner supply-revision lock coordinates cooperating writers. The conditional UPDATE includes the item, owner and submitted version. Success also writes the related activity and audit records in the transaction.

Orders: lifecycle, idempotency, numbering and apply

A phone that loses the response after placing an order cannot infer whether the database committed. Send the same localId and the same saved fields. On the first submission the API takes the owner’s supply-revision lock, checks ownership, allocates the order number and saves the order. A matching replay returns 200. Different notes or persisted line fields under that key return 409. An explicitly closed interrupted submission also returns 409.

{{x:B/app/services/orders.py:135-147|The owner lock and replay check happen before a new order is allocated.}}

Pending can become ordered, received or declined. Ordered can become partially received, received or declined. Partially received can become received or declined. An unapplied received order can still be declined. Applying a received order checks its items and units and updates stock in one transaction. A missing item or changed unit returns 409 with no partial credit. A replay of a completed apply returns 200 and adds nothing. Only pending and declined orders are deletable.

Activity log versus audit log

{{s:B/app/services/audit.py#log_audit}} adds an AuditLog row to the current session and deliberately does not commit: the caller's commit writes the change and its audit row together, or neither. Item create, update, stock update and delete, category delete (one audit row per removed item), order apply and order delete write audit rows. Auth events write activity rows only.

The audit log has no API and no retention policy, and not every write produces both kinds of history. Describe it as "before-and-after snapshots for selected inventory changes", not as a complete audit trail.

Reset and bulk-operation guards

The app's "start fresh" and replace-all features delete many rows from the phone, one request at a time, after saving a local JSON backup. Because those requests are not one transaction, the server offers opt-in guards so a reset cannot destroy changes made after the backup:

  • DELETE /items/{id}?version=v locks the item and refuses (409) if its version changed.
  • DELETE /categories/{id}?onlyIfEmpty=true&expectedUpdatedAt=… locks the category, refuses if it changed or still has items, and never deletes a default category.

Ordinary deletes keep their simple behaviour; only resets opt in. A reset can still stop half-way, which is why the app keeps the backup.
