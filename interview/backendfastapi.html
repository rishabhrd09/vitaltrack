Part 1 · Orientation

The backend at a glance

In short: one FastAPI application, served by Gunicorn with two Uvicorn workers in a Docker container, owning one PostgreSQL database through async SQLAlchemy. Everything else in this book is a closer look at one part of that sentence.

1.1 How to present the backend

30 seconds

"It's a FastAPI service on Python 3.12 with async SQLAlchemy and PostgreSQL. Routes are thin: dependencies handle the database session and authentication, Pydantic validates input, and handlers do owner-scoped queries with explicit transactions. It runs as a Docker container on Render, and migrations run at start-up."

2 minutes

Add the patterns: a version-checked UPDATE for concurrent edits, an idempotency key for order creation, row locks for authentication changes, advisory locks for per-account names and the AI budget, history rows written in the same transaction, a body-size middleware, redacting logs, and a test suite that runs against real PostgreSQL in two schema modes.

Say it in the interview

"The backend is small on purpose: one service, one database, explicit transactions. The care went into correctness under concurrency and retries, and into making failures visible and safe."

1.4 One request at a glance

FastAPI constructs the application once. Its installed middleware wraps each request. For a normal application request, CORS is the outermost application-added layer, followed by IngressGuard, RequestCapacity, AIBodyLimit, then the security-header and request-ID layers in their configured order. Starlette also supplies framework-level error handling. Middleware can answer early, so a denied request may never execute a route.

Trace a browser refresh in two steps. A matching OPTIONS request can finish at CORS. The POST continues through ingress validation and capacity and body checks before the browser session handler checks the origin and refresh cookie. A 200 preflight and a 503 POST are consistent outcomes.

2.1 Type hints, Annotated and Mapped

Type hints are optional annotations that tools read. FastAPI and SQLAlchemy read them at run time too, which is why they matter here more than in a script.

  • Annotated[T, metadata] (PEP 593) attaches extra information to a type. app/api/deps.py defines CurrentUser = Annotated[User, Depends(get_current_user)], so a handler parameter current_user: CurrentUser means "a User, produced by that dependency".
  • Mapped[...] in SQLAlchemy 2.0 declares a column's Python type; Mapped[Optional[str]] becomes a nullable column.
  • if TYPE_CHECKING: imports in the models avoid circular imports at run time while keeping type checkers informed.
  • str | None (PEP 604) and Optional[str] mean the same thing; both styles appear.

2.2 async, await and the event loop

An async def function returns a coroutine. When it reaches await on something that is not ready, such as a database reply, it suspends and the event loop runs other ready work. That is how one worker process serves many concurrent requests while each one mostly waits.

  • Await yields only when it has to wait. An awaited result that is already available can continue without switching tasks.
  • Blocking calls hurt every request on that worker. A slow synchronous call (CPU-heavy hashing, a blocking HTTP client) stops the loop. CareKosh uses async drivers (asyncpg, httpx) for I/O and moves Argon2 to a thread.
  • Timeouts are explicit. asyncio.timeout bounds the AI body read and provider calls; asyncio.wait_for bounds the database health probe at 2 seconds.

2.3 The GIL, threads and processes

CPython's global interpreter lock lets one thread run Python bytecode at a time inside a process. Threads still help with blocking I/O and with C code that releases the lock; processes give real CPU parallelism because each has its own interpreter.

ToolUsed in CareKosh forShares memory?
Event loop (one per worker)All request handling and database I/OYes, inside the worker
Thread pool (anyio.to_thread.run_sync)Argon2 hashing and verificationYes
Processes (2 Gunicorn workers)Parallel request handling on one instanceNo: anything in memory is per worker
PostgreSQLDurable business records, transaction locks and AI budgetsShared by API workers. Hosted limit counters reside in Redis.

That last row is a design rule worth saying out loud: anything that must be consistent across workers and instances lives in PostgreSQL, not in a Python variable.

2.4 Context managers and generators

A context manager runs set-up and guaranteed clean-up around a block (with / async with). A generator function with yield pauses and resumes. FastAPI combines the two: a dependency that yields gives a value to the handler and runs its clean-up afterwards.

2.5 Decorators

A decorator wraps a function to register it or change its behaviour. In this code:

  • @router.post("/login", response_model=AuthResponse) registers a route with its metadata.
  • @limiter.shared_limit("5/minute", scope="auth:login") on login wraps the route with a rate check; slowapi requires the handler to accept request: Request.
  • @field_validator("SECRET_KEY") plus @classmethod registers a Pydantic validator.
  • @asynccontextmanager turns the lifespan generator into an async context manager.
  • @app.middleware("http") registers a function as BaseHTTPMiddleware.

2.6 Exceptions, secrets and constant-time comparison

  • HTTPException turns into a JSON response with {"detail": …} and the given status; raising it inside a dependency stops the request before the handler.
  • raise … from None hides the original exception chain. The key vault uses it so a decryption failure never reveals why it failed.
  • secrets.token_urlsafe(32) draws 32 bytes from the operating system's cryptographically secure generator and encodes them as 43 URL-safe characters.
  • hashlib.sha256 turns that token into the 64-character digest stored in the database.
  • secrets.compare_digest compares in constant time. The email helper's verify_token uses it; the routes themselves compare digests inside SQL WHERE clauses.

Part 3 · Framework

FastAPI internals, as CareKosh uses them

In short: FastAPI is Starlette (routing, middleware, requests) plus Pydantic (validation) plus a dependency-injection system driven by type hints. Most bugs and most interview questions live in the order these pieces run.

3.1 The application factory and lifespan

create_app builds the app: middleware, routers, the rate limiter, exception handlers and health endpoints. The module ends with app = create_app(), which is what Gunicorn imports as app.main:app.

  • API docs are hidden by default. docs_url, redoc_url and openapi_url are set only when DEBUG is true, so production does not publish its schema.
  • Lifespan replaces the older start-up and shutdown events: create tables in development only, and dispose of the engine's connections at shutdown.
  • Sentry is initialised at import time only if SENTRY_DSN is set, with personal data, request bodies, local variables and trace propagation to outside services all turned off.

Repository evidence · app/main.py · app/api/v1/auth.py

3.2 Path operations and responses

Each resource has an APIRouter with a prefix (/auth, /items …), included under a parent router with prefix /api/v1. Patterns worth recognising:

  • response_model filters and serialises the return value; it is why internal columns such as hashed_password never leak.
  • status_code=201 on creates; a handler can still change it through a Response parameter, as order creation does when a localId replay returns 200.
  • Returning a JSONResponse directly bypasses the response model. The item 409 does this to send server_version and server_quantity.
  • response_class=HTMLResponse for the pages behind email links; three of them use include_in_schema=False to stay out of the OpenAPI schema.

3.3 Dependency injection

A dependency is a function FastAPI calls before the handler, because the handler's parameter type says so. Dependencies can depend on other dependencies; FastAPI resolves the graph once per request and caches each dependency's result within that request.

3.4 Dependencies with yield: when does the clean-up run?

CareKosh pins FastAPI 0.162.0. Its DB alias explicitly uses Depends(get_db, scope="function"). The handler and its session-based authentication dependency share the dependency result. After the handler returns, the dependency completes before the response is sent. This allows a failing final commit to affect the HTTP outcome.

Leaving scope unspecified on a yielding dependency gives it request scope in this version. Reusing DB prevents an accidental second session with a different cleanup time. Explicit commits inside a handler can finish a transaction earlier. A subsequent rollback cannot undo an already committed transaction.

3.5 Validation order and error responses

A favourite trick question: "does FastAPI validate the body before or after authentication?" In this app:

  1. Malformed JSON fails with 422 while the body is parsed, before any dependency runs.
  2. Dependencies run next. A bad token gives 401 even if the body is also invalid.
  3. Field validation errors (wrong types, out-of-range values) give 422, but only after get_current_user may already have queried the user.

3.7 Background tasks

Registration, verification resend, forgot-password, reset-password and the account-deletion request add email sends to FastAPI's BackgroundTasks. They run in the same worker process after the response is sent.

3.9 ASGI servers: Uvicorn under Gunicorn

ASGI is the interface between an async server and an async app. Uvicorn implements it; Gunicorn manages processes. The container runs gunicorn app.main:app --worker-class app.worker.CareKoshUvicornWorker --workers 2, bound to 0.0.0.0:$PORT by the entrypoint.

5.3 Models, relationships and loading strategy

The User model declares its collections (categories, items, orders, activity logs, refresh tokens) with lazy="selectin": when a user is loaded, SQLAlchemy loads each collection with one extra SELECT … WHERE user_id IN (…). That avoids N+1 queries when you need the collections, and costs a lot when you do not.

  • Authentication only needs scalars, so every user lookup on the auth path uses .options(noload("*")), and handlers avoid db.refresh(user), which would reload every collection.
  • Version note: SQLAlchemy 2.0 documents noload as a legacy feature. lazyload("*") or raiseload("*") are the modern ways to express "do not load", and raiseload turns an accidental access into an error. Changing it needs tests, because noload silently gives empty collections.
  • Cascades: relationships use cascade="all, delete-orphan" and foreign keys use ON DELETE CASCADE, so deleting a user or a category removes its children in the database.
Don't say

"selectin is always better." It is better than lazy loading inside loops, but the best query is the one you do not run.

5.5 Transactions, isolation and locks

PostgreSQL's default isolation level is Read Committed: each statement sees data committed before it started. The rule that makes CareKosh's conditional updates safe:

Read Committed and UPDATE

When an UPDATE finds a row that a concurrent transaction is changing, it waits. If that transaction commits, PostgreSQL re-evaluates the WHERE clause against the new row version, and skips the row if it no longer matches. So two UPDATE … WHERE version = 3 statements cannot both succeed.

  • Deadlock avoidance: applying an order updates items sorted by item id. Two applies that share items take their row locks in the same order and queue instead of deadlocking.
  • Lock waits are bounded: migrations set lock_timeout = 30s; the AI budget sets a few seconds and answers "busy" (503) instead of piling up requests.
  • Lost updates are prevented by the version check, not by a stricter isolation level. Serializable isolation would also work, at the cost of retrying failed transactions.

6.5 Reset and bulk-operation guards

The app's "start fresh" and replace-all features delete many rows from the phone, one request at a time, after saving a local JSON backup. Because those requests are not one transaction, the server offers opt-in guards so a reset cannot destroy changes made after the backup:

  • DELETE /items/{id}?version=v locks the item and refuses (409) if its version changed.
  • DELETE /categories/{id}?onlyIfEmpty=true&expectedUpdatedAt=… locks the category, refuses if it changed or still has items, and never deletes a default category.

Ordinary deletes keep their simple behaviour; only resets opt in. A reset can still stop half-way, which is why the app keeps the backup.

12.4 Neon PostgreSQL

  • Connection: the service's DATABASE_URL is rewritten to the asyncpg driver; Neon's query parameters are removed and TLS is requested with ssl=True outside development and testing.

A shared Redis limiter coordinates protected requests across workers. The database connection budget still grows with the number of processes and instances. 14.2 Consistency and idempotency

  • Inside the server: single-database transactions; every invariant either in a constraint or in one conditional statement.
  • Across the network: a lost reply is the classic problem. Orders use an idempotency key; other creates are guarded by duplicate checks (names) or are naturally safe to repeat (status changes to the same status, revocations).
  • Exactly-once effects are built from at-least-once delivery plus idempotent handling: the order localId, the apply claim, the refresh-token claim and single-use email tokens are all examples.
Say it in the interview

1What does an async def function return when you call it?basic

Short answer. A coroutine object. Nothing runs until it is awaited or scheduled on an event loop.

2What is the difference between concurrency and parallelism?basic

Short answer. Concurrency is making progress on several tasks by interleaving them; parallelism is running them at the same instant on several cores.

Deeper. One Uvicorn worker gives concurrency: its event loop switches between requests while they wait on PostgreSQL. Two Gunicorn worker processes give parallelism on two cores.

3What is the GIL and does it matter for this backend?intermediate

Short answer. CPython's global interpreter lock lets one thread run Python bytecode at a time per process. It matters little here because requests mostly wait on I/O, and parallelism comes from two worker processes.

Deeper. CPU-heavy work in a request thread would still block the event loop, which is why Argon2 runs through anyio.to_thread. Whether that thread runs truly in parallel depends on the C library releasing the GIL; either way the loop stays responsive.

Avoid saying. "Python can't do concurrency because of the GIL."

4Why does the login route hash and verify passwords in a thread?intermediate

Short answer. Argon2 is deliberately slow (about 24 ms and 64 MiB per hash here). Running it on the event loop would freeze every other request on that worker for that time.

Deeper. anyio.to_thread.run_sync(verify_password, …) sends the call to a worker thread and awaits the result, so the loop keeps serving. The same applies at registration, password change and reset.

5What happens if an async route calls a blocking function?intermediate

Short answer. The whole event loop stops until it returns, so every request on that worker waits, even simple ones.

Deeper. Use async libraries (asyncpg, httpx), move blocking work to a thread (anyio.to_thread, asyncio.to_thread) or a process, or declare the route with plain def so FastAPI runs it in its thread pool.

Short answer. So objects keep their loaded values after commit. Otherwise accessing an attribute would trigger a reload, which is implicit I/O that async code cannot perform.

64What is the difference between a session, a connection and a transaction?advanced

Short answer. A connection is a database socket from the pool; a transaction is a unit of atomic work on one connection; a session is SQLAlchemy's unit of work that begins transactions as needed and can run several in sequence.

Deeper. In CareKosh a request's session commits the write, then a refresh starts a new transaction, which get_db commits at teardown.

125How would read replicas affect consistency?advanced

Short answer. Replicas lag, so a read right after a write could miss it. Route reads that must see your own writes to the primary, or wait for the replica to reach the write's position.

Deeper. CareKosh has no replicas, so the server always reads its own writes. Adding them would need a routing rule, for example primary for a few seconds after a user's write, or for any request that follows a mutation.

16.1 Known limitations

A shared Redis limiter coordinates protected requests across workers. The database connection budget still grows with the number of processes and instances. 17.1 Glossary

Coroutine
The object an async def function returns; it runs when awaited or scheduled on an event loop.
Event loop
The scheduler that runs coroutines and switches between them at await points.
GIL
CPython's global interpreter lock: one thread runs Python bytecode at a time per process.
Dependency (FastAPI)
A function FastAPI calls before a handler because a parameter's type asks for it; cached per request.
Middleware
Code that wraps every request and response; the last one added runs outermost.
Session (SQLAlchemy)
A unit of work that tracks objects and runs one transaction at a time on a pooled connection.
Read Committed
PostgreSQL's default isolation: each statement sees data committed before it began.
Compare-and-swap
An update that only applies if the current value (here, a version) matches the expected one.
Advisory lock
A lock on an application-chosen number; pg_advisory_xact_lock holds it until the transaction ends.
Expand and contract
A migration strategy: add new structures, move code and data, then remove the old ones later.
Outbox
A table of pending messages written in the same transaction as the change, sent later by a worker.
Idempotent
Safe to repeat: doing it twice has the same effect as doing it once.
