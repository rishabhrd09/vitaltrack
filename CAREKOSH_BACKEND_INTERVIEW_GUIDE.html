02 The Big Picture: What CareKosh Is

Before we dissect optimistic locking, JWT rotation and connection-pool tuning, you need the aerial view. What is this system for? What shape does its runtime have? And where does each later chapter sit on the map? Read this once and the rest of the guide becomes navigable.

In one line CareKosh (codename VitalTrack) is an async FastAPI inventory API for home-ICU and medical supplies. Gunicorn and Uvicorn run it on Render. Its processes keep no session state: the data lives in PostgreSQL (intended: Neon), and it serves a React Native mobile client.

The product in plain terms

CareKosh is the backend for a medical / home-ICU inventory app. The user is typically a caregiver managing critical supplies for a patient at home — oxygen consumables, dressings, medications, feeding-tube kits. The mobile app (React Native / Expo) lets them do four things. They organize supplies into Categories and track Items with live stock levels and low-stock thresholds. They raise Orders: a purchase workflow that moves through a status lifecycle; a separate apply step then adds the ordered quantities to inventory. And they review an Activity feed of inventory, order and sign-in events. The whole API is what powers those screens.

Two product realities shape almost every engineering decision you will see:

📵

Server-first writes, cached reads

The client uses server-first writes and a persisted display cache. Offline views may be available, but there is no offline write/sync queue and no optimistic update: the app refreshes its cache only after the server confirms a write. local_id is not evidence of synchronization; on the feature branch the app sends one only when creating an order, as a retry key.

🩺

Safety-critical data

Stock correctness matters to users. Item/order stock changes use transactions and targeted audit records. Not every operation has a before/after audit; the display cache can be stale.

Runtime topology

Here is the production topology the repository declares (Dockerfile, docker-entrypoint.sh, render.yaml); live Render and Neon settings cannot be verified from the source. Trace the path of one request through it, then we'll narrate each hop.

  1. Mobile → HTTPS — the Expo app makes TLS requests to the public API URL. Native HTTP clients are not subject to CORS (browsers enforce it), which is why the configuration can use a wildcard origin. The reverse also holds: CORS is not authentication, and no CORS_ORIGINS value would stop the Android app (or curl) from calling the API; bearer tokens and owner-scoped queries do that work. The render.yaml blueprint currently sets CORS_ORIGINS='["*"]' even for production. So the app runs in allow-all, no-credentials mode (more in the security chapter).
  2. Render edge → Gunicorn — Render terminates TLS and forwards to the container. The process manager is Gunicorn, configured with --worker-class uvicorn.workers.UvicornWorker --workers 2 (Dockerfile:81). Gunicorn owns the master process and supervises workers.
  3. Uvicorn (2 workers) → FastAPI — each worker is an async ASGI event loop running one copy of our app. Two workers means two independent event loops and two independent DB connection pools.
  4. FastAPI app → Neon Postgres — handlers run on the loop and await non-blocking SQL over asyncpg against the managed Postgres instance. TLS to the database, with certificate and host-name checks, is required outside development and testing.
  5. Attached services — Brevo sends transactional email (verification, password reset) when MAIL_PASSWORD is set; Sentry captures exceptions and a 10% trace sample when SENTRY_DSN is set. Both are optional and configured purely through environment variables.
  6. Probes — Render's single health check (healthCheckPath: /live, render.yaml:20) and the container's HEALTHCHECK (Dockerfile:74-75) both poll /live, which checks only the process. That is deliberate: a brief Neon outage should not trigger restarts. The other probe, /health, runs SELECT 1 with a 2-second timeout and returns 503 when the database is unavailable. It is a readiness signal for clients, the mobile preflight check and local docker-compose. As configured, Render does not use it, so a database outage neither restarts nor depools the instance. Neither probe identifies the deployed code: both report APP_VERSION, a setting that defaults to 1.0.0 and that render.yaml does not set, so a healthy /health says nothing about which commit is running.
🔬 Under the Hood

Why Gunicorn and Uvicorn? Uvicorn is the ASGI server that actually speaks HTTP and drives the asyncio event loop. Gunicorn is a mature, widely used process manager: it forks workers, restarts crashed ones, reloads on SIGHUP and shuts down gracefully on SIGTERM (waiting up to graceful_timeout for in-flight requests). Running Uvicorn as a Gunicorn worker class combines Uvicorn's async server with Gunicorn's supervision and multi-process fan-out. This repo uses uvicorn.workers.UvicornWorker, which Uvicorn 0.34 marks as deprecated; the maintained options are the separate uvicorn-worker package (uvicorn_worker.UvicornWorker) or Uvicorn's own --workers supervisor. Two workers on a small Render plan is a deliberate concurrency-vs-memory trade-off.

Stateless app, attached backing services

The architecture is textbook Twelve-Factor. The application process holds no durable state of its own: no local files, no in-memory sessions, no sticky data. Everything the app must keep lives in an attached backing service: Postgres for data, Brevo for mail, Sentry for telemetry. Each is configured purely from environment variables (DATABASE_URL, the Brevo API key in MAIL_PASSWORD, SENTRY_DSN). Configuration arrives the same way, parsed once into a typed, validated settings object (Chapter on config). This is what makes the app horizontally scalable and disposable. Either of the two workers — or a fresh replacement after a crash — can serve any request, because the truth lives in the database, not in the process. One deliberate departure: schema migrations run at container start (docker-entrypoint.sh) rather than as a separate one-off admin process, as Twelve-Factor XII suggests.

💡 Interview Insight

When an interviewer asks "how would you scale this?", the answer is unlocked by statelessness. Because no request depends on process-local memory, you scale by adding workers/instances behind the load balancer. The shared limits are in PostgreSQL. One is the connection budget. Others are lock hot spots. One is the per-day order-number counter row: it is held until the order commits, so concurrent order creation for all users queues on it. Another is the user-row locks during login and refresh. On the feature branch, every AI reservation also takes one global transaction-scoped advisory lock (pg_advisory_xact_lock(72401931)) for a short counting transaction. An honest caveat worth volunteering: slowapi here keeps its counters in process memory, because no shared storage is configured. So each of the two workers, and each instance, counts separately, and the counters reset on every restart.

One entrypoint: the application factory

Everything starts from a single ASGI callable that Gunicorn/Uvicorn imports as app.main:app. That object is built by an application factory, create_app(), and instantiated exactly once at module load.

    app = FastAPI(
        title=settings.APP_NAME,
        version=settings.APP_VERSION,

The factory pattern (create_app() in app/main.py, called at the bottom of the module) gives you centralized, explicit ordering of middleware, routers and handlers in one function. That order is exactly what determines runtime behaviour. Be precise about what it does not buy here:

  • It is not side-effect free at import. Importing app.main also installs the redacting log-record factory, configures logging, initialises Sentry when SENTRY_DSN is set, loads and validates settings, and creates the database engine.
  • Tests do not build fresh apps. The factory, create_app(), takes no parameters and reads module-level settings. So the test suite reuses the module-level app and overrides get_db and the limiter, instead of building an app from overridden settings.

Notice the docs are gated on DEBUG — in production Swagger and the full OpenAPI schema are simply not exposed, shrinking the attack surface.

📝 Note

The factory pairs with an ASGI lifespan context manager (app/main.py). The code before yield runs once on startup. The code after it runs on graceful shutdown, where await dispose_engine() closes the pool cleanly. Table creation there is gated to development only — production relies entirely on Alembic migrations.

Follow one request

03 End-to-End Request Lifecycle

We trace a single authenticated request: POST /api/v1/items with a bearer token and a JSON body. We follow it from the raw TCP socket all the way back to JSON on the wire. This is the spine of the whole guide: almost every other chapter is a zoom-in on one stage you meet here.

In one line One client request is handled cooperatively on one event loop (the BaseHTTPMiddleware layers run inner work in child tasks). It passes through the middleware onion and resolves its dependencies (DB session and current user). Then the handler runs and commits its writes explicitly before returning, and the response model is serialized. On an error, the get_db dependency rolls back pending work, but an earlier commit stays durable. Every await yields control back to the loop.

The journey, stage by stage

FastAPI is a thin, ergonomic layer over Starlette (the ASGI toolkit) and Pydantic (validation). The app object built by create_app() is, underneath, a callable implementing the ASGI contract async def __call__(scope, receive, send). Everything below is what happens between Uvicorn invoking that callable and the bytes leaving the socket.

  1. Uvicorn accepts the socket & builds the ASGI scope — Uvicorn (the ASGI server) accepts the TCP connection and parses the raw HTTP/1.1 bytes. It then builds an ASGI scope dict: type="http", method, path, headers, query string and client address. It then calls app(scope, receive, send) on the running event loop. receive is an awaitable that streams the request body in chunks; send pushes response events back out.
  2. The middleware onion (inbound) — the request climbs the wrapped layers. The crucial gotcha: add_middleware prepends, so registration order is the reverse of inbound execution order. Registered as CORS, then add_request_id, then add_security_headers, and finally (on the feature branch, after the routers) the pure-ASGI AIBodyLimit app/main.py, the user-middleware inbound order is AIBodyLimit → security-headers → request-id → CORS. (On main, without AIBodyLimit, it is security-headers → request-id → CORS.) Starlette wraps these in ServerErrorMiddleware (outermost) and places ExceptionMiddleware between CORS and the router. AIBodyLimit reads the entire body first: 2,000,000 bytes at most for ordinary routes, 12,000 for AI JSON routes and 900,000 for /ai/transcribe (413 above that); an AI request without a Bearer header gets 401 before any body is read, and an AI request body has a 10-second read deadline (408). The two function middlewares then call await call_next(request) to descend inward.
  3. Routing & path-operation match — Starlette's router matches POST /api/v1/items against the merged route table (the /api/v1 aggregate router plus the health routes) and selects the matching path operation function.
  4. Body parsing, then dependency resolution — for a route with a body, FastAPI first reads it and decodes the JSON. Malformed JSON is rejected right here with a 422 (json_invalid): no token check and no SQL. Then FastAPI walks the dependency graph. First, get_db opens an AsyncSession and yields it app/core/database.py; no connection is taken from the pool until the first query runs. Then get_current_user reads the bearer credential, verifies the JWT, loads the user row with noload("*") and checks its session_version app/api/deps.py. A bad token stops the request here with 401, before any body validation.
  5. Pydantic validates parameters and body — only now are path, query and body values checked against the handler's schemas. A validation failure never reaches your code: errors are collected, the handler is skipped, and RequestValidationError is raised only after get_db has exited (so a valid token has already cost one user SELECT). The global handler reshapes it into a structured {field, message, code} 422 app/main.py.
  6. The handler coroutine runs — the async path operation executes on the event loop, await-ing non-blocking asyncpg I/O over a pooled connection. Each await is a suspension point where the loop is free to service other requests. Like every write endpoint that uses get_db (the routers contain 25 explicit await db.commit() calls), the handler commits explicitly before returning. (The feature branch's /ai/* routes are the exception: they do not use get_db and run their consent and usage writes in their own short transactions.) That lets it call db.refresh() and serialize the persisted row: app/api/v1/items.py, for example, commits and then refreshes the new item.
  7. Response serialization — when the handler returns, FastAPI serializes the result through the route's response_model (Pydantic), filtering and coercing fields to JSON-native types.
  8. Dependency teardown — the safety net — get_db's post-yield code runs. First comes await session.commit(): a fallback that usually just ends the read transaction that db.refresh() began, because the handler already committed its writes. Then finally: await session.close() returns the connection to the pool app/core/database.py. Its real guarantee is the except: await session.rollback() branch — an exception rolls back only the currently uncommitted transaction. Timing matters: in the pinned FastAPI 0.115.6 this teardown runs after the response is serialized but before it is sent, so a failing teardown commit becomes an error response. FastAPI 0.118 moved teardown to after sending; re-check this if you upgrade.
  9. Headers stamped on the way out — the response descends the onion outward. CORS adds Access-Control-* headers only when the request carried an Origin header (browsers do; native mobile requests normally don't). The request-id wrapper echoes X-Request-ID. The security wrapper stamps nosniff, X-Frame-Options: DENY, the legacy X-XSS-Protection: 1; mode=block, Referrer-Policy, Cache-Control: no-store and (prod only) HSTS app/main.py. Unhandled-exception 500s produced by ServerErrorMiddleware skip all three wrappers; this was reproduced on 7 and 8 October 2026 (no X-Request-ID, no security headers, no Cache-Control).
  10. JSON returned — Uvicorn serializes the ASGI send events back into HTTP bytes and writes them to the socket. Any background tasks (the auth emails) run only after the body has been sent. The coroutine is done; the connection may be kept alive for the next request.
🔬 Under the Hood

ASGI = scope + receive + send. ASGI replaces WSGI's single synchronous (environ, start_response) call with three async primitives. The first, scope, is a dict describing the connection. Its type is "http", "websocket" or "lifespan", and middleware should copy it before changing it. The second, receive, is an awaitable you call to pull inbound events (body chunks, disconnects). The third, send, is an awaitable you call to push outbound events: http.response.start with status and headers, then http.response.body. Middleware is just a callable that wraps another ASGI app and can intercept any of these. Because every primitive is a coroutine, a single OS thread can multiplex thousands of mostly idle connections — the loop parks a request at each await and runs another. Database-bound concurrency is still capped by the connection pool (up to 15 connections per worker here, with a 30-second wait for a free one).

The middleware onion, concretely

The two original custom middlewares are function middlewares (Starlette's BaseHTTPMiddleware), registered with the @app.middleware("http") decorator. (The feature branch adds a third, AIBodyLimit, written as a raw ASGI class so it can read the body stream and swap in its own receive callable before anything parses the request.) They follow the chain-of-responsibility shape: do something, call inward, then mutate the response on the way back out.

app/main.pyPython
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID") or uuid4().hex
    response = await call_next(request)   # <-- descend into inner layers + handler
    response.headers["X-Request-ID"] = request_id
    return response                        # <-- response now flows back outward

The wrappers add headers after call_next returns a response. That includes errors converted by the inner ExceptionMiddleware (HTTPException, 422, 409, 429). Unhandled exceptions are different. The outer ServerErrorMiddleware turns them into the 500 JSON. So in this Starlette version (0.41.3), those responses carry no X-Request-ID, no security headers and no CORS headers. A CORS preflight (an OPTIONS request with an Origin) may short-circuit before reaching a route. On the feature branch, the responses that AIBodyLimit produces itself (401 for an AI request without a bearer token, 413 for an oversized body, 408 for a slow AI request body) are also built outside the two function middlewares and CORS, so they lack the security headers, X-Request-ID and CORS headers too.

Dependency resolution: session, then user

FastAPI's DI is recursive. The handler declares db: DB and current_user: CurrentUser; those aliases app/api/deps.py expand to Depends(get_db) and Depends(get_current_user). Critically, get_current_user itself depends on get_db app/api/deps.py, and FastAPI resolves the shared dependency once per request. So the auth lookup and the handler run inside the same session — and, until the handler commits, the same transaction.

app/api/deps.py (excerpt)Python
payload = decode_token(credentials.credentials)

The noload("*") is a deliberate performance choice. It switches off the model's eager selectin relationship loads, so the bearer-token check on every request stays a single scalar SELECT. Without it, each check would fan out into extra SELECT … IN queries it doesn't need. That protection covers only this dependency. In the September version, login, refresh, register and PATCH /auth/me also called db.refresh(user) after committing, which re-ran every selectin loader and loaded the user's whole data graph (seven extra SELECTs in a local measurement). The feature branch no longer does: each of those handlers carries a "No db.refresh(user)" comment and serializes the scalar columns it already holds (expire_on_commit=False keeps them readable), and every User query in auth.py passes noload("*"). (main still calls db.refresh(user) in those four handlers.) The dependency raises 401 in three cases. The token may be missing, malformed, expired or not an access token. The user may no longer exist. Or its session_version may no longer match after a password change or reset. A disabled account gets 403, and so does an unverified email when verification is required. In every case the handler never runs.

The transaction boundary — when exactly does it commit?

get_db is an async-generator dependency, which FastAPI treats as setup/teardown around the handler. It scopes the session — SQLAlchemy's Unit of Work, which collects changes and flushes them together — to the request. Each transaction, however, ends wherever a handler commits:

app/core/database.pyPython
async with AsyncSessionLocal() as session:
    try:
        yield session            # <-- handler runs here, with the session
        await session.commit()   # <-- after the handler returns and the response
                                 #     is serialized (FastAPI 0.115.6)
    except Exception:
        await session.rollback() # <-- rolls back only work not yet committed
        raise
    finally:
        await session.close()    # <-- always returns the connection to the pool
💡 Interview Insight

Rollback cancels only the current uncommitted transaction. A handler often commits before refreshing or serializing its response; a later failure cannot undo that commit. A request error therefore does not prove no write occurred. This is why lost-response create retries still need an idempotency design. On the feature branch, POST /orders has one when the client sends a localId; item and category creates still rely only on their duplicate-name 409.

⚠️ Pitfall

Because handlers keep using ORM objects after they commit (they db.refresh() then serialize the row into the response model), the session factory sets expire_on_commit=False app/core/database.py. By default SQLAlchemy expires every ORM attribute on commit, so the next attribute read triggers a lazy reload — and in async SQLAlchemy an implicit lazy load raises MissingGreenlet. Keeping attributes un-expired makes post-commit access safe — the kind of subtle async detail interviewers love to probe.

📝 Note

There is a twin, get_db_context app/core/database.py, with the same commit/rollback/close logic exposed as an @asynccontextmanager. Its only caller today is the /health readiness probe, which wraps the whole session in asyncio.wait_for(..., 2.0) so a slow database cannot hang the probe. It is also the helper to use from scripts or jobs that run outside FastAPI's Depends machinery. (The feature branch's AI routes take a third route: they open AsyncSessionLocal() directly for each short step — authentication, the usage reservation and its settlement — so no pooled connection is held while the server waits up to 25 s for the model provider.)

One event loop, many yield points

The whole chain — middleware, dependency resolution, handler, commit, serialization — runs as cooperative tasks on one event loop (the BaseHTTPMiddleware layers run inner work in child tasks). There is no thread per request. Every await (the DB round-trip in get_current_user, the inserts in the handler, the commit) is a suspension point: the loop parks this request and runs another while Postgres is busy. That is why an async stack can hold thousands of mostly idle connections on a handful of OS threads. Database-bound concurrency is bounded by the 15-connection pool per worker, not by the loop.

✅ Pro Tip

The corollary an interviewer wants to hear: one synchronous blocking call poisons the whole loop. Think of a naive time.sleep(), a sync requests.get() or a CPU-bound hot loop inside a handler. Each one blocks the single thread and stalls every other in-flight request, not just the one that called it. In async FastAPI, "await everything I/O-bound, offload everything CPU-bound" is the load-bearing rule.

🛡️ Security / OWASP

Response middleware stamps responses returned through call_next, including handled errors. Unhandled exceptions are converted into 500s by the outer ServerErrorMiddleware, so in this Starlette version (0.41.3) those 500s lack the security headers, Cache-Control: no-store, X-Request-ID and CORS headers (reproduced 7 and 8 October 2026; tracked as finding A-13 in the API traceability guide). Do not claim every response carries the same headers.

Exception responses hide database internals, and the local logging factory removes raw exception values. Rollback covers pending work only; previously committed writes remain even if response serialization or later code fails.

04 Project Structure & Layered Architecture

CareKosh keeps its packages layered by import direction: each directory owns one kind of responsibility, and imports point inward. Most workflow logic, however, lives in the route handlers themselves (a transaction-script style: each handler is a procedure that runs one business transaction), with thin helpers in services. Knowing that shape honestly — and when you would extract a service layer — is what lets you defend it in an interview.

In one line Imports point inward (api → schemas/services/models → core). Request handling is mostly transaction-script code in the api routers, with two small inventory helpers in services (audit staging, advisory name locks) plus, on the feature branch, three AI-module files. The dependency-injection seam is the Annotated aliases in deps.py.

The shape of the codebase

Open app/ and you find six packages plus main.py, not a tangle. The api package holds routers and the dependency wiring. The schemas are the Pydantic validation boundary. The services package holds two small shared helpers (audit staging and advisory name locks), and on the feature branch also the AI module's body-limit middleware, guard and provider adapter. The models are the SQLAlchemy ORM. The core package is the infrastructure spine (config, database engine, security, logging). And utils holds helpers like the rate limiter and the email client. The rule that makes this a layering rather than just folders: import arrows point one way (the single exception is named at the end of this chapter).

Walking each layer, top to bottom

Trace a single request and the layers introduce themselves in order. An HTTP call lands on a router in app/api/v1/. The router's signature pulls in a validated schema (the request body) and injected dependencies — a DB session, the current user — resolved by FastAPI. The handler itself holds most of the workflow: ownership checks, status transitions, conditional updates and the commit. It calls small service helpers where they exist (for example log_audit), and queries and changes models directly. Models and services rely on core for the session factory and config. The utils package sits off to the side and depends only on core (email.py reads settings). Every layer below is reachable from the one above; apart from that one exception, never the reverse.

🔬 Under the Hood

Annotated[T, Depends(f)] attaches DI metadata to a type without changing the type itself. FastAPI inspects the function signature, sees the Depends marker inside the annotation, and registers f as a provider it must resolve before calling the handler. The alias is just that annotation given a name. So DB = Annotated[AsyncSession, Depends(get_db)] is DRY dependency injection: define the wiring once and reuse it in every endpoint, while your IDE still sees a real AsyncSession.

Why the dependency direction matters

The discipline is simple to state: api may import from schemas, services, models and core, while core imports only from core. For example, deps.py imports get_db from core.database, decode_token from core.security, settings, is_email_configured from utils.email, and the User model. None of those modules imports from api (app/api/deps.py). Config and the database engine do not import routers, although config carries policy values such as REQUIRE_EMAIL_VERIFICATION and token/email expiry settings. One honest exception arrived with the feature branch: app/services/ai_guard.py imports get_current_user and the HTTPBearer scheme from app/api/deps.py, a services → api arrow. It creates no import cycle (deps.py imports nothing from services), but it is the kind of drift a reviewer should name; resolving the user in the api layer and passing only its id to the guard would restore the one-way rule.

  1. Testability — Because the seam is DI, a test overrides get_db with a test session and the entire stack runs against a throwaway database, no production wiring touched. The suite does exactly this (override get_db, disable the limiter) and drives the app in-process over ASGITransport.
  2. Change isolation — Resource routers that say user: CurrentUser do not change if token verification changes inside deps.py/core.security. auth.py, which issues, rotates and revokes tokens and hashes passwords, would change.
  3. Transaction handling — get_db (app/core/database.py) owns the session lifecycle and rolls back uncommitted work on error. But write handlers commit explicitly (items.py, orders.py, categories.py, auth.py), and two handlers roll back explicitly (the HTML email-verification page and the order-create localId race). Logic added to get_db's commit would therefore run after the data is already committed.

Foundations

05 Async, the Event Loop & ASGI vs WSGI

This codebase is built on one deceptively simple promise: a single Python worker can keep many requests in flight at once. That works because waiting on I/O can release the event loop. (How many CareKosh can actually sustain has not been measured; database-bound work is capped at 15 pooled connections per worker.) Each request still consumes memory, connections and other resources. Know exactly why that is true, and the one thing that breaks it. That knowledge separates a candidate who has "used FastAPI" from one who can reason about a production system under load.

In one line FastAPI runs your async def handlers on a single-threaded event loop. An await on I/O yields the loop to other requests. But a blocking call (like a slow Argon2 hash) freezes every request on that worker. That is why this code pushes hashing onto a thread with anyio.to_thread.run_sync(...).

Concurrency from first principles

A coroutine is a function you can pause and resume. When you write async def, calling it does not run the body — it returns a coroutine object. The event loop is the scheduler that actually drives coroutines forward. It runs one coroutine until it hits an await on something not yet ready (a socket with no bytes, a DB query in flight). At that point the coroutine yields control back to the loop, and the loop picks another ready coroutine to advance. This is cooperative multitasking: tasks voluntarily hand back the CPU at await points. Nothing preempts them.

The payoff is concurrency without threads. While one request waits 30 ms for Postgres to answer, the loop is not idle — it advances 50 other requests. A single OS thread, doing nothing during I/O, multiplexes thousands of in-flight operations. That is the entire reason an async web server scales the way it does.

🔬 Under the Hood

The event loop is essentially a while True loop wrapped around the OS epoll/kqueue syscall. It registers every pending socket with the kernel, then sleeps until the kernel reports that some file descriptors are ready. For each ready descriptor, it resumes the coroutine that was awaiting it, runs it until the next await, and loops. "Async I/O" is not magic parallelism — it is one thread reacting to kernel readiness notifications, fast.

async vs threads vs processes — and the GIL

Why not just use threads? Because standard CPython builds have a Global Interpreter Lock (GIL): only one thread executes Python bytecode at a time. The optional, experimental free-threaded build available since Python 3.13 removes it; this project runs regular CPython 3.12. Threads help when work is I/O-bound, because a blocked thread releases the GIL so another can run. But they cost context switches and memory, and they give no true parallelism for Python-level CPU work. The async model avoids thread overhead entirely for I/O. There is one thread and no locks around shared state between tasks. A coroutine only pauses at explicit await points, so there are no surprise interleavings in the middle of a statement. For CPU-bound work you still need real parallelism — which means processes (multiple workers, each with its own GIL) or, pragmatically, threads for native code that releases the GIL.

ASGI vs WSGI — and why FastAPI needs ASGI

WSGI (Web Server Gateway Interface) is the old Python standard: a synchronous callable app(environ, start_response) that handles exactly one request, top to bottom, on the calling thread. It has no concept of await and no model for long-lived, two-way connections. It can stream a response body through an iterable, but it has no WebSockets or lifespan events. It also cannot express a coroutine that pauses mid-request. Flask and Django classically ran on WSGI servers (Gunicorn, uWSGI), getting concurrency from threads, processes or green threads (gevent/eventlet).

ASGI (Asynchronous Server Gateway Interface) is the async successor. The app is an async callable: async def app(scope, receive, send). The scope describes the connection (an http request, a websocket, or a lifespan event); receive/send are awaitable channels for streaming messages in and out. Because the app is a coroutine, it can await the database and yield the loop. And because the protocol models persistent connections, it supports WebSockets and long-lived streams, which WSGI structurally cannot. FastAPI is a Starlette subclass that implements exactly this interface. Uvicorn is the ASGI server: it parses raw HTTP off the socket into a scope and calls your app on the loop. In this project, that callable is the module-level app object imported as app.main:app app/main.py. In production it is served by Gunicorn with two uvicorn.workers.UvicornWorker processes (Dockerfile CMD); the uvicorn.run("app.main:app", ...) call in app/main.py is only the local python -m entry point.

The one pitfall that matters: blocking the event loop

Here is the trap that separates correct async code from a production incident. The loop is single-threaded. Suppose an async def handler calls a function that does CPU work or blocking I/O without awaiting: a tight loop, a synchronous HTTP client, a slow cryptographic hash. That handler never yields. The loop is stuck inside that one call. Every other in-flight request on that worker is frozen until it returns, because there is no other thread to run them. One slow operation in one request degrades latency for all concurrent requests.

⚠️ Pitfall

Calling a blocking library inside an async def route doesn't just slow that request — it stalls the entire worker. A single time.sleep(5), requests.get(...), or unthreaded password hash inside a coroutine makes your p99 latency for every concurrent caller spike by the same duration. Async failures are rarely loud; they show up as mysterious tail-latency under load.

The exact mitigation in this codebase

Password hashing is the canonical offender. This app uses Argon2 — an intentionally memory-hard, CPU-bound key-derivation function (KDF) whose slowness is the security property. It runs with argon2-cffi's default cost through passlib: argon2id, 64 MiB of memory, 3 passes, 4 lanes (RFC 9106's second recommended, low-memory option). That is about 20 ms per verify on a multi-core laptop (a local measurement); it has not been measured on the production instance. Running it directly in a handler would pin the loop for the whole hash. So every call site wraps the synchronous hash_password / verify_password in anyio.to_thread.run_sync(...). That sends the blocking function to a worker thread and awaits the result, which frees the loop to serve other requests while the hash runs.

⚠️ Misconception — "async makes it faster"

Async does not make CPU-heavy work faster. An Argon2 hash costs the same CPU time whether it runs on the event loop or in a thread (about 20 ms locally; a single verify on a laptop took about 23 ms on 7 October 2026; never measured on the production instance). Moving it to a thread only keeps the loop free for other requests; the login itself still waits for the hash, and every concurrent hash still competes for the container's CPU and 64 MiB of memory each. Async helps with waiting (database, network), not with computing.

💡 Interview Insight

"Why hash in a thread, but query the database on the loop?" is the question that proves you actually understand async. The answer: Argon2 is CPU-bound. It keeps the CPU busy with no I/O wait, so there is no natural await point. Left on the loop, it blocks everything, so you move it to a thread. A Postgres query is I/O-bound. The work happens in the database, and the async driver (asyncpg) yields the loop as soon as the request is on the wire. It resumes when the answer arrives. Threading the DB call would add overhead for zero benefit; threading the hash is mandatory. The discriminator is CPU-bound vs I/O-bound, not "slow vs fast."

🔬 Under the Hood — why a thread, not a process, for Argon2

The textbook rule, straight from Python's own asyncio docs, is CPU-bound → process pool, blocking I/O → thread pool. The reason is the GIL: only one thread can execute Python bytecode at a time, so threads give no real parallelism for Python-level CPU work. Argon2 looks like it should therefore need a process. It doesn't: argon2-cffi (and bcrypt) do the heavy computation in native code (C via CFFI for argon2-cffi, Rust for bcrypt 4.x) that releases the GIL while hashing. So a worker thread really does run the hash in parallel with the event loop, given a spare CPU core. (On a fractional-CPU container, the hash and the loop share the same quota.) And it avoids a process pool's pickling, IPC and cold-start costs. That is the exact reason the right tool here is anyio.to_thread.run_sync and not a ProcessPoolExecutor. If you're tempted to say "CPU-bound always means processes," this GIL-releasing native code is the senior-level exception to name.

The two escapes from blocking

When you must run blocking code, you have two sanctioned escapes, and FastAPI gives you both:

  1. Offload to a thread yourself — anyio.to_thread.run_sync(fn, *args) (or the lower-level loop.run_in_executor). You stay in an async def handler and explicitly punt the blocking call to AnyIO's worker-thread pool. This is exactly what the auth routes do. AnyIO's default limiter (40 tokens per event loop, that is, per worker) bounds threads, not memory. Each Argon2 hash here allocates 64 MiB, so 40 concurrent hashes need about 2.5 GiB per worker. On a small instance (render.yaml declares plan: starter), memory and CPU quota run out long before the thread cap. A dedicated, smaller CapacityLimiter for hashing, plus rate limits, would be the real backpressure.
  2. Write a plain def route — declare the path operation as def (not async def). FastAPI detects it and runs the entire handler in the threadpool automatically, so blocking inside it never touches the loop. The catch: a def route can't await the async DB session, so you'd lose the async ORM. The auth routes are async def precisely so they can await asyncpg while still threading just the hash.
✅ Pro Tip

Reach for a sync def route when the whole handler is blocking (e.g. a legacy sync SDK with no async equivalent). Reach for anyio.to_thread.run_sync when the handler is mostly async (awaiting the DB) and only one call blocks. You keep the async benefits and move just that one hot spot to a thread. This codebase is a textbook case of the second.

💡 Interview Insight — the hidden concurrency ceiling

"You have 200 concurrent requests hitting a sync def handler that does blocking work — what happens?" Strong answer: at most 40 run at once. FastAPI and Starlette offload sync handlers and sync dependencies to AnyIO's worker-thread pool. Its default CapacityLimiter is 40 tokens, shared by the whole worker process (one event loop per worker). Request 41 queues behind them. Crucially that 40-thread ceiling is independent of your SQLAlchemy pool_size — they are two separate bottlenecks that compose, and whichever is smaller bites first. Naming both ceilings — and that the thread pool is shared with sync dependencies — is exactly the kind of detail that signals you've run async in production.

Async drivers vs sync drivers — the silent trap

An async stack is only async end-to-end if every layer cooperates. This project pairs SQLAlchemy 2.0's async engine with asyncpg, the native async Postgres driver, configured at app/core/database.py. The asyncpg driver performs non-blocking socket I/O, so await db.execute(...) really yields the loop while Postgres works. The classic mistake is to use the synchronous driver (psycopg2) or call a synchronous ORM method inside an async def handler. That call blocks the socket read on the loop's thread. It silently brings back the very stall you were avoiding, without obvious symptoms.

⚠️ Pitfall

Mixing a sync ORM/driver into async code is the most insidious blocking bug, because nothing crashes — it just doesn't scale. A handler using psycopg2 under an event loop will appear correct in a single-user test and collapse under concurrency, since each query blocks the loop for its full round-trip. On the async engine, the entire data path (driver, session, queries) must be awaited. That is why the session factory is async_sessionmaker(class_=AsyncSession, ...) and the dependency yields an AsyncSession at app/core/database.py.

📝 Note

The async session factory sets expire_on_commit=False app/core/database.py for a related reason. With expiry on, reading an ORM attribute after commit triggers a lazy reload. That is implicit I/O, which async SQLAlchemy forbids, so it would raise wherever a handler reads attributes after its own await db.commit() (chapter 08 has the details). It is a small but telling sign of how "everything must be awaited" reshapes ordinary ORM habits in an async world.

Putting it together: one worker, many requests

Trace a burst of logins hitting a single Uvicorn worker. Uvicorn parses each request into an ASGI scope and schedules the login coroutine on the loop. Each coroutine reaches await db.execute(...) — asyncpg sends the query and yields, so the loop immediately advances the next pending login. As Postgres answers come back, the kernel marks those sockets ready and the loop resumes each coroutine to the next step: the Argon2 verify. That verify is dispatched to the thread pool via anyio.to_thread.run_sync, so even the CPU-bound check doesn't monopolize the loop. The net effect: a single thread keeps dozens of logins in flight at once. None of them can block the others, because the Argon2 step runs off the loop. (The September version also ran a post-commit db.refresh(user) that loaded the user's related rows; the feature branch removed it, while main still has it, see chapter 08.) The limits are real, though. Each in-flight login holds one pooled connection and a SELECT … FOR UPDATE lock on that user's row while its Argon2 verify runs in the thread pool. So at most 15 logins per worker can be in that phase; the rest wait for a connection (up to 30 s). Production runs two such workers. That is the whole design, in one request.

1 · Routing & path operations

A path operation is a function plus a decorator that registers it on an APIRouter. The router in app/api/v1/items.py is created with a prefix and OpenAPI tags, APIRouter(prefix="/items", tags=["Items"]), then individual operations attach to it. What makes FastAPI feel magical is that it introspects the function signature at registration time: there is no separate route table that re-declares each parameter. The type hints are the schema.

app/api/v1/items.py (excerpt)Python
@router.get(
    "",
    response_model=ItemList,
    summary="List all items",
)
async def list_items(
    db: DB,
    current_user: CurrentUser,
    category_id: Optional[str] = Query(None, alias="categoryId"),
    # … isActive, isCritical, lowStockOnly, outOfStockOnly filters …
    search: Optional[str] = Query(None, max_length=100),
    page: int = Query(1, ge=1),
    page_size: int = Query(50, ge=1, le=100, alias="pageSize"),
) -> ItemList:

FastAPI classifies each parameter by a simple set of rules, visible in this one signature (app/api/v1/items.py):

  • Path params — names that appear in the route template, like item_id in @router.get("/{item_id}") at app/api/v1/items.py. They are taken straight from the URL.
  • Query params — scalar-typed parameters that are not in the path (required when they have no default), or ones wrapped in Query(...), like page and search above. The ge=1, le=100 and max_length=100 constraints are enforced before your code runs.
  • Body params — params typed as a Pydantic BaseModel, like data: ItemCreate in app/api/v1/items.py. FastAPI reads the request body, parses JSON, and validates it against the model.
  • Dependencies — anything resolved via Depends(), here hidden behind the DB and CurrentUser aliases (more on those next).

Two more declarative knobs do real work. status_code=status.HTTP_201_CREATED on the create handler (app/api/v1/items.py) sets the success status without you ever touching a Response object. And response_model — ItemList on the list endpoint, ItemResponse on the single-item endpoint (app/api/v1/items.py) — declares the output contract, which is what powers serialization, filtering, and the OpenAPI schema.

🔬 Under the Hood

FastAPI calls inspect.signature() on every handler at startup, walks the parameters, and builds a Dependant object — a tree describing how to extract and validate each argument. At request time it executes that tree, not your raw function directly. The classification (path vs query vs body) is decided once at registration, so the per-request cost is just running the pre-built extractors. That is why the type hints must be accurate: they are compiled into the request contract.

2 · Dependency Injection — Depends() and the resolution graph

Dependency injection is FastAPI's most distinctive feature. A dependency is just a callable. Depends(callable) tells FastAPI: call this, validate its own parameters recursively, and pass the result in. CareKosh defines its building block — the per-request DB session — as a yield-dependency:

app/core/database.py (excerpt)Python
async def get_db():
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
        finally:
            await session.close()

This is the setup/teardown pattern. Everything before yield runs before the handler, and the handler receives the yielded session. Everything after yield runs once the handler has returned or raised. In FastAPI 0.115.6 that is after the response has been serialized but before it is sent. That makes get_db the session boundary: it commits whatever is still pending on success, rolls back on any exception and always closes. Write handlers commit explicitly inside it. (The full transaction story lives in the persistence chapter — here the point is purely how FastAPI drives the generator.)

The Annotated type-alias pattern

Repeating db: AsyncSession = Depends(get_db) in forty handlers is noise. CareKosh collapses each dependency into a reusable type alias at the bottom of app/api/deps.py:

app/api/deps.pyPython
CurrentUser = Annotated[User, Depends(get_current_user)]
ActiveUser = Annotated[User, Depends(get_current_active_user)]
VerifiedUser = Annotated[User, Depends(get_current_verified_user)]
SuperUser = Annotated[User, Depends(get_current_superuser)]
OptionalUser = Annotated[Optional[User], Depends(get_optional_user)]
DB = Annotated[AsyncSession, Depends(get_db)]
Pagination = Annotated[PaginationParams, Depends()]

Only DB and CurrentUser are used by routes today; ActiveUser, VerifiedUser, SuperUser, OptionalUser and Pagination are defined but unused (the list routes declare their own page/pageSize query parameters). The feature branch's five /ai/* routes use a third alias defined in app/api/v1/ai.py, Principal = Annotated[AIPrincipal, Depends(principal)]. Its principal function opens a short session of its own and calls get_current_user directly, so the same token, session-generation, active-account and email-verification rules apply without holding a get_db session for the whole request.

Annotated[T, Depends(...)] bundles the type with the injection metadata (the Depends) in a single name. Your editor and type-checkers use the type (T); FastAPI does not validate a dependency's return value against it. A handler then reads as plain English — db: DB, current_user: CurrentUser — and FastAPI unwraps the alias to find the dependency. It is DRY, it keeps type information for IDEs and type-checkers, and it centralizes the wiring: change how get_current_user works and every endpoint inherits it. Note Pagination = Annotated[PaginationParams, Depends()] at app/api/deps.py — with no argument, Depends() uses the annotated class itself as the callable, instantiating PaginationParams (app/api/deps.py) from the request's page/page_size query params.

The auth dependency chain (sub-dependencies)

Dependencies can depend on other dependencies, forming a graph FastAPI resolves bottom-up. The verified-user check does not re-authenticate — it depends on get_current_user and only adds one rule on top:

app/api/deps.py (excerpt)Python
async def get_current_user(
    db: Annotated[AsyncSession, Depends(get_db)],
    credentials: Annotated[
        Optional[HTTPAuthorizationCredentials],
        Depends(security),
    ],
) -> User:
    if not credentials:
        raise HTTPException(401, "Not authenticated", ...)
    payload = decode_token(credentials.credentials)
    if not payload or payload.type != "access":
        raise HTTPException(401, "Invalid or expired token", ...)
    result = await db.execute(
        select(User).where(User.id == payload.sub).options(noload("*"))
    )
    user = result.scalar_one_or_none()
    if not user or payload.session_version != user.session_version:
        raise HTTPException(401, "User not found", ...)
    if not user.is_active:
        raise HTTPException(403, "User account is disabled")
    require_email_verification(user)  # 403 EMAIL_NOT_VERIFIED when the policy is on
    return user


async def get_current_verified_user(
    user: Annotated[User, Depends(get_current_user)],
) -> User:
    if not user.email or not user.is_email_verified:
        raise HTTPException(403, "Email verification required")
    return user

If a route asked for VerifiedUser (none does today), FastAPI would resolve a chain. First, get_db opens a session. Next, security (the HTTPBearer(auto_error=False) at app/api/deps.py) extracts the bearer token. Then get_current_user (app/api/deps.py) decodes the JWT (signature, expiry, type "access") and loads the user with noload("*") to suppress relationship fan-out. It returns 401 if the user is missing or the token's session_version no longer matches (sessions revoked by a password change or reset), and 403 for inactive accounts. It also applies the email-verification policy: 403 EMAIL_NOT_VERIFIED when REQUIRE_EMAIL_VERIFICATION is on and email is configured. Finally, get_current_verified_user (app/api/deps.py) adds the verified check. The get_current_superuser dependency (app/api/deps.py) follows the same shape. Each layer is a small, testable, composable unit — the chain-of-responsibility pattern expressed as function signatures.

💡 Interview Insight

When an interviewer asks "what does Depends() actually return, and when is it cached?", they want two facts. (1) It returns the callable's return value — for Depends(get_current_user), the resolved User; for a yield-dependency, the yielded value. (2) Results are cached per request by default. Because get_db appears both in get_current_user and directly in the handler (via DB), FastAPI calls it once and shares the same AsyncSession across the whole request. That is exactly why the auth lookup and the handler's queries share one session — and one transaction, until the handler commits. The cache key is the callable plus its security scopes; pass use_cache=False to force re-execution.

  1. Build the tree — when the route is registered, FastAPI turns the signature into a Dependant tree. It is not de-duplicated: get_db appears twice, under the handler and under get_current_user.
  2. Resolve depth-first, in parameter order — per request it first runs get_db (for db). Next come current_user's own dependencies: get_db again (served from the cache), then the HTTPBearer credentials. Then it runs get_current_user, and only then validates the handler's path, query and body parameters. So an authenticated request with a schema-invalid body still performs the user lookup first. (Malformed JSON never gets this far: the body is decoded before any dependency runs, so it fails with 422 without a token check.)
  3. Cache within the request — each callable runs at most once; later nodes reuse the cached value, so one DB session is shared.
  4. Inject & run — resolved values are passed as named arguments and the handler executes.
  5. Tear down in reverse — after the handler returns, yield-dependencies run their post-yield code (commit/rollback/close) in reverse resolution order. In FastAPI 0.115.6 this happens after the response is serialized and before it is sent; 0.118 moved it after sending.

3 · Pydantic v2 — validation in, serialization out

FastAPI uses Pydantic at both ends of a handler, and they are deliberately different models. The request model validates and coerces untrusted input; the response model filters and shapes trusted output. CareKosh's item schemas show the split cleanly.

The custom 422 handler

When request validation fails, FastAPI raises RequestValidationError. CareKosh intercepts it to return a cleaner, structured body instead of FastAPI's default error format:

app/main.py (excerpt)Python
@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request, exc):
    errors = []
    for error in exc.errors():
        errors.append({
            "field": ".".join(str(loc) for loc in error["loc"]),
            "message": error["msg"],
            "code": error["type"],
        })
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={"error": "Validation Error",
                 "message": "Request validation failed",
                 "details": errors, ...},
    )

This reshapes Pydantic's raw error list into a flat {field, message, code} array (app/main.py) — far friendlier for a mobile client to render inline next to the offending form field. The status stays 422 Unprocessable Entity, the semantically correct code for "well-formed JSON that violates the schema." In this app malformed JSON also gets a 422 (code json_invalid), because FastAPI turns the decode error into the same exception. The handler copies only location, message and type, so submitted values (passwords, tokens) are never echoed back.

💡 Interview Insight

"Why two classes — why not reuse one model for request and response?" Because they have opposite trust and shape requirements. The request model is a gate: it rejects bad input, sanitizes strings, and forces version to be present. The response model is a filter. It whitelists which fields leave the server, so a misnamed column on the ORM object can't accidentally leak. It also applies camelCase aliases and defines the OpenAPI output schema. Sharing one model would mean a field that is optional-on-create becomes optional-on-read, secrets on the ORM object could leak, and you'd lose the 201-with-different-shape pattern. Separation is a security and contract decision, not boilerplate.

Settings done right

07 Configuration & the 12-Factor App

Configuration is where most production incidents quietly begin: a forgotten secret, a database URL that doesn't parse, a wildcard CORS rule shipped to a browser-facing production API. CareKosh's production blueprint does set a wildcard. That is acceptable only because its client is a native app, which CORS does not govern. This chapter shows how CareKosh turns a pile of environment variables into a typed, validated, fail-fast object. It also shows why that one design choice maps cleanly onto Factor III of the Twelve-Factor App.

In one line A single Settings(BaseSettings) class parses the environment once at startup and coerces every value to its declared type. Its validators reject a placeholder or short SECRET_KEY and a missing production FRONTEND_URL. It normalises (but does not validate) DATABASE_URL, and hides SECRET_KEY and MAIL_PASSWORD behind SecretStr. It is created once at import; @lru_cache makes any later call return the same instance.

The shape of the configuration object

Everything lives in one class, app/core/config.py. Because it subclasses BaseSettings from pydantic-settings, each declared field is read automatically from an environment variable of the same name. It is also read from a .env file whenever one exists in the working directory; real environment variables win. Each value is then coerced and validated against its Python type annotation. A string "8000" becomes an int; "true" becomes a bool. If coercion fails, construction raises — the app refuses to boot.

app/core/config.py (excerpt; comments clarified)Python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        case_sensitive=False,
        extra="ignore",
    )

    APP_NAME: str = "CareKosh API"
    DEBUG: bool = False
    ENVIRONMENT: str = "development"  # development, staging, production
    PORT: int = 8000
    DATABASE_URL: str = "postgresql+asyncpg://postgres:postgres@localhost:5432/vitaltrack"

Three flags in model_config carry real weight. The first, case_sensitive=False, means database_url and DATABASE_URL both bind, which is convenient across shells and platforms. The second, extra="ignore", matters for the .env file. With pydantic-settings' default extra="forbid", an unrecognised key in .env is a ValidationError at start-up; "ignore" drops it instead. Unrecognised OS environment variables (such as ones Render injects) are never read by BaseSettings at all, whatever extra says. The third, env_file=".env", is read from the working directory whenever the file exists, in any environment. Real environment variables take priority over .env values, and .dockerignore keeps .env out of the image. In production, the environment is the config.

Factor III: config in the environment

The Twelve-Factor App's third factor draws a hard line between code and config. Anything that varies between deploys (DB credentials, the signing secret, allowed origins) belongs in the environment, never in the codebase. The litmus test the factor proposes: could you open-source the repo this minute without leaking a single credential? Here, yes — every secret has a placeholder default and is read from the environment at runtime.

🔬 Under the Hood

The payoff of Factor III is one artifact, many environments: the production image is configured purely by environment variables (local development uses Dockerfile.dev with --reload). CareKosh saw this when it moved from Railway to Render + Neon (commit 9d7091c). The new DATABASE_URL and secrets went into Render's dashboard. But Neon's URL format still needed small Python changes: the DATABASE_URL validator began stripping query parameters, and database.py and alembic/env.py added ssl=True. Config-in-environment kept the migration small; it did not make it zero-code. Nor does it move data: changing DATABASE_URL only points the app at another database. On the next start the entrypoint's alembic upgrade head builds the schema there, empty; existing rows must be copied separately (for example with pg_dump/pg_restore), and the old database keeps everything it had.

Field validators: turning env strings into safe, correct values

Annotations handle type correctness; @field_validator functions handle semantic correctness. CareKosh defines four, and each one encodes a lesson learned in production.

1. Rewriting the database driver — ensure_asyncpg_driver

Managed Postgres providers hand you a URL in their format, not yours. Render gives postgresql://…; Neon sometimes gives postgres://… and appends ?sslmode=require&channel_binding=require. SQLAlchemy's async engine needs the postgresql+asyncpg:// scheme, and SQLAlchemy's asyncpg dialect hands URL query items to asyncpg.connect() as keyword arguments, where sslmode is not accepted (asyncpg's own DSN parser would read it). This validator — declared mode="before" so it runs on the raw string prior to type validation — normalises all of that at app/core/config.py.

app/core/config.py (excerpt)Python
@field_validator("DATABASE_URL", mode="before")
@classmethod
def ensure_asyncpg_driver(cls, v):
    if isinstance(v, str):
        # Strip query parameters (e.g., ?sslmode=require from Neon)
        # SQLAlchemy passes URL query items as asyncpg.connect() keywords.
        # sslmode is not a supported keyword; SSL is set via connect_args instead.
        if "?" in v:
            v = v.split("?")[0]
        if v.startswith("postgresql://") and "+asyncpg" not in v:
            v = v.replace("postgresql://", "postgresql+asyncpg://", 1)
        elif v.startswith("postgres://"):
            v = v.replace("postgres://", "postgresql+asyncpg://", 1)
    return v
📝 Note

The comments in this teaching excerpt clarify the older source comment; the application code has not changed. Asyncpg's own DSN parser accepts sslmode, but that differs from SQLAlchemy forwarding it as a keyword. The validator drops the entire query string, not only sslmode. It silently discards channel_binding, options, application_name, connect_timeout, sslrootcert and driver options such as ssl or the SQLAlchemy dialect's prepared_statement_cache_size. Then database.py passes ssl=True only when ENVIRONMENT is not development/testing. In asyncpg, ssl=True means a default SSL context with certificate and hostname verification (verify-full) — stricter than libpq's sslmode=require. In development/testing no ssl argument is passed, so asyncpg falls back to PGSSLMODE or prefer, and a URL's sslmode=require is not enforced. Channel binding is not available through asyncpg. Sources: asyncpg 0.30.0 connection API and SQLAlchemy 2.0.36 dialect.

2 & 3. Fail-closed production gates

Two validators encode start-up gates, reading the already-validated ENVIRONMENT from info.data. The first, reject_weak_secret_in_production (app/core/config.py), rejects the shipped CHANGE-THIS… placeholder whenever ENVIRONMENT is anything other than development or testing: staging, production and a misspelled value alike. Why validate at startup instead of first use?

The deepest design decision here is when validation runs. The line settings = get_settings() executes at import. In the container, the first import happens in the entrypoint's alembic upgrade head step, before Gunicorn starts. So a missing production FRONTEND_URL or a placeholder or short SECRET_KEY stops the deploy immediately and loudly. Not everything is checked: MAIL_PASSWORD has no validator (blank silently disables email; a wrong Brevo key only shows up when a send fails), and DATABASE_URL is rewritten, not validated.

🔬 Under the Hood

This is the fail-fast principle. A bad DATABASE_URL or a placeholder secret should never become a latent fault that surfaces under production traffic. Validating at boot means such an error stops the container before it serves traffic, the deploy fails, and the previous version keeps serving. A wrong DATABASE_URL is caught on the same start-up path, but by the entrypoint's alembic upgrade head, which exits 1. It is not caught by Settings validation, nor by the /live health check, which never touches the database. Lazy "validate on first use" turns a deploy-time error into a runtime error with a much larger blast radius — and a far worse on-call story.

Talking to Postgres

08 The Database Layer: Async SQLAlchemy 2.0

Authenticated domain requests and the /health readiness probe touch Postgres — all through one carefully tuned async engine per worker process; /live does not touch the database. This chapter dissects that layer end to end. It covers how the connection pool is sized and heals itself, and why a server-side statement_timeout is an important resilience layer (and what it does not cover). It shows how get_db manages a session whose pending transaction can be committed or rolled back. And it explains the SQLAlchemy 2.0 idioms — Mapped, select(), noload — that keep an async ORM from blowing up in your face.

In one line Each worker process has one async engine. It has a 15-connection ceiling (two Gunicorn workers → up to 30 per container), an 8 s server-side statement timeout and pre-ping recovery. A yield-dependency gives every request one session, rolls back on error and always closes it. Inside that session, write handlers commit explicitly.

The async engine: asyncpg under the hood

The whole layer is built on create_async_engine driving the asyncpg driver. Unlike the classic synchronous psycopg2, asyncpg speaks the Postgres wire protocol on top of the asyncio event loop. So a coroutine waiting on I/O — a query result coming back over the socket — yields control instead of blocking the thread. That non-blocking property is why a worker can keep many requests in flight while they wait on I/O. Here, though, every authenticated request also needs one of that worker's 15 pooled connections, so database-bound concurrency per worker is 15. The engine is the bridge between the event loop and the database.

📝 Three things people conflate — engine, sessionmaker, session

Keep the lifetimes straight and most beginner confusion evaporates. The engine is long-lived application infrastructure. It is built once at import, owns the connection pool and lives for the whole process. It knows how to talk to Postgres, but it is not a session. The async_sessionmaker (AsyncSessionLocal) is a factory — the stamp that mints sessions; it isn't a session either. An AsyncSession is one request's unit of work: open it, query / add / commit / refresh, close it. The engine is shared by the whole app; a fresh session is minted per request by get_db. In one line: the engine is not a session, and the sessionmaker is not a session — it's the thing that makes them.

app/core/database.py (excerpt)Python
# Cap every statement at 8s so one hung query can't pin a pooled connection
# indefinitely and cascade into pool exhaustion (RESIL-1).
_server_settings = {"statement_timeout": "8000"}

Notice the SSL toggle at app/core/database.py. Managed Postgres (Neon) mandates TLS, but local Docker and CI do not — and forcing it there would break the dev loop. SSL is passed through connect_args, not baked into the URL, on purpose. The config validator strips Neon's ?sslmode=require query parameter (with the rest of the query string), because SQLAlchemy's asyncpg dialect would pass sslmode to asyncpg.connect() as a keyword argument it does not accept. So TLS is re-applied here as a driver argument: verify-full (certificate and hostname checks) outside development/testing. Note that every other ENVIRONMENT value, including staging or a typo, gets TLS.

The connection pool, demystified

Opening a Postgres connection is expensive — a TCP handshake, a TLS handshake, authentication, and session setup. A pool amortizes that cost by keeping a set of live connections open and lending them out. The engine here exposes three knobs that together define its concurrency envelope.

SettingValue (default)What it does
pool_size5Persistent connections kept open and reused for the life of the process.
max_overflow10Burst connections opened on demand above pool_size, then closed when returned. Effective ceiling = 5 + 10 = 15 concurrent connections per worker process.
pool_timeout30sHow long a coroutine waits for a free connection once all 15 are checked out before raising TimeoutError (which surfaces as a generic 500, not a 503). 🔬 Under the Hood

The real maximum per engine is 15, not 5. There is one engine per worker process, so the Dockerfile's two Gunicorn workers allow up to 30 app connections per container. Add Alembic's connection at start-up, and possibly more while an old and a new instance overlap during a deploy. Think of pool_size as the steady-state floor and max_overflow as the elastic ceiling. When demand inside one worker exceeds 15, the 16th coroutine doesn't fail immediately. It waits up to pool_timeout for a connection to be returned. That is exactly the backpressure you want under load, instead of opening unbounded connections and crushing Postgres' own max_connections limit.

pool_pre_ping: defeating stale connections

A pooled connection is a long-lived socket, and long-lived sockets die silently. Neon (and any PgBouncer-style proxy) closes idle connections after a timeout; a network blip or a database restart can sever a connection while the pool still believes it's healthy. The next coroutine to borrow that connection would fail with a closed-connection error (asyncpg raises ConnectionDoesNotExistError or InterfaceError; libpq clients print "server closed the connection unexpectedly").

pool_pre_ping=True at app/core/database.py closes that gap. On every checkout, the pool runs a tiny check; if it fails, the connection is discarded and a fresh one is opened, all invisibly to your handler. The cost is roughly three round trips per checkout with asyncpg. Item, category and order write handlers check out twice (again for db.refresh() after their commit); on the feature branch the auth handlers no longer refresh after committing. That is cheap in-region and noticeable across regions, and usually worth it against managed or proxied databases.

statement_timeout: an important resilience layer

The single most interview-worthy line in this file is the one that looks the most innocuous: _server_settings = {"statement_timeout": "8000"} at app/core/database.py. It tells Postgres, at the session level, to force-abort any single SQL statement that runs longer than 8000ms. The comment labels it RESIL-1, and the reasoning is a small but vicious failure-cascade.

  1. A query hangs — a missing index, a lock wait, or a pathological plan makes one statement run effectively forever.
  2. It pins its connection — that connection is checked out of the pool and cannot be returned while the query is in flight.
  3. Repeat under load — a few such queries consume all 15 of a worker's connections. Now every other request on that worker blocks waiting on the pool.
  4. Pool exhaustion → outage — after pool_timeout (30s) the waiters start raising TimeoutError; the service is effectively down even though the database itself is up.

The 8 s server-enforced timeout breaks the chain at step 1 for a long-running statement: Postgres aborts it (time spent waiting for locks included). The application still has to roll back and close its session before the connection is reused, so pool recovery still depends on the app. Know what it does not bound:

  • time a transaction sits idle between statements, such as login holding a FOR UPDATE row lock while Argon2 runs in a thread. PostgreSQL's idle_in_transaction_session_timeout covers that, and it is not set;
  • waits for a pool connection (pool_timeout, 30 s);
  • connection set-up (asyncpg's 60 s connect timeout; Neon cold starts);
  • a dead network path — only a client-side timeout (asyncpg command_timeout, not set here, or asyncio.wait_for, as /health uses) can bound that.

Server- and client-side timeouts are complementary; neither replaces the other.

💡 Interview Insight

When an interviewer asks "what's your maximum number of DB connections and what happens under load," they're probing whether you understand pool exhaustion as a cascading failure. The senior answer connects three facts. The ceiling is 15 per worker process (30 per container with two workers). A hung query pins a connection indefinitely. And a server-side statement_timeout is one of the controls that stop one slow statement from exhausting the pool. Naming that causal chain is what separates a staff-level answer from "we set a timeout somewhere."

The session factory: configured for async correctness

Sessions are minted from a single async_sessionmaker. Two flags matter — one critically, because this is an async app — and one is a legacy leftover.

Keep ORM attributes loaded and usable after commit (the async landmine — see below).

⚠️ Pitfall

By default SQLAlchemy sets expire_on_commit=True: after commit() it marks every loaded attribute as expired, so the next attribute access triggers a fresh SELECT to reload. In a sync app that's just a lazy reload. In an async app the implicit I/O raises MissingGreenlet (greenlet_spawn has not been called). In this codebase the risk comes from the handlers' own explicit await db.commit() calls. Several handlers keep reading attributes after committing; resend-verification, for example, reads user.email and user.name right after its commit. With expiry on, those reads would raise. The post-yield commit in get_db is not the trigger. In FastAPI 0.115.6 it runs after the handler has returned and the response has been serialized, just before it is sent (0.118+ runs it after sending). Setting expire_on_commit=False keeps already-loaded values readable after a commit. One nuance worth naming: expire_on_commit=False fixes only this trigger — the post-commit expired-column reload. A second, independent MissingGreenlet trigger remains: lazily touching an unloaded relationship (say user.items), which no commit flag fixes — that one is solved only by eager loading (next section). Conflating the two is a common mistake; a strong answer separates them.

⚠️ Pitfall — one AsyncSession, one task

An AsyncSession is a single in-progress transaction on a single connection: a mutable, stateful object with no internal locking. As SQLAlchemy's own AsyncSession docstring puts it, the session is "not safe for use in concurrent tasks". The classic trap is fanning out queries with asyncio.gather(...) that all share the same db session. Interleaved access corrupts its state. The mnemonic: "Session per thread (sync), AsyncSession per task (async)". CareKosh avoids the problem because every request gets its own session from get_db, and handlers await their queries one after another. But the moment you parallelize DB work, create a fresh session per task.

get_db: a session per request

The data layer is injected into handlers through a single yield-based dependency. FastAPI treats a generator dependency as setup and teardown. The code before yield runs before the handler, and the handler receives the yielded value. The code after yield runs after the handler returns (or raises). That structure gives every request one session that spans the whole request; write handlers commit explicitly inside it.

app/core/database.pyPython
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
        finally:
            await session.close()

Read the control flow carefully — every line is load-bearing (app/core/database.py):

  • yield session hands the live session to the handler. Everything the handler does — reads, mutations, even an audit-log row added by a service helper — accumulates in this one session.
  • await session.commit() runs only if the handler returned without raising. For read-only routes this is the real commit. Write handlers already call await db.commit() themselves. The mutation, activity row and audit row are added first, so they commit atomically. Handlers usually await db.refresh(obj) afterwards, so the commit in get_db normally just ends that follow-up read transaction.
  • except → rollback() → raise discards whatever is still uncommitted and re-raises. A failure before the handler's own commit leaves the database untouched. A failure after it (for example in db.refresh() or response validation) returns an error although the write is already committed. That is why client retries need idempotency. On the feature branch POST /orders has it when the client sends a localId (migration 0010); an order create without one, and item and category creates, do not. The IntegrityError that later surfaces as a global 409 has been rolled back here.
  • finally → close() always returns the connection to the pool, success or failure — this is what keeps the per-worker 15-connection ceiling honest.
🔬 Under the Hood

This is Unit of Work at the handler level: changes are tracked in the session, and the route handler's single explicit commit makes the mutation, activity and audit rows atomic. The service helpers (log_audit, lock_inventory_names) never commit. They add to the session, so the audit record rides the same transaction as the change it describes. The get_db dependency guarantees a rollback when an exception escapes and a close at the end; it is not the commit point for writes.

There is a twin, get_db_context at app/core/database.py, with identical commit/rollback/close logic exposed as a plain @asynccontextmanager. It serves code not driven by Depends. Today that is the /health readiness probe in app/main.py, which calls it directly under asyncio.wait_for; any future script or job could use it too.

SQLAlchemy 2.0 style: the modern idioms

This codebase is fully on the SQLAlchemy 2.0 API surface, which is worth being fluent in because it differs sharply from the 1.x patterns most older tutorials teach.

📐

Typed models

DeclarativeBase + Mapped[T] / mapped_column(...) replace the legacy Column. The Python type drives both mypy and ORM nullability.

🔎

Statement-first queries

Construct a select(), await db.execute(...), then call .scalar_one_or_none() / .scalars() — no more db.query(...).

You can see both halves in the auth dependency, which loads a user by id:

app/models/user.py (simplified)Python
class User(UUIDMixin, TimestampMixin, Base):
    __tablename__ = "users"

    email: Mapped[Optional[str]] = mapped_column(
        String(255), unique=True, index=True, nullable=True,
    )
    hashed_password: Mapped[str] = mapped_column(String(255), nullable=False)

The annotation carries semantic weight: Mapped[Optional[str]] infers a nullable column while Mapped[str] infers NOT NULL. The code also passes nullable= explicitly. Note that an explicit nullable= overrides the annotation without any warning, so keeping Mapped[Optional[...]] and nullable= in agreement is a review convention, not something SQLAlchemy enforces.

The async lazy-loading hazard

The relationship above declares lazy="selectin", and the auth query above passes noload("*"). These two choices are both answers to the same async-specific danger.

SQLAlchemy keeps an identity map per session and, by default, lazy-loads relationships: accessing user.items for the first time fires a fresh query. In a sync app, fine. In an async app, that implicit query happens during plain attribute access — outside an await — and SQLAlchemy raises MissingGreenlet because it can't suspend to do I/O. So every relationship the model declares uses lazy="selectin". It eagerly batches all children with a single WHERE fk IN (...) query up front. That kills the classic N+1 problem and keeps the loaded object graph fully serializable after the request commits.

But eager loading on every authenticated request is wasteful when the auth dependency only needs scalar fields like is_active. That's why get_current_user overrides the model default with noload("*") at app/api/deps.py. It switches off the five selectin relationships entirely (the DB-1 optimization). So authenticating each request doesn't drag in every category, item and order the user owns. Caveat, now fixed: in the September version, login, POST /auth/refresh, register and PATCH /auth/me called await db.refresh(user) after committing. Session.refresh() re-runs the selectin loaders, so those endpoints loaded the user's whole graph: categories and their items, items, orders and order items, activity logs and refresh tokens. That was seven extra SELECTs in a local measurement, and the cost grew with account age. The feature branch drops the refresh (each handler has a "No db.refresh(user)" comment) and serializes the scalar columns already loaded, which keeps DB-1 effective there; main still refreshes. The lesson still stands: Session.refresh() on an aggregate root with eager collections is not a cheap call.

✅ Pro Tip

Three things make response building safe here. Handlers convert ORM rows to Pydantic themselves (model_validate with from_attributes=True). Response schemas read only columns (plus the selectin-loaded Order.items). And expire_on_commit=False keeps values readable after the handlers' explicit commits. Dropping from_attributes gives a ValidationError, not MissingGreenlet; touching a lazy relationship (for example Item.category, which uses the default lazy="select") or an expired attribute is what raises MissingGreenlet.

Deterministic constraint names for Alembic

One detail on Base pays off every time you write a migration: a MetaData naming convention.

app/core/database.pyPython
convention = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",

class Base(DeclarativeBase):
    metadata = MetaData(naming_convention=convention)

Without a convention, PostgreSQL names unnamed constraints itself (users_pkey, items_category_id_fkey…). Those names are deterministic, but unknown to the model and different on other databases. So autogenerate can't reliably emit a DROP CONSTRAINT, and downgrades become fragile. With the convention, names are templated: pk_users, fk_items_category_id_categories, and ix_users_email (email uniqueness is a unique index, because the column is unique=True, index=True). Because the ck template includes %(constraint_name)s and env.py passes target_metadata, explicitly named checks are prefixed too: chk_items_quantity_non_negative is created as ck_items_chk_items_quantity_non_negative, both by create_all and by migration 0004. Every constraint gets a stable, human-readable identity that Alembic can reference across environments.

📝 Note

Schema in this app is created two ways. In development, the lifespan calls create_tables() (Base.metadata.create_all via run_sync) for a fast loop; it records no Alembic revision. Production never runs create_all. Instead, docker-entrypoint.sh runs alembic upgrade head on every container start, before Gunicorn, and aborts start-up if a migration fails. An advisory lock in alembic/env.py serialises concurrent starts: a second runner waits up to the 30-second lock_timeout, then fails. That is exactly why the deterministic naming convention matters.

The full request → DB journey

Putting it together, here is the path a single mutating request takes through this layer:

  1. Inject the session — FastAPI resolves db: DB; get_db enters AsyncSessionLocal() and yields (autoflush=False, expire_on_commit=False). A connection is checked out on the first execute.
  2. Authenticate and query — get_current_user and the handler share that session; each statement runs over a pooled asyncpg connection, capped server-side at 8 s.
  3. Commit in the handler — write handlers add the mutation, activity and audit rows, call await db.commit() themselves, then usually await db.refresh(obj), which starts a new (read) transaction.
  4. Build the response — the handler returns a Pydantic model built with model_validate(obj); FastAPI validates and serializes it against response_model (camelCase via serialization_alias).
  5. Tear down — only now does get_db's post-yield code run. It calls commit(), which normally just ends the refresh's read transaction, or rollback() and re-raise on an exception. Then close() returns the connection to the pool.
  6. Send — Starlette sends the response; background tasks such as emails run afterwards.

This is the FastAPI 0.115.6 order. From 0.118, the teardown in step 5 runs after sending.

🛡️ Security / OWASP

The async ORM is also a defense. Building queries with select(User).where(User.id == user_id) uses parameter binding. So user_id is sent to Postgres as a bound value, never pasted into the SQL string. That structurally closes off SQL injection (OWASP Top 10:2021 A03, Injection; A05 in the 2025 edition). The same applies to every where() and filter in the app: as long as values flow through SQLAlchemy expressions rather than raw f-strings, value injection is structurally prevented. The remaining escape hatches are raw text() built with string formatting, literal_column(), or user-controlled identifiers such as ORDER BY columns. This codebase uses none of them with request data. Its only text() calls in app/ are SELECT 1, a bound-parameter advisory lock, the feature branch's constant AI budget lock (SELECT pg_advisory_xact_lock(72401931)) and the constant local_id IS NOT NULL index predicate on the Order model.

The mixins: DRY columns via the MRO

Almost every model is declared class Item(UUIDMixin, TimestampMixin, Base) app/models/item.py. The two mixins are plain (non-Base) classes whose attributes are mapped_column declarations. SQLAlchemy's declarative machinery walks the full Method Resolution Order, collects the annotations from each mixin, and merges them into one Table. Listing the mixins before Base is a convention; SQLAlchemy documents no required order, and normal method-resolution rules matter only if two bases define the same attribute.

app/core/database.py (excerpt)Python

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(timezone.utc),
        nullable=False,
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),

        onupdate=lambda: datetime.now(timezone.utc),
        nullable=False,
    )


class UUIDMixin:
    id: Mapped[str] = mapped_column(
        String(36), primary_key=True, default=lambda: str(uuid4()),
    )

Two subtleties worth internalizing. First, the UUID and both timestamps are generated app-side by Python callables when the ORM flushes the INSERT — there is no server_default. So the id is available right after db.flush(), without a RETURNING round trip; the create handlers use it to write activity and audit rows. The downside: the clock source is the app server. And a raw-SQL INSERT that bypasses SQLAlchemy would supply no created_at and violate NOT NULL. Second, onupdate is a SQLAlchemy-side default. It is added to every UPDATE that SQLAlchemy compiles, unless the statement sets updated_at itself. That includes ORM flushes and Core/ORM update() statements alike, such as this codebase's compare-and-swap UPDATEs. Only raw SQL (text() or external tools) skips it.

🔬 Under the Hood

Mapped[str] vs Mapped[Optional[str]] is not just typing sugar. SQLAlchemy 2.0 reads the PEP 484 annotation at class-creation time and infers nullability from it: Mapped[str] implies NOT NULL, Mapped[Optional[str]] implies nullable. This codebase also passes nullable= explicitly. An explicit nullable= silently overrides the annotation, so keeping the two in agreement is a review convention, not something SQLAlchemy checks.

Relationships: one user, many of everything

The User declares five one-to-many collections, and each repeats the same three options app/models/user.py.

app/models/user.pyPython
items: Mapped[list["Item"]] = relationship(
    "Item",
    back_populates="user",
    cascade="all, delete-orphan",
    lazy="selectin",
)

back_populates wires a bidirectional link so setting one side updates the in-memory other side. cascade="all, delete-orphan" propagates save/merge/delete from parent to child and deletes any child de-associated from its parent. And lazy="selectin" is the choice with the biggest trade-off. On Order.items it lets responses serialize line items without an async lazy load. On User, though, it means any plain select(User) also loads all five collections — and, through nested selectin, every category's items and every order's lines. That is why every User query in deps.py and auth.py adds noload("*") (the DB-1 comment in deps.py). A safer default for an aggregate root is lazy="raise" (or "select") plus an explicit selectinload() on the queries whose responses need the collection.

💡 Interview Insight

When an interviewer sees lazy="selectin", they are really probing three things at once. Do you understand the N+1 problem? Do you know the trade-offs between lazy strategies? And do you know why async makes this non-optional? With the default lazy="select", touching user.items fires one query per parent (N+1). The lazy="joined" option avoids that, but with five collections on User a single join produces a cartesian row explosion. The selectin strategy issues exactly one extra query per relationship via WHERE items.user_id IN (...): O(1) extra queries and no row multiplication.

🔬 Under the Hood

The async angle is the kicker. SQLAlchemy's asyncio support forbids implicit I/O during attribute access. A classic lazy load would need to await with no greenlet to suspend into, so it raises MissingGreenlet. The selectin strategy loads the collection up front inside the awaited query. So later access (during Pydantic serialization) reads data that is already loaded. That is why lazy="selectin" + expire_on_commit=False + from_attributes (plus an explicit await db.refresh() after writes) make Order serialization safe after commit. User's collections are never serialized and are suppressed with noload("*").

Two-layer delete cascade

Every user_id FK is declared ForeignKey("users.id", ondelete="CASCADE") app/models/category.py, and five of the six user-owned domain tables are also reachable through a User relationship with cascade="all, delete-orphan" (audit_log has no User collection, and neither do the feature branch's ai_consents and ai_usage). The two layers cover different deletion paths — and this codebase's account deletion relies on the database one.

The textbook trap is the question: "you already have ondelete=CASCADE — why also cascade in the ORM?" Here the account-deletion path answers it. Confirm-delete loads the user with noload("*"), so the Session sees empty collections and the ORM emits only DELETE FROM users. PostgreSQL's ON DELETE CASCADE then removes the owned rows, including audit_log, which has no ORM relationship. Category deletion is the opposite case: selectin has already loaded the items, so the ORM deletes each one. Standout decision #1 — the denormalized order snapshot

This is the most interview-worthy decision in the schema. An OrderItem does not hold a foreign key to items. Its item_id is an indexed String(36): a soft reference. The row stores name, brand, unit, quantity, current_stock and minimum_stock as values supplied by the client at creation.

app/models/order.py (excerpt)Python
# Reference to inventory item (NOT a ForeignKey)
item_id: Mapped[str] = mapped_column(String(36), nullable=False, index=True)

# Snapshot of item details at time of order
name: Mapped[str] = mapped_column(String(255), nullable=False)
quantity: Mapped[int] = mapped_column(Integer, nullable=False)       # to order
current_stock: Mapped[int] = mapped_column(Integer, nullable=False)  # at order time
minimum_stock: Mapped[int] = mapped_column(Integer, nullable=False)  # at order time

An order is a historical business document. Its lines store what the client submitted at creation: name, brand, unit, the ordered quantity, and the current_stock/minimum_stock the client saw. So later renames, restocks or deletions of the Item do not rewrite it. The server checks only that each item_id belongs to the user; it does not re-read or verify the snapshot fields against the live Item. Line items have no update endpoint, but the order's status, timestamps and notes change, and pending or declined orders can be deleted. If item_id were a real FK with ondelete=CASCADE, deleting an item would silently erase order history. Keeping it a soft reference plus a value snapshot decouples point-in-time accuracy from the live catalog. The trade-off — storage duplication and snapshot drift — is the entire point; it is the same pattern e-commerce uses so a price change never rewrites a past invoice.

💡 Interview Insight

The question: "Why denormalize here when you spent the rest of the schema normalizing?" The answer they want is the difference between two things. A reference always reflects current truth; a snapshot reflects the truth at one moment. Orders, invoices, and audit rows are snapshots by nature. Bonus points for noting the soft item_id gives you no referential-integrity guarantee — orphaned references are possible by design.

Standout decision #2 — optimistic concurrency via version

Item carries an integer version with both a Python default=1 and a DDL server_default="1" app/models/item.py. The protocol is enforced by the schemas: ItemUpdate.version and StockUpdate.version are required ints that "must match server's current version" app/schemas/item.py.

app/models/item.py (excerpt)Python
version: Mapped[int] = mapped_column(
    Integer, default=1, server_default="1", nullable=False,
)

The client reads an item (gets version=N); an edit (PUT) or stock change (PATCH …/stock) must echo version=N. The handler's conditional UPDATE compares the supplied value to the row's current version and rejects a mismatch with 409 Conflict, incrementing on success. This is a compare-and-swap that prevents the lost-update anomaly. That is critical for a multi-device app where two phones can edit the same item. (The app is server-first: each edit is sent immediately and fails if the server is unreachable. It has no stock +/- control: a person changes a quantity only through the Edit Item form, which sends PUT /items/{id} with the version; PATCH …/stock exists in the API but has no caller in the app. The app now captures the version with its form values, closing finding A-1; chapter 11 explains the original failure and its fix.)

🔬 Under the Hood

This is application-managed optimistic locking, deliberately not SQLAlchemy's built-in __mapper_args__ = {"version_id_col": version}. The built-in auto-appends WHERE version = :old to every UPDATE and raises StaleDataError on a zero-row match — which surfaces as a generic 500 unless caught. Managing the check in the route handler gives full control over the HTTP status and the error body. As for the dual default: default=1 is applied by the ORM at insert. Meanwhile server_default="1" writes DEFAULT '1' into the DDL, so even raw-SQL or backfilled rows start at 1. The comparison can never trip over a NULL version.

Standout decision #3 — the audit ledger vs the activity feed

This system has two logging tables, and the distinction matters. The first, activity_logs, is the user-facing domain feed ("you created an item"). It is mutable, has an updated_at and uses a typed ActivityActionType enum. The second, audit_log, is the system ledger. It is insert-only by application convention (no update endpoint, no updated_at) and stores JSONB before/after snapshots. The database does not enforce immutability, and ON DELETE CASCADE removes a user's audit rows when the account is deleted.

Tellingly, AuditLog opts out of the mixins (as do the small OrderNumberCounter table added in 0007 and the feature branch's AIConsent; AIUsage takes only UUIDMixin). It inherits only from Base and redeclares its id and created_at inline app/models/audit_log.py.

    ...

💡 Interview Insight

The opt-out is judgment, not an oversight. An insert-only ledger should not silently inherit a future change to a shared mixin. Coupling it to TimestampMixin, which carries a mutable updated_at, would signal the wrong intent for an insert-only table. Immutability here is a convention, not a database guarantee; enforcing it would take revoked UPDATE/DELETE privileges or a trigger, plus a retention decision for account deletion. Knowing when not to reuse a mixin is exactly the senior signal interviewers fish for.

The before/after snapshots use Postgres JSONB. The snapshot shape varies per entity_type: an Item and an Order have different fields. A schemaless column avoids both a wide sparse table and a per-entity audit table. It is still queryable (e.g. new_values->>'quantity' = '0') and GIN-indexable.

🔬 Under the Hood

JSON stores the raw input text and re-parses it on every read. JSONB stores a decomposed binary form. It is slightly slower to write, but it supports containment operators (@>, ?), efficient field extraction and GIN indexes. For an audit table that is written once and queried later during investigations, JSONB is the right call. The cost is Postgres lock-in, since postgresql.JSONB is dialect-specific.

How the audit row stays atomic

The audit service deliberately db.add()s the entry but never commits app/services/audit.py.

app/services/audit.py (excerpt)Python
    entry = AuditLog(
        user_id=user_id, entity_type=entity_type, entity_id=entity_id,
        action=action, old_values=old_values, new_values=new_values,
    )
    db.add(entry)
    # Do NOT commit — let the caller's transaction commit both the
    # mutation and the audit atomically

Write handlers commit explicitly. The item handlers stage the mutation, the activity row and the audit row, then call await db.commit() once. So the three land in a single transaction: either all persist or none do. The get_db dependency (which opened the session) commits again after the handler returns; that is normally an empty or read-only transaction. Its rollback only covers work that was never committed. An exception after the handler's commit cannot undo the write.

⚠️ Pitfall

If log_audit committed internally, you would split the work across two transactions and open three failure modes. (1) The audit commits, then the mutation rolls back: a phantom audit for a change that never happened. (2) The mutation commits but a later step fails: a real change with no audit, a silent gap. (3) The inner commit ends the unit of work too early and fights the outer commit. Atomic audit logging is what lets the audited item mutations be trusted — but the ledger covers item mutations (including one row per item of a category delete and one per line of an order apply) and order deletions only, so it is not a complete mirror of persisted state. Category, order-creation, profile, password and order-status changes write no audit row.

Non-native enums: plain VARCHAR, not a Postgres ENUM type

OrderStatus (6 values) and ActivityActionType (~19 values) are Python str, Enum classes persisted with native_enum=False app/models/order.py.

app/models/order.py (excerpt)Python
status: Mapped[OrderStatus] = mapped_column(
    SQLEnum(OrderStatus, native_enum=False, length=20),
    default=OrderStatus.PENDING, nullable=False,
)

native_enum=False tells SQLAlchemy not to emit CREATE TYPE ... AS ENUM; the column is a plain VARCHAR(length). There is no CHECK constraint: since SQLAlchemy 1.4, Enum(create_constraint=...) defaults to False, and migration 0001 creates orders.status as String(20) and activity_logs.action as String(30). Membership is enforced only by the Python Enum on the ORM path.

Two consequences are worth knowing:

  • The database stores member names. Without values_callable, SQLAlchemy persists PENDING, STOCK_UPDATED, ORDER_APPLIED; API responses emit the lowercase values ("pending"). Raw SQL must therefore use the uppercase names (reproduced on 7 October 2026: orders.status held STOCK_UPDATED and activity_logs.action held ITEM_CREATE while the API returned stock_updated and item_create).
  • Unknown strings get in. An unknown string written outside the ORM is accepted by PostgreSQL but raises LookupError when the ORM loads the row.

The trade-off versus a native ENUM is operability: Before PostgreSQL 12, ALTER TYPE ... ADD VALUE could not run inside a transaction block, and the new value is still unusable until commit. Enum values also cannot be dropped. Here, by contrast, adding a member is a code change, plus an optional migration if you decide to add a CHECK. The schema is PostgreSQL-specific anyway (JSONB, advisory locks, ON CONFLICT), so SQLite portability is not a benefit here. Because the class subclasses str, the value serializes straight to its string ("pending").

Category, Item, Order, and ActivityLog each carry a nullable, indexed local_id: Mapped[Optional[str]] app/models/item.py. The item and order create schemas accept localId; the category schema accepts snake_case local_id, and activity rows are written by the server. Responses echo it as localId. So a client could match a locally generated record to the server's canonical id. The app is server-first and has no offline write queue, so it does not use local_id for reconciliation. Migrations & constraint naming

Ten Alembic migrations carry the schema forward on the feature branch (main has the first six). They start from the initial table set, then add username support, email verification, the version/audit-log/quantity-check batch, account-deletion tokens and the order_items positive-quantity CHECK (0006, the head of main). 0007 adds users.session_version, order_number_counters and token-digest indexes, and its downgrade deliberately raises. 0008 and 0009 add the AI consent and usage tables and their scope and provider columns. The last, 0010, takes a SHARE lock on orders (it waits for in-flight order writes, then blocks new ones, not reads, until the migration transaction commits) and adds the partial unique index on (user_id, local_id). All pending revisions run in one transaction, so earlier locks are also held to the end. A linear chain from an empty database to 0010 was upgraded successfully on PostgreSQL 16 on 7 October 2026 and again on 8 October 2026; an empty database proves the chain, not an upgrade of real legacy data. They all survive because constraint names are deterministic: Base.metadata is built with a naming convention app/core/database.py.

  1. Indexes become ix_<label> — predictable across databases. (Email uniqueness is the unique index ix_users_email.)
  2. Unique constraints become uq_<table>_<col>.
  3. Foreign keys become fk_<table>_<col>_<reftable>.
  4. Checks & PKs become ck_<table>_<name> and pk_<table> — so the explicitly named chk_items_quantity_non_negative becomes ck_items_chk_items_quantity_non_negative.

10 Authentication and authorization

Related guides: the complete developer guide explains the auth concepts from scratch, the API traceability guide traces each of the 18 auth routes to its code, tables and tests, and the documentation index lists the rest.

In one line Signed HS256 JWTs (JWS: signed, not encrypted) plus database state. Every request re-loads the user and compares a per-user session generation. Refresh tokens are single-use rows claimed under a user-row lock. A password change or reset revokes everything at once.

Authentication combines signed HS256 JWTs with database state. It is not a database-free hot path: get_current_user loads the account, compares session_version (a 401 if it no longer matches), then checks the active flag and the email-verification policy (403s). The default access lifetime is 30 minutes; the refresh lifetime is 30 days. An access token carries sub, exp, iat, type=access and session_version; a refresh token adds a jti that is stored in refresh_tokens. A legacy token without a generation claim is treated as generation zero, for migration compatibility. The policy is applied on every authenticated request, not only at login: a disabled account gets 403 at once, and so does an unverified email (EMAIL_NOT_VERIFIED) as soon as the verification policy is in force.

Passwords and account changes

  • Hashing. Passlib supports Argon2 and legacy bcrypt verification. Legacy bcrypt hashes are verified but never upgraded: CryptContext(deprecated="auto") marks bcrypt deprecated, yet no login path calls verify_and_update(), so a bcrypt hash stays bcrypt until the password changes. Argon2 runs with argon2-cffi's defaults (argon2id, 64 MiB, 3 passes, 4 lanes).
  • Off the event loop. Hashing and verification are offloaded to AnyIO worker threads; this avoids blocking the event loop but still consumes CPU and memory. Do not quote a hash latency without measuring the actual runtime.
  • Profile changes. Email changes are support-only (400 "contact support"), matching the existing read-only UI. The API accepts name, phone and username updates; a username taken by someone else gets 400, and a simultaneous claim of the same name ends in 409 through the unique constraint. An explicit null for name or phone is ignored, so a phone number cannot be cleared that way, although an empty string does clear it (reproduced 7 October 2026; items behave differently, see chapter 11). The current app's Profile screen sends only name and username and has no phone field.
  • Password change. POST /auth/change-password (authenticated) verifies the current password, stores the new hash, increments session_version, clears pending reset and deletion tokens and revokes every refresh row. All existing access and refresh tokens stop working at their next check (an old access token gets 401 "User not found"). Unlike reset, it sends no notification email and has no rate limit. The API offers this, but the current app has no change-password screen.

Refresh: two levels of coordination

  1. Validate the refresh JWT's signature, expiry, type and jti (its unique token ID).
  2. Lock the user row first (SELECT … FOR UPDATE) and check the active flag, the verification policy and the session generation.
  3. Claim the refresh row with a conditional UPDATE where it has not been revoked and has not expired; RETURNING identifies the winner.
  4. Mint the replacement pair, persist its refresh row and commit together.

The conditional claim protects one token against concurrent rotation. The shared user-row lock additionally orders refresh against password changes and resets, so a rotation cannot escape credential invalidation. A replayed refresh token gets 401. There is no token-family reuse detection: replaying an old token does not revoke the newer tokens issued from it. The race and the replay were reproduced on 7 October 2026 and again on 8 October 2026: two simultaneous refreshes with one token gave one 200 and one 401, and a replayed old token got 401. Nothing in the refresh handler touches the successor token on a failed claim. Inspect auth.py for the complete transaction rather than copying a reduced SQL example as the whole flow.

Rate limits. Only five auth routes carry a rate limit: register (3/hour), login (5/minute), resend-verification (3/hour), forgot-password (3/hour) and the reset-password POST (5/hour). Refresh, logout, change-password (which runs a password verify) and verify-email are not limited, and the test suite disables the limiter. Rate limiting is best effort: five auth routes, counters in memory per worker process, reset on restart; an open finding about how clients are identified is tracked privately.

Logout versus password recovery

Ordinary logout needs a valid access token and the refresh token in the body. It revokes only that refresh row; the access token itself, or a copy of it, stays valid until it expires (up to 30 minutes), because there is no access-token deny-list. This was reproduced on 7 and 8 October 2026 (finding A-14 in the API traceability guide). Password change or reset is stronger: in one transaction it increments the account generation, clears old reset/deletion challenges and revokes all refresh rows. Old access and refresh tokens then fail on their next authorization check, including the current device's old tokens. An operation that was already authorized and in flight is not retroactively cancelled.

Email verification and single-use challenges

For an account with an email address, verification is required only when both REQUIRE_EMAIL_VERIFICATION and the mail configuration (MAIL_PASSWORD) are set. The policy is checked on login, on protected bearer requests and on refresh. Registration keeps its token response shape, but the mobile registration flow discards those tokens pending verification, without revoking the refresh row (finding A-9). While the policy is enforced, an unverified user also cannot log out, change the password or request deletion, because those routes run the same check.

Verification uses a conditional update on the token digest and expiry; reset selects a digest/expiry match under a user-row lock. Verification links expire after 24 hours and reset links after 1 hour. Only one concurrent use of a link succeeds. The database stores SHA-256 digests of high-entropy challenges, but the raw link is still a bearer capability and must be protected. Generic forgot/resend messages reduce account enumeration through response content, but they do not prove timing indistinguishability, and registration still answers 400 "Email already registered" or "Username already taken".

Account deletion

  1. DELETE /auth/me requests confirmation (an email with a single-use link valid for 24 hours). It needs an email address on the account (400 otherwise) and a configured mail service (503 otherwise), and deletes nothing.
  2. GET /confirm-delete/{token} renders a confirmation page without deleting anything, so mail scanners that open links are harmless.
  3. POST to that URL performs the deletion after validating the challenge under a lock. Cancellation (POST /auth/cancel-delete, which has no button in the current app) coordinates on the same account row.

User-owned data is removed by the database's ON DELETE CASCADE: categories, items, orders and their lines, refresh tokens, activity and audit rows, and on the feature branch the AI consent and usage rows. The global daily order counter remains, to prevent order-number reuse. This two-step flow, the cancellation and the cascade were reproduced on 7 and 8 October 2026. This is an application control, not proof of compliance with every retention or erasure obligation.

11 Domain & CRUD Design

Related guides: the API traceability guide traces every items, categories, orders and activities route to its handler, tables, tests and mobile caller; the complete developer guide covers the same concepts for onboarding; the documentation index lists the rest.

Four resources — Items, Categories, Orders, and a read-only Activity feed — carry the whole product. What makes this layer interview-worthy is not that it does CRUD, but how it guards writes that race. Item edits and stock changes are compare-and-swap UPDATEs on version. Order transitions, apply and delete are guarded on status. Every query is hard-scoped to the owner, and the order workflow is a guarded finite state machine. Creates, item deletes and category writes are ordinary writes without a version check. This chapter takes you under the hood of each.

In one line Authorization is a WHERE user_id = :me predicate on every query. Correctness under concurrency comes from an atomic UPDATE … WHERE version = :v (and WHERE status = :old) that lets exactly one of two racing writers win. The loser gets 409 on item edits and on most status races (400 if it already read the new status). It gets 400 when it loses the apply claim or an order-delete race.

The domain is deliberately small and single-tenant-per-user. There is no organization, no team, no role hierarchy on these resources — a user owns rows, and that ownership is the authorization model. Each router is mounted under /api/v1 and follows REST conventions.

Ownership scoping: authorization as a WHERE clause

There is no ACL table, no permission check, no if user.can_edit(item). Authorization is collapsed entirely into the query predicate: every SELECT, UPDATE, and DELETE appends Item.user_id == current_user.id. The list endpoint opens with exactly that app/api/v1/items.py, and the single-item read repeats it app/api/v1/items.py:

app/api/v1/items.pyPython
result = await db.execute(
    select(Item).where(
        Item.id == item_id,
        Item.user_id == current_user.id,   # ownership IS the authz check
    )
)
item = result.scalar_one_or_none()

if not item:
    raise HTTPException(
        status_code=status.HTTP_404_NOT_FOUND,   # not 403
        detail="Item not found",

Two design choices here are worth defending in an interview. First, when the row isn't yours, the query simply returns zero rows and the handler raises 404, not 403. The system refuses to distinguish "doesn't exist" from "exists but isn't yours". So it never leaks the existence of another user's resource id. Second, the predicate is also baked inside the atomic write statements: you'll see Item.user_id == current_user.id in the CAS UPDATE at app/api/v1/items.py. So even the optimistic write path cannot touch a row you don't own.

This defends against A01:2021 Broken Access Control / IDOR. But it's only as strong as the discipline behind it: a single handler that forgets the user_id predicate becomes a silent horizontal-privilege-escalation bug. The robust hardening is a base-query/repository helper that always injects the scope, or Postgres Row-Level Security as defense-in-depth.

⚠️ Pitfall

The search filter is a leading-wildcard ILIKE '%term%' across name/description/brand app/api/v1/items.py. A leading wildcard stops any btree index from serving the ILIKE predicate, so PostgreSQL filters every row of that user (found through the user_id index). Fine at household-inventory cardinality; to scale you'd reach for a Postgres trigram GIN index (pg_trgm), full-text search, or an external search engine. Offset pagination similarly degrades on deep pages — keyset/cursor pagination is the answer at scale. (Side note: the search term is not escaped, so a % or _ typed by a user acts as a wildcard.)

Optimistic concurrency: the compare-and-swap that anchors the system

This is the centerpiece. The Item model carries a version integer (app/models/item.py, server-default 1). Item edits (PUT /items/{id}) and stock changes (PATCH /items/{id}/stock) must send the version the client last read. Create and delete do not. So a device holding a stale copy can still delete the item. (In the current app every quantity change goes through the Edit Item form and PUT; there is no stock +/- control and no caller of PATCH …/stock. The app also makes no optimistic updates: it refreshes its cached list only after a write succeeds.) Here is the move that matters: the handler reads the item, but it does not mutate the loaded ORM object. Instead it issues a single guarded UPDATE whose WHERE clause carries the version check app/api/v1/items.py:

app/api/v1/items.py — update_stock (excerpt; comments added; PUT builds the same UPDATE over every changed column)Python
cas_result = await db.execute(
    update(Item)
    .where(
        Item.id == item_id,
        Item.user_id == current_user.id,
        Item.version == data.version,        # the guard lives in SQL
    )
    .values(quantity=data.quantity, version=Item.version + 1)
    .returning(Item.version)
)
if cas_result.scalar_one_or_none() is None:
    return JSONResponse(
        status_code=409,
        content={
            "error": "Version conflict",
            "message": "This item was modified by someone else. Please refresh and try again.",
            "server_version": item.version,      # already-loaded, stale values
            "server_quantity": item.quantity,
        },
    )
🔬 Under the Hood

Why is this not the classic read-then-write race? Because the safety check is never evaluated in Python between the read and the write. It lives inside the UPDATE's WHERE clause, and PostgreSQL evaluates the predicate and performs the write as one atomic statement. Suppose two requests both read version=5. The first UPDATE matches, bumps the version to 6 and holds the row lock until its transaction commits. The second UPDATE waits for that lock, then re-checks its WHERE clause against the committed row (this is READ COMMITTED behaviour). It matches zero rows, because 6≠5. The intervening SELECT carries no correctness weight at all — it exists only to return a 404 and to have values for the conflict body. For PATCH …/stock no lock is held between the read and the write. PUT differs in one way: when the body includes a name (the Edit Item form always sends one), the handler first takes the account's name advisory lock, so concurrent Edit Item saves queue there before the SELECT; the guarded UPDATE still decides the winner. So this optimistic scheme scales better than pessimistic SELECT … FOR UPDATE under low contention. The cost is client-visible conflicts when contention is high.

One detail separates a senior answer from a junior one: on conflict the handler returns the values it already loaded rather than calling db.refresh(item). A concurrent DELETE could make the row vanish, and refreshing a deleted row raises — which would turn a clean 409 into a 500. Returning the stale snapshot keeps the conflict response well-formed no matter what the other writer did.

The order lifecycle as a finite state machine

Order workflow is a declarative transition table mapping each status to a frozenset of legal next states app/api/v1/orders.py:

app/api/v1/orders.py (excerpt; names shortened, comments added)Python
LEGAL_STATUS_TRANSITIONS = {
    OrderStatus.PENDING:            frozenset({ORDERED, RECEIVED, DECLINED}),
    OrderStatus.ORDERED:           frozenset({PARTIALLY_RECEIVED, RECEIVED}),
    OrderStatus.PARTIALLY_RECEIVED: frozenset({RECEIVED}),
    OrderStatus.RECEIVED:          frozenset(),   # no status-endpoint moves; POST /apply → STOCK_UPDATED
    OrderStatus.DECLINED:          frozenset(),   # terminal
    OrderStatus.STOCK_UPDATED:     frozenset(),   # terminal
}

The helper _validate_status_transition app/api/v1/orders.py rejects any edge not in the table (400). It treats a same-state transition as an idempotent no-op: it returns early, so retries are safe. And it explicitly forbids reaching STOCK_UPDATED through the generic status endpoint; that terminal state is only reachable via POST /orders/{id}/apply. Frozensets give O(1) membership tests and immutable values (the dict itself is an ordinary module-level mapping). Each status change stamps its timestamp (ordered_at, received_at, declined_at; applied_at on apply). Note what the machine does not model: partially_received stores no received quantities, so a later apply always adds the full ordered quantity of every line.

The current app exercises only a slice of this machine: it offers pending → received ("Have you received the order?") and received → apply ("Update Stock"). It shows a Remove button for every status, but the server deletes only pending or declined orders, so removing any other order gets 400. It also renders partially_received as "Unknown". The full state machine is reachable through the API.

But legality validation in Python is about rules, not concurrency. Concurrency safety comes from the write being a guarded CAS on status, mirroring the item pattern app/api/v1/orders.py:

app/api/v1/orders.py (excerpt)Python
transition_result = await db.execute(
    update(Order)
    .where(
        Order.id == order.id,
        Order.user_id == current_user.id,

The status == old_status guard means the transition fires only if the order is still in the status we validated against. A stale read can't commit a stale precondition. If a concurrent request already advanced the order, this UPDATE matches zero rows and the handler returns 409 (this is the CONC-3 hardening). A loser that read the new status before validating gets 400 instead (illegal transition). The Python check decides what's legal; the database re-checks the precondition atomically at write time.

Applying an order to stock: claim, then apply

The most delicate operation is apply_order_to_stock. It must add each line's quantity to inventory exactly once, even if a user double-clicks "Apply". The design is a two-phase "claim then apply":

  1. Pre-flight resolve — confirm every order line's item still exists and belongs to the user app/api/v1/orders.py, so a missing item aborts before any state change (no partial application).
  2. Claim the order — atomically flip RECEIVED → STOCK_UPDATED with a guarded UPDATE. This is an exactly-once latch: any second apply, concurrent or later, matches zero rows and gets 400 app/api/v1/orders.py.
  3. Apply the stock — only the request that won the claim loops over the order's lines (sorted by item id), adding each line's full ordered quantity with DB-side arithmetic app/api/v1/orders.py.
  4. Commit once — claim + every increment + audit logs are all-or-nothing in a single transaction app/api/v1/orders.py.
app/api/v1/orders.py (excerpt; simplified)Python
# Phase 2 — claim: the terminal status IS the dedupe key
claim_result = await db.execute(
    update(Order)
    .where(Order.id == order.id,
           Order.user_id == current_user.id,
           Order.status == OrderStatus.RECEIVED)

    .returning(Order.id)

🔬 Under the Hood

The ordering is the whole trick. Of two concurrent requests, only one can match status=RECEIVED — the DB serializes them via row lock, the first flips it to STOCK_UPDATED, the second sees zero rows and 400s. Because the claim happens before any stock mutation, the terminal status itself becomes the dedupe key. And the increment is quantity = quantity + delta evaluated by the database, not quantity = python_value — so even the stock change is atomic, never last-writer-wins. Claiming first means the loser does no work and takes no item locks. Applying first would only be safe if the final status write were the same guarded UPDATE, and a zero-row result rolled the whole transaction back. An unguarded status write there would double-credit.

💡 Interview Insight

"How do you prevent two phones from corrupting stock?" Answer with this pattern: a status CAS as an exactly-once latch, plus DB-side + delta increments, all in one transaction. Be precise: this is an exactly-once effect, not an idempotent response. Per RFC 9110, idempotent means repeating the request has the same effect as sending it once. Here, a retry after a lost 200 gets 400. Apply takes no idempotency key (unlike order creation on the feature branch, which accepts a localId), so the client must re-read the order to learn that it was applied. Reproduced on 7 and 8 October 2026: apply incremented each quantity and version once, a second apply got 400, and an apply whose order referenced a deleted item got 409 with nothing changed. That last order then stays received: it can be neither declined nor deleted (finding A-16).

Categories, denormalized snapshots, and transaction boundaries

Categories add one notable rule: a category flagged is_default cannot be deleted — the handler returns 409 before touching anything app/api/v1/categories.py, since deleting a category cascades to its items. The flag is client-controlled: create and update both accept is_default, so a PUT can clear it before a DELETE. The server seeds no categories, and the mobile starter-inventory builder creates its categories without the flag.

Order creation, meanwhile, stores a denormalized snapshot. The server first checks that every item_id belongs to the user app/api/v1/orders.py. Then each OrderItem saves the name, brand, unit and stock figures sent by the client. The body must still contain an orderId (422 if it is missing), but the server ignores its value, along with the client's status, timestamps and totals (it computes the totals itself), and it silently drops the line fields categoryName, isEssential and notes, which have no columns. An order needs 1–1,000 lines, each with a quantity of 1–999,999. So the order is a historical record that survives even if the live item is later renamed or deleted. (That's also why apply needs its missing-items pre-check — the snapshot is a copy, not a live foreign-key reference.)

Transaction boundaries are explicit: each write handler commits its own work once. The session is opened by the get_db dependency; the item handlers stage the mutation plus an ActivityLog plus an AuditLog and persist them with one await db.commit() app/api/v1/items.py. Category create, order create and order status changes stage an ActivityLog only. Category delete stages one ActivityLog plus one AuditLog per contained item, order apply adds an ActivityLog and one AuditLog row per order line, and order delete writes an ActivityLog and an order AuditLog row. Category update writes neither. (The September version of this guide said order delete wrote neither row, which is still true on main; the feature branch writes both.) The item flow is db.add → db.flush() → stage activity + audit → commit() → refresh(). The flush sends the INSERT; the id comes from the UUIDMixin Python default at flush, not from the database. Crucially the audit service only db.adds and never commits, deferring to the caller — so an audited stock change can never exist without its audit row, or vice versa. They share one transaction and roll back together.

📝 Note

Order IDs use a persistent daily counter allocated atomically through PostgreSQL INSERT ON CONFLICT UPDATE RETURNING, plus the existing unique order_id constraint. It survives row/account deletion. The counter row is updated in the order's own transaction, so a rolled-back create does not consume a number, and concurrent creates queue on that one row until the creating transaction ends. The day is the UTC date, and one counter row per day is shared by all users, so one user's numbers have gaps. Reproduced on 7 and 8 October 2026: a deleted order's number was not reused, and a rolled-back create did not consume one. Category/item name checks now serialize normal create/rename paths through per-owner/type transaction advisory locks. Direct SQL/imports can bypass that application policy; legacy duplicates remain and no new database uniqueness rule is claimed for names. One known defect: a name that sanitises to nothing (for example " " or "<b></b>") is accepted and stored as an empty string (reproduced 8 October 2026).

Defense in depth

12 Security Hardening

Security in this backend is not one feature — it is a stack of independent layers, each of which assumes the layer above it might fail. This chapter walks the perimeter inward. It covers rate limiting in application handlers, browser response headers, the CORS credentials invariant and hashed tokens at rest. Then it covers enumeration defenses, parameterized SQL, secret management and attack-surface reduction. The unifying idea is defense in depth — no single control is trusted to be sufficient.

In one line Rate limiting is best effort: five auth routes, counters in memory per worker process, reset on restart; an open finding about how clients are identified is tracked privately. Responses get security headers and a browser CORS policy (which is not an access control). Requests are authorized with tokens validated by type: JWT signature and generation, or challenge digest and expiry. The OpenAPI surface is hidden while DEBUG is off (the default; render.yaml does not set it).

A leaked database yields password and challenge-token hashes rather than usable credentials, although profile, contact and inventory data remain readable. A stolen reset link is single-use and time-bounded. The table below maps the threats this codebase actually defends against to the concrete control and the file that implements it. Layer 2 — Security response headers

Security headers are added to responses that pass through the configured middleware. Unhandled-exception 500s do not: Starlette's outer ServerErrorMiddleware produces them outside this middleware, so they carry none of these headers (reproduced 7 and 8 October 2026). On the feature branch the same is true of the 401, 408 and 413 responses that the outer AIBodyLimit produces itself. X-XSS-Protection is a legacy header, not a substitute for escaping or a modern content-security policy.

app/main.pyPython
@app.middleware("http")
async def add_security_headers(request: Request, call_next):
    response = await call_next(request)
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["X-Frame-Options"] = "DENY"
    response.headers["X-XSS-Protection"] = "1; mode=block"
    response.headers["Referrer-Policy"] = "strict-origin-when-cross-origin"
    response.headers["Cache-Control"] = "no-store"
    if settings.ENVIRONMENT == "production":
        response.headers["Strict-Transport-Security"] = "max-age=31536000; includeSubDomains"
    return response

Note the structure: the headers are applied after await call_next(request), so they wrap whatever the inner layers produced (app/main.py). Each one maps to a specific threat model:

X-Content-Type-Options: nosniff
Stops browsers from MIME-sniffing a response into an executable type — defeats drive-by content-type confusion.
X-Frame-Options: DENY
The page may not be framed at all — clickjacking protection.
X-XSS-Protection: 1; mode=block
Legacy header that modern browsers ignore. OWASP now advises not setting it, or sending X-XSS-Protection: 0, because the old XSS auditor could itself be abused. This code still sends 1; mode=block, and the comment above the header block calls the set "OWASP recommended". CSP is the modern control.
Referrer-Policy: strict-origin-when-cross-origin
Limits how much of the URL (paths, query) leaks to third parties via the Referer header.
Cache-Control: no-store
Prevents browsers and proxies from caching potentially sensitive medical API responses.
Strict-Transport-Security
Tells browsers that received it over HTTPS to use only HTTPS for a year — sent only when ENVIRONMENT is production. Browsers ignore HSTS on plain-HTTP responses, so http://localhost would not be affected. The gate avoids pinning hosts that might not always serve valid HTTPS. It would matter on an HTTPS localhost, where HSTS covers every port. It protects browser flows such as the email-link pages; the mobile app relies on its https:// build URL and disabled cleartext.
🔬 Under the Hood

Why is HSTS gated on environment but the others are not? HSTS is a persistent browser commitment: once a browser sees max-age=31536000 over HTTPS it refuses plain-HTTP to that host for a year. An HTTPS development host would be pinned for a year (HSTS is ignored over plain HTTP); the others (nosniff, DENY) have no downside in dev, so they ship unconditionally. Content-Security-Policy is not set. Most responses are JSON, but the backend also serves HTML for email links: the verify-email result, the password-reset form (with an inline script) and the account-deletion confirmation form. There, a CSP would add defense in depth: at least frame-ancestors 'none', plus a hash- or nonce-based script policy for the reset page.

Layer 3 — The CORS wildcard-vs-credentials invariant

You met the CORS branch in the request-lifecycle chapter; here is the security rule it encodes. The branch is chosen by CORS_ORIGINS, not ENVIRONMENT: if the list contains "*", the app sets allow_origins=["*"] with allow_credentials=False; otherwise it sends the listed origins with allow_credentials=True (app/main.py). The repository's production blueprint (render.yaml) sets CORS_ORIGINS='["*"]', so repo-declared production uses the wildcard branch (and even logs "CORS: Development mode"), while docker-compose.dev.yml uses an explicit list. Because clients authenticate with bearer tokens rather than cookies, the credentials flag is not what protects this API. The wildcard/credentials split itself is not a stylistic choice — the Fetch/CORS spec forbids combining Access-Control-Allow-Origin: * with Access-Control-Allow-Credentials: true, and browsers reject any response that does. The reasoning: the wildcard says “any site may read this,” while credentials say “this response is authenticated” — allowing both would let evil.com read a logged-in user's data.

🛡️ Security / OWASP

CORS is browser-enforced, not a server-side authorization control. A native mobile app, curl, or a server-side attacker ignores CORS entirely. Tightening CORS_ORIGINS would therefore neither protect the API nor restrict the Android app, which is not subject to it. Real authorization here comes from JWT bearer auth plus ownership scoping — never from the CORS config. State this explicitly; interviewers love watching candidates mistake CORS for access control.

Layer 4 — Tokens hashed at rest, looked up by digest

Email-verification, password-reset, and account-deletion tokens are bearer secrets: anyone holding the raw value can act on it, exactly like a password. So the raw token is emailed to the user and only its SHA-256 hash is stored in the database. If the DB leaks, an attacker holds hashes that cannot be reversed into valid links.

app/utils/email.py — generate_verification_token (used) and verify_token (currently unused)Python
def generate_verification_token() -> tuple[str, str]:
    unhashed_token = secrets.token_urlsafe(32)
    hashed_token = hashlib.sha256(unhashed_token.encode()).hexdigest()
    return unhashed_token, hashed_token

def verify_token(unhashed_token: str, hashed_token: str) -> bool:
    computed_hash = hashlib.sha256(unhashed_token.encode()).hexdigest()
    return secrets.compare_digest(computed_hash, hashed_token)

Two subtleties. First, why SHA-256 and not Argon2 like the password? Because the token is secrets.token_urlsafe(32) — 256 bits of cryptographically random data — so brute force is infeasible regardless of hash speed; a single fast pass is enough. The deterministic, unsalted digest is also what makes an indexed lookup possible. A user password is low-entropy and human-chosen, so it needs the deliberately slow, memory-hard Argon2 KDF (app/core/security.py). Second, the check is a database lookup by digest (…WHERE password_reset_token = sha256(raw) AND expiry > now), not a Python comparison. Lookup timing cannot help an attacker, who cannot choose digest prefixes without a SHA-256 preimage. When application code compares two secrets directly, secrets.compare_digest is the right tool; it is present in the unused verify_token helper. A naive == short-circuits on the first mismatched byte.

🛡️ Security / OWASP

Reset and verification tokens are treated as secrets at rest, with the same care as passwords. They are hashed and time-bounded, with application redaction; platform-log verification is still pending. On a successful password reset, every refresh token for the user is revoked in the same transaction (app/api/v1/auth.py). That invalidates sessions on all other devices, the standard account-takeover defense.

Layer 5 — Anti-enumeration

The reset and resend-verification endpoints must never become an oracle that tells an attacker which emails are registered. So they return an identical response whether or not the account exists, is inactive, or is already verified:

The asymmetry worth naming: /register returns 400 “Email already registered” or “Username already taken” (app/api/v1/auth.py), and authenticated profile updates also report taken usernames, so existence leaks there. For email addresses this is a design choice, not a necessity: OWASP's authentication guidance recommends the same generic “check your email” response, and a common addition is to notify the existing owner by email. Username uniqueness is inherently observable, so it depends on throttling. (For this product, account existence also reveals that a household manages home-ICU supplies — health-adjacent information.)

💡 Interview Insight

The sharp follow-up is the residual timing side-channel: when the user is absent, login skips the expensive Argon2 verify entirely, so a “missing user” response can be measurably faster. The honest answer names it, then notes the partial mitigation present: the login rate limit (best effort; counters in memory per worker process). The fuller fix is to verify against a dummy hash for missing users, which equalizes timing. Off-thread hashing keeps the event loop responsive; it does not equalize response times.

Layer 6 — SQL injection prevented by parameterized construction

There is no string-built SQL anywhere in the request path. Every query goes through SQLAlchemy's expression language, which sends parameterized statements — values travel separately from the SQL text, so a user input can never be parsed as SQL.

app/api/v1/auth.py (forgot-password and resend-verification)Python
result = await db.execute(
    select(User).options(noload("*")).where(User.email == data.email.lower()).with_for_update()
)

The data.email.lower() value is bound as a driver-level parameter, not concatenated. The app's raw statements are the readiness probe's constant text("SELECT 1") (app/main.py), the inventory lock's text("SELECT pg_advisory_xact_lock(:key)") with a bound parameter, and on the feature branch the AI guard's constant text("SELECT pg_advisory_xact_lock(72401931)") (app/services/ai_guard.py). Search terms are bound values too; % and _ inside them act as LIKE wildcards, which affects matching, not SQL structure. This is the cheapest, most complete control in the table: injection is prevented by construction, not by escaping.

Two more rings round out the posture. Layer 8 — IDOR defense: ownership scoping

Logout is one example — it revokes a refresh token only if it belongs to the caller:

Production readiness

13 Reliability & Observability

A backend that handles medical inventory cannot afford to confuse "my database is briefly unreachable" with "my process is dead". Nor can it leak a SQL constraint name to an attacker on a 500. This chapter is about the unglamorous machinery that keeps the service up, lets you see inside it when something breaks, and fails in safe, boring ways. That means split health probes, server-side timeouts, graceful shutdown, redacted text logs and optional Sentry. It also means a response X-Request-ID (not yet written to logs) and global exception handlers that return generic JSON instead of Starlette's plain-text error.

In one line /health is readiness: it probes the DB under a 2 s timeout and returns 503 if the DB is down. The /live endpoint is liveness: it checks only the process and never touches the DB. Mixing them up is how a brief DB blip becomes a cluster-wide restart storm.

Two probes, two different orchestrator actions

The most important reliability decision in this codebase is that there are two health endpoints, not one. They answer two independent questions. The /live endpoint asks: is this process alive, and is the event loop responsive? The /health endpoint asks: can this instance actually serve traffic right now, including its dependencies? Kubernetes attaches a different recovery action to each probe type (liveness → restart, readiness → stop routing traffic). Render is simpler: it has one health-check path per service; after about 15 s of failures it stops routing to the instance and after about 60 s it restarts it. The repository's render.yaml points that path at /live (the live dashboard setting is not verified), so Render neither depools nor restarts on a database outage; /health is used by clients and docker-compose.

"If the database goes down, which endpoint fails and what should the orchestrator do?" is a staff-level filter. The answer they want: /live stays 200, /health returns 503; a Kubernetes-style orchestrator depools the instance (removes it from the load balancer) but does not restart it. On Render, with a single check pointed at /live, the instance simply keeps serving (and failing DB-bound requests) until the database recovers. The trap is wiring the DB check into the liveness probe — then a transient blip restart-loops every pod at once, turning a recoverable dependency hiccup into a full outage. This codebase points Render's healthCheckPath and the Dockerfile HEALTHCHECK at /live precisely so a Neon serverless cold start can't trigger a restart storm. A regression test checks that render.yaml still says /live. (It cannot see a different value set in the Render dashboard.)

🔬 Under the Hood

Why the asyncio.wait_for(..., timeout=2.0) wrapper? A health probe that can block indefinitely is worse than no probe. If a TCP connection to Postgres hangs (half-open socket, network partition), a bare await db.execute(...) never returns. The health endpoint itself hangs, the orchestrator's probe times out ambiguously, and the failure mode is undefined. The wait_for call imposes a hard ceiling: the probe coroutine is cancelled at 2 s, and the function reliably returns False → 503. A health check must always answer quickly, even when the answer is "no."

⚠️ Pitfall

The server-side statement_timeout is 8000ms but the readiness probe caps at 2.0s. That gap is intentional, but reason about it together: a slow-but-alive DB responding between 2s and 8s will be marked unready (503) even though the query would eventually succeed. For a readiness check that's the correct call: you don't want to send user traffic to an instance whose DB is crawling. But it's the kind of subtlety an interviewer will poke at.

⚠️ Misconception — "healthy means my release is live"

A 200 from /health proves only that some process could reach some database within 2 s. It does not say which commit is running: both probes report version from the APP_VERSION setting (default "1.0.0" in app/core/config.py; an environment variable can override it, and render.yaml does not set it), and nothing else in the API reports a build or commit. Nor does it say which migration the database is at. To know what is deployed, check the platform's deploy record for the commit and run alembic current against the target database. Resilience baked into the connection layer

Reliability isn't only about probes; it's about each request degrading gracefully. Two engine settings carry most of that weight.

app/core/database.py (excerpt; comments added)Python
# Cap every statement at 8s so one hung query can't pin a pooled connection
# indefinitely and cascade into pool exhaustion (RESIL-1).
_server_settings = {"statement_timeout": "8000"}

engine = create_async_engine(
    settings.DATABASE_URL,
    pool_size=settings.DATABASE_POOL_SIZE,       # 5 persistent
    max_overflow=settings.DATABASE_MAX_OVERFLOW, # +10 burst -> 15 per worker
    pool_timeout=settings.DATABASE_POOL_TIMEOUT, # 30s backpressure
    pool_pre_ping=True,                          # discard dead connections
    connect_args=_connect_args,
)

The pool-exhaustion story. Each worker's engine can open at most 15 connections (5 pooled + 10 overflow); with two Gunicorn workers an instance can open 30, and an overlapping deploy doubles that. Without statement_timeout, a single runaway query would hold its connection forever. Under load, a handful of such queries drain a worker's 15 connections. Every later request on that worker then blocks for the full pool_timeout (30 s) waiting for a checkout, and the service effectively stalls. One slow query grows into an outage. The Postgres-side 8 s timeout aborts the offending statement; once the application rolls back and closes its session, the connection returns to the pool app/core/database.py. It does not limit time spent between statements while a transaction holds a connection; login, for example, keeps its row lock and connection while Argon2 runs. No idle-in-transaction timeout is set either. Separately, pool_pre_ping=True tests a connection when it is checked out. It transparently replaces connections that Neon or a proxy silently killed while idle, so a request after an idle period gets a fresh connection instead of a closed-connection 500.

Graceful shutdown via lifespan

On SIGTERM (a deploy, a scale-down), the Gunicorn master — PID 1 after the entrypoint's exec — tells each Uvicorn worker to stop. Each worker stops accepting connections, finishes in-flight requests and their background tasks, then fires the ASGI lifespan.shutdown event, which runs everything after yield in the lifespan context manager. Here that means dispose_engine(), which closes every pooled connection cleanly instead of leaving Postgres to reap orphaned sockets app/main.py. Gunicorn's graceful timeout and Render's shutdown delay (both 30 s by default) cap this; anything still running is killed.

3 — X-Request-ID. A middleware reuses any inbound X-Request-ID (from a gateway or the client; the value is not validated). Otherwise it mints a fresh uuid4().hex: 122 bits of randomness, effectively collision-free. It echoes the ID on responses that pass through the middleware, so a client can quote it in a bug report. Unhandled-exception 500s do not carry it, nor do the 401, 408 and 413 responses that AIBodyLimit sends itself. It is not in the CORS expose list, so browser code on another origin cannot read it.

app/main.pyPython
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID") or uuid4().hex
    response = await call_next(request)
    response.headers["X-Request-ID"] = request_id
    return response
✅ Pro Tip

The win is end-to-end correlation. In a distributed system, one user action traverses load balancer → API → DB → external services. A stable ID threaded through every log line lets you reconstruct the causal chain with a single grep <request-id>. Honoring an inbound ID is what preserves an upstream gateway's trace across the whole hop, instead of regenerating it and severing the chain. Here is the honest critique of this implementation, and a great thing to volunteer in an interview. The ID isn't bound to a contextvars.ContextVar or injected into the log formatter. So the in-handler log lines don't actually carry it yet. The mature fix: store it in a contextvar at the start of the middleware, and add a logging filter that copies it onto every LogRecord. Longer term, adopt W3C traceparent + OpenTelemetry so it propagates to downstream spans automatically.

Global exception handlers: never leak internals

Three handlers are registered in register_exception_handlers app/main.py, next to slowapi's own 429 handler. Starlette's ExceptionMiddleware chooses a handler by walking the exception class's MRO (method resolution order). So the most specific registered class wins, regardless of registration order. The Exception handler runs separately, in the outermost ServerErrorMiddleware. The governing principle: log enough server-side to locate the failure (exception type and code locations; values are withheld by app/core/logging.py) and return a safe generic message to the client.

The handler returns a generic database-error response. The local logging layer deliberately omits exception values and retains types/code locations. This reduces sensitive-data exposure but also limits diagnostics; it is not a guarantee that every hosting log is scrubbed.

📝 Note

Registering a handler for bare Exception replaces Starlette's plain-text "Internal Server Error" with a JSON body (stack traces are rendered only with debug=True, which this app does not set). The trade-off: you are now blind to those bugs unless logging/Sentry is solid — which is exactly why the Sentry layer exists. Two Starlette nuances worth naming. First, Starlette installs this handler on ServerErrorMiddleware, the outermost layer. So the 500 it produces bypasses the security-header, request-ID and CORS middleware. The exception is then re-raised to the server for logging. Second, an exception raised inside an @app.middleware function skips the HTTPException, IntegrityError and validation handlers and ends in this same generic 500. To keep headers and the request ID on 500s, catch exceptions in an outer middleware or add them in the handler.

BackgroundTasks: don't block the response on SMTP/HTTP

Registration and password-reset flows need to send email, but a transactional email round-trip to Brevo's HTTP API can take hundreds of milliseconds (not measured here; the client allows up to 10 s) app/utils/email.py. Blocking the user's response on it would couple their perceived latency to a third party's. Instead the handler queues the send with FastAPI's BackgroundTasks and returns immediately; the task runs after the response is flushed.

app/api/v1/auth.py (excerpt)Python

🔬 Under the Hood

BackgroundTasks runs after the response is sent but in the same process and event loop — it is not a distributed queue. That suits a fire-and-forget, best-effort email (the send itself is wrapped in try/except and only logs on failure, so a Brevo outage never 500s the registration). But it has limits an interviewer will probe. Tasks don't survive a crash, an OOM kill or a shutdown that exceeds the grace period (a graceful restart normally lets them finish). There's no retry or dead-letter queue. And a slow task still consumes a worker's loop time. For guaranteed delivery you'd graduate to a real broker — Celery/RQ on Redis, or a managed queue — and treat the email as a durable job. Knowing when in-process background tasks are sufficient (low-stakes, idempotent-ish notifications) versus when they're not is the real signal.

📝 Current addition (7 Oct 2026) — failure handling around the model call

The feature branch's /ai/interpret is the app's main request path that waits on a third party in the foreground (the gated transcribe/speak routes and the 5 s email-service-status check also call out), so it is fenced in. The provider call has a 25 s total deadline (plus a 5 s connect timeout), no automatic retry and no failover. No pooled database connection is held while it runs: the usage reservation commits first in its own short transaction, and the settlement runs afterwards in another, wrapped in asyncio.shield so a client disconnect cannot cancel it. If the settlement itself fails, the row stays "reserved"; it still counts against the daily limits and stops counting as in-flight when it expires. Errors are mapped, not leaked: provider 429 → 429, other provider HTTP errors → 502, a timeout or network failure → 504 (still counted against quotas; the timeout case was reproduced 7 and 8 October 2026). On the phone, the assistant gives up after 50 s, while ordinary API requests have a 90 s overall deadline.

Reliability requires measured failure behavior. The code has timeouts, probes and best-effort background email, while deployment checks, alerts, restore evidence and the open rate-limiter finding remain open. Exceptions are redacted, not logged in full.

The image and its start-up

  • The non-root (uid 1000), multi-stage python:3.12-slim image starts two Gunicorn-managed Uvicorn workers, each with its own pool of up to 15 database connections (5 + 10 overflow), so up to 30 per instance.   • The shell entrypoint parses the database host and port out of DATABASE_URL and waits for it with pg_isready (up to 30 tries, 2 s apart, then carries on with a warning). Actual platform shutdown behaviour still requires an image test.
  • The worker class uvicorn.workers.UvicornWorker is deprecated in the pinned Uvicorn 0.34; the maintained options are the uvicorn-worker package or Uvicorn's own --workers supervisor.

Automatic downgrade is refused, because removing generation/counter history can reopen security and numbering defects. A rollback image is not automatically schema- or behaviour-compatible.

⚠️ Misconception — "rolling back the code rolls back the database"

Redeploying an older image changes only the code. The entrypoint runs alembic upgrade head, never a downgrade, so the database keeps every migration the newer image applied. An older image that still contains those revision files then runs its code against the newer schema. An image that predates them (for example main's, whose migrations stop at 0006) cannot start at all: its Alembic cannot locate the database's revision, the entrypoint exits 1, and Render keeps the version that is already running. Undoing a migration is a separate, deliberate alembic downgrade — and 0007's downgrade deliberately raises an error, so once 0007 is applied there is no automatic way back. (0008–0010 do have downgrades: they drop the AI tables and columns, or only the 0010 index, and every order row stays.) A schema problem after a release is therefore fixed forward or restored from a backup, and a restore can lose writes made after it.

16 System design: grow from measurements

In one line A small monolith on PostgreSQL. Scale it by measuring the real bottleneck first and choosing the smallest change that fixes it — not by drawing a million-user diagram.

CareKosh is deliberately a small monolith with PostgreSQL. The owner's planning target is up to 10,000 accounts and perhaps 100–1,000 concurrently active users. Both numbers are planning assumptions, not measured capacity. Registered accounts are not concurrent users, and active users are not concurrent requests: most active users are idle between taps, and the server sees requests, not people. No load test in this repository demonstrates any of these capacities.

First measure the bottleneck

Define the traffic mix, per-account data size, and p95/p99 latency and error targets. Then measure query plans and eager-loading cost (the post-commit db.refresh(user) on login and refresh, which loaded the user's whole graph, is gone on the feature branch but still present on main; /items/stats still loads every active item into memory to count them). Measure connection waits, and row and advisory lock waits (including the per-day order-counter row and, if AI is enabled, the single global AI budget lock). And measure the CPU and memory used by password hashing: 64 MiB per Argon2 hash. At the defaults, two workers can open up to 30 application connections per instance; multiple services and overlapping deployments add to that budget.

17 Design Patterns & SOLID

When an interviewer asks "where do you use design patterns?", the worst answer is a recital of the Gang-of-Four catalogue. Unit of Work — one session per request, one commit per write

get_db app/core/database.py scopes one session per request. As a yield-based dependency, it gives FastAPI a setup/teardown hook. It opens one session and hands it to the handler. On a clean return it calls commit(); on any exception it calls rollback() and re-raises; and in finally it always calls close(). But the atomic boundary for writes is the handler's own explicit await db.commit(). A handler that stages an item, an ActivityLog and an AuditLog commits them together, so all three persist or none do. The post-yield commit in get_db then usually just ends the read-only transaction that the handler's post-commit refresh() (or a GET) started — SQL after a commit begins a new transaction, so this is one session per request, not one transaction. Its real roles are session scope and rollback on error.

app/core/database.pyPython
async with AsyncSessionLocal() as session:
    try:
        yield session
        await session.commit()      # success → commit anything still pending
    except Exception:
        await session.rollback()    # any raise → undo work not yet committed
        raise
    finally:
        await session.close()       # always return the connection to the pool
🔬 Under the Hood

The session is a SQLAlchemy Identity Map + Unit of Work: it tracks loaded objects and accumulates pending changes, flushing SQL lazily and committing once. The handlers treat the session as a repository-ish data-access seam — queries like select(Item).where(Item.user_id == current_user.id) stand in for a repository method. There's no explicit Repository class here, but the Session is the abstraction that hides connection management and change tracking from the handler.

Singleton settings via lru_cache

Configuration is parsed and validated exactly once. The function get_settings() is called a single time at import (settings = get_settings()), and every module imports that object. @lru_cache makes any later call return the same instance. So the environment is read once at start-up — one fail-fast point, one source of truth. It's the functional idiom for a Singleton: memoize a zero-argument constructor.

A helper that defers the commit

The audit helper app/services/audit.py shows a subtle, mature decision. The function log_audit builds an AuditLog and db.add()s it, but deliberately does not commit. Its comment says to let the caller's transaction commit the mutation and the audit row together. This keeps the audit row format in one place while respecting the transaction the handler commits. If the service committed internally, you could end up with an audit row for a change that later rolled back — a corrupted ledger.

⚠️ Pitfall

A helper that commits "to be safe" silently fractures the transaction boundary. Here the helper stages the row and trusts the handler's single commit to make it atomic with the business mutation. Committing inside the helper would create phantom audit entries (audit persisted, mutation rolled back) or unaudited mutations — the exact failure modes a compliance-grade trail must never have.

Middleware onion — Chain of Responsibility

Each middleware is a handler in a chain: it does a little work, calls await call_next(request) to delegate inward, then optionally mutates the response on the way out. The correlation-ID and security-headers middleware app/main.py stamp headers after call_next returns, so they decorate whatever the inner layers produced. CORS is configuration-selected: wildcard without credentials when CORS_ORIGINS contains "*" (as the repository's production blueprint does), otherwise specific origins with credentials — same slot, different settings. DTO boundary & Snapshot

Q01FoundationalWhat is ASGI, and why does FastAPI need it instead of WSGI?›

WSGI (Web Server Gateway Interface) is the old synchronous contract between Python web servers and apps: one callable, app(environ, start_response), called once per request, blocking until it returns. It has no concept of await, long-lived connections, or WebSockets. ASGI (Asynchronous Server Gateway Interface) generalises it: the app is async def __call__(self, scope, receive, send), where scope describes the connection, and receive/send are async channels for streaming events.

FastAPI is built on Starlette, an ASGI framework, and an app object is an ASGI callable — that is exactly what Uvicorn imports as app.main:app and invokes. ASGI is what lets a single worker handle thousands of concurrent connections cooperatively (every await on I/O yields control), and it's what makes WebSockets, SSE, and long-polling possible. With WSGI you'd need one thread or process blocked per in-flight request. The trade-off: in async code you must never call a blocking library, or you stall the whole event loop.

Q02FoundationalWhat does async/await actually do, and how does one worker serve many requests?›

An async def function is a coroutine function: calling it doesn't run it, but returns a coroutine object that the event loop drives. The keyword await is a cooperative yield point. When you await something I/O-bound (a DB query, an HTTP call), the coroutine suspends and hands control back to the event loop. The loop is then free to advance other coroutines while the OS waits on that socket. When the I/O completes, the loop resumes your coroutine where it left off.

So a single-threaded worker interleaves many requests: while request A is blocked on await db.execute(...), the loop runs request B's code. This is concurrency without parallelism — one CPU, many in-flight I/O operations. It beats a thread-per-request model for I/O-bound web work because there's no thread context-switching or memory overhead, and it sidesteps the GIL (which only matters for CPU-bound parallelism). The catch: the model only works if every request spends its time waiting, not computing. A CPU-bound chunk (e.g. password hashing) must be pushed off the loop — see Q03.

Q03AdvancedWhat's the single biggest async pitfall, and how does this codebase avoid it?›

Blocking the event loop. Because one thread drives every concurrent request, a single synchronous CPU-bound (or blocking-I/O) call freezes all of them until it returns. Argon2 password hashing is deliberately slow and memory-hard: 64 MiB per hash with this project's settings, and about 20 ms on a laptop (a local measurement on 7 October 2026, never on the production instance). Calling it directly inside an async def route would stall every other request on that worker for that time.

CareKosh avoids this by offloading the hash to a worker thread via AnyIO, keeping the loop free:

app/api/v1/auth.py (excerpts from register and login)Python
hashed_password=await anyio.to_thread.run_sync(hash_password, data.password),
# ... and on login:
if not user or not await anyio.to_thread.run_sync(
    verify_password, data.password, user.hashed_password
):

The same pattern is used on register, login, change-password, and reset app/api/v1/auth.py. The DB query, by contrast, stays on the loop — it's I/O-bound and asyncpg is non-blocking, so await db.execute() yields naturally. The rule: await I/O on the loop; push CPU work to a thread. And name the misconception before the interviewer does: async does not make the hash itself any faster. The thread costs the same CPU time and 64 MiB; it only stops one login's hash from freezing everyone else's requests.

Q04IntermediateHow does FastAPI's dependency injection work, including yield dependencies?›

You declare a parameter as Depends(callable). FastAPI builds a dependency graph per request, resolves each callable (sync or async), injects the result and caches it for that request. So if two dependencies both depend on get_db, the session is created once. A yield dependency is a generator. Code before yield is setup, and the yielded value is injected. Code after yield runs at teardown; in the pinned FastAPI 0.115.6, that is after the response is serialized and before it is sent. The file app/core/database.py uses this for the per-request session:

app/core/database.pyPython
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
        finally:
            await session.close()

This gives every request one session that rolls back on any exception and always closes — the natural place for cross-cutting setup/teardown. Write handlers commit explicitly inside it; the post-yield commit is a safety net for anything still pending. DI is also how the authenticated user is injected, without the handler knowing how it's built. Q06IntermediateWhy are there separate request and response Pydantic models, and what is from_attributes?›

The wire model and the storage model have different shapes and different trust levels, so they're different classes. A request model (e.g. UserRegister) validates and coerces untrusted input — it includes the plaintext password and enforces rules; a response model (e.g. UserResponse) defines what's safe to expose and never includes hashed_password. Using response_model=UserResponse means even if the handler returns a full ORM object, FastAPI filters the output to only the response model's fields — a built-in guard against accidental data leakage.

To turn an ORM object into a response model, you need from_attributes (formerly "ORM mode"). In Pydantic v2 that is model_config = ConfigDict(from_attributes=True). It lets UserResponse.model_validate(orm_user) read attributes off the SQLAlchemy instance instead of expecting a dict. Forget it and you get a validation error trying to serialize the model. This request/response split is also what makes the OpenAPI schema accurate and is a textbook example of the DTO / boundary pattern.

Q08AdvancedIn FastAPI, when should a route be def vs async def?›

FastAPI accepts both and treats them differently. An async def route runs directly on the event loop — correct when its body only awaits non-blocking I/O (async DB driver, async HTTP client). A plain def route is run by FastAPI in an external threadpool, so it won't block the loop even if it does blocking work. So the decision rule is about what the body does, not preference:

  • Body awaits async I/O (like every handler here, using asyncpg) → async def.
  • Body calls a blocking/sync library (a sync DB driver, requests, heavy CPU) and you can't make it async → def, and let FastAPI offload it.
  • Worst case: async def that calls a blocking function directly — it stalls the loop for every concurrent request. That's the trap Q03 is about; the fix is either def or anyio.to_thread.run_sync.

CareKosh uses async def everywhere because its I/O (DB, email) is async, and surgically threads only the CPU-bound Argon2 hash.

Q10AdvancedWhat is a connection pool, and how does statement_timeout protect it?›

Opening a Postgres connection is expensive (TCP + TLS + auth + backend process). A pool keeps a set of live connections and lends them to requests, recycling instead of reopening. The async engine configures it explicitly app/core/database.py: pool_size=5, max_overflow=10, pool_timeout=30 and pool_pre_ping=True. That allows up to 15 connections per engine. There is one engine per Gunicorn worker process, and the Dockerfile starts 2, so one container can open up to 30. Pre-ping is a tiny health check that discards dead connections before handing them out, so a Neon idle-disconnect doesn't surface as a random error.

The subtle hardening is a per-statement timeout pushed to the server:

app/core/database.pyPython

Without it, one pathological query can run forever, pinning its pooled connection. Under load those hung connections accumulate until the pool is exhausted and healthy requests start timing out waiting for a connection — a cascading failure from one bad query. Capping every statement at 8 s bounds the blast radius. It's a small line with a big resilience payoff — though it limits single statements only, not time a transaction sits idle holding a connection.

Q11IntermediateExplain the transaction-per-request pattern — when does the commit actually fire?›

Short answer: it is one session per request, not one transaction; the write handler commits, and the dependency is the safety net. Each request gets one AsyncSession from the get_db yield-dependency (SQLAlchemy's Unit of Work). In practice the handler does its db.add() / db.execute() calls and then commits explicitly with await db.commit() before returning — so it can refresh() and serialize fresh data (e.g. app/api/v1/auth.py). The dependency's post-yield code also commits on success, but that's a fallback; its load-bearing job is to roll back on error:

flow: handler runs (and usually commits) → returns → get_db resumes past its yield → await session.commit() (it ends any transaction begun after the handler's commit, such as the refresh() read; the AI routes skip get_db and use their own short sessions) → session.close(). If the handler raises before its explicit commit, the except branch rolls everything back, so the writes staged so far are all-or-nothing. That is why a handler can create a user, a refresh-token row and an activity-log row, and trust that they all persist or none do. Anything that fails after the handler's own commit (await db.refresh(), response serialization) cannot be undone. The data stays committed even if the client sees a 500. That is why order creation on the feature branch accepts a localId: a retry with the same key returns the order already created instead of a second one. A create without a key (older app builds, or main) can still produce a duplicate on retry. Handlers that need an ID mid-flow use await db.flush() (sends the SQL, stays in the transaction) rather than committing early. The mental model: the handler owns the commit point; the dependency is the safety net that rolls back uncommitted work and always closes the session.

Q12AdvancedWhat is the N+1 query problem, and why does the auth path use noload("*")?›

Q13AdvancedOptimistic vs pessimistic concurrency — how does item update implement it?›

Pessimistic locking takes a lock up front (SELECT ... FOR UPDATE) so other writers and lockers of that row wait (plain reads are not blocked in PostgreSQL) — safe, but it serializes writers and can deadlock. Optimistic concurrency assumes conflicts are rare: you carry a version, and on write you check it hasn't changed; if it has, you reject and let the client retry. CareKosh uses optimistic control for item edits via items.version, plus a per-account, transaction-scoped advisory lock for the duplicate-name check. PUT /items/{id} takes that lock whenever the body includes a name, before its SELECT; the Edit Item screen always sends the name, so every Edit Item save takes it. Item create and category create/rename take it too; PATCH …/stock does not. Elsewhere it uses pessimistic row locks: SELECT … FOR UPDATE on users in the login, refresh and password flows. The optimistic check-and-bump happens inside a single SQL UPDATE (a compare-and-swap):

SQL equivalent (app/api/v1/items.py)SQL
UPDATE items SET ..., version = version + 1
 WHERE id = :id AND user_id = :uid AND version = :client_version

If zero rows match, the version moved on (or the row vanished). The handler then returns 409 Conflict with {error, message, server_version, server_quantity}, built from the values it read before the UPDATE app/api/v1/items.py. That is usually the newer server state. But in a same-instant race it can still echo the client's own version, so the client should re-fetch. (The app now invalidates affected active queries after 409 and captures the form version with its values. Retry retains the original version; reopen the form before editing again. A-1 is fixed locally.) Doing the compare in the WHERE clause (not in Python after a read) is what makes it race-safe — there's no read-then-write gap. This is the same idea as an HTTP ETag/If-Match, a DynamoDB conditional write, or a Kubernetes resourceVersion.

Q14StaffTwo phones edit the same item's stock at once — how do you prevent corruption?›

When applying an order to stock, the quantity is incremented in SQL:

SQL equivalent of the SQLAlchemy update() in app/api/v1/orders.pySQL
UPDATE items SET quantity = quantity + :qty, version = version + 1
 WHERE id = :id AND user_id = :uid

Q15AdvancedWhy does order_items.item_id have no foreign key — isn't that a bug?›

Q16AdvancedWhat does expire_on_commit=False do, and what async trap does it dodge?›

By default SQLAlchemy expires all loaded objects after commit(), so the next attribute access re-fetches from the DB to guarantee freshness. In async code that lazy re-fetch is a landmine. Accessing an expired attribute after commit triggers implicit I/O outside an await, which raises MissingGreenlet: SQLAlchemy can't do sync I/O on the event loop. The session is configured with expire_on_commit=False app/core/database.py precisely so objects stay usable after the handler's own await db.commit(). For example, resend-verification reads user.email and user.name right after committing, without a surprise query.

The related discipline: in async SQLAlchemy you must load relationships explicitly (eager strategy or an awaited query), never rely on implicit lazy access. That's also why the models choose lazy="selectin" and the auth path uses noload("*") — the loading strategy is always a conscious, awaited decision, never an accidental sync round trip.

Q17IntermediateWhy store enums as VARCHAR (native_enum=False) instead of a native Postgres ENUM?›

OrderStatus and ActivityActionType are mapped with SQLEnum(..., native_enum=False, length=...), which stores the enum member's name (e.g. 'RECEIVED') in a plain VARCHAR column rather than a Postgres ENUM type. No CHECK constraint exists — SQLAlchemy's create_constraint defaults to False and migration 0001 declares status as sa.String(20) — so only the Python Enum enforces the allowed set. The motivation is migration ergonomics: a native Postgres ENUM is a database type, and adding a value requires ALTER TYPE ... ADD VALUE (which historically couldn't run inside a transaction) while removing values is genuinely painful (renaming has been possible since PostgreSQL 10) and Alembic autogenerate handles it poorly. With a VARCHAR-backed enum, evolving the set of statuses is just application code (plus optionally a CHECK constraint) — no fragile type migration.

The trade-off is that the database no longer enforces the allowed set by type. You rely on the application (the Python Enum), and here there is no CHECK constraint behind it. So an unknown string written by raw SQL is accepted, and the ORM raises LookupError when it loads that row. Raw SQL must also use the uppercase member names. For a fast-moving product where status values change, that flexibility usually wins. It's a small modeling decision interviewers like because it shows you've felt the pain of enum migrations.

Q18IntermediateWhat pagination does this use, and what's wrong with OFFSET at scale?›

Q21StaffWalk through refresh-token rotation and prove it's race-safe.›

Refresh locks the user row before claiming the refresh row. Q22AdvancedWhy Argon2 over bcrypt or SHA-256, and what does deprecated="auto" buy you?›

Never store passwords with a fast hash like SHA-256 — its speed is exactly what lets an attacker try billions of guesses/second against a stolen dump. Password hashes must be deliberately slow and salted. Argon2 won the 2015 Password Hashing Competition, and its Argon2id variant is the current OWASP and RFC 9106 first choice. It is memory-hard: it needs significant RAM per hash. That defeats the GPU/ASIC parallelism that makes bcrypt brute-forcing cheaper. The config registers it with a fallback app/core/security.py:

pwd_context = CryptContext(schemes=["argon2", "bcrypt"], deprecated="auto")

Salting is automatic. Passlib generates a unique salt per hash and stores it in the encoded string, so identical passwords get different hashes (defeating rainbow tables). The deprecated="auto" setting marks every scheme except the default (argon2) as deprecated. That makes upgrade-on-login possible — but only if the login path calls pwd_context.verify_and_update() (or needs_update()) and saves the new hash. CareKosh's login calls verify() only, so bcrypt or older-parameter hashes are verified but never re-hashed today. Its effective Argon2id parameters are argon2-cffi's defaults (t=3, m=64 MiB, p=4) — RFC 9106's second recommended option — above the OWASP minimum.

Q23AdvancedHow does the auth flow prevent email enumeration, and why are reset tokens hashed?›

Q24AdvancedWhat's the difference between liveness and readiness probes, and why does conflating them cause outages?›

They answer different questions. Liveness asks: is the process alive, or wedged and in need of a restart? Readiness asks: can it serve traffic right now? CareKosh exposes both app/main.py. The /live endpoint returns 200 unconditionally (process-only, never touches the DB). The /health endpoint probes the DB with SELECT 1 under a 2-second asyncio.wait_for, and returns 503 if the database is unreachable.

The failure mode of mixing them up: suppose your liveness probe checked the DB. A brief Neon blip would make every container report "dead". The orchestrator would kill and restart healthy app processes en masse, and the restart storm would amplify the outage. Yet the apps were fine; they just needed the DB to come back. Correct design: liveness must depend only on the process; readiness can depend on dependencies and is used to pull a pod out of the load-balancer rotation without killing it. The container HEALTHCHECK and Render's single health check (as render.yaml configures it) both probe /live for exactly this reason — a deliberate trade-off, since Render's own advice is a check that touches something critical, such as a simple database query. Be precise about the consequence. Nothing platform-level polls /health here (clients and local compose do). So a database outage neither restarts nor depools the instance: it keeps serving, and DB-bound requests fail until the database returns.

Q28Advanced"Pin the algorithm" — what are the alg:none and RS256/HS256 confusion attacks?›

A JWT's header declares the signing algorithm in an alg field — and the classic vulnerability is a verifier that trusts that field. Two attacks follow. (1) alg:none: the attacker sets "alg":"none" and strips the signature; a naive library reads "none," concludes the token is already verified, and accepts it. (2) RS256→HS256 confusion: the server expects asymmetric RS256 (verify with the public key). The attacker re-signs the token as HS256 (symmetric HMAC), using that public key as the HMAC secret. A library that picks the algorithm from the header then verifies it successfully, because the public key is, by definition, public. (RFC 8725, the JWT Best Current Practices, lists both attacks among its threats and requires libraries to let callers restrict the algorithms.)

The defense is to pin the algorithm at verification time — never let the token choose. CareKosh does exactly this. Its call jwt.decode(token, secret, algorithms=[settings.JWT_ALGORITHM]) passes an explicit allow-list of one (HS256). So a forged none or a swapped RS256 token is rejected before its claims are ever read app/core/security.py. Strong answer names both attacks and the one-line fix; weak answer just says "JWTs are signed so they're safe."

Q29AdvancedArgon2id vs bcrypt vs scrypt vs PBKDF2 — which, with what parameters, and what's bcrypt's gotcha?›

OWASP's Password Storage cheat sheet gives an explicit order of preference: Argon2id first, then scrypt, then bcrypt (acceptable for legacy), and PBKDF2 when FIPS-140 compliance forces it. The baseline Argon2id parameters are m=19456 (19 MiB memory), t=2 (iterations), p=1 (parallelism). The ranking is about memory-hardness: Argon2id and scrypt force an attacker to spend RAM per guess, which defeats the cheap massive parallelism of GPUs/ASICs; bcrypt is only CPU-hard. A fast general-purpose hash like SHA-256 is disqualified — its speed is exactly what lets an attacker try billions of guesses per second against a stolen dump.

The interview gotcha is bcrypt's 72-byte limit: most implementations silently truncate the password at 72 bytes, including the pinned bcrypt 4.2.1 (bcrypt 5.0 raises an error instead), and the original truncates at the first null byte. Teams that "fix" long passwords by pre-hashing with SHA-256 then feeding the digest to bcrypt can introduce a null-byte collision if they're not careful. CareKosh avoids all of this by defaulting to Argon2id: argon2-cffi defaults via passlib (t=3, m=64 MiB, p=4), no 72-byte cap and a self-describing PHC string. Bcrypt is kept only as a verify-only fallback, and re-hash-on-login is not implemented app/core/security.py. (Source: OWASP Password Storage cheat sheet.)

Q30IntermediateWhich HTTP methods are idempotent/safe, and what's the difference between "idempotent" and "double-apply-safe"?›

RFC 9110 (HTTP Semantics) calls a method idempotent when the intended effect on the server of several identical requests with that method is the same as the effect of one such request. So GET, HEAD, PUT, DELETE, OPTIONS and TRACE are idempotent; POST and PATCH are not. Safe methods (read-only, no intended state change) are GET, HEAD, OPTIONS, TRACE — and all safe methods are also idempotent.

Interviewers probe a senior distinction here. RFC 9110 idempotency means the server-side effect of N identical requests equals the effect of one, even if later responses differ; a repeated DELETE may return 404. Retry-transparency means a repeat returns the original result. CareKosh's POST /orders/{id}/apply is idempotent in effect. The guarded compare-and-swap (UPDATE … WHERE status = 'RECEIVED' RETURNING) lets exactly one call credit stock, and turns repeats into a side-effect-free 400 app/api/v1/orders.py. It is not retry-transparent: a client whose first response was lost gets 400 "Order must be in 'received' status" and cannot tell "already applied" from "never received". An idempotency key with stored-response replay (next question) closes that gap.

Q31AdvancedHow does HTTP's ETag/If-Match relate to the version column you use for optimistic concurrency?›

They are the same idea at two layers. So the family is: version column → ETag/If-Match (HTTP) → DynamoDB conditional writes → Kubernetes resourceVersion. All are optimistic concurrency control: no lock, carry a version, reject the stale writer (409/412) instead of overwriting. Q32StaffHow would you make POST /orders truly idempotent against client retries?›

The standard pattern is a client-supplied idempotency key (Stripe popularized it). The client generates a unique key per logical operation and sends it in an Idempotency-Key header. The first time the server sees a key, it processes the request and stores the key alongside the resulting status code and response body. On any retry with the same key, it returns the stored response without re-executing. So a network retry that already succeeded server-side can't create a second order.

Concretely for CareKosh: a small idempotency_keys table (key, user_id, request_fingerprint, response_status, response_body, created_at). Add a unique constraint on (user_id, key) to win the race atomically (insert-or-conflict), and replay the saved body on a hit. Two details interviewers reward. (1) Store and replay failures too (even a 500), so a retry is deterministic. (2) Compare the request fingerprint to the stored one, and reject (422) if the same key is reused with different parameters; that's misuse, not a retry. Note the relationship to delivery semantics: networks give you at-least-once; true exactly-once is a fiction unless the consumer is idempotent — the key is what makes the consumer idempotent. (Source: Stripe idempotency docs.)

Q33AdvancedCan you share one AsyncSession across asyncio.gather to parallelize queries?›

No — and it's a deliberate interview trap. An AsyncSession is a single, stateful, in-progress transaction on one connection, with no internal locking. As the SQLAlchemy 2.0 API reference for AsyncSession puts it, the session is "not safe for use in concurrent tasks". Fan out three queries with asyncio.gather(q1(db), q2(db), q3(db)) sharing the same db. Their I/O interleaves on one connection mid-statement, which corrupts session state and raises errors. The mnemonic is "Session per thread (sync), AsyncSession per task (async)."

To genuinely parallelize, give each task its own session from the sessionmaker (each checks out its own pooled connection). CareKosh never hits this, because every request gets one session from get_db and handlers await their queries one after another app/core/database.py. For a per-user CRUD workload, that is the right and simplest choice. The moment you reach for concurrent DB fan-out, you reach for a session per task. (Source: SQLAlchemy 2.0 asyncio docs.)

Process vs thread vs coroutine?Process = own memory + own GIL (true parallelism). Thread = shared memory, OS-scheduled, GIL-bound for Python bytecode. Coroutine = cooperative, single-thread, yields at await — concurrency without parallelism.
What is the GIL?The Global Interpreter Lock: in CPython (the Dockerfile's python:3.12 default build) only one thread executes Python bytecode at a time. C extensions can release it during pure-C work, and argon2-cffi does. That is why hashing in a worker thread runs in parallel with the event loop. The asyncpg driver doesn't need to: it gets concurrency from non-blocking sockets on the event loop.
HS256 vs RS256?HS256 = symmetric HMAC; one shared secret signs and verifies. RS256 = asymmetric; private key signs, public key verifies. CareKosh uses HS256 — fine for one backend, doesn't scale to untrusted verifiers.
What is a connection pool?A reusable set of open DB connections so you skip TCP+TLS+auth handshakes per query. Here: pool_size=5 + max_overflow=10 → at most 15 per worker process; with the Dockerfile's 2 Gunicorn workers that is up to 30 per container. app/core/database.py
selectin vs joined loading?selectin = one extra batched WHERE fk IN (...) per relationship (no row blow-up). joined = a LEFT JOIN — multiplies rows across collections (cartesian). CareKosh declares selectin on its relationships — and suppresses it with noload("*") where it isn't wanted.
What is N+1?One query loads N parents, then one lazy query per parent loads its children — 1+N round-trips. Fixed by eager batching (selectin) or a join.
expire_on_commit?When True, all attributes expire after commit and re-load on next access. Set False here so reads after a handler's own commit don't trigger forbidden async lazy I/O. app/core/database.py
OFFSET pagination vs keyset?OFFSET skips N rows (simple, but slow at deep pages and drifts under inserts). Keyset (cursor) filters WHERE id > :last — O(1)-ish, stable, but no random page jumps.
201 vs 200 vs 204?200 = OK with a body. 201 = Created (often with a Location header). 204 = No Content — success, empty body (e.g. a DELETE).
What is CORS preflight?A browser OPTIONS request sent before a "non-simple" cross-origin call, asking the server which methods/headers/origins are allowed. CORSMiddleware short-circuits it.
Behind a reverse proxy, which client address can you trust?The socket address is the proxy's. An address carried in a request header is trustworthy only if a proxy you have verified added it and clients cannot reach the app around that proxy; otherwise the client may have written it.
Salting vs peppering?A salt is a per-hash random value stored with the hash (in Argon2's PHC string). A pepper is a secret added to all hashes, stored outside the DB (e.g. in config).
Stateless vs stateful auth?Stateless = the token alone proves identity, with no server lookup. Stateful = the server keeps session state it can revoke. CareKosh is hybrid. Access JWTs are signature-checked, and then the user row is loaded on every request (is_active, session_version), so a password change or reset revokes them immediately. Refresh tokens are tracked by jti in the database. Plain logout revokes only the refresh row.
What is a race condition?Two concurrent operations interleave on shared state, and the outcome depends on timing. Examples: two refreshes claiming the same token, or two concurrent applies of the same order crediting stock twice.
Optimistic vs pessimistic locking?Optimistic = no lock held between read and write; check a version at write time, reject on mismatch (CareKosh's Item.version → 409). Pessimistic = SELECT ... FOR UPDATE locks the row up front (CareKosh does this on users in login, refresh and password flows).
What is a migration?A versioned schema change (an Alembic revision) applied in order. Reversibility is optional, not guaranteed: CareKosh's 0007 downgrade deliberately raises. Rolling back code never reverses a migration by itself, and an image older than the database's revision fails its own alembic upgrade head and does not start. The boot entrypoint runs alembic upgrade head (all pending revisions in one transaction under an advisory lock) and aborts if it fails. docker-entrypoint.sh:49-56
Liveness vs readiness?Liveness = "is the process alive?" → fail ⇒ restart (/live, no DB). Readiness = "can I serve?" → fail ⇒ stop routing traffic (/health, runs SELECT 1). In CareKosh, only /live is wired to a platform probe (Render healthCheckPath in render.yaml, and the Docker HEALTHCHECK). The /health endpoint is used by clients, such as the app's preflight check, and by docker-compose. So a DB blip neither restarts nor depools the instance. app/main.py
What is backpressure?Bounding work in flight so a slow downstream slows or sheds upstream load instead of queuing without limit. CareKosh has only a weak form. The setting pool_timeout=30 bounds how long a request waits for one of its worker's 15 connections. Waiting requests still pile up for up to 30 s, then fail as a generic 500. Real backpressure would add admission control (e.g. Uvicorn's limit_concurrency or a 503 + Retry-After shedding path) and a shorter pool timeout.
JWT vs session cookie?JWT = self-contained signed token, sent in a header, stateless, hard to revoke. Session cookie = opaque ID referencing server-side state, revocable, browser-managed, CSRF-prone.
What is CSRF? Does a Bearer-token API need CSRF protection?CSRF tricks a browser into sending its ambient credentials (cookies) cross-site. A Bearer-token API does not need CSRF defense — the token is attached explicitly by JS, never auto-sent by the browser. CareKosh uses Bearer, so it's exempt.
Why can't Allow-Origin: * be combined with credentials?The Fetch/CORS spec forbids it — a wildcard origin with Access-Control-Allow-Credentials: true is rejected by the browser, since returning * while allowing cookies/Authorization would let any site read authenticated responses. Use an explicit origin with credentials. (CareKosh's code enforces the invariant — wildcard ⇒ allow_credentials=False, explicit list ⇒ True — and the repo's production blueprint currently sets CORS_ORIGINS='["*"]', so production as configured there also runs wildcard/no-credentials (the live value is not verified). That is harmless for the Android app, because CORS is browser-only, and Bearer tokens are ordinary headers, not CORS credentials.)
Is a JWT encrypted?No. Header and payload are base64url-encoded, not encrypted — anyone can read the claims. The signature guarantees integrity, not confidentiality. Never put secrets in a JWT (use JWE if you must).
Rate-limiting algorithms?Fixed window (cheap, allows boundary bursts) · sliding window (smooths the boundary) · token bucket (bursts up to capacity, refills at a rate) · leaky bucket (constant drain). Here, slowapi uses fixed-window counters (its default), held in each worker process's memory. Two Gunicorn workers mean two sets of counters, reset on every restart. app/utils/rate_limiter.py
Read replicas & replication lag?Replicas scale read-heavy load but lag behind the primary, so a read-after-write may miss your own write. Fix "read-your-writes" by routing that read to the primary (or pinning briefly).
PgBouncer transaction pooling — what breaks?It reuses one server connection per transaction, which gives massive connection fan-in. But session state doesn't survive across transactions. That includes session-level SET, session-level advisory locks, LISTEN/NOTIFY, and server-side prepared statements unless PgBouncer's prepared-statement support is enabled. Transaction-scoped locks such as CareKosh's pg_advisory_xact_lock are fine. Disable asyncpg's statement cache via connect_args (CareKosh's DATABASE_URL validator strips URL query parameters) and note the statement_timeout startup parameter asyncpg sends: poolers that do not track it reject it. Neon's pooler is one, so a -pooler URL would make every CareKosh connection fail (use the direct URL or set the timeout another way).
The 40-thread sync ceiling?FastAPI/Starlette run sync def handlers and sync deps in AnyIO's worker-thread pool — default CapacityLimiter = 40 tokens per worker process, independent of the DB pool_size. Request 41 queues.
Two triggers of MissingGreenlet?(1) post-commit expired-attribute reload — fixed by expire_on_commit=False; (2) touching an unloaded relationship lazily — fixed by loading it explicitly: eager loading (selectin/joined), an awaited refresh/query, or AsyncAttrs.awaitable_attrs. Different causes, different fixes.
at-least-once vs exactly-once delivery?Networks/queues deliver at-least-once (retries duplicate). "Exactly-once" is a fiction unless the consumer is idempotent (dedupe on a key) — the receiver guarantees it, not the transport.
Thread pool vs process pool for CPU work?Default: process pool for CPU-bound (GIL blocks true thread parallelism), thread pool for blocking I/O. Exception: GIL-releasing C extensions (Argon2, numpy) run truly parallel in a thread pool — why hashing goes to a thread, not a process.

Part B — Brainstorming & open-ended design

Now the interviewer leans back and says "suppose we wanted to add X." There is no single right answer; they are watching how you decompose. The reliable opening move: restate the goal, name the dominant constraint, then sketch the change across the layers you already know — model, schema, service/transaction, and operational concern. CareKosh hands you several primitives to reach for. Below are six prompts with a 3–4 bullet approach each.

✅ Pro Tip

Open every design answer by anchoring to existing structure: "CareKosh already has X, so I'd extend it by…". Reusing local_id, version, the per-request session with one commit per write, and the AuditLog ledger signals you read the system instead of bolting on a greenfield design.

1. Add multi-tenant orgs to CareKosh

  • Decide the isolation model first — shared-DB + org_id discriminator column (cheapest, what I'd choose) vs schema-per-tenant vs DB-per-tenant. State the trade-off: row-level is simplest to operate but leans entirely on query scoping for isolation.
  • Add org_id to every tenant-scoped table and a composite index (org_id, ...). Today rows are scoped by user_id; the org becomes the new tenancy boundary above the user.
  • Enforce scoping centrally, not per-handler — derive current_org in a dependency. Then apply it to every ORM query automatically (e.g. a SQLAlchemy do_orm_execute hook with with_loader_criteria), so no endpoint has to remember WHERE org_id = :org. A dependency alone cannot add predicates to queries. Forgetting it on one endpoint is a cross-tenant data leak.
  • Defense-in-depth at the DB — Postgres Row-Level Security policies keyed on a session variable, so even a query that forgets the filter can't read another org's rows.

2. Add real-time low-stock alerts

  • Detect at the write boundary — stock changes in PATCH /items/{id}/stock, PUT /items/{id} and order apply. Each can compare the new quantity with minimum_stock (the apply UPDATE would add minimum_stock to its RETURNING list). Each can then emit an event when stock crosses below the threshold, inside the same transaction that changed it.
  • Don't push from the request thread — enqueue the alert: an outbox row committed atomically with the stock change, drained by a worker. Then a flaky notification provider never rolls back the inventory update. CareKosh already uses post-commit BackgroundTask for emails as a lighter version of this.
  • Choose the transport by latency need — WebSocket/SSE for a live dashboard, push notification or email for a phone. ASGI makes WebSockets first-class.
  • Debounce — suppress repeat alerts for an item already below threshold so a steady drain doesn't spam; track "last alerted at" per item.

3. Make it offline-first with conflict resolution

📝 Note

The schema has a head start. Categories, items, orders and activity logs already carry a nullable, indexed local_id (a client-generated UUID), and Item carries a version (app/models/item.py). The current app is server-first: it sends a localId only when creating an order (as a retry key, feature branch) and never for items or categories, so offline sync is design material, not a feature.

  • Identity mapping via local_id — the client creates rows offline with its own UUID; the API persists it as local_id and returns the canonical id so the client can reconcile. (Scaffolding only — there is no live /sync/upsert endpoint today; CI even rejects /sync routes. The order retry key from migration 0010 shows the shape a per-user unique index on (user_id, local_id) would take for other tables.)
  • Conflict detection via version — the optimistic-lock version is exactly the conflict signal. If the client's base version is stale, the server rejects (409) and the client must reconcile.
  • Pick a resolution policy — last-write-wins (simplest), server-wins, or field-level merge. For medical inventory I'd surface the conflict to the user rather than silently LWW, since stock counts are safety-critical.
  • Pull deltas with a watermark — clients pull changes since a server-assigned sequence. (Or use updated_at with an overlap window, because updated_at comes from the app clock at statement time, not commit order.) Add tombstones or soft deletes too. CareKosh hard-deletes items, categories and orders today, and no timestamp watermark can report a hard delete.

4. Add role-based access control (RBAC)

  • Extend, don't replace, the dep chain — deps.py already defines composable guards (CurrentUser, plus the currently unused VerifiedUser/SuperUser); RBAC generalizes that boolean ladder into roles/permissions.
  • Model it — roles table, permissions table, role_permissions join, and a user_roles assignment (org-scoped if combined with prompt 1).
  • Enforce declaratively — a require_permission("item:delete") dependency factory, so routes read Depends(require_permission(...)) and authz stays in the DI layer. To surface permissions in OpenAPI, use Security(...) with scopes (CareKosh publishes OpenAPI only when DEBUG is on).
  • Audit the grants — write role/permission changes into the existing AuditLog with JSONB before/after — privilege escalation is exactly what auditors check.

5. Export 10M-row reports without OOM

  • Never materialize the full result set — the failure mode is loading 10M ORM rows into memory. Stream instead.
  • Server-side cursor + chunked rows — use a streaming/server-side cursor and yield_per so the DB sends rows in batches; map each batch to CSV lines.
  • Stream the HTTP response — StreamingResponse over an async generator so bytes flow as they're produced; constant memory regardless of row count. On CareKosh's pinned FastAPI 0.115.6, the get_db session is already committed and closed before the body streams. Yield-dependency exit runs before the response is sent; FastAPI changed this in 0.118.0. So the generator must open and close its own session (async with AsyncSessionLocal()), and keep each fetch under the 8 s statement_timeout.
  • For very large or slow exports, go async-job — start a background job that writes to object storage (S3), and email a signed download link. Then a 10-minute export doesn't hold an HTTP connection or a pooled DB connection. (Recall that the 8s statement_timeout would kill a single giant query anyway.)

6. Add full-text search over items

  • Start in Postgres, not a new system — a tsvector column over name/brand/supplier_name with a GIN index handles ranked, stemmed search with zero new infrastructure.
  • Keep the index fresh — a generated column or a trigger updates the tsvector on write. For user-typed input, query with @@ websearch_to_tsquery(...) (or plainto_tsquery), because to_tsquery raises on free text. Rank with ts_rank.
  • Scope it to the tenant — combine the FTS predicate with the existing user_id/org_id filter so search never crosses tenancy.
  • Reach for Elasticsearch/OpenSearch only when you outgrow PG — typo-tolerance, faceting, cross-entity search, or huge scale. Name the cost: a second datastore to keep in sync (CDC/outbox), which is real operational weight.
🔬 Under the Hood

Notice the through-line in every prompt: the hard part is rarely the feature — it's the boundary. Multi-tenancy is a query-scoping boundary; alerts and exports are a "don't block / don't hold a connection" boundary; offline-sync is an identity-and-conflict boundary. Senior design answers spend their words on the boundary and its failure mode, not on the happy path. Interviewers are listening for one instinct. It is the same instinct that makes each CareKosh write handler commit its changes together in one explicit commit and cap statements at 8 s. It also points the platform health check at the DB-free /live, so a DB blip neither restarts nor depools the instance.

🛡️ Security / OWASP

Every "add a feature" answer should end with a one-line security rider. Multi-tenancy → Broken Access Control (A01) if scoping is forgotten. RBAC → audit the grants. Exports → don't leak other tenants' rows through a forgotten filter. Naming the OWASP risk unprompted is a strong staff-level tell.

🔬 Under the Hood

With the default expire_on_commit=True, commit() expires every loaded attribute, so the next plain attribute access must reload it. In sync code that is an implicit SELECT. Under asyncio the ORM cannot run implicit, un-awaited I/O and raises MissingGreenlet. Setting it to False keeps committed values readable. The alternatives are an explicit await session.refresh(obj), which the item, category and order handlers also call after commit (on the feature branch the auth handlers no longer do), or AsyncAttrs. Knowing this single line is the difference between "I copied a tutorial" and "I understand the async session lifecycle."

Second, the primitive that keeps Argon2 — deliberately slow, CPU-bound hashing — from freezing the entire event loop:

app/api/v1/auth.py — excerpt from register() (comment added)Python
import anyio

# Argon2 is CPU-bound; run it on a worker thread so the
# event loop stays free to serve other requests.
hashed_password=await anyio.to_thread.run_sync(hash_password, data.password),
⚠️ Pitfall

A common interview trap: candidates say "FastAPI is async, so it's fast" and then call a synchronous, CPU-bound function directly inside an async def handler. That blocks the single event-loop thread for the full duration of an Argon2 hash, and every concurrent request queues behind it. (Measure it; it depends on parameters and CPU — about 20 ms on a multi-core laptop here, measured 7 October 2026, never on the production instance.) The fix is exactly the line above. What the question really tests is whether you can explain why: one event-loop thread; AnyIO's own worker-thread pool, 40 threads by default; and a C hash that releases the GIL.

Runtime & concurrency

This cluster is about how Python serves a request without blocking. The single most important fact: the event loop runs on one thread. So CPU-bound work like Argon2 must be moved off it, or every concurrent request on that worker stalls behind it. A thread helps here because argon2-cffi releases the GIL while hashing.

TermOne-line definition
ASGIAsynchronous Server Gateway Interface — the async contract app(scope, receive, send) that lets a server stream requests into an async app; FastAPI is an ASGI callable.
WSGIASGI's synchronous predecessor (one request per worker thread, blocking) — Flask/Django-classic; cannot natively express await.
event loopThe single-threaded scheduler that runs coroutines, suspending each one at await so the thread can serve other requests during I/O waits.
coroutineCalling an async def function (a coroutine function) returns a coroutine object that can suspend at await and resume later, rather than running to completion in one go.
awaitSuspends the current coroutine until the awaitable completes; control returns to the event loop only if it actually has to wait — the suspension point that makes single-threaded concurrency possible.
GILCPython's Global Interpreter Lock — only one thread executes Python bytecode at a time, so threads help I/O concurrency but not CPU parallelism.
UvicornThe ASGI server that parses HTTP into a scope and calls the app on the event loop; runs app.main:app.
GunicornA production process manager that forks multiple UvicornWorker processes for parallelism, restarts crashed ones, reloads on SIGHUP and shuts down gracefully on SIGTERM. (Uvicorn 0.34 deprecates uvicorn.workers in favour of the uvicorn-worker package.)
workerOne OS process serving requests; N workers sidestep the GIL by giving you N independent interpreters (and N copies of in-memory state).
middlewareA layer wrapping the app like an onion. Because add_middleware prepends, the last registered runs outermost. They are registered CORS → request-id → security headers → (feature branch) AIBodyLimit, so they run inbound as AIBodyLimit → security headers → request-id → CORS → router, all inside Starlette's ServerErrorMiddleware.
🔬 Under the Hood

VitalTrack threads Argon2 off the loop with anyio.to_thread.run_sync because hashing is CPU-bound and has no await point. Run inline, it would freeze the event-loop thread and stall every other in-flight request for the full hash time. Measure it on the target instance; the audit measured a median of about 22 ms on an 18-core arm64 laptop (7 October 2026; not the production instance). The thread gives real parallelism only because argon2-cffi releases the GIL. See app/api/v1/auth.py.

Auth, tokens & hashing

TermOne-line definition
JWTJSON Web Token — a signed credential (header.payload.signature) whose signature and expiry can be verified without a DB lookup; CareKosh still loads the user on every request (see access token).
JWS vs JWECareKosh tokens are JWS (signed with HS256), not JWE (encrypted). Anyone holding one can read its claims.
claimA key/value statement inside a JWT payload; VitalTrack issues sub, exp, iat, a custom type, a custom session_version (both tokens) and jti (refresh tokens only) (app/core/security.py).
session_versionA per-user generation number carried in every token. Password change or reset increments it, so all older access and refresh tokens fail on their next use.
jtiJWT ID — a unique token identifier; refresh tokens store it (unique=True) so a specific token can be revoked or rotated.
HS256 / HMACSymmetric signing: HMAC-SHA256 with a shared secret. Fast, but verifier and signer share the same key (vs. asymmetric RS256).
access tokenShort-lived JWT (type=access, 30 minutes) sent on every authenticated request. Signature and expiry are checked without the database. But CareKosh's get_current_user still loads the user row every time, to check is_active, the email-verification policy and session_version. So a password change or reset revokes old access tokens immediately.
refresh tokenLonger-lived token (type=refresh) used only to mint new access tokens; stored server-side by jti so it can be revoked.
token rotationEach refresh atomically revokes the presented token and issues a new pair, so a single refresh token can be redeemed only once, even under a race (app/api/v1/auth.py). There is no reuse detection: if an attacker redeems a stolen token first, their new token keeps working and the legitimate client just gets 401. RFC 9700 (an OAuth authorization-server BCP, applicable by analogy) recommends revoking the active token when a rotated one is replayed; here, only a password change or reset (a session_version bump) ends every session.
Argon2The memory-hard, GPU-resistant password hash (Argon2id) and VitalTrack's preferred scheme — RFC 9106, OWASP-recommended.
bcryptAn older adaptive hash kept as a fallback scheme so legacy bcrypt hashes still verify. CareKosh does not upgrade them today: no code calls pwd_context.verify_and_update() or needs_update(), so a bcrypt hash stays bcrypt after login.
saltPer-password random bytes mixed into the hash so identical passwords produce different digests, defeating rainbow tables (Argon2 embeds it).
hashingOne-way transformation of a password into a verifiable digest; deliberately slow for passwords (the opposite goal of a fast hash).
app/core/security.py (excerpt; comments added)Python
pwd_context = CryptContext(
    schemes=["argon2", "bcrypt"],
    deprecated="auto",
)

def hash_password(password: str) -> str:
    return pwd_context.hash(password)          # first scheme = argon2

def verify_password(plain_password: str, hashed_password: str) -> bool:
    return pwd_context.verify(plain_password, hashed_password)  # argon2 OR legacy bcrypt

The deprecated="auto" flag marks any hash not made with the first scheme as needing an update. An app can use this to re-hash with Argon2 after a successful login (pwd_context.verify_and_update()) — algorithm agility without a forced password reset. CareKosh does not do this yet.

🛡️ Security / OWASP

Per the OWASP Password Storage Cheat Sheet, the modern answer to "how do you store passwords?" is Argon2id. OWASP's minimum is 19 MiB of memory, t=2, p=1, with bcrypt only for legacy systems. CareKosh's stored hashes show the settings actually used — argon2-cffi's defaults, e.g. the prefix $argon2id$v=19$m=65536,t=3,p=4$. Quoting the exact scheme list at app/core/security.py and the threaded-off-the-loop hashing turns a textbook answer into a code-grounded one.

SQLAlchemy & the session

TermOne-line definition
SQLAlchemyThe Python ORM + Core toolkit; VitalTrack uses 2.0-style typed mapping (Mapped[...] / mapped_column) over async asyncpg.
ORMObject-Relational Mapper — maps rows to Python objects and tracks their changes, so you write objects instead of raw SQL.
sessionThe per-request workspace holding loaded objects and pending changes; one is opened and yielded per request, write handlers commit it explicitly, and get_db always closes it.
unit of workThe pattern where changes are tracked and flushed in one atomic commit. In CareKosh each write handler stages its changes and commits them once; get_db scopes the session and rolls back uncommitted work on error.
identity mapThe session guarantee that one row maps to exactly one Python object within that session, so reads are consistent and de-duplicated.
connection poolA reused set of open DB connections. VitalTrack runs pool_size=5 + max_overflow=10 → up to 15 connections per worker process (config.py defaults, overridable by env). With the Dockerfile's 2 Gunicorn workers, that is up to 30 per container (app/core/database.py).
pool_pre_pingA liveness check on checkout (with asyncpg: BEGIN, an empty statement, ROLLBACK) that discards connections silently killed by an idle timeout or proxy, avoiding closed-connection errors.
statement_timeoutA Postgres-side 8s per-statement cap (server_settings) so one runaway query can't pin a pooled connection and cascade into pool exhaustion.
expire_on_commitSet to False so already-loaded attributes stay readable after commit. In async code an implicit post-commit reload raises MissingGreenlet; an explicit await session.refresh() is fine.
lazy / eager loadingLazy fetches a relationship on first access (risking N+1); eager pre-fetches it with the parent query.
selectinAn eager strategy issuing one extra query WHERE fk IN (...) to batch-load children — the canonical N+1 fix, and async-safe (app/models/user.py). On User it would load the whole graph, so CareKosh suppresses it with noload("*").
N+1The anti-pattern of 1 query for parents + N queries for each parent's children; selectin collapses it to 1+1.
⚠️ Pitfall

Forgetting expire_on_commit=False in an async app is a classic production bug. Everything passes in tests that don't read attributes after a commit. Then real requests raise greenlet_spawn has not been called, because code (a handler, or Pydantic) touches an expired attribute and triggers implicit lazy I/O. See app/core/database.py.

Transactions, concurrency & the database

TermOne-line definition
transactionA group of statements that commit all-or-nothing; in VitalTrack each write handler's explicit commit is the boundary — the audit row and the mutation commit together.
isolation levelPostgreSQL defaults to READ COMMITTED. A blocked UPDATE re-evaluates its WHERE clause against the committed row, which is what makes UPDATE … WHERE … RETURNING a safe compare-and-set.
advisory lockpg_advisory_xact_lock(key): a transaction-scoped application lock. CareKosh uses it to serialize duplicate-name checks per owner (app/services/inventory_lock.py), concurrent migration runners (alembic/env.py) and, on the feature branch, every AI quota reservation under one global key (app/services/ai_guard.py).
ACIDAtomicity, Consistency, Isolation, Durability — the guarantees a relational transaction provides.
optimistic concurrencyAssume no conflict; the client sends the version it read and the server rejects on mismatch (409) — VitalTrack's app-managed locking (app/models/item.py).
versionAn integer column bumped on each update; the comparison token that detects a lost update without locking the row.
pessimistic lockLock the row up front (SELECT ... FOR UPDATE) so other writers and lockers wait (plain reads are not blocked) — safer under heavy contention, costlier in throughput. CareKosh locks the user row this way in login, refresh and password flows.
compare-and-setAtomic "update only if unchanged"; refresh rotation uses UPDATE ... WHERE not revoked RETURNING so a token is single-use even under a race.
foreign keyA column referencing another table's PK, enforcing referential integrity; all child FKs here use ondelete="CASCADE".
CASCADEDeleting a parent deletes its children. DB-level ondelete="CASCADE" applies to any DELETE that reaches PostgreSQL. ORM-level cascade="all" (which includes "delete") applies to session.delete() of a parent, for the collections the session has loaded; "delete-orphan" additionally deletes a child removed from its parent's collection.
indexA lookup structure (default B-tree) speeding reads on a column at a small write cost; VitalTrack indexes FKs, local_id and the stored token digests. A partial index covers only rows matching a predicate: the feature branch's uq_orders_user_id_local_id is unique on (user_id, local_id) only WHERE local_id IS NOT NULL.
JSONBPostgres binary JSON — parsed once, GIN-indexable, queryable (@>, ->>); used for audit before/after snapshots (app/models/audit_log.py).
denormalizationDuplicating data on purpose; OrderItem stores the item fields the client sent at order time, so order history survives the item being renamed or deleted.
snapshotA point-in-time copy of data stored as a historical record (the order line) rather than a live reference to the source row. In CareKosh the values are client-supplied; the server checks only item ownership.
💡 Interview Insight

"You already have ondelete=CASCADE in the DB — why also cascade in the ORM?" is a trap. The crisp answer: they cover different deletion paths. The ORM delete cascade only fires for objects deleted through the session, and only for collections it has loaded. The DB cascade covers deletes that bypass the ORM (raw SQL, bulk delete, admin tooling). CareKosh's account deletion loads the user with noload("*"), so the DB cascade does that work. (passive_deletes=True only skips collections that are not yet loaded, so it would not stop the per-item deletes in category deletion, where selectin has already loaded the items.)

That is why CareKosh's render.yaml points Render's single health check at /live.

Reading the "Auth required?" column

There is no auth middleware. A route requires authentication if and only if its handler signature includes the CurrentUser dependency alias: Annotated[User, Depends(get_current_user)] app/api/deps.py. That dependency extracts the bearer token, decodes the access JWT and loads the user with noload("*"). It returns 401 if the user is missing or the token's session_version is stale, 403 if the account is disabled, and 403 EMAIL_NOT_VERIFIED when the verification policy is on. Routes without it are public by construction. The email-link routes (verify-email, reset-password, confirm-delete) are intentionally public because the high-entropy token from the email is the credential. The one exception to the "if and only if" is the feature branch's /ai/* group: those routes authenticate through their own Principal dependency (which calls the same get_current_user), and the AIBodyLimit middleware already refuses them with 401 when no Bearer header is present.

💡 Interview Insight

The asterisks mark routes that don't use the CurrentUser dependency, yet are not open to anonymous abuse. They authenticate with a secret carried in the body or URL rather than an access-token header. The /refresh route takes a signed refresh JWT. The verify-email, reset-password and /confirm-delete routes take the raw token from the email link, and the server stores only its SHA-256 digest. An interviewer asking "which of your endpoints are unauthenticated?" wants to hear that nuance. "Public to the access-token dependency" is not the same as "requires no proof of identity". The credential just lives somewhere other than the Authorization header.

The route count is a contract, not a coincidence

Add up the versioned routes and you get exactly 44 route objects under /api/v1 on the feature branch: 18 auth + 6 categories + 8 items + 6 orders + 1 activities + 5 AI (39 on main, which has no AI routes). That number is enforced — but only as a number. A standalone gate script counts every registered route whose path starts with /api/v1 and fails the CI job if the total differs from the expected 44 (it passed locally on 7 and 8 October 2026). It also fails if a health route is mounted under the versioned prefix or a legacy /sync route comes back. It does not look at methods, paths, auth dependencies, rate limits or response shapes.

✅ Pro Tip

This is a cheap, useful pattern worth mentioning in an interview. A "route inventory" assertion catches a router that fails to register, a duplicate decorator, or an /api/v1 route added or removed without updating the expected count. The diff that changes the count forces a human to update the expected number and so to acknowledge that the API surface changed. It does not catch a renamed or swapped route, a removed auth dependency, a changed rate limit, or a debug route mounted outside /api/v1; those need route-level tests.

🛡️ Security / OWASP

An enumerated, count-pinned endpoint catalog is a partial control against OWASP API9:2023 — Improper Inventory Management. Undocumented or forgotten endpoints (a stale debug route, a deprecated /sync handler) are a classic breach vector. Here the route count is asserted in CI, and the legacy /sync routes are explicitly forbidden from returning. The interactive docs at /docs are gated behind DEBUG app/main.py, which defaults to false; render.yaml does not set it. So production does not advertise its schema unless DEBUG is turned on.

One last cross-check on totals: the gate counts 44 because health and root are mounted on the bare app object, outside the versioned router. Including those three operational routes, the feature branch serves 47 routes (and, since each route object has exactly one method, 47 method-and-path operations) with DEBUG=false — 44 product API routes plus /, /health and /live. This was counted from app.routes on 7 October 2026 and again from the registered app on 8 October 2026; on main the totals are 39 and 42. DEBUG=true adds four documentation routes: /docs, /docs/oauth2-redirect, /redoc and /openapi.json. Keep the distinction crisp: the count gate guards the 44; Render probes /live (as render.yaml configures it); clients and Docker Compose probe /health.
