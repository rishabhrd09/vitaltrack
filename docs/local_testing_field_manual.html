The dev loop you use every day is a stack of abstractions. Each abstraction is a tiny miracle. Each one hides something useful. When the miracle stops working, you need to see what it hid.

Most React Native developers learn the dev loop the same way they learn to drive a car: as a sequence of motions that produce a desired outcome. Plug in phone. Run a magic command. Chapter 02

The fundamental problem

React Native combines a JavaScript runtime with native Android UI. Its installed Android app is still an APK. The hybrid shape dictates everything that follows — the existence of Expo Go, the role of Metro, the need for ADB. Understand the hybrid, and the rest is consequence.

CareKosh is a React Native app. To explain why our development setup looks the way it does, we have to explain what a React Native app actually is. The answer is more interesting than the marketing suggests. A React Native app is two halves welded together at runtime, and the welding is the source of nearly every confusion in this book.

02.01 Two halves, welded at runtime

The first half is native Android UI. React Native core components use platform view implementations: text, editable text, scrolling and view groups. This is not a one-to-one widget mapping: Fabric may flatten layout-only views, and nested text can share a text implementation. CareKosh uses TouchableOpacity/Pressable for buttons; its main screens are not rendered by a browser. Native rendering does not guarantee instant input or smooth frames: JavaScript, rendering and native work can still block.

The second half is JavaScript. Your component tree, state management, business rules and API calls are all written in TypeScript and JSX. They all run inside a JavaScript engine that's bundled into the app process. Hermes, in our case — a small, fast VM Facebook built specifically for React Native.

How do the two halves talk? CareKosh runs React Native 0.81 with the New Architecture, which is on by default in Expo SDK 54 and is the only mode Expo Go supports. There, the halves talk through JSI (JavaScript Interface): JavaScript holds references to C++ objects and calls them directly, without serialising messages. The New Architecture replaces the legacy bridge path for core rendering and modules with JSI/Fabric/TurboModules. React Native 0.81 still supports legacy compatibility paths; SDK 54 can use the old architecture in a custom build, while Expo Go requires the new one. Direct interoperability does not make every operation synchronous. See React Native architecture and Expo architecture compatibility.

02.02 The two halves must coexist on the phone

A complete React Native app therefore has two parts that need to coexist on the phone at the same time:

  1. The native shell — an APK that provides UI primitives, navigation, camera, file access, network stack, and the JavaScript engine itself.
  2. The JavaScript bundle — the bundled reachable JavaScript modules containing the component tree and app logic. Development serves JavaScript; release builds normally compile it to Hermes bytecode. Size depends on build mode and dependencies; no current 10 MB measurement is recorded.

How these two parts get onto the phone is where production and development diverge — sharply.

02.03 How production ships this

For the Play Store, both halves are baked into one binary. EAS (Expo's cloud build service) does the work, in two separate commands. CI's production build job is disabled, so this is a manual flow:

# Release flow (details: EXPO_AND_PLAY_STORE_GUIDE.md)
eas build --profile production --platform android
  ↓
EAS cloud bundles the JS, packages it with the native shell,
signs it → AAB stored on EAS
eas submit --profile production --platform android
  ↓
uploads that AAB to the Play Console internal track (eas.json)

A production build takes a while; queue and build times vary. Google Play then generates optimised APKs from the AAB for each device; users install those, never the AAB itself. Both halves of the app are already inside, fused, and the app just runs. Beautiful for shipping. Disastrous for iteration.

02.04 Why we don't do that for development

Imagine making a one-line change to a TypeScript file and waiting fifteen minutes for a fresh APK build. Multiply by hundreds of edits per day. Multiply by the number of times you'll get the change wrong on the first try. The math is fatal.

So for development, we use a clever trick: a fixed, pre-built native shell that knows how to fetch any compatible JavaScript bundle from a server. The shell never changes. Only your JS bundle changes. The iteration loop becomes:

Edit a .tsx file → save in the editor
        ↓ (< 1 second)
Metro re-bundles incrementally
        ↓ (< 1 second)
Expo Go fetches the patch over your USB cable or Wi-Fi
        ↓
Hermes hot-reloads the affected modules
        ↓
You see the change — round trip in seconds, not minutes.

That fixed shell is Expo Go — an APK you install once per Expo SDK version. For this project that means the SDK 54 build from expo.dev/go; the Play Store build supports only the newest SDK. The server is Metro — a Node.js process you run on your laptop. Your JS bundle is the only thing that changes between edits. This is the entire reason this whole setup exists.

The thesis of the dev loop

Production fuses the native shell and the JS bundle into one APK. Development separates them — fixed shell on the phone (Expo Go), JS bundle served fresh from your laptop (Metro). Everything else in this manual follows from that. It explains how the bundle gets from your laptop to the phone, how the phone reaches the right backend, and how the cable and the network divide the work.

02.05 The trade-off this creates

Splitting the shell from the bundle is wonderful for iteration speed but it does cost something: you can only use native modules that Expo Go's shell already contains. Suppose your code imports a library that depends on its own native code (Swift, Kotlin, C++). An example is burnt, which shows native toasts (SPIndicator/AlertKit on iOS, ToastAndroid on Android) and does not work in Expo Go. Expo Go will not contain that library's native implementation; importing or calling its native APIs can fail unless the library guards for availability.

That is why CareKosh's everyday screens use only libraries that are pure JavaScript, or whose native code already ships in Expo Go for SDK 54. Examples of the latter are Expo SDK modules such as expo-secure-store, expo-print and expo-audio, react-native-reanimated and react-native-gesture-handler, among others. For example, it uses react-native-toast-message instead of burnt. The "must work in Expo Go" constraint keeps the development loop fast, at the cost of occasionally picking the second-best library.

03.01 Metro — the JavaScript packager

Metro is a JavaScript bundler in the same family as Webpack or Vite, but purpose-built for React Native. It knows about .tsx and .jsx files, knows React Native's resolver rules (which platform-specific file to pick, e.g. Foo.android.tsx versus Foo.ios.tsx), and knows how to serve incremental hot-reload patches.

When you run npm run start:staging -- --localhost, the npm script executes cross-env EXPO_PUBLIC_API_URL=https://… expo start --clear, which boots Metro. From that moment, Metro:

  1. Starts an HTTP server on port 8081 — or the next free port if 8081 is busy; always use the port it prints.
  2. Prints a QR code to the terminal pointing at itself.
  3. Watches the filesystem for changes.
  4. Builds the development bundle when requested. Cold build time varies. It follows the import graph from the configured entry point (Expo Router also discovers route modules), resolves reachable project and dependency modules, and transforms TypeScript/JSX into JavaScript. It does not bundle every file in node_modules, and transpilation is not TypeScript type checking; run tsc --noEmit separately.
  5. On every save, recomputes which modules changed and pushes an update over a WebSocket to whoever is listening (Expo Go, in our case).

Metro never runs your app. It just packages it. When you press Save in VS Code, Metro recomputes the changed modules. When Expo Go asks for the bundle, Metro hands it over. After that, Metro mostly waits for the next file change. But in development the app still depends on it. Images loaded with require() are served by Metro on demand, Fast Refresh uses Metro's WebSocket, and every reload fetches a new bundle. Keep Metro and its connection up while you work.

Local-only by design

Metro is a development tool. It never ships to production. Your Render-hosted backend has nothing to do with Metro and never talks to it. If your phone can reach the backend but can't reach Metro, the problem is between the phone and your laptop — not between the phone and the cloud.

03.02 Expo Go — the generic native shell

Expo Go is a regular Android app. Each Expo Go build supports exactly one Expo SDK version, so you install the build that matches the project: for CareKosh (Expo SDK 54), the SDK 54 build from expo.dev/go. The Play Store build tracks the newest SDK and cannot open this project. Inside that APK, three things sit waiting:

  • The native shell that React Native needs. The React Native runtime (JSI and the Fabric renderer) and the fixed set of native modules included in that Expo Go build — camera, file system, secure storage, gestures, async storage, the lot.
  • A JavaScript engine. Hermes — a small VM Facebook built specifically for React Native. Smaller and faster to start than V8.
  • A bundle loader. A piece of code that knows how to take a Metro URL, fetch the bundle, hand it to Hermes, and start the root component the bundle registers.

When you point Expo Go at exp://127.0.0.1:8081 — what Expo CLI prints and puts in the QR code when you start with --localhost — the loader does the following:

1. Parse the exp:// URL → host=127.0.0.1, port=8081
2. GET the project manifest from http://127.0.0.1:8081, then the launch
   bundle it names: /node_modules/expo-router/entry.bundle?platform=android&dev=true&…
3. Receive the development JS bundle over the connection
4. Pass the bundle string into Hermes
5. Hermes parses + executes
6. The bundle registers the root component: AppRegistry.registerComponent('main', …)
7. Expo Go's native shell sees the registration, mounts your App
8. React, through the Fabric renderer, turns the component tree into native Android views
9. Splash screen disappears, your app's first screen appears

Expo Go is a generic shell. It can load any Expo-compatible JS bundle built for the same SDK version — CareKosh, a different app, a tutorial demo. They all work because the native APIs they call (camera, file system, etc.) are already present in Expo Go's shell.

The cost of generality

Expo Go's shell is fixed. You cannot add new native dependencies at runtime. If a library requires native code absent from Expo Go, an unguarded import or native API call can fail. This is why CareKosh's everyday screens use only native code Expo Go already contains, and why commit 4e2a31f picked react-native-toast-message instead of burnt for the toast UI. The one exception, the October 2026 voice module, is loaded as optional, so Expo Go runs the app without it (§02.05).

Chapter 04

The three connection modes

Once Metro is running on your laptop and Expo Go is installed on your phone, the question becomes: how does Expo Go reach Metro? Three answers exist. Each has sharp trade-offs. Picking the right one is half the battle.

The bundle has to get from the laptop to the phone somehow. The internet connection between them — over Wi-Fi, USB, or a public tunnel — determines almost everything else about your dev experience. The decision tree below tells you which mode to pick first; the rest of this chapter explains why.

CH 04 · The three connection modes Local Testing · Field Manual 17

04.01 LAN mode — over Wi-Fi

The default for plain npx expo start. Both devices sit on the same Wi-Fi network. The phone reaches the laptop using the laptop's LAN IP — typically something like 192.168.1.5:8081.

For LAN plus a local Docker backend, run npm start with vitaltrack-mobile/.env set to EXPO_PUBLIC_API_URL=http://<your LAN IP>:8000. The repository-root setup-local-dev.sh (macOS/Linux) or setup-local-dev.bat (Windows) writes that file for you, but only if it doesn't exist yet, using the IP detected at that moment. If your laptop's IP changes, edit the file and restart Metro. (Plain npm start has no cross-env URL, so it relies on .env, and falls back to http://localhost:8000 without one.)

The QR code in your terminal encodes exp://192.168.1.5:8081 with whatever your actual LAN IP is. Expo Go scans the code, fetches the bundle directly over Wi-Fi. When this works, it's beautiful — no cable, no fuss.

When LAN fails — and it fails more often than you'd expect — it's almost always one of three reasons:

  • The Wi-Fi access point has client isolation enabled (devices on the same network can't see each other). This is common on guest networks, university Wi-Fi, hotel Wi-Fi, and corporate guest networks.
  • The laptop and phone are on different subnets — wired desktop on 192.168.0.x, phone on a separate guest network 192.168.10.x. Same physical building, different logical networks.
  • The laptop's firewall (Windows Defender on first run, especially) is blocking inbound TCP on port 8081 — or on 8000, for a local backend. The repository's fix-firewall.ps1 (PowerShell, run as Administrator) adds an inbound rule for TCP 8000 only, on both the Private and Public network profiles, so the port is also open on café or hotel Wi-Fi. It does not open Metro's 8081, and it has no undo script. When you no longer need the rule, run Remove-NetFirewallRule -DisplayName "VitalTrack-Backend-8000" in an Administrator PowerShell.

04.02 USB mode — adb reverse

The phone is plugged into the laptop with a USB data cable. The adb reverse command sets up a TCP tunnel: it makes adbd open a listening socket on the phone's localhost:8081. When anything on the phone connects to that port, adbd accepts the connection and relays it over the adb connection to the laptop's localhost:8081, where Metro is listening. Nothing is intercepted; adbd simply is the listener.

The same trick can forward the API port: adb reverse tcp:8000 tcp:8000 lets the phone hit http://localhost:8000 and reach the local Docker FastAPI backend running on the laptop.

USB mode is the most reliable mode. It doesn't depend on Wi-Fi state, doesn't depend on the network at all (for Metro traffic), usually avoids LAN inbound-firewall issues; USB drivers, debugging policy, occupied ports and host security software can still block it. The trade-off is small: the phone is tethered to the laptop. Fine at a desk; awkward when you want to walk around showing the app to someone.

04.03 Tunnel mode — public URL

Sometimes LAN won't work and USB isn't an option: a colleague wants to test on their phone, or you're presenting a demo from across the room. Then Tunnel mode is another fallback when both ends can reach its service.

Run npm run start:staging -- --tunnel. This keeps the staging API URL; plain npx expo start --tunnel would fall back to .env or http://localhost:8000. Expo installs the ngrok client (@expo/ngrok) if needed and prints a public URL like exp://<random>-<user>-8081.exp.direct. Your laptop's Metro server is now reachable over the public internet through this URL. Only Metro is tunnelled; API calls still go wherever EXPO_PUBLIC_API_URL points.

Trade-offs to know about:

  • Slower. Every byte of the JS bundle now travels phone → exp.direct → your laptop and back. The first bundle load takes noticeably longer than LAN or USB. Hot reloads also have higher latency.
  • Both sides need internet. If your laptop is offline, tunnel mode can't work even though both phone and laptop can otherwise see each other.
  • Doesn't help your local Docker backend. The phone can hit Metro over the tunnel, but EXPO_PUBLIC_API_URL=http://localhost:8000 won't work because the phone's localhost is no longer connected to your laptop. In tunnel mode, use staging instead: npm run start:staging -- --tunnel. Do not use production for development work.

05.01 Phase 1, narrated

You sit down at your laptop. Your phone is charged but not connected. CareKosh source is checked out at ~/code/vitaltrack/vitaltrack-mobile. Terminal is open in that directory.

  1. Plug in the USB data cable. Establishes the physical channel between phone and laptop. Make sure it's a data cable, not charge-only — many bundled USB-C cables don't carry data.

  3. adb devices in Terminal. Phone shows up with status device. If it shows unauthorized, you missed the dialog or the trust didn't store; re-plug.

  5. npm run start:staging -- --localhost. The npm script runs cross-env EXPO_PUBLIC_API_URL=https://… expo start --clear. 05.02 Phase 2, narrated

From the QR scan to the dashboard: duration varies with bundle size, cache, transport, authentication and backend availability.

  1. Expo Go parses the URL exp://127.0.0.1:8081 and opens an HTTP connection to that address, first for the project manifest and then for the launch bundle the manifest names.
  2. The connection reaches adbd, which has been listening on the phone's port 8081 since step 4.
  3. The connection is tunneled over the USB cable, through the adb server on the laptop, to the laptop's own localhost:8081 — where Metro is listening.
  4. Metro receives an HTTP request like GET /node_modules/expo-router/entry.bundle?platform=android&dev=true&hot=false&lazy=true… (named after package.json main). On the first request Metro builds the bundle; later requests reuse its cached transforms.
  5. The JavaScript bundle travels back through the same tunnel: laptop's Metro → laptop's adb server → USB cable → phone's adbd → Expo Go's HTTP client.
  6. Expo Go feeds the bundle to Hermes. Hermes parses and executes it. The bundle registers the root component (AppRegistry.registerComponent('main', …)).
  7. Expo Go's native shell mounts your App component. React, through the Fabric renderer, builds the native view tree. Splash screen disappears. Your auth screen or dashboard appears.

05.03 Phase 3, narrated

The app is running. Now it needs data from the backend. With a staging or production API, this is where the USB cable becomes irrelevant. (With a local backend behind adb reverse tcp:8000 tcp:8000, these calls ride the cable too.)

  1. The app calls fetch() with the API URL Metro injected into the bundle — https://staging-api.carekosh.com/api/v1/auth/me with a JWT in the Authorization header.
  2. The native fetch implementation issues an HTTPS request — not over the USB cable. Over the phone's own internet connection, whichever it is (Wi-Fi or LTE).
  3. DNS resolves the hostname to the API's edge (Render, or a CDN in front of it). TLS handshake. The encrypted request travels over the public internet.
  4. The hosting edge routes the request to the staging FastAPI service. (The live staging setup is managed in the Render dashboard; render.yaml declares only production.) FastAPI verifies the JWT, loads the user, queries PostgreSQL (intended: Neon) and returns JSON.
  5. The response travels back: Render → public internet → phone's Wi-Fi/LTE → the fetch promise resolves. This /auth/me response updates the Zustand auth store. Subsequent inventory/order queries populate TanStack Query; subscribed components render those results.

05.04 Phase 4, narrated

You spot a typo. You fix it in VS Code and press Save. The fix appears in the running app within a couple of seconds, without restarting.

  1. You save the .tsx file in VS Code.
  2. Metro's filesystem watcher detects the change.
  3. Metro recomputes which parts of the bundle changed (incremental rebuild — typically under one second).
  4. Metro pushes a "hot update" message to Expo Go via WebSocket on the same port 8081. (Same tunnel as the bundle load — adb reverse handles WebSocket too.) The development update client applies changed modules in Hermes; Fast Refresh coordinates the React update. React re-renders affected components. You see your change.
The single most useful sentence in this book

The USB cable carries steps 8–11 (initial bundle load) and step 21 (hot reload). With a staging or production API, the internet carries steps 15–18 (API calls). With a local backend reached through adb reverse tcp:8000, the cable carries those calls too. In development the app also loads assets from Metro and needs Metro for every reload, so keep the connection up while you work.

06.03 Step 3 — Set up the USB tunnel

adb reverse tcp:8081 tcp:8081

Why: This is the core trick of USB mode, and probably the single command in this book most worth understanding. Read carefully — the syntax is asymmetric.

The two arguments are tcp:<phone-side-port> tcp:<laptop-side-port>. Read the command aloud as: "adbd, listen on TCP port 8081 on the phone, and relay every connection you accept there to TCP port 8081 on the laptop". The opposite direction is adb forward tcp:X tcp:Y, which relays a laptop port to a phone port; Metro does not need it.

You can verify the rule exists at any time:

adb reverse --list

# Output (the first column varies by device):
(reverse) tcp:8081 tcp:8081
adb reverse is not sticky

In practice the rule is lost when any of these happen (Android's documentation does not describe its lifetime): phone unplugged, phone rebooted, laptop rebooted, adb kill-server run, USB cable physically jiggled hard enough to disconnect briefly. If you pressed a in Expo CLI, it set the Metro-port rule itself and removes it when it exits. After any of those, re-run the command. Symptom: Expo Go suddenly hangs while loading from 127.0.0.1:8081 when it was working a minute ago — you've lost the tunnel.

If you also want the phone to reach a local Docker backend on your laptop, add a second tunnel for the API port:

adb reverse tcp:8000 tcp:8000

Why: Same trick, different port. Now localhost:8000 on the phone reaches the FastAPI backend running in Docker on the laptop. Skip this if you're hitting staging (or, for a brief read-only check, production) — those are real public URLs reached over the phone's own Wi-Fi/LTE, not over USB.

06.06 Step 6 — Verify it actually works

Loading the bundle proves Metro reached you. Cached screens do not prove the backend is reachable. The app restores its last query cache (if saved within the last 24 hours) and its session from device storage. It does this even when the current backend is unreachable, or is a different backend. To prove the backend path:

  1. On the phone, open <API URL>/health in the browser (for a local backend, after adb reverse tcp:8000 tcp:8000). Expect status "healthy" and database "connected".
  2. In the app, pull to refresh Inventory or Orders, or save a small throwaway change through the Edit Item form (there is no stock +/- control; quantities are edited in that form). Confirm it succeeds and appears in the backend logs. The profile menu (top-bar avatar) → Help & Support → "Refresh from server" refetches only items and categories, not orders or activity.

When you switch backends, log out and back in: login and logout both clear the query cache, in memory and on disk.

If instead the status pill stays on "Connecting…", screens show only cached data, or you see "Unable to connect to server…" or "Couldn't save" messages, something's broken in the chain. (The raw "Network request failed" appears only in the Metro log.) An ordinary API call now has a 90 s overall deadline, including response parsing. A paused backend can therefore show a delayed timeout; read-query retries can extend the overall screen wait beyond a single call. For a timed-out save, check the refreshed data before retrying because the server may have committed. The next chapter narrows down where.

The query cache on reconnect — changed 6 October 2026

Earlier (before commit 07847a4, 6 October 2026): only TanStack Query's focusManager was wired (to AppState). Its onlineManager was not connected to NetInfo, so getting the network back did not by itself trigger a refetch. Current (7 October 2026, 03cfebb): providers/QueryProvider.tsx wires onlineManager to NetInfo and focusManager to AppState. When the phone reports a connection again, or the app returns to the foreground, active stale queries refetch (30 seconds by default; orders use staleTime: 0). Query data is persisted to AsyncStorage. A saved copy is restored only if it is less than 24 hours old (the persister's default maxAge, counted from the last save; the copy is re-saved on every cache change, so the data in it can be older); auth queries are not persisted. There is no offline write queue: mutations are never persisted or retried automatically (networkMode: 'always', retry: 0), so a save is blocked by a screen guard or attempted without being queued; ordinary requests have no deadline, so network failure can be delayed. The failure then shows as a "Couldn't …" dialog or toast with a retry option.

NetInfo describes the phone's own network, not the USB tunnel. The screens' "Offline" check uses NetInfo's isConnected; TanStack Query additionally requires that internet reachability is not reported as false. In USB mode with a local backend, keep the phone's Wi-Fi or mobile data on. Otherwise the app can show "Offline", or TanStack Query can hold back retries and reconnect refetches, even though adb reverse would still reach your laptop. (Read from the code; not device-tested in this review.)

CORS doesn't affect the Android app

CORS is a rule that browsers enforce when a web page calls another origin. Expo Go and the Android APK are not browsers, so CORS_ORIGINS neither lets the app in nor keeps it out — and it is not authentication either. The comments in docker-compose.yml suggesting that ["*"] is what lets your phone connect are misleading. If the phone can't reach the API, check the URL, adb reverse, the Wi-Fi network and the firewall. CORS matters only when a web page calls the API, for example under npm run web.

Deleting the volume deletes the database

Use it only on disposable local data, never as a routine fix. The two files use separate volumes.

Switching branches with an upgraded database

The database remembers the newest migration it has run. main (835fad3) knows migrations only up to 0006, and migration 0007 deliberately cannot be downgraded. Start main's code against a database already at 0010 and alembic upgrade head fails, because it cannot find revision 0010_order_local_id_unique. With docker-compose.yml the container then stops (and keeps restarting and failing). The dev image's start script carries on and starts the server against the mismatched schema, so read its log. Keep a separate, disposable database for each line of code.

Added in October 2026. Chapter 07

Three things that confuse everyone

If you only remember three things from this book, make it these. They explain the majority of "wait, why doesn't this work?" moments in the dev loop.

Every developer who works on a React Native app for long enough hits the same three confusions. Each is a category of bug that produces dozens of distinct symptoms. Each has a single conceptual fix. Once you have the model, the symptoms collapse into one diagnosis.

07.01 localhost is ambiguous

localhost is not a global address. It always means this machine, and this machine changes depending on whose perspective you're taking. The same word, used by code on the laptop versus code on the phone, points to two completely different computers.

The fix is what we covered in section 06.03: adb reverse tcp:8000 tcp:8000 bridges the two interpretations. After that command, the phone's localhost:8000 does reach the laptop's localhost:8000 — but only by special arrangement, over an adb connection (USB, wireless debugging, or an emulator).

This single confusion explains many recurring bug categories:

  • "My local Docker backend isn't reachable from the app" — usually because EXPO_PUBLIC_API_URL=http://localhost:8000 was set but no adb reverse tcp:8000 tcp:8000 was run.
  • "It worked yesterday and now it doesn't" — the reverse rule was lost when the phone rebooted overnight.
  • "It works in USB mode but not LAN mode" — LAN mode needs the laptop's actual IP (http://192.168.1.5:8000), not localhost.
  • "It works on the emulator but not on my phone" — the Android emulator reaches the laptop at 10.0.2.2 (http://10.0.2.2:8000, as vitaltrack-mobile/.env.example notes); a physical phone needs adb reverse or the LAN IP.
Rule of thumb

Never let localhost appear in EXPO_PUBLIC_API_URL unless you've also run a matching adb reverse. If you'd rather not think about it, point at staging (npm run start:staging) — a public URL that works the same from any network with internet access. Use npm run start:prod only for a brief, read-only smoke test with a dedicated test account. Never run Start Fresh, Replace All, order apply ("Update Stock") or account deletion against production. A development build runs unreleased code. These flows change or delete real caregiver data immediately, and account deletion sends real emails.

07.02 The USB cable carries Metro traffic — and the API only if you reverse its port

This is the most common mistake new developers make on this stack. They ask: "I'm on USB, why doesn't the phone reach my Docker backend?" The answer: the cable carries only what you route through it with adb reverse. Everything else uses the phone's own internet.

Concretely, here's how the two channels divide labor:

  • If EXPO_PUBLIC_API_URL is https://staging-api.carekosh.com, every API call goes over the phone's own internet (Wi-Fi or LTE) — directly to the public API. The USB cable is irrelevant for these calls.
  • If EXPO_PUBLIC_API_URL is http://localhost:8000, the phone tries to reach its own port 8000. That only succeeds if a matching adb reverse rule turned it into a tunnel back to the laptop's Docker.

The consequence is that you can be in USB mode (Metro over USB) and hitting staging (API over the phone's Wi-Fi) at the same time. They're independent. Two separate channels, two separate questions, two separate things to debug.

With a staging or production API, briefly unplugging the cable leaves already-loaded screens working, because the app's API calls don't use USB. But development assets, Fast Refresh and any reload still need Metro, so plug back in before you change code. With a local backend over adb reverse, unplugging breaks every API call.

07.03 Metro and the backend never meet

Metro serves your code. The backend serves your data. They usually run on different machines, and always on different ports, with different protocols.

Both are involved when the app first loads — Metro to deliver the code, then the backend to deliver the data once the code is running. But they don't know about each other and don't share state. They are completely separate processes; with local Docker they happen to run on the same laptop.

So when your dashboard renders empty, the question is sharp: did Metro deliver the bundle? You can tell, because the app rendered something. If it didn't, Expo Go shows its own error screen saying it could not connect to the development server. Did the backend not respond? You'd see a login stuck on "CareKosh server is waking up…", "Failed to load data", "Unable to connect to server…", a "Couldn't save" message, a status pill stuck on "Connecting…", or screens showing only cached data. These are two different problems with two different fixes. Knowing which side broke is half of debugging.

A simple discriminator

If the app reaches its own first screen (login or tabs), Metro worked and the bundle is running in Hermes. Later failures can come from the API, authentication, cached state, rendering or frontend logic; inspect the failed request and app logs before assigning a cause. If Expo Go never gets past its loading/splash view, or reports that it cannot reach the development server, bundle transport is one possibility; an application startup exception or native failure can also leave the splash visible. Note that Expo Go's own splash appears before your bundle runs, so a splash alone proves nothing.

08.03 A worked example: "I'm running npm run start:staging -- --localhost, why does adb reverse fail?"

This question came up recently. Here's the diagnosis in the model from this book:

The actual problem

If adb reverse returns an error, read it:

  • unauthorized — the phone has not trusted this laptop yet (fix sequence below).
  • no devices/emulators found — the phone is not connected, or USB debugging is off.
  • more than one device/emulator — pick one, for example an emulator running next to the phone: adb -s <serial> reverse tcp:8081 tcp:8081.
  • device offline — usually clears with adb kill-server && adb start-server.

Until adb devices shows your phone with status device, no adb reverse will succeed.

Fix sequence for unauthorized:

  1. Look at the phone screen — Android shows an "Allow USB debugging?" dialog with the laptop's RSA key fingerprint when you connect to a new computer. Tap "Always allow from this computer" → OK.
  2. If you don't see the dialog, make sure the phone is unlocked when you plug it in; locked phones don't show the prompt. Try a different USB cable (some are charge-only), or a different USB port.
  3. If the dialog still doesn't appear: adb kill-server && adb start-server && adb devices — that re-triggers the prompt.
  4. Last resort — phone Settings → System → Developer Options → "Revoke USB debugging authorizations" → unplug, replug → fresh prompt.

And the second half of that same question — do I even need adb reverse?

A useful realization

If you're running npm run start:staging, the app points at https://staging-api.carekosh.com. That's a public URL the phone reaches over its own Wi-Fi/LTE, so you never need adb reverse for the API. For Metro you have two choices:

  • LAN: run npm run start:staging (no --localhost) and scan the QR code, which contains your laptop's LAN IP. No adb reverse needed.
  • USB: run npm run start:staging -- --localhost plus adb reverse tcp:8081 tcp:8081 (use the port Metro prints). The QR code then points at 127.0.0.1 and works only through the reverse tunnel.
